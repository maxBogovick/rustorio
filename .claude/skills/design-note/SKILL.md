# Проектная сверка — до первой строки кода

Читается **один раз на карточку**, между «прочитал задачу» и «начал писать».

Результат — **проектная записка ≤15 строк**, которую агент выдаёт ДО кода. Она нужна не для
отчётности: это точка, где владелец отменяет неверное решение за 30 секунд вместо вычитывания
300 строк готового кода. Ревьюер потом сверяет записку с диффом.

**Правило против сочинений.** Записка — 15 строк, не эссе. Если сверка занимает больше, чем сама
задача, значит карточка слишком крупная — это повод остановиться и сказать об этом.

## Блок A. Задача и план (если здесь «нет» — дальше не идём)

1. Что именно требует карточка — своими словами, одной фразой?
2. Какие ADR она называет и что каждый из них **запрещает**? Текста ADR нет под рукой —
   попроси его, а не реконструируй по названию.
3. Решение нарушает хоть один ADR? → **СТОП**: это развилка, её закрывает владелец.
4. Решение выходит за раздел «Границы» карточки? → **СТОП**, сначала спроси.

## Блок B. SOLID — вопросами, а не принципами

1. **S** — если завтра поменяется правило X, сколько классов придётся тронуть? Назови число и
   классы. Больше двух — ответственность размазана.
2. **O** — что произойдёт при добавлении **новой руды** и **нового здания**? Перечисли файлы.
   Появился новый файл в списке — работаешь против цели проекта.
3. **L** — новая реализация интерфейса выполняет контракт целиком или где-то бросает
   «не поддерживается»? Второе — не наследование, а протечка.
4. **I** — интерфейс заставляет реализовать ненужное? Образец размера — `TickContext`: шесть
   методов, а не весь `World`.
5. **D** — класс сам достаёт зависимость (статика, синглтон, `new` внутри) или получает в
   конструкторе? Здесь — только конструктор (`OreLayout`, `RecipeBook`).

## Блок C. Паттерны

1. Какой паттерн применяешь и **как он называется**? Паттерн без имени — случайность.
2. Такая задача уже решалась? Переиспользуй, не изобретай параллельный механизм:
   **Strategy** (`OreLayout`, `PlacementRule`) · **Factory Method** (`BuildingFactory`) ·
   **Memento/Codec** · **Command + Undo** (`domain.action`) · **Observer**
   (`ProductionListener`) · **Repository** (`SaveRepository`) · **Port/Adapter**
   (`TickContext`) · **Registry + Prototype** — целевой паттерн движка.
   **Decorator** (`SpeedModule`) устаревает — новых декораторов не вводить.
3. Абстракция ради одной реализации — не паттерн, а долг.

## Блок D. Java 25

**Проверяй версии по документации, а не по памяти.**

Доступно: `record`, `sealed` (где множество действительно закрыто), pattern matching,
деконструкция записей, `switch`-выражения, sequenced collections, текстовые блоки, flexible
constructor bodies, scoped values.

Запрещено: **любые preview-фичи** (`--enable-preview` не включён); value-классы Valhalla (их
нет); виртуальные потоки и любая многопоточность в симуляции — тик детерминированный и
однопоточный, это решение владельца, а не оптимизация по дороге.

Вопрос для записки: современное применено там, где **упрощает** код, а не демонстрирует знание?

## Блок E. То, что обычно не перечисляют

1. **YAGNI** — абстракция «на будущее» без второй реализации сегодня убирается.
2. **Связность** — новый межпакетный импорт? Сверь с `package-info.java` и границами.
3. **Иммутабельность** — новое состояние `final` по умолчанию; мутабельное поле объясняется в
   javadoc.
4. **Ошибки** — некорректный вход даёт исключение с внятным сообщением, не тихое «ничего».
5. **Дизайн API** (всё, что увидит мододел) — минимальная поверхность, `Optional` только как
   возврат, имена нельзя будет переименовать позже.
6. **Детерминизм** — `HashMap`-итерация, `Set.of`, системное время, несеянный RNG, `hashCode`
   в логике: нельзя.
7. **Бюджет производительности** — код в тике или на кадре: без аллокаций в цикле, без скана
   мира, без `Enum.values()` в цикле. Порог 1.02 мс.
8. **Тестируемость** — если ответ «никак, потому что окно», вынеси чистую часть в отдельный
   класс (образец — `CameraViewport`).
9. **Совместимость сейвов** — правка меняет то, что пишется в файл? Нужен план миграции, а не
   молчаливая смена формата. См. правило `persistence`.
10. **Диагностируемость** — сообщение об ошибке называет мод, файл и поле.
11. **Именование** — имя описывает роль, а не реализацию (`TransportNode`, не `BeltLikeThing`).

## Блок F. Расширяемость — главный вопрос проекта

1. Код добавляет новое место, которое придётся править при добавлении контента (`switch`,
   `instanceof`, `if` по типу)? → регресс главной метрики; ищи другое решение или фиксируй как
   осознанный компромисс с обоснованием. Храповик `ContentCouplingRatchetTest` это считает.
2. Сможет ли сторонний разработчик воспользоваться добавленным, **не меняя ядро**?
3. Закрыл тип (`final`, `sealed`, package-private)? Это решение с причиной в javadoc — или привычка?
4. Что этот код усложнит для следующих фаз?

## Формат записки (выдать до кода)

```
ПРОЕКТНАЯ ЗАПИСКА · <ID карточки>
Решение: <одна-две фразы: что и как делаю>
Столп GDD: <какому из трёх служит>
Паттерн: <имя или «без паттерна, прямой код»>
ADR: <номера> — не нарушены / нарушение: <что> → СТОП
Новая руда → правим файлов: N (было N) · Новое здание → N (было N)
Java: <что современного применил и зачем; preview не использую>
Детерминизм: <не затрагиваю / затрагиваю так-то>
Тест-доказательство: <какой тест и что он ловит>
Риск: <что может пойти не так>
Следы на будущее: <что усложняю/упрощаю для следующих фаз>
Отброшенная альтернатива: <что рассматривал и почему отказался>
```

Последняя строка обязательна. Решение, у которого не было альтернативы, обычно не было решением.

## Чего по итогам сверки делать НЕ надо

- Не рефакторить соседний код, который «тоже нарушает» — записать, не чинить.
- Не вводить абстракцию, которую сверка «подсказала», если карточка её не требует.
- Не переписывать существующие паттерны под более модные.
- Не превращать записку в проект следующих трёх фаз. 15 строк.
