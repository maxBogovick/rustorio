# Проектная сверка — до первой строки кода

Читается **один раз на карточку**, между «прочитал задачу» и «начал писать». Результат —
записка ≤15 строк, которую владелец читает за полминуты и успевает отменить неверное решение
до того, как появятся 300 строк кода.

Здесь только вопросы, на которые не отвечает машина. Границы пакетов, `package-info`,
null-контракт, wildcard-импорты, цитаты ID, порог мс/тик — всё это уже проверяется сборкой,
и в записке им места нет. Каталог паттернов с адресами образцов и статус фич Java — в
`/java-modern`, не здесь.

## Восемь вопросов

**1. Задача.** Что требует карточка — одной фразой, своими словами?

**2. Границы.** Что раздел «Границы» карточки прямо запрещает? Решение выходит за них → **СТОП**,
спроси. Упирается в решение, которое владелец уже принял → тоже СТОП: принятое не переигрывают
молча.

**3. Расширяемость — главная метрика проекта.** Что придётся тронуть, когда добавят **новую руду**
и **новое здание**? Назови файлы. Появился новый `switch`, `instanceof` или `if` по типу контента —
это регресс, храповик `ContentCouplingRatchetTest` его посчитает. Добавление контента должно быть
данными, а не правкой кода.

**4. Кто ещё это тронет.** Если завтра поменяется правило X, сколько классов придётся править?
Больше двух — ответственность размазана. Зависимости приходят в конструктор, класс не достаёт их
сам (`OreLayout`, `RecipeBook`). Интерфейс не заставляет реализовать лишнее — образец размера
`TickContext`: пять методов, а не весь `World`.

**5. Детерминизм.** Порядок итерации, который видно снаружи (сейв, дамп, UI, хеш), системное
время, несеянный RNG, `hashCode` в логике, любая многопоточность в тике — нельзя. Затрагиваешь —
скажи как.

**6. Совместимость.** Правка меняет то, что пишется в файл сейва или видит мододел? Тогда нужен
план: миграция состояния или бамп версии, а для публичного API — согласованное имя, потому что
переименовать позже нельзя. Детали — правило `persistence`, оно подгрузится само.

**7. Цена в тике и на кадре.** Аллокация в цикле, скан мира, `Enum.values()` при отрисовке?
Вердикт по итогу выносит `./gradlew benchmark`.

**8. Чем докажешь.** Какой тест падает на текущем коде и зеленеет после правки? Нет такого теста —
значит, ты не знаешь, что чинишь.

## Формат записки (выдать до кода)

```
ПРОЕКТНАЯ ЗАПИСКА · <карточка>
Решение: <что и как делаю, одна-две фразы>
Столп GDD: <какому из трёх служит>
Границы карточки: не нарушены / нарушение: <что> → СТОП
Новая руда → правим файлов: N · Новое здание → N
Детерминизм: <не затрагиваю / затрагиваю так-то>
Совместимость: <сейв и API не трогаю / план такой-то>
Тест-доказательство: <имя теста и что он ловит>
Риск: <что может пойти не так>
Отброшенная альтернатива: <что рассматривал и почему отказался>
```

Последняя строка обязательна. Решение, у которого не было альтернативы, обычно не было решением.

## Чего по итогам сверки делать НЕ надо

- Не чинить соседний код, который «тоже нарушает» — записать в отчёт, не трогать.
- Не вводить абстракцию, которую подсказала сверка, если карточка её не требует.
- Не превращать записку в план следующих трёх фаз. Пятнадцать строк.
