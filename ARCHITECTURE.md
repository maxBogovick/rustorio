# Архитектура Rustorio — читай это, если не знаешь «что делать»

Этот документ — твоя карта. Он отвечает на три вопроса:
1. **Где точка входа и как работает «ядро».**
2. **Какой ритуал повторять каждый раз, чтобы правильно взаимодействовать с миром.**
3. **Пошаговые рецепты** для типовых задач (добавить здание, предмет, поведение…).

Принцип, по которому всё построено (Р. Нистром, *Game Programming Patterns*):
> Хорошая архитектура — это когда, чтобы внести правку, нужно **держать в голове
> как можно меньше**. Каждый файл — про одну вещь. Меняешь одно — не ломаешь другое.

Поэтому здесь **нет** ECS, трейт-объектов и «абстракций на будущее». Для игры такого
размера это было бы лишней сложностью. Простой прямой код — это осознанный выбор, а
не «недоделка». Когда игра дорастёт (сотни разных зданий) — см. раздел «Когда усложнять».

## 1. Ядро: игровой цикл (паттерн «Game Loop»)

Точка входа — **`src/main.rs`**. Весь «движок» там, в 4 строках:

```rust
loop {
    input::handle(&mut game); // 1. ВВОД:   действия игрока меняют мир
    game.update();            // 2. АПДЕЙТ: симуляция двигает мир по тикам
    render::draw(&game);      // 3. РЕНДЕР: только читаем мир и рисуем
    next_frame().await;
}
```

Игра — не программа, которая ждёт ввода. Она **живёт сама**: даже если ты не трогаешь
мышь, ленты едут, печи плавят. Поэтому цикл крутится всегда, а три фазы расцеплены —
каждая занимается своим и не мешает другим.

### Фиксированный тик (почему мир ведёт себя одинаково на любом железе)

`game.update()` использует приём «фиксированный шаг + аккумулятор» (Gaffer,
*Fix Your Timestep*). Кадры рисуются с разной частотой, но **симуляция всегда идёт
шагами по `TICK` секунд**:

```
timer += время_прошлого_кадра;
пока timer >= TICK:      // сколько «наигранного» времени накопилось —
    timer -= TICK;       // столько шагов и делаем
    systems::step(...);  // ← один честный шаг мира
```

Медленный компьютер = реже кадры, но мир тикает так же. Быстрый = плавнее картинка,
мир тикает так же. Один код — предсказуемое поведение везде.

## 2. ЗОЛОТОЕ ПРАВИЛО: однонаправленный поток данных

Это ответ на «какую последовательность шагов повторять, чтобы правильно
взаимодействовать с миром». Данные всегда текут в одну сторону:

```
   [ игрок ]                         [ экран ]
       │                                 ▲
       ▼                                 │
   input.rs  ──►  Game / World  ──►  render.rs
   (МЕНЯЕТ)      systems.rs        (только ЧИТАЕТ)
                  (МЕНЯЕТ)
```

Три железных правила:
- **input** — меняет мир по воле игрока (поставить/убрать/выбрать).
- **systems** — меняет мир по правилам игры (копать/плавить/везти), только внутри тика.
- **render** — **никогда не меняет мир**. Только читает `&Game` и рисует.

Если держишься этого — баги «а почему у меня что-то поменялось при отрисовке?» просто
не возникают. Мутация мира живёт ровно в двух местах: `input.rs` и `systems.rs`.

> Мелочь, но показательная: даже «клетку под курсором» считает `input` и кладёт в
> `game.hover`, а `render` её только читает. Так отрисовка не ходит к мыши сама и
> остаётся честно чистой функцией от состояния.

## 3. Слои и файлы (снизу вверх)

Стрелки зависимостей смотрят **вниз**: верхний слой знает про нижний, но не наоборот.
Это и есть «расцепление» — нижние файлы можно читать и тестировать в одиночку.

```
        main.rs                 точка входа + игровой цикл (склейка)
        ───────────
   ФАЗЫ ЦИКЛА:
        input.rs  systems.rs  render.rs
        (ввод)    (симуляция) (рисуем)
        ───────────
   СОСТОЯНИЕ:
        game.rs                 Game: мир + инструмент + пауза + тик-таймер
        world.rs                сетка клеток + place/remove/tile/neighbor
        ───────────
   ДАННЫЕ:
        building.rs             enum Building + поведение одного здания
        types.rs                Direction, Item, Tool — общий «словарь»
        config.rs               ВСЕ настройки (числа, размеры, баланс)
```

| Файл | Одна ответственность | Меняешь его, когда… |
|------|----------------------|---------------------|
| `config.rs` | все настройки-числа | крутишь баланс, размер поля, скорость |
| `types.rs` | базовые типы | добавляешь предмет / инструмент / направление |
| `building.rs` | что умеет здание | добавляешь здание или меняешь его поведение |
| `world.rs` | хранение поля | меняешь структуру мира (запасы руды, слои) |
| `systems.rs` | шаг симуляции | добавляешь новое правило мира (истощение руды…) |
| `game.rs` | общее состояние | добавляешь глобальное состояние (счёт, режим) |
| `input.rs` | ввод → изменения | новая клавиша / действие мышью |
| `render.rs` | картинка | как всё выглядит (цвета, формы, HUD) |
| `main.rs` | цикл | почти никогда |

## 4. Рецепты (пошагово — просто иди по списку)

### 🏭 Добавить новое здание (например, Сборщик)
Компилятор — твой помощник: добавь вариант enum и иди по его ошибкам сверху вниз.
1. `types.rs`: добавь `Tool::Assembler` (и строку в `Tool::name`).
2. `building.rs`: добавь вариант `Building::Assembler { … }`.
   Компилятор подсветит **каждый** `match`, который надо дополнить
   (`new`, `update`, `output`, `can_accept`, `remove_output`, `accept`, `dir`) —
   это и есть твой список задач. Заполняй по одной.
3. `render.rs`: добавь ветку в `draw_building` (как выглядит).
4. `input.rs`: привяжи клавишу (`Key5 → Tool::Assembler`).
5. `README.md`: обнови подсказку по управлению.

### 📦 Добавить новый предмет (например, Шестерёнку)
1. `types.rs`: добавь `Item::Gear`.
2. `render.rs`: добавь цвет в `item_color`.
3. Реши, кто его производит/принимает — правь `update`/`can_accept` нужных зданий.

### ⚙️ Изменить поведение машины
Только `building.rs`, метод `update` (внутренняя работа) или
`output`/`can_accept`/`accept` (обмен предметами). Больше нигде.

### 🌍 Добавить новое ПРАВИЛО мира (например, руда истощается)
1. `world.rs`: при необходимости добавь данные (напр. `ore_amount: u32` в `Tile`).
2. `systems.rs`: напиши функцию-систему `fn deplete_ore(world: &mut World)` и
   добавь её вызов в `step`. Порядок систем в `step` = порядок событий за тик.

### 🎛️ Покрутить баланс/скорость/размер
Только `config.rs`. Пересобрал — увидел эффект.

### ⌨️ Добавить управление
Только `input.rs`.

### 🎨 Поменять внешний вид
Только `render.rs` (вся палитра — сверху файла).

## 5. Как проверять, что «я взаимодействую с миром правильно»

Логика мира (`world` + `systems`) — **чистая**: ей не нужны окно, мышь и время.
Значит, её можно проверять тестами без запуска игры. Пример уже есть в
`systems.rs` (`#[cfg(test)]`): собрали мир из зданий, прогнали N тиков, проверили
результат. Запуск:

```bash
cargo test        # быстрая проверка логики
cargo clippy      # линтер: подсказывает идиоматичный Rust
cargo run         # увидеть глазами
```

Привыкни к ритму: **правка → `cargo test`/`clippy` → `cargo run`**. Тесты ловят
«сломал логику», clippy учит писать красиво, run показывает результат.

## 6. Когда усложнять (и чем)

Пока зданий единицы — `enum` идеален: компилятор проверяет все случаи, всё на виду.
Задумайся о смене подхода, только когда почувствуешь **реальную** боль:

- **Очень много типов зданий с общим поведением** → трейт `trait Machine` и
  `Vec<Box<dyn Machine>>` (полиморфизм). Но это скрывает проверку исчерпывающести —
  плати за гибкость осознанно.
- **Тысячи сущностей, важна скорость** → готовый ECS-крейт (`hecs`, `legion`).
- **Отмена действий (undo), запись реплеев** → паттерн «Command»: ввод порождает не
  прямые правки, а объекты-команды, которые умеют делать и отменять себя.
- **Много игровых режимов (меню/игра/пауза-экран)** → паттерн «State».

Правило простое: **не добавляй абстракцию раньше, чем появилась проблема, которую
она решает.** Преждевременная гибкость — это тоже сложность, только бесполезная.
