## Урок 0. Как вообще работает программа на Rust

Прежде чем говорить об игре, разберёмся, из чего вообще состоит программа.

**Что происходит, когда ты пишешь код.** Ты пишешь текст (`.rs`-файлы). Его читает
**компилятор** (`rustc`) и переводит в машинный код — то, что понимает процессор.
Результат — исполняемый файл, который можно запускать. Rust — **компилируемый**
язык: сначала вся программа переводится целиком, и только потом запускается. Это
важно: **многие ошибки ловятся ещё до запуска**, на этапе компиляции. Это твой друг.

**Cargo** — «прораб» проекта. Он качает зависимости, компилирует, запускает. Главные команды:

| Команда | Что делает |
|---------|-----------|
| `cargo run` | собрать и запустить игру (откроется окно) |
| `cargo test` | прогнать тесты (проверка логики без окна) |
| `cargo clippy` | линтер: советует, как писать идиоматичнее |
| `cargo build --release` | собрать быструю (оптимизированную) версию |

**Из чего состоит наш проект.** Файл `Cargo.toml` — «паспорт» проекта (имя, версия,
зависимости). Папка `src/` — исходники. Точка входа — функция `main` в `src/main.rs`:
именно с неё начинается выполнение. Всё остальное (`world.rs`, `building.rs`, …) —
это **модули**, куски кода, разложенные по полочкам (о них — Урок 7).

🧠 **Аналогия.** Компилятор — строгий редактор, который вычитывает всю книгу до
печати и не даёт опубликовать текст с ошибками. `main` — первая страница, с которой
читатель (процессор) начинает. Модули — главы книги.

🎯 Открой терминал в папке проекта и выполни `cargo run`. Появилось окно? Отлично.
Закрой его. Теперь `cargo test` — увидишь `test result: ok`. Ты только что собрал и
проверил настоящую программу на Rust.

## Урок 1. Игровой цикл — сердце любой игры

**Проблема, которую решает игра.** Обычная программа (например, калькулятор) ждёт,
пока ты что-то введёшь, отвечает и снова ждёт. Игра — **другая**. В игре мир живёт
сам: даже если ты убрал руки с клавиатуры, ленты едут, печи плавят, время идёт.

📖 *«Unlike most other software, games keep moving even when the user isn't providing
input.»* («В отличие от большинства программ, игры продолжают двигаться, даже когда
пользователь ничего не вводит».) — [Game Programming Patterns, «Game Loop»](https://gameprogrammingpatterns.com/game-loop.html)

Значит, нам нужен **вечный цикл**, который крутится снова и снова, кадр за кадром.
Этот цикл называется **игровой цикл** (game loop) и состоит из трёх шагов-фаз:

```
loop {                        // «крутись вечно»
    input   → собрать, что нажал игрок, и поменять мир
    update  → продвинуть симуляцию (ленты, печи…)
    render  → нарисовать текущее состояние на экране
}
```

Почему именно **три отдельные** фазы, а не одна каша? Потому что они про разное:
ввод — редкие события (клик мышью), симуляция — постоянные правила, отрисовка —
картинка. Разделять их — значит уметь менять одно, не ломая другое (об этом — Урок 7).

**Смотрим наш код.** Открой [`src/main.rs`](src/main.rs). Вот сердце всей игры:

```rust
loop {
    input::handle(&mut game); // 1. ввод  → намерения игрока меняют мир
    game.update();            // 2. апдейт → системы двигают мир по тикам
    render::draw(&game);      // 3. рендер → только читаем мир и рисуем
    next_frame().await;       // отдать кадр экрану и ждать следующий
}
```

Разберём построчно:
- `loop { … }` — бесконечный цикл. В Rust это буквально ключевое слово `loop`.
- `input::handle(&mut game)` — вызываем функцию `handle` из модуля `input`. `&mut game`
  означает «даём функции временно **менять** объект игры» (об `&mut` — Урок 6).
- `game.update()` — метод игры, продвигающий симуляцию (Урок 2).
- `render::draw(&game)` — рисуем. Обрати внимание: тут `&game` **без** `mut` — рисование
  только **читает** мир, менять не может (об этом правиле — ниже).
- `next_frame().await` — команда движка macroquad: «покажи готовый кадр и жди
  следующего». `await` — потому что кадр приходит асинхронно; тебе пока достаточно
  знать, что это «дождись следующего кадра».

🧠 **Аналогия.** Повар на кухне в бесконечном ритме: (1) *принял заказ* (input),
(2) *поготовил* (update), (3) *выдал блюдо* (render) — и снова заказ. Три разные
роли, но один непрерывный ритм.

🎯 В `main.rs` поменяй местами `game.update()` и `render::draw(&game)`. Запусти.
Заметил, что картинка теперь «отстаёт» на кадр? Верни назад. Ты почувствовал, зачем
важен **порядок** фаз.

## Урок 2. Фиксированный тик — почему игра одинаковая на любом железе

**Проблема.** Разные компьютеры рисуют кадры с разной скоростью: у одного 30 кадров
в секунду, у другого 240. Если двигать ленты «на каждый кадр», то на быстром ПК
ленты поедут в 8 раз быстрее! Это недопустимо — игра должна вести себя **одинаково**.

**Решение — фиксированный шаг + аккумулятор.** Идея: рисуем кадры с любой скоростью,
но **симуляцию** продвигаем строго порциями по `TICK` секунд. Копим прошедшее время
в «копилке» (аккумуляторе) и, пока в копилке хватает на целый тик, делаем шаг.

Это классический приём, ему посвящена знаменитая статья:

📖 Идея статьи «Fix Your Timestep!»: симуляция должна идти **фиксированными**
шагами `dt` (например, 1/60 секунды), а «лишнее» время переносится в следующий кадр
через переменную-аккумулятор. Если этого не делать, симуляция «плавает» и может
попасть в «спираль смерти» (spiral of death), когда не успевает за реальным временем.
— [Gaffer On Games, «Fix Your Timestep!»](https://gafferongames.com/post/fix_your_timestep/)

**Смотрим наш код.** Открой [`src/game.rs`](src/game.rs), метод `update`:

```rust
pub fn update(&mut self) {
    if self.paused { return; }          // на паузе мир не тикает
    self.timer += get_frame_time();     // копим реальное время в «копилку»
    while self.timer >= TICK {          // пока накопили на целый шаг —
        self.timer -= TICK;             //   вычитаем один шаг из копилки
        systems::step(&mut self.world, TICK); // …и делаем ровно один шаг мира
    }
}
```

- `get_frame_time()` — сколько секунд занял прошлый кадр (macroquad считает сам).
- `while self.timer >= TICK` — важный момент: не `if`, а `while`. Если компьютер
  «затупил» и один кадр длился долго, мы сделаем **несколько** шагов подряд, чтобы
  догнать реальное время. На быстром ПК — иногда ноль шагов за кадр. Итог: **мир
  тикает одинаково везде**, просто картинка где-то плавнее.

📖 Ровно про это Нистром: *«The game simulates at a constant rate using safe fixed
time steps across a range of hardware. It's just that the player's visible window
into the game gets choppier on a slower machine.»* («Игра симулируется с постоянной
скоростью безопасными фиксированными шагами на разном железе. Просто окно, через
которое игрок видит игру, становится более рваным на слабой машине».)
— [Game Programming Patterns, «Game Loop»](https://gameprogrammingpatterns.com/game-loop.html)

🎯 Открой [`src/config.rs`](src/config.rs) и поменяй `TICK` с `0.18` на `0.05`.
Запусти. Ленты поехали быстрее. Верни `0.18`. Ты нашёл «скорость времени» игры — и
она в **одном** месте, как и должно быть.

## Урок 3. Данные, часть 1: `struct` (структуры)

Теперь — из чего сделан наш мир. Начнём со `struct` (структура).

**`struct` — это способ склеить несколько значений в один именованный тип.** Как
анкета с полями.

🧠 **Аналогия.** Анкета «Клетка поля»: поле «есть ли руда» (да/нет) и поле «какое
здание стоит» (или пусто). Заполненная анкета — одна клетка.

Смотрим [`src/world.rs`](src/world.rs):

```rust
pub struct Tile {
    pub ore: bool,                 // есть ли под клеткой руда (true/false)
    pub building: Option<Building>,// здание — или пусто
}
```

- `pub` — «публичное», видно из других модулей (Урок 7).
- `bool` — тип «да/нет» (`true`/`false`).
- `Option<Building>` — **очень важный тип Rust**. Он значит «либо есть `Building`,
  либо ничего (`None`)». В Rust **нет** «null», который в других языках роняет
  программы. Вместо этого есть честный `Option`: `Some(здание)` или `None` (пусто).
  Компилятор заставит тебя обработать оба случая — поэтому «здание внезапно
  оказалось пустым» тут не выстрелит.

Само поле — тоже структура:

```rust
pub struct World {
    pub width: i32,               // ширина в клетках
    pub height: i32,              // высота в клетках
    pub(crate) tiles: Vec<Tile>,  // все клетки одним списком
}
```

- `i32` — целое число (32 бита).
- `Vec<Tile>` — **вектор**, растущий список значений типа `Tile`. Мы храним все
  клетки поля одним плоским списком, а клетку (x, y) находим по формуле
  `индекс = y * ширина + x`. Это стандартный быстрый способ хранить 2D-сетку.
- `pub(crate)` — «видно внутри нашего проекта, но не наружу» (Урок 7).

🎯 Найди в `world.rs` метод `idx`. Убедись, что он реализует ту самую формулу
`y * self.width + x`. Это и есть «перевод (x, y) в номер в списке».

## Урок 4. Данные, часть 2: `enum` (перечисления)

Ты уже спрашивал: *«разве хорошо делать `Building` как enum?»* — отличный вопрос,
на него отвечает этот урок и Урок 8. Сначала — что такое `enum`.

**`enum` (перечисление) — это тип, значение которого может быть одним из
нескольких заранее перечисленных вариантов.**

📖 *«…enums give you a way of saying a value is one of a possible set of values.»*
(«…перечисления дают способ сказать, что значение — это одно из возможного набора
значений».) — [The Rust Book, «Defining an Enum»](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)

Простейший пример — `Direction` из [`src/types.rs`](src/types.rs):

```rust
pub enum Direction {
    North,  // север
    East,   // восток
    South,  // юг
    West,   // запад
}
```

Значение типа `Direction` — это **ровно одно** из четырёх. Не два, не «нечто
среднее». Либо `North`, либо `East`, и т.д.

**Суперспособность Rust: варианты могут нести данные внутри себя.**

📖 *«Rather than an enum inside a struct, we can put data directly into each enum
variant.»* («Вместо перечисления внутри структуры мы можем положить данные прямо в
каждый вариант перечисления».)
— [The Rust Book, «Defining an Enum»](https://doc.rust-lang.org/book/ch06-01-defining-an-enum.html)

Именно так сделаны наши здания в [`src/building.rs`](src/building.rs):

```rust
pub enum Building {
    Miner   { dir: Direction, cooldown: f32, output: Option<Item> },
    Belt    { dir: Direction, item: Option<Item> },
    Furnace { dir: Direction, input: Option<Item>, progress: f32, output: Option<Item> },
    Chest   { items: u32 },
}
```

Читается так: «Здание — это **либо** Бур (со своим направлением, откатом и выходом),
**либо** Лента (с направлением и предметом), **либо** Печь, **либо** Ящик». У каждого
варианта — **своё** содержимое. Данные и «что это за штука» неразделимы.

🧠 **Аналогия.** `enum` — это «тип с галочкой»: галочка стоит ровно напротив одного
пункта, и у каждого пункта своя приложенная записка с деталями.

Про страх «1000 вариантов» — полностью в Уроке 8. Короткий ответ: варианты — это
**поведения** (их мало), а разнообразие машин — это **данные** (их сколько угодно).

🎯 В `types.rs` у `Direction` есть метод `rotate_cw` (поворот по часовой). Прочитай
его. Видишь, что это просто таблица «из чего во что»? North→East→South→West→North.

## Урок 5. `match` и исчерпывающесть — компилятор как наставник

У нас есть `enum`. Как с ним работать? Через `match` — главный инструмент Rust.

📖 *«Rust has an extremely powerful control flow construct called `match` that allows
you to compare a value against a series of patterns and then execute code based on
which pattern matches.»* («В Rust есть чрезвычайно мощная конструкция управления
`match`, позволяющая сравнить значение с рядом образцов и выполнить код в
зависимости от того, какой образец совпал».)
— [The Rust Book, «The `match` Control Flow Construct»](https://doc.rust-lang.org/book/ch06-02-match.html)

Пример из `types.rs` — по направлению вернуть смещение по сетке:

```rust
pub fn delta(self) -> (i32, i32) {
    match self {
        Direction::North => (0, -1),   // если North → (0, -1)
        Direction::East  => (1, 0),    // если East  → (1, 0)
        Direction::South => (0, 1),
        Direction::West  => (-1, 0),
    }
}
```

Каждая строка — **рукав** (arm): слева образец (`Direction::North`), справа код (`(0, -1)`).

**Вот почему `enum` + `match` — это счастье для новичка.** Rust требует, чтобы ты
обработал **все** варианты. Забыл один — программа **не скомпилируется**.

📖 *«Matches in Rust are exhaustive: We must exhaust every last possibility in order
for the code to be valid.»* («Сопоставления в Rust исчерпывающи: мы обязаны перебрать
все до единого варианты, иначе код недопустим».)
— [The Rust Book, «The `match` Control Flow Construct»](https://doc.rust-lang.org/book/ch06-02-match.html)

Практический смысл: когда ты добавишь новое здание (новый вариант `enum`), компилятор
**сам покажет каждое место**, где надо дописать поведение. Это не «ругань» — это
**бесплатный список задач**. Идёшь по ошибкам сверху вниз — и ничего не забудешь.

**Страж (match guard).** Иногда рукав должен срабатывать только при доп. условии.
Для этого есть `if` после образца:

📖 *«A match guard is an additional `if` condition, specified after the pattern in a
`match` arm, that must also match for that arm to be chosen.»* («Страж — это
дополнительное условие `if`, указанное после образца в рукаве `match`, которое тоже
должно выполниться, чтобы этот рукав был выбран».)
— [The Rust Book, «Pattern Syntax»](https://doc.rust-lang.org/book/ch19-03-pattern-syntax.html)

Мы используем это в [`src/building.rs`](src/building.rs), в `update`:

```rust
Building::Miner { cooldown, output, .. } if output.is_none() && has_ore => {
    // копаем только если выход свободен И под нами руда
    …
}
```

Тут `if output.is_none() && has_ore` — это страж. Кстати, именно на эту красоту нас
навёл линтер `clippy` (Урок 9): раньше был вложенный `if`, стало — страж.

🎯 Открой `building.rs`, метод `dir`. Мысленно добавь новый вариант
`Building::Pipe { … }` (не пиши, просто представь). Понимаешь, что компилятор
заставит дописать его в `dir`, `output`, `can_accept` и т.д.? Это и есть «наставник».

## Урок 6. Владение и заимствование — тот самый borrow checker

Это самая знаменитая (и поначалу пугающая) часть Rust. Спокойно — на нашем коде всё
станет очевидным.

**Владение (ownership).** В Rust у каждого значения есть ровно один **владелец**.
Когда владелец «уходит», значение убирается из памяти. Это позволяет Rust быть
безопасным **без** сборщика мусора (как в Java/C#) и **без** ручного освобождения
(как в C). Ты не можешь случайно «использовать удалённое» — компилятор не даст.

**Заимствование (borrowing).** Часто нужно не забирать значение себе, а лишь
**одолжить** его на время — по ссылке. Ссылки бывают двух видов:
- `&T` — «читать» (неизменяемая ссылка). Можно много одновременно.
- `&mut T` — «менять» (изменяемая ссылка). Можно только **одну** за раз.

📖 Правило №1: *«At any given time, you can have either one mutable reference or any
number of immutable references.»* («В любой момент времени можно иметь либо одну
изменяемую ссылку, либо любое число неизменяемых».)
📖 Правило №2: *«References must always be valid.»* («Ссылки всегда должны быть
действительны».)
— [The Rust Book, «References and Borrowing»](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)

🧠 **Аналогия.** Значение — это документ. `&T` — фотокопии для чтения: делай сколько
хочешь, все читают спокойно. `&mut T` — единственный оригинал с ручкой для правок:
пока он у одного человека, больше **никто** не может ни читать, ни писать. Так Rust
на этапе компиляции исключает «двое одновременно портят одно и то же» (гонки данных).

**А теперь — зачем это в нашей игре.** В [`src/systems.rs`](src/systems.rs) предметы
едут по лентам. Казалось бы, просто: «возьми предмет из клетки A и положи в клетку B».
Но A и B — это два элемента **одного** `Vec<Tile>`. Чтобы менять оба, нужны **две**
изменяемые ссылки в один и тот же `Vec` одновременно — а правило №1 это **запрещает**.

Поэтому мы делаем передачу в **две фазы**:

```rust
// Фаза (а): СНАЧАЛА только ЧИТАЕМ и составляем список «что куда двинуть».
let mut moves: Vec<(usize, usize, Item)> = Vec::new();
for i in 0..world.tiles.len() {
    …   // читаем, кто хочет отдать и кто может принять — и запоминаем в moves
}

// Фаза (б): ПОТОМ по очереди применяем — по одному изменяемому займу за раз.
for (i, j, item) in moves {
    if let Some(b) = &mut world.tiles[i].building { b.remove_output(); } // заём №1 (закончился)
    if let Some(b) = &mut world.tiles[j].building { b.accept(item); }    // заём №2 (отдельно)
}
```

Мы **обошли** ограничение красиво: в фазе (а) только читаем (много `&`, это можно), а
в фазе (б) берём изменяемый заём **по одному за раз** (сначала на `i`, он завершился,
потом на `j`). Бонус: это ещё и **правильнее** по логике — все передачи считаются от
единого «снимка» мира, без случайностей из-за порядка.

Это не «Rust мешает» — это Rust **заставил нас написать более корректный код**. Именно
поэтому borrow checker поначалу бесит, а потом ты понимаешь, что он ловит настоящие баги.

🎯 Прочитай `move_items` целиком. Найди переменную `claimed` (это `Vec<bool>`). Догадайся,
зачем она: чтобы в **одну** клетку за один тик не пропихнули **два** предмета две ленты
сразу. Подсказка — комментарий рядом.

## Урок 7. Модули и слои: `mod`, `use`, `pub`, `pub(crate)`

Когда файлов много, важно, чтобы каждый отвечал за **одну** вещь и чтобы было понятно,
кто от кого зависит. Это и есть «архитектура».

**Модуль** — это отдельный файл-полка (`world.rs`, `building.rs`, …). Чтобы Rust его
подключил, в `main.rs` есть строки `mod world;`, `mod building;` и т.д. `use ...` —
это «взять что-то из другого модуля к себе», чтобы писать короче.

**Видимость** (кто что видит):
- по умолчанию всё **приватно** — видно только внутри своего модуля;
- `pub` — публично, видно отовсюду;
- `pub(crate)` — видно **внутри нашего проекта**, но не наружу (если бы проект был
  библиотекой). Мы так пометили `tiles` в `World`: системам он нужен, а «внешнему
  миру» — нет.

**Слои проекта** (стрелки зависимостей смотрят **вниз** — верхнее знает про нижнее,
но не наоборот; это и есть «расцепление»):

```
main.rs            ← точка входа + игровой цикл
  ├─ input.rs      ← фаза 1: ввод
  ├─ systems.rs    ← фаза 2: симуляция
  ├─ render.rs     ← фаза 3: отрисовка
  ├─ game.rs       ← состояние игры
  ├─ world.rs      ← данные поля
  ├─ building.rs   ← поведение здания
  ├─ types.rs      ← базовый «словарь»
  └─ config.rs     ← настройки-числа
```

**Золотое правило потока данных** (запомни как таблицу умножения):
- **input** — МЕНЯЕТ мир (по воле игрока);
- **systems** — МЕНЯЕТ мир (по правилам игры);
- **render** — только ЧИТАЕТ мир, **никогда не меняет**.

Почему это важно? Потому что тогда, чтобы понять «откуда в мире взялось изменение»,
надо смотреть **только в два места** (input и systems), а не во все десять. Это и есть
смысл хорошей архитектуры:

📖 По Нистрому, хорошая архитектура — про изменение: *«the measure of a design is how
easily it accommodates changes»* и цель — *«minimize the amount of knowledge you need
to have in-cranium before you can make progress»* («мера качества дизайна — насколько
легко он принимает изменения»; «свести к минимуму объём знаний, который надо держать в
голове, прежде чем начать что-то делать»).
— [Game Programming Patterns, «Architecture, Performance, and Games»](https://gameprogrammingpatterns.com/architecture-performance-and-games.html)

🎯 Открой `render.rs`. Найди хоть одну строку, которая **меняет** мир (что-то
присваивает в `world`/`game`). Не найдёшь — и это правильно. Рендер только читает.

## Урок 8. Масштаб: почему `enum`, а не 1000 вариантов

Теперь полный ответ на твой вопрос. Разберём страх «1000 enum» по косточкам.

### 8.1. Главное недоразумение: контент ≠ код

Ты смешиваешь два **разных** числа:
- сколько разных **поведений** (бур, лента, печь-крафтер, ящик…) — их **мало**,
  ~10–15 на всю Factorio, и растут медленно;
- сколько разных **штук** (машин, рецептов, предметов) — их **сотни**, но это
  **данные**, а не новый код.

Каменная печь, стальная печь, электропечь — это **не** три варианта `enum`. Это
**одно** поведение «плавит по рецепту», которое отличается только числами. Разнообразие
даёт **таблица данных**, а не новый `match`.

### 8.2. Как это в коде (data-driven)

Плохо (то, чего ты боишься, — и правильно боишься):
```rust
enum Building { StoneFurnace {…}, SteelFurnace {…}, ElectricFurnace {…}, /* …1000 — НЕТ */ }
```

Правильно — печь и сборщик схлопываются в **одно** поведение `Crafter`, а вариативность
уезжает в данные:
```rust
struct Recipe { input: Item, output: Item, time: f32 }
static RECIPES: &[Recipe] = &[
    Recipe { input: Item::IronOre,   output: Item::IronPlate, time: 1.2 },
    Recipe { input: Item::IronPlate, output: Item::Gear,      time: 0.8 },
    // 500 рецептов = 500 строк ДАННЫХ, ноль нового кода и ноль новых match
];

enum Building {
    Miner   { dir: Direction, cooldown: f32, output: Option<Item> },
    Crafter { dir: Direction, recipe: usize, input: Option<Item>, progress: f32, output: Option<Item> },
    Belt    { dir: Direction, item: Option<Item> },
    Chest   { items: u32 },
}
```
Enum остаётся из ~4–10 вариантов **навсегда**, а контент растёт в `RECIPES`.

### 8.3. У всякого выбора есть цена: «проблема выражения»

Честно про минус enum. У любого дизайна две оси роста: добавлять **новые типы**
(кейсы) и добавлять **новые операции** над ними. Сделать так, чтобы легко было и то,
и другое, — известная сложная задача.

📖 «Проблема выражения»: *«The goal is to define a data abstraction that is extensible
both in its representations and its behaviors, where one can add new representations
and new behaviors to the data abstraction, without recompiling existing code, and
while retaining static type safety.»* («Цель — определить абстракцию данных, расширяемую
и по представлениям, и по поведениям: можно добавлять новые представления и новые
поведения, не перекомпилируя существующий код и сохраняя статическую типобезопасность».)
— [Wikipedia, «Expression problem»](https://en.wikipedia.org/wiki/Expression_problem) (формулировка Филипа Уодлера)

Практический перевод:
- **`enum`** — легко добавлять **операции** (новый метод = один `match`), но добавить
  **новый тип** = тронуть каждый `match` (правда, компилятор укажет где — Урок 5).
- **Трейт-объекты** — наоборот: легко добавить **новый тип** (в отдельном файле), но
  добавить **операцию** = дописать во все реализации, и теряется проверка всех случаев.

### 8.4. Альтернатива №1: трейт-объекты (динамическая диспетчеризация)

«Трейт» (`trait`) — это набор методов-обещаний, общий для разных типов (интерфейс).
«Трейт-объект» — значение, тип которого известен только во время выполнения.

📖 *«A trait object points to both an instance of a type implementing our specified
trait and a table used to look up trait methods on that type at runtime.»*
(«Трейт-объект указывает и на экземпляр типа, реализующего указанный трейт, и на
таблицу для поиска методов трейта у этого типа во время выполнения».)
📖 *«In dynamic dispatch cases, the compiler emits code that at runtime will know which
method to call.»* («При динамической диспетчеризации компилятор порождает код, который
уже во время выполнения узнаёт, какой метод вызвать».)
— [The Rust Book, «Trait Objects»](https://doc.rust-lang.org/book/ch18-02-trait-objects.html)

Минусы для нас: (1) теряется исчерпывающая проверка; (2) есть накладные расходы на
поиск метода в таблице; (3) — и это главное для фабрики — **взаимодействие разных
типов** (бур отдаёт → лента принимает → печь принимает) через полиморфизм делается
мучительно (классическая «двойная диспетчеризация»), а через `match` — тривиально.
Трейт-объекты реально нужны в основном для **модов/плагинов**: когда сторонний код
должен добавлять здания, не трогая твой.

### 8.5. Почему `enum`/дженерики ещё и быстрые

`enum` + `match` — это **статическая** диспетчеризация: компилятор знает всё заранее.

📖 *«…we pay no runtime cost for using generics.»* и *«Rust accomplishes this by
performing monomorphization of the code using generics at compile time.»* («…мы не
платим во время выполнения за использование дженериков»; «Rust достигает этого,
выполняя мономорфизацию кода с дженериками во время компиляции»).
— [The Rust Book, «Performance of Code Using Generics»](https://doc.rust-lang.org/book/ch10-01-syntax.html)

То есть простой путь тут ещё и **не медленнее**, а часто быстрее «гибкого».

### 8.6. Альтернатива №2: ECS (когда игра станет огромной)

Когда сущностей тысячи и упираешься в скорость — используют **ECS** (Entity-Component-
System): сущность — это не `enum` и не класс, а набор **компонентов** (`Position`,
`Inventory`, `Crafter{recipe}`…), а логика живёт в **системах**, которые обходят
компоненты. Разнообразие — из **композиции** компонентов + данных. Это то, как
устроены игры уровня Factorio. Классика темы в Rust — доклад Кэтрин Уэст (см.
«Материалы»). Важно: наш раздел `world.rs` (данные) + `systems.rs` (логика) — это
**уже** мышление ECS в миниатюре, так что переход будет плавным, ничего не пропадёт.

### 8.7. Вывод

Начинать с `enum` — **не** ошибка новичка, а правильная первая ступень. Переходи выше
только когда почувствуешь настоящую боль (много вариаций → данные; моды → трейты;
тысячи сущностей и тормоза → ECS). Не раньше:

📖 Книга прямо предупреждает про **преждевременные абстракции**: «speculative design»
(проектирование под воображаемые будущие нужды) создаёт сложность, которая может
никогда не окупиться, а лишние слои прячут реальную работу кода.
— [Game Programming Patterns, «Architecture, Performance, and Games»](https://gameprogrammingpatterns.com/architecture-performance-and-games.html)

## Урок 9. Проверяем себя: тесты и `clippy`

**Тесты** — код, который проверяет твой код. Наша логика мира **чистая** (не нужны
окно, мышь, время), поэтому её легко проверять. Смотри конец [`src/systems.rs`](src/systems.rs):

```rust
#[cfg(test)]                 // «компилируй это только при `cargo test`»
mod tests {
    …
    #[test]                  // это — тест
    fn miner_belt_chest_delivers_items() {
        let mut w = World::new(3, 1);
        w.tiles[0].ore = true;                                    // руда под буром
        w.place(0, 0, Building::new(Tool::Miner, Direction::East));
        w.place(1, 0, Building::new(Tool::Belt,  Direction::East));
        w.place(2, 0, Building::new(Tool::Chest, Direction::East));
        for _ in 0..40 { step(&mut w, TICK); }                    // прогнали 40 тиков
        // …и проверяем, что в ящик что-то доехало (assert!)
    }
}
```

`assert!(...)` — «утверждаю, что это правда; если нет — тест падает». Запуск: `cargo test`.

**`clippy`** — линтер, «строгий, но добрый учитель стиля». Он не про ошибки, а про
«так писать красивее/идиоматичнее». Именно clippy подсказал нам заменить вложенный
`if` на match-guard (Урок 5). Запуск: `cargo clippy`. Полный каталог его подсказок —
[rust-lang.github.io/rust-clippy](https://rust-lang.github.io/rust-clippy/).

🎯 Твой ежедневный ритм разработки:
```
правка → cargo test  (не сломал ли логику?)
       → cargo clippy (можно ли красивее?)
       → cargo run    (как это глазами?)
```

```rust
},
```

**За что отвечает каждое поле** (это «состояние» одного конкретного сборщика на поле):

| Поле | Тип | За что отвечает простыми словами |
|------|-----|----------------------------------|
| `dir` | `Direction` | Куда сборщик «смотрит» = в какую сторону он **отдаёт** готовую шестерёнку соседу. |
| `input` | `Option<Item>` | **Входной карман**: лежит ли внутри пластина-сырьё. `Some(пластина)` = лежит, `None` = пусто (вспомни `Option` из Урока 3). |
| `progress` | `f32` | **Таймер сборки**: сколько секунд уже собираем. Растёт от `0.0` до `ASSEMBLE_TIME`. |
| `output` | `Option<Item>` | **Выходной карман**: лежит ли готовая шестерёнка и ждёт, когда её заберут. `Some(шестерёнка)` или `None`. |

Почему именно эти четыре поля? Потому что у любой машины-крафтера один и тот же
жизненный цикл, и каждое поле — это одна его часть:

```
  сосед кладёт          таймер копит секунды        сосед забирает
  пластину              (пока не готово)            шестерёнку
  ── input=Some(Plate) ──►  progress растёт  ──►  output=Some(Gear) ──►  отдаём в сторону dir
       (метод accept)        (метод update)         (метод output → remove_output)
```

Теперь запусти `cargo build`. Компилятор начнёт ругаться «не обработан `Assembler`» —
и это **хорошо**: он ведёт тебя по всем `match`, где надо дописать поведение (Урок 5 и
Приложение про ошибки). Каждый метод-`match` отвечает на **один вопрос** о здании:

| Метод | На какой вопрос он отвечает |
|-------|------------------------------|
| `new` | Как создать новый (пустой) сборщик? |
| `update` | Что сборщик делает сам за один тик? |
| `output` | Что и **куда** он готов **отдать** соседу? |
| `can_accept` | Какой предмет он готов **принять**? |
| `accept` | Куда положить принятый предмет? |
| `remove_output` | Убери отданный предмет из выходного кармана. |
| `dir` | В какую сторону он смотрит? |

Идём по вопросам — вот что писать в каждый метод:

**`new` — «как создать пустой сборщик».** (Вверху файла добавь `ASSEMBLE_TIME` в строку
`use crate::config::...`.) Все карманы пустые, таймер на нуле:
```rust
Tool::Assembler => Building::Assembler { dir, input: None, progress: 0.0, output: None },
```

**`update` — «что делает за тик».** Один в один как Печь, только другая константа и
другой результат. Читается так: «если выход свободен И во входе есть пластина —
копи `progress`; как накопили `ASSEMBLE_TIME` секунд, переложи: в выход — шестерёнку,
вход опустоши, таймер сбрось».
```rust
Building::Assembler { input, progress, output, .. }
    if output.is_none() && input.is_some() =>      // ← «страж»: только когда есть сырьё и выход пуст
{
    *progress += dt;                               // капаем время (dt — длина тика)
    if *progress >= ASSEMBLE_TIME {                // накопили сколько нужно?
        *output = Some(Item::Gear);                //   → положить готовую шестерёнку в выход
        *input = None;                             //   → сырьё израсходовано, вход пуст
        *progress = 0.0;                           //   → обнулить таймер к следующей штуке
    }
}
```
(`*progress` со звёздочкой — потому что `progress` тут ссылка на поле, а звёздочка
значит «работать с самим значением по этой ссылке». Подробнее — Урок 6.)

Плюс в самом конце `update` есть ветка «остальные ничего не делают за тик», которая
перечисляет все варианты (без `_`). Допиши в неё Сборщик — на случай, когда его страж
не сработал (выход занят / нет сырья):
```rust
Building::Miner { .. }
| Building::Furnace { .. }
| Building::Belt { .. }
| Building::Assembler { .. }   // ← добавили
| Building::Chest { .. } => {}
```

**`output` — «что и куда я готов отдать».** Вот эту ветку ты особенно просил разобрать.
Её вызывают **системы** (`systems.rs`) на каждом тике, обходя все здания с вопросом:
«тебе есть что передать соседу?». Метод должен ответить `Some((предмет, направление))`
или ничего. В этом методе **два места** для Сборщика — компилятор укажет на оба.

Первое — «отдаю, когда в выходе что-то есть» (рядом с такими же ветками Печи/Бура):
```rust
Building::Assembler { dir, output: Some(it), .. } => Some((*it, *dir)),
```
Разберём **по кусочкам**:
- `Building::Assembler { … }` — «если это Сборщик…»;
- `output: Some(it)` — «…и в выходном кармане **что-то лежит** (не `None`), назови это
  `it`». Это и есть сила сопоставления с образцом: мы **одновременно** проверяем
  «там `Some`» и **достаём** содержимое в переменную `it`;
- `dir` — заодно достаём направление в переменную `dir`;
- `..` — «остальные поля (`input`, `progress`) мне здесь не нужны, пропусти их»;
- `=> Some((*it, *dir))` — ответ: «да, **отдаю предмет `it` в сторону `dir`**». Пара
  `(*it, *dir)` — это (что отдать, куда отдать). Звёздочки — берём сами значения из
  ссылок (`Item` и `Direction` — маленькие Copy-типы, копировать их дёшево).

Второе — «а если выход пуст, отдавать нечего». В конце метода есть ветка, которая
**перечисляет все варианты** и возвращает `None` (в нашем коде НЕТ `_` — специально,
чтобы компилятор ловил новые здания). Допиши в этот список Сборщик:
```rust
Building::Miner { output: None, .. }
| Building::Belt { item: None, .. }
| Building::Furnace { output: None, .. }
| Building::Assembler { output: None, .. }   // ← добавили
| Building::Chest { .. } => None,
```
Если забудешь — компилятор так и скажет: «случай `Assembler { output: None }` не покрыт».
Это и есть та самая «карта задач» в действии.

Именно поэтому Печь/Бур/Лента/Сборщик отдают предметы «наружу» одинаково: система не
знает и не хочет знать, кто перед ней, — она просто спрашивает `output()`.

**`can_accept` — «что я готов принять».** Тоже два места. Сначала — «принимаю Пластину,
когда вход пуст»:
```rust
Building::Assembler { input: None, .. } => item == Item::IronPlate,
```
А затем допиши Сборщик в конечную ветку «всё остальное не принимает» (тоже без `_`):
```rust
Building::Miner { .. }
| Building::Belt { .. }
| Building::Furnace { .. }
| Building::Assembler { .. } => false,   // ← добавили (занятый сборщик ничего не берёт)
```
Читается: «если это Сборщик с **пустым** входом — верни `true`, только когда
предлагаемый `item` — Пластина». Сосед-лента спросит это, прежде чем толкнуть предмет.

**`accept` — «куда положить принятое».** Кладём во входной карман:
```rust
Building::Assembler { input, .. } => *input = Some(item),
```

**`remove_output` — «убери отданное».** Систем вызовет это после успешной передачи,
чтобы выход снова стал пустым:
```rust
Building::Assembler { output, .. } => *output = None,
```

**`dir` — «куда смотрю».** Возвращаем направление:
```rust
Building::Assembler { dir, .. } => Some(*dir),
```

### Шаг 4 — как это выглядит (`src/render.rs`)

**Сначала про систему координат экрана** (без этого отрисовка — магия). Экран — это
сетка пикселей. Точка `(0, 0)` — **левый верхний** угол. **X растёт вправо, Y растёт
вниз** (да, вниз — так принято в 2D-графике). Каждая клетка поля — квадрат со стороной
`TILE` пикселей. Функция `draw_building`, в которую мы дописываем, уже получает:
- `sx`, `sy` — пиксельные координаты **левого верхнего угла** этой клетки;
- `pad` — маленький отступ внутрь (чтобы между зданиями была видна сетка);
- `inner` — сторона внутреннего квадрата = `TILE - 2*pad`.

Их считать не надо — они уже есть в начале функции. Мы просто ими пользуемся.

**Цвет шестерёнки.** Функция `item_color` — это маленький `match`, который говорит,
каким цветом рисовать каждый предмет. Добавь строку про `Gear`:
```rust
Item::Gear => color_u8!(150, 200, 150, 255),  // зеленоватый
```
`color_u8!(R, G, B, A)` — это цвет числами от 0 до 255: **R**ed, **G**reen, **B**lue и
**A**lpha (непрозрачность; `255` = полностью непрозрачный). `(150, 200, 150)` — больше
зелёного, поэтому кружок-шестерёнка получится салатовым.

**Рисуем само здание.** Добавь ветку в `match` внутри `draw_building`:
```rust
Building::Assembler { dir, input, progress, output } => {
    draw_rectangle(sx + pad, sy + pad, inner, inner, color_u8!(90, 110, 170, 255));
    draw_arrow(sx, sy, *dir, WHITE);
    let frac = (progress / ASSEMBLE_TIME).clamp(0.0, 1.0);
    draw_rectangle(sx + pad, sy + TILE - pad - 4.0, inner * frac, 4.0, YELLOW);
    if let Some(it) = output { draw_item(sx, sy, *it); }
    else if let Some(it) = input { draw_item(sx, sy, *it); }
}
```
Теперь **каждая строка по отдельности**:

- `Building::Assembler { dir, input, progress, output } =>` — «если рисуем Сборщик,
  достань его поля в переменные `dir`, `input`, `progress`, `output`, чтобы дальше их
  использовать». Здесь **нет** `..`, потому что нам нужны все четыре поля.

- `draw_rectangle(sx + pad, sy + pad, inner, inner, color_u8!(90, 110, 170, 255));`
  — рисуем **тело** здания: квадрат. Аргументы `draw_rectangle` — это
  `(x, y, ширина, высота, цвет)`. То есть: левый-верхний угол в `(sx+pad, sy+pad)`
  (клетка плюс отступ), размер `inner × inner`, цвет — синевато-фиолетовый.

- `draw_arrow(sx, sy, *dir, WHITE);` — рисуем белую стрелку-треугольник, показывающую,
  **куда** сборщик отдаёт (`dir`). `*dir` — берём само значение направления из ссылки.
  `WHITE` — готовый белый цвет из macroquad. (`draw_arrow` — наша функция, она уже
  есть в `render.rs`; ей всё равно, для какого здания рисовать стрелку.)

- `let frac = (progress / ASSEMBLE_TIME).clamp(0.0, 1.0);` — считаем **долю
  готовности** от 0 до 1. `progress` — сколько секунд уже собираем, `ASSEMBLE_TIME` —
  сколько нужно всего. Их деление даёт долю: `progress=0.4`, `ASSEMBLE_TIME=0.8` →
  `frac=0.5` (собрано наполовину). `.clamp(0.0, 1.0)` — «зажать» число в диапазон
  `[0; 1]`, чтобы из-за случайного перебора не получилось больше 1. `let frac = …` —
  заводим локальную переменную с этим числом.

- `draw_rectangle(sx + pad, sy + TILE - pad - 4.0, inner * frac, 4.0, YELLOW);` —
  рисуем **жёлтую полоску прогресса** у нижнего края клетки. Разберём координаты:
  - X = `sx + pad` — левый край, как у тела;
  - Y = `sy + TILE - pad - 4.0` — почти самый низ клетки (`sy + TILE` — это нижняя
    граница клетки; отнимаем отступ и высоту полоски `4`, чтобы она села аккуратно);
  - ширина = `inner * frac` — **вот вся суть**: ширина = полная ширина × доля
    готовности. Пусто → полоска нулевая; готово → полоска во всю клетку;
  - высота = `4.0` пикселя; цвет — `YELLOW`.
  Итог: жёлтая полоска, растущая слева направо по мере сборки. Точно такую же ты уже
  видел у Печи — это визуальный «прогресс-бар».

- `if let Some(it) = output { draw_item(sx, sy, *it); }` — рисуем **кружок-предмет** в
  центре клетки. `if let Some(it) = output` читается: «если в выходном кармане
  что-то лежит — назови это `it` и выполни блок». `draw_item` (наша функция) рисует
  кружок цветом предмета (тем самым из `item_color`). `*it` — само значение предмета.

- `else if let Some(it) = input { draw_item(sx, sy, *it); }` — «а если выход **пуст**,
  но во **входном** кармане что-то есть — нарисуй входной предмет». Приоритет у готовой
  шестерёнки (`output` важнее); если оба кармана пусты — не рисуем ничего.

> `ASSEMBLE_TIME` тут доступен, потому что вверху `render.rs` уже есть
> `use crate::config::*;` («возьми из config всё») — просто пользуйся.

## 🧯 Приложение: как читать ошибку компилятора

Главный навык новичка в Rust — **не бояться красного текста**. Ошибка компилятора —
это не «ты плохой», это подробная подсказка. Официальная документация прямо на этом настаивает:

📖 *«An important part of the process of learning Rust is learning how to read the
error messages the compiler displays: These will guide you toward working code.»*
(«Важная часть обучения Rust — научиться читать сообщения об ошибках, которые
показывает компилятор: они ведут тебя к работающему коду».)
— [The Rust Book, «Introduction»](https://doc.rust-lang.org/book/ch00-00-introduction.html)

И почему это вообще так строго:

📖 *«In Rust, the compiler plays a gatekeeper role by refusing to compile code with
these elusive bugs, including concurrency bugs.»* («В Rust компилятор играет роль
привратника, отказываясь компилировать код с этими неуловимыми багами, включая баги
многопоточности».) — [The Rust Book, «Introduction»](https://doc.rust-lang.org/book/ch00-00-introduction.html)

**Разберём настоящую ошибку.** Допустим, в Практикуме ты добавил вариант
`Building::Assembler`, но забыл дописать его в `match` внутри `dir`. Компилятор скажет
примерно так:

```
error[E0004]: non-exhaustive patterns: `&Assembler { .. }` not covered
   --> src/building.rs:145:15
    |
145 |         match self {
    |               ^^^^ pattern `&Assembler { .. }` not covered
    |
    = help: ensure that all possible cases are being handled by adding
            a match arm with a wildcard pattern or an explicit pattern
```

Читаем по частям — **сверху вниз, слева направо**:
1. `error[E0004]` — код ошибки. Его можно даже загуглить или выполнить
   `rustc --explain E0004` — получишь подробное объяснение прямо в терминале.
2. `non-exhaustive patterns: ... not covered` — **суть**: «сопоставление неполное,
   вариант `Assembler` не обработан». Помнишь Урок 5 про исчерпывающесть? Вот она.
3. `--> src/building.rs:145:15` — **где именно**: файл `building.rs`, строка `145`,
   столбец `15`. Можно кликнуть в редакторе и попасть прямо туда.
4. Стрелочки `^^^^` — показывают **конкретное место** в коде.
5. `= help: ...` — **что делать**: добавь недостающий рукав. Компилятор буквально
   говорит решение.

**Алгоритм, когда видишь ошибку (заучи):**
1. Не паникуй, не удаляй код наугад.
2. Прочитай **первую** ошибку (не последнюю!). Часто одна ошибка порождает каскад —
   чини самую верхнюю, остальные могут исчезнуть сами.
3. Посмотри на `-->` — открой это место.
4. Прочитай `help:` — обычно там прямая подсказка.
5. Не понял код `error[EXXXX]` — выполни `rustc --explain E0004` (подставь свой номер).
6. Исправил — снова `cargo build`. Повторяй, пока не станет чисто.

🧠 **Аналогия.** Компилятор Rust — не злой вахтёр, а дотошный корректор, который
подчёркивает каждую опечатку и на полях пишет, как её исправить. Другие языки
«пропустят» тебя, а баг всплывёт у игрока. Rust ловит это **сейчас**, пока дёшево.

🎯 Проверь на себе: открой `src/building.rs`, в методе `dir` **удали** строку
`Building::Chest { .. } => None,` и запусти `cargo build`. Прочитай ошибку целиком —
узнаёшь `E0004`? Верни строку назад. Теперь ты знаешь эту ошибку в лицо.

## Словарь терминов

| Термин | Простыми словами |
|--------|------------------|
| **Компилятор** | Программа, переводящая твой код в машинный и проверяющая его до запуска. |
| **Cargo** | «Прораб»: собирает, запускает, тестирует проект. |
| **Crate** | Единица компиляции/пакет в Rust. Наш проект — один crate. |
| **Модуль (`mod`)** | Файл-полка с кодом; способ разложить проект по темам. |
| **`struct`** | Тип-«анкета»: несколько именованных полей вместе. |
| **`enum`** | Тип-«галочка»: значение — ровно один из перечисленных вариантов, каждый со своими данными. |
| **`match`** | Разбор значения по образцам; в Rust обязан покрыть все случаи. |
| **Страж (match guard)** | Доп. `if`-условие в рукаве `match`. |
| **`Option<T>`** | «Либо значение (`Some`), либо ничего (`None`)» — честная замена null. |
| **`Vec<T>`** | Растущий список значений одного типа. |
| **Владение (ownership)** | У каждого значения один владелец; уходит владелец — освобождается память. |
| **Заимствование (borrow)** | Одолжить значение по ссылке: `&T` (читать) или `&mut T` (менять). |
| **Borrow checker** | Часть компилятора, следящая за правилами ссылок. |
| **Игровой цикл (game loop)** | Вечный цикл input→update→render. |
| **Тик (tick)** | Один фиксированный шаг симуляции. |
| **Система (system)** | Функция, продвигающая мир (в ECS — обработчик компонентов). |
| **Трейт (`trait`)** | Набор методов-обещаний, общий интерфейс для разных типов. |
| **Трейт-объект (`dyn`)** | Значение, чей тип известен во время выполнения; динамическая диспетчеризация. |
| **Диспетчеризация** | «Какой метод вызвать»: статическая (в компиляции) vs динамическая (в рантайме). |
| **Мономорфизация** | Rust «размножает» дженерик-код под конкретные типы → нет накладных расходов. |
| **ECS** | Entity-Component-System: данные-компоненты + системы; для больших игр. |
| **Data-driven** | Разнообразие задаётся таблицами данных, а не новым кодом. |
| **Линтер (`clippy`)** | Советчик по стилю и идиоматичности. |

## Как учиться (метод, а не только материал)

Материалы бесполезны без метода. Вот проверенный цикл:

1. **Читай мало, делай много.** Прочитал урок — сразу открой код и повтори руками.
2. **Ломай нарочно.** Убери точку с запятой, поменяй тип, удали рукав `match`. Прочитай
   ошибку компилятора **целиком** — Rust объясняет ошибки лучше почти всех языков.
   Ошибка — это урок, а не наказание.
3. **Меняй по одной вещи.** Не переписывай пол-игры за раз. Одна правка → `cargo run` →
   посмотрел результат → следующая. Так всегда понятно, что именно сработало.
4. **Объясни вслух.** Если можешь объяснить кусок кода «резиновой уточке» (или коту) —
   ты его понял. Не можешь — вернись и перечитай.
5. **Строй своё.** После практикума придумай своё здание/предмет и добавь по рецепту из
   Урока 8/Практикума. Собственная идея запоминается в разы лучше чужой.

> Ты не «самый тупой программист» — ты просто в начале. Каждый, кто пишет на Rust
> сегодня, когда-то ругался на borrow checker. Разница только в количестве повторений.
> Открывай код, делай задания 🎯 — и через неделю этот файл будет казаться очевидным. 🦀
