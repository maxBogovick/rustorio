# Дизайн: жидкости и электричество как примитивы движка

Статус: **принят владельцем 05.08.2026**, реализация по карточкам §10. До этого движок был
предметным, а мод `waterworks` — инсценировкой на предметах; он остаётся как пример «как было».

> **Область.** Запрет снят: «Вне рамок» в `GDD.md` больше не числит жидкости, трубы и
> электричество. Правка GDD сделана первым шагом, до кода.

Решения владельца по §11 (развилки закрыты, дальше не переигрываются):

1. Область — открыта, GDD поправлен.
2. Ток — **опция A**: питания требуют только объявившие здания; существующий контент без миграции.
3. Соединение тока — **столбы с радиусом** (`POLE`), не простая смежность.
4. Имена публичного API — **приняты как предложены** в §5 и §8.

Документ отвечает на «как», сверяясь с ограничениями репозитория (`AGENTS.md`): детерминизм,
бюджет тика, границы пакетов, расширяемость данными, совместимость сейва, имена публичного API.

## 1. Что должно получиться

Настоящая цепочка Factorio, а не её пересказ предметами:

```
река ──насос──► [сеть воды] ──► котёл(+уголь) ──► [сеть пара] ──► генератор ──► [электросеть] ──► электро-машины
```

Три новых примитива в домене: **жидкость** (тип + объём), **сеть** (труб и проводов) и
**мощность** (производство/потребление за тик). Всё, что можно, — данными: новая жидкость и новая
жидкостная машина заводятся JSON-ом, без правки кода (иначе `ContentCouplingRatchetTest` посчитает
новый `switch`/`instanceof` по типу контента как регресс).

## 2. Опорный приём: инкрементальная сеть, как у лент

Правило репозитория: **не сканировать мир каждый тик, считать инкрементально при изменении**
(`AGENTS.md`; образец — `World.statusCounts`). У движка уже есть ровно нужный паттерн — `BeltSegment`:
лента собирается в сегмент при постановке/сносе, а тик стоит O(длины сегмента), не O(мира).

И сеть труб, и электросеть строятся тем же приёмом: **связный компонент, поддерживаемый
инкрементально при `place`/`remove`**, а не пересобираемый обходом мира каждый кадр. Постановка и
снос — действия игрока, там O(размера сети) допустимо (та же логика, что у `PlacementVeto`).

## 3. Жидкость — ядро решения

**Решение: жидкость — самостоятельный тип `FluidType` в отдельном реестре, а не флаг на
`ItemType`.**

Почему не флаг на предмете:

- жидкость — непрерывный **объём**, а не штучные единицы; предмет-с-флагом протащил бы «а это
  жидкость?»-ветку в каждый путь, где сейчас ходит `ItemType`, — ровно тот `if`-по-типу, что
  запрещён;
- раздельные типы держат потоки несмешиваемыми на уровне компилятора: труба возит `FluidType`,
  лента — `ItemType`, перепутать нельзя.

```
FluidType(ContentId id, String label, String colorRgb)   // минимум; температуры в v1 нет
```

Реестр: `RegistrationContext.fluids() : Registry<FluidType>` — симметрично `items()`/`techs()`.
Ванильная вода/пар переезжают из предметов в жидкости; предметная вода из `waterworks` остаётся как
отдельный пример «как было».

## 4. Сеть труб (`FluidNetwork`)

Аналог `BeltSegment`, но с тремя отличиями:

1. **связность 2D** — четыре соседа, без направления (у ленты — прямой ряд по направлению);
2. хранит **тип жидкости + суммарный объём**, а не список штук;
3. **уравнивать по тику не нужно.** Сеть — это **одно ведро**: `capacity = число_труб ×
   ёмкость_трубы`, «насколько полна труба» = `объём / capacity`. Никакого перетекания тайл-в-тайл
   каждый тик (в отличие от лент, где каскад обязателен). Это ключевой выигрыш: **сеть труб дешевле
   ленты** — за тик её не трогает вообще никто, кроме краёв (насос долил, котёл забрал).

Правила:

- **одна жидкость на сеть.** Пустая труба принимает жидкость той сети, к которой присоединилась.
  Две непустые сети разной жидкости **не сливаются** — соединяющая труба остаётся границей
  (принадлежит той стороне, к которой встала первой). Смешивания воды и пара нет by construction.
- **постановка** трубы: union с совместимыми (пустыми или той же жидкости) соседними сетями;
- **снос** трубы: возможен распад на несколько компонент → ограниченный flood-fill затронутой сети,
  объём делится между компонентами **пропорционально ёмкости** (детерминированно). Стоимость
  O(размера сети), только при сносе. Правка при реализации: «пропорционально числу труб» неверно,
  как только узлы разной ёмкости — бак это одна клетка на 25 труб, и компоненте досталось бы
  больше, чем она вмещает. По ёмкости доля всегда в пределах своего лимита.

Обход для split/merge и для сейва идёт **по координатам** (не по hash/ссылке) — иначе плавающий
порядок сломает детерминизм.

## 5. Как машины касаются жидкости

`TickContext` намеренно узкий (пять методов — «шесть вещей, что зданию нужны от мира»). Жидкость
требует его расширить — но точечно, а не выдать весь мир. Предлагаемый минимум:

```
FluidPort fluidPort(int x, int y, Direction side);   // ручка к соседней сети со стороны side
// FluidPort: FluidType fluid(); long amount(); long capacity();
//            long insert(FluidType f, long amount);  // вернёт сколько влезло
//            long extract(FluidType f, long amount);  // вернёт сколько выдала
```

Домен по-прежнему не знает про `World` напрямую — порт идёт через `TickContext`, реализует его
`World` (единственная реализация). Имена этих методов — **публичный API, называет владелец**,
переименовать потом нельзя.

Машины (все — новые Java-классы движка, конфигурируемые данными, как `Miner`/`Furnace`):

| Здание | Аналог | Поведение |
|---|---|---|
| **Труба** (`PIPE`) | Belt | узел `FluidNetwork`, ничего не «тикает» |
| **Бак** (`TANK`) | Chest | труба с большой ёмкостью |
| **Насос** (`PUMP`) | Miner | производит воду в соседнюю сеть; своё правило размещения «у воды» |
| **Котёл** (`BOILER`) | Furnace | забирает воду из сети + топливо-предмет → выдаёт пар в другую сеть |
| **Генератор** (`GENERATOR`) | — | забирает пар → добавляет мощность в электросеть (см. §6) |

**Насос у воды.** `PlacementRule` — функциональный интерфейс, расширяется: добавляем правило
`ADJACENT_TO_WATER` (`WATER` есть в соседней клетке). Данными это не выразить (правил в схеме
фиксированный набор), поэтому правило — код движка, а не мода.

## 6. Электричество (`PowerNetwork`)

Тот же инкрементальный компонент, что и трубы, но за тик по нему идёт **дешёвый проход-сумма**:
сложить производство, сложить спрос; спрос ≤ предложения → все запитаны, иначе доля по спросу
(тай-брейк — по координате, детерминированно). Стоимость O(размера сети) за тик — мерить
бенчмарком.

**Ток опционален (решение владельца, опция A).** Требуют питания только здания, которые это
объявили; бур/печь/лаба продолжают работать даром. Новые электро-машины — требуют. Весь текущий
контент, карты и сейвы живут без миграции. Отвергнута опция B (ток нужен всем, как в Factorio):
она стоит пересмотра баланса и миграции каждой карты, а цепочка замыкается честно и без неё —
генератор даёт мощность, её потребляет хоть одна электро-машина, и пар перестаёт быть тупиком.

**Как соединяется ток (решение владельца):** здание-**столб** (`POLE`) с радиусом; машины в радиусе
столба входят в одну сеть. Простая смежность (сеть растёт по соседним клеткам, как труба) отвергнута:
дешевле в реализации, но планировка электросети перестаёт быть отдельной задачей игрока.

## 7. Формат сейва

**Бамп версии не понадобился** — остаётся v9. Правка при реализации: при кодековом формате новый
прототип не меняет форму файла, строка здания как была `{x, y, prototypeId, state}`, так и осталась,
а `state` пишет кодек самого прототипа. Сейв, написанный до жидкостей, грузится целиком и без
изменений — это показывает `GoldenSaveTest` на файле `src/test/resources/saves/world-v9.json`,
лежащем в репозитории с прошлой версии. Бамп ради бампа отверг бы каждый сейв на диске, не защитив
ни от чего. Бампить придётся тогда, когда изменится форма УЖЕ существующего состояния.

- **Топология сетей не сериализуется** — восстанавливается из геометрии зданий на загрузке, ровно
  как сейчас пересобираются сегменты лент. Сохраняется только состояние на тайле: труба хранит свою
  долю жидкости (`тип + amount`), на загрузке сети пересобираются и суммируют доли. Единица
  персистентности — тайл (как `BeltState` хранит `held`).
- Электричество — почти целиком транзиентно (пересчитывается за тик): хранить нечего, кроме факта
  существования зданий (накопители-аккумуляторы — вне v1).
- **Миграция:** сейв v9 не знает про жидкости/ток → грузится как пустые сети; новые поля
  опциональны. Предметные сейвы (в т.ч. `waterworks`) не затронуты. Детали — правило `persistence`.

## 8. Мод-API (имена — за владельцем)

- `RegistrationContext.fluids()` — реестр `FluidType`.
- Здание в JSON получает опциональные жидкостные порты: `fluidInput`/`fluidOutput` (id жидкости +
  стороны). Так data-мод описывает свою жидкостную машину на новом архетипе без Java.
- Код-мод получает capability-интерфейсы (как `TransportNode` для лент): свой узел сети / свой
  потребитель тока — классом вне `domain.building`.
- `BuildingType`: **дописать** `PIPE, TANK, PUMP, BOILER, GENERATOR, POLE` в конец (не вставлять —
  первые девять держат клавиши 1–9; приём уже узаконен для `FILTER`/`INSERTER`/`ASSEMBLER`).
  Полное «открытие» enum'а — вне области; дописать ванильные виды — принятый паттерн.

## 9. Рендер

- **Уровень заполнения.** `Appearance` сейчас = спрайт + один числовой значок + статус. v1:
  показывать заполнение готовым значком (процент), чтобы не менять публичный тип. Настоящая полоска
  и цвет жидкости — отдельным шагом, расширением `Appearance` (правка API → согласование).
- Спрайты стыков трубы (какие стороны соединены), оверлей сетей поверх карты — отдельный шаг.
- Бюджет кадра для `com.graphics` — правило `graphics.md`.

## 10. Разбивка на карточки

Каждая — своя проектная записка, сейв-совместимость, тесты (падающий до, зелёный после), бенчмарк.

1. **Примитив жидкости + сеть труб.** `FluidType`, `fluids()`, `FluidNetwork`, архетипы `PIPE`/`TANK`,
   расширение `TickContext` жидкостным портом, сейв v10. Тест: три трубы = одно ведро; постановка
   сливает сети, снос делит объём пропорционально. Производителей ещё нет — жидкость впрыскивается
   тестом напрямую.
2. **Насос + котёл.** `PUMP` с правилом `ADJACENT_TO_WATER`, `BOILER` (вода+топливо→пар, две сети).
   Тест: насос наполняет сеть, котёл осушает и наполняет паровую.
3. **Электричество.** `PowerNetwork`, `GENERATOR` (пар→мощность), одна электро-машина с
   опциональным питанием (опция A). Тест: генератор питает машину; при нехватке — доля по спросу.
4. **Рендер и UI.** Полоска заполнения, стыки труб, оверлей сети, места в хотбаре, docs для
   мододелов (howto: своя жидкость, своя жидкостная машина).

## 11. Риски и открытые вопросы владельцу

Риски:

- **Электричество инвазивно.** Гейт «запитано» в потребителе; опция A (опциональный ток) снимает
  риск для существующего контента.
- **Распад 2D-сети при сносе** — flood-fill O(размера сети). Ограничен размером сети и происходит
  только при действии игрока; бенчмарк подтвердит.
- **Детерминизм сетей** — идентичность компонент и порядок обхода строго по координатам, не по
  hash/ссылке.

Вопросы, которые нельзя решить кодом, — закрыты владельцем 05.08.2026, ответы в шапке документа.
Новые продуктовые развилки (баланс мощности, ёмкости трубы и бака, радиус столба, стоимость
рецептов) поднимаются в проектной записке своей карточки, а не решаются по дороге.
