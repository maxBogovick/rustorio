# Урок 4 — Общий тип «здание»: убираем дублирование

В уроке 3 зданий стало два, и код начал двоиться: под буры — своя карта, под ящики — своя, у
каждого свои `has…`/`place…`, в отрисовке — два отдельных цикла. Мы специально не стали это
лечить сразу — сначала надо было ПОЧУВСТВОВАТЬ боль. Теперь чувствуем. Лечим.

Это первый настоящий рефакторинг курса. Ничего нового для игрока не появится — она будет
работать ровно как в уроке 3. Изменится только КОД: станет одно вместо двух.

---

## Чему ты научишься

- **Видеть повод для рефакторинга.** Дублирование — это не «некрасиво», а конкретная боль:
  каждое новое здание заставляет копировать обвязку. Научишься замечать этот сигнал.
- **Извлекать общий тип.** Найдёшь, что́ у разных классов ОБЩЕЕ, и вынесешь это в интерфейс
  `Building`, оставив различия внутри.
- **`sealed`-интерфейсы и проверка полноты.** Поймёшь, зачем «запечатывать» список наследников и
  как компилятор за это награждает: `switch` без забытых веток.
- **Пат­терн-матчинг в `switch`** (`case Miner _`, `case Chest chest`) — современный способ
  разобрать значение по типу.
- **Где чему место.** Почему правила МЕСТА остаются в мире, а ПОВЕДЕНИЕ переезжает в само здание.
- **Упаковку координат в ключ** (`(int) (k >> 32)`) — как две координаты живут в одном `long`.

**Что меняем — одним взглядом:**

```
БЫЛО (урок 3)                          СТАЛО (урок 4)
─────────────────────────────         ─────────────────────────────
World                                  World
  Map<Long, Miner>  miners               Map<Long, Building> buildings   ← одна карта
  Map<Long, Chest>  chests               tick(): один цикл
  hasMiner / hasChest                    forEachBuilding(...)
  placeMiner / placeChest                placeMiner / placeChest  (различие осталось)
  tick(): два прохода
  forEachMiner / forEachChest          Building (sealed)
                                          ├── Miner   (tick: копает и отдаёт)
Miner   — сам по себе                     └── Chest   (accept/count)
Chest   — сам по себе
```

## 1. Что у зданий общего?

Спросим прямо: что мир хочет от «здания вообще», не зная, бур это или ящик?

- **держать его в клетке** — и бур, и ящик занимают клетку;
- **дать ему прожить тик** — мир раз в шаг обходит все здания и говорит каждому «твой ход».

Вот и всё общее. Различия (бур копает и отдаёт руду; ящик копит) — это уже ВНУТРИ каждого
здания. Значит, общий тип нужен ровно с одним методом — «проживи тик»:

```java
// com/rustorio/Building.java
public sealed interface Building permits Miner, Chest {
    /** Прожить один тик. Мир передаёт, ГДЕ здание стоит — чтобы оно достало соседей. */
    default void tick(World world, int x, int y) {}
}
```

Два решения тут стоят объяснения.

**`sealed … permits Miner, Chest`.** Зданий ровно два ИЗВЕСТНЫХ сорта, и список закрыт: чужой
класс не станет зданием исподтишка. Взамен компилятор дарит проверку полноты — скоро увидим, как
она ловит забытые ветки. Это та же идея «карта задач», что уже работает в атласе спрайтов:
компилятор сам показывает пальцем на всё, что надо дописать.

**`default` пустой `tick`.** Большинство зданий (ящик) на тик ничего не делает — просто стоит.
Пустая реализация по умолчанию избавляет такие здания от переопределения; активные (бур)
переопределяют.

Как теперь связаны типы — «запечатанный» интерфейс и два его единственных наследника:

```
              Building  «sealed interface»
              + tick(World, x, y)   ← по умолчанию пустой
                        ▲
          permits ──────┴────── permits
          │                          │
     ┌─────────┐               ┌───────────┐
     │  Miner  │               │   Chest   │
     ├─────────┤               ├───────────┤
     │ cooldown│               │ count     │
     │ tick()  │               │ accept()  │
     └─────────┘               │ count()   │
                               └───────────┘
```

Стрелки — «реализует». Слово `permits` подчёркивает, что список закрыт: НИКТО, кроме `Miner` и
`Chest`, зданием быть не может. Именно это знание и позволяет компилятору проверять полноту.

## 2. Поведение переезжает ВНУТРЬ здания

Раньше `Miner.tick()` возвращал руду, а раскладывал её по соседям сам мир. Теперь бур знает своё
поведение целиком — «добыл и отдал соседу»:

```java
// Miner implements Building
@Override
public void tick(World world, int x, int y) {
    if (--cooldown > 0) return;                    // ещё копаем
    cooldown = MINE_TIME;
    world.offerToNeighbor(x, y, Item.IRON_ORE);    // отдать добычу соседу-ящику (если есть)
}
```

Мир больше не разбирает, что бур там намайнил, — он лишь предоставляет буру МАРШРУТ до соседей.
А ящик своего поведения на тик не имеет, поэтому `tick` не переопределяет вовсе:

```java
// Chest implements Building
public void accept(Item item) { count++; }  // принять предмет от соседа
public int  count()           { return count; }
```

Обрати внимание, как сместилась ответственность: **правила МЕСТА (где строить) остались в мире,
а правила ПОВЕДЕНИЯ (что делать в тик) уехали в само здание.** Мир — про поле, здание — про себя.

Вот что происходит на поле. Бур стоит на руде, ящик — рядом; раз в 3 тика порция руды переходит
из бура в соседний ящик:

```
      столбцы →                          x   x+1
    ┌───────────┬───────────┐          ┌──────┬──────┐
    │   БУР     │  ЯЩИК      │   тик:   │ БУР  │ ЯЩИК │
    │  (руда)   │  count=7   │  ─────►  │      │ +1 → │  count=8
    └───────────┴───────────┘          └──────┴──────┘
       (x, y)     (x+1, y)         offerToNeighbor(x, y) нашёл ящик справа
```

А вот тот же шаг во времени — кто кого зовёт за один тик:

```
World.tick()
   │  для каждого здания:
   └─► building.tick(this, x, y)
          │
          бур готов? (cooldown = 0)
            ├─ нет ─► ждём следующий тик
            └─ да  ─► world.offerToNeighbor(x, y, руда)
                         │
                         сосед — ящик?
                           ├─ да  ─► chest.accept()  →  count++
                           └─ нет ─► руда пропала
```

## 3. Мир: одна карта вместо двух

Теперь главное упрощение. Две карты схлопываются в одну — `Map<Long, Building>`:

```java
private final Map<Long, Building> buildings = new HashMap<>();

public boolean isFree(int x, int y) { return !buildings.containsKey(key(x, y)); }

public void placeMiner(int x, int y) {
    if (inBounds(x, y) && hasOre(x, y) && isFree(x, y)) buildings.put(key(x, y), new Miner());
}
public void placeChest(int x, int y) {
    if (inBounds(x, y) && isFree(x, y)) buildings.put(key(x, y), new Chest());
}

public void tick() {                                 // ОДИН цикл на все здания
    for (Map.Entry<Long, Building> e : buildings.entrySet()) {
        long k = e.getKey();
        e.getValue().tick(this, (int) (k >> 32), (int) k);
    }
}
```

Сравни с уроком 3: пропали `hasMiner`/`hasChest`, пропали парные `forEach`, `tick` из двух
частей стал одним циклом. `placeMiner` и `placeChest` остались раздельными — и это ПРАВИЛЬНО:
они по-настоящему разные (буру нужна руда, ящику — нет). Мы убрали дублирование, а не стёрли
осмысленные различия. Это две разные двери в один и тот же склад зданий.

Доставку руды мир по-прежнему берёт на себя, но теперь через общую карту:

```java
public boolean offerToNeighbor(int x, int y, Item item) {
    return offer(x + 1, y, item) || offer(x - 1, y, item)
        || offer(x, y + 1, item) || offer(x, y - 1, item);
}
private boolean offer(int x, int y, Item item) {
    if (buildings.get(key(x, y)) instanceof Chest chest) { chest.accept(item); return true; }
    return false;   // в этой клетке нет того, кто примет предмет
}
```

`instanceof Chest chest` — «если сосед оказался ящиком, вот он, зови его `chest`». Пока принимать
предметы умеет только ящик; станет больше — здесь и добавим.

### Откуда взялся `(int) (k >> 32)`: ключ-координата

Ключом карты `Map<Long, Building>` должен быть ОДИН объект, а координаты у нас две — `x` и `y`.
Проще всего склеить их в одно 64-битное число: старшую половину отдаём под `x`, младшую — под
`y`. Так пара `(x, y)` превращается в один `long`, и карта работает с ним как с обычным числом.

```
  long-ключ, 64 бита:

   ┌───────────────── x (32 бита) ─────────────────┬───────────────── y (32 бита) ─────────────────┐
   │ 0000 0000 0000 0000 0000 0000 0000 0011        │ 0000 0000 0000 0000 0000 0000 0000 0101        │
   └────────────────────────────────────────────────┴────────────────────────────────────────────────┘
          старшие 32 бита = x = 3                            младшие 32 бита = y = 5
```

**Упаковка** (`key`) — `x` двигаем в старшую половину, `y` кладём в младшую:

```java
((long) x << 32) | (y & 0xFFFFFFFFL)     //  x<<32 — «сдвинуть влево на 32 бита», | — склеить
```

**Распаковка** — обратные две операции, ровно те, что смущали:

```java
int x = (int) (k >> 32);   //  >> 32 — сдвинуть старшую половину ВНИЗ, в младшие биты; (int) обрезает
int y = (int)  k;          //  просто (int) — приведение отбрасывает старшие 32 бита, остаются младшие
```

Чтобы не разбрасывать эту битовую магию по коду, в `World` заведены две крошечные функции —
`keyX(k)` и `keyY(k)`: и `tick`, и `forEachBuilding` зовут их вместо голых сдвигов, а «как именно
упакованы координаты» описано в одном месте.

## 4. Отрисовка: один обход, `switch` по зданию

В уроке 3 было два цикла — по бурам и по ящикам. Теперь один обход `forEachBuilding`, а ЧТО
рисовать, решает `switch` по сорту здания:

```java
world.forEachBuilding((x, y, building) -> {
    float px = grid.x(x), py = grid.yBottom(y);
    switch (building) {
        case Miner _ -> batch.draw(textures.miner[0], px, py, tile, tile);
        case Chest chest -> {
            batch.draw(textures.chest, px, py, tile, tile);
            font.draw(batch, Integer.toString(chest.count()), px + 3, py + tile - 3);
        }
    }
});
```

Здесь окупается `sealed`. Компилятор ЗНАЕТ, что зданий ровно два, поэтому `switch` без `default`
проходит проверку полноты. `case Miner _` — сорт нам важен, а сама переменная не нужна, оттого
`_`. `case Chest chest` — переменную берём, чтобы спросить `chest.count()` и подписать число.

Вот и обещанная «карта задач»: добавишь в `permits` третье здание — **этот `switch` перестанет
компилироваться**, пока не добавишь ветку. Компилятор сам приведёт тебя сюда. Ничего не забудешь.
