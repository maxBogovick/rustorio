# Урок 6 — «Кто примет предмет?»: убираем перебор типов

В уроке 5 мы честно оставили запашок и показали на него пальцем. Пора убрать. Речь про то, как
мир доставляет предмет соседу:

```java
// как было (урок 5)
private boolean offer(int x, int y, Item item) {
    Building building = buildings.get(key(x, y));
    if (building instanceof Chest chest)     { chest.accept(item);   return true; }
    if (building instanceof Furnace furnace) { return furnace.accept(item);       }
    return false;
}
```

Каждое новое принимающее здание дописывает сюда ещё один `if (… instanceof …)`. Мир вынужден
знать в лицо всех, кто умеет принимать предметы. Это та же болезнь дублирования, что и в уроке 4,
только переехавшая в маршрутизацию. Лечим тем же лекарством — **полиморфизмом**.

---

## Чему ты научишься

- **Приём «заменить условие полиморфизмом».** Вместо «мир перебирает типы» — «мир задаёт вопрос,
  а объект отвечает за себя». Один из самых частых и полезных рефакторингов.
- **Различать ХОРОШИЙ и ПЛОХОЙ разбор по типу.** Не всякий `switch`/`instanceof` — зло. Увидишь,
  почему `offer` надо убрать, а `switch` в отрисовке — оставить.
- **Наращивать общий словарь типа.** У `Building` уже был `tick`; добавим `accept` — и поймёшь,
  когда метод заслуживает переезда в общий интерфейс.

---

## 1. Идея: пусть здание отвечает за себя

Вопрос, который мир задаёт соседу, простой: «предмет берёшь?» Сейчас мир отвечает на него ЗА
здание — сам смотрит на его тип. Но кто лучше знает, берёт ли здание предмет, чем само здание?

Значит, «принять предмет» — это ещё один общий глагол, которым мир говорит со зданиями. Первый
был `tick` («проживи шаг»). Второй — `accept` («вот предмет, берёшь?»). Добавим его в общий тип:

```java
// Building
default boolean accept(Item item) {
    return false;   // по умолчанию здание НЕ принимает ничего
}
```

Как и у `tick`, реализация по умолчанию — пустая (точнее, «нет, не беру»). Это честно: большинство
зданий предмет не берёт. Бур только отдаёт руду — он `accept` не переопределяет и молча отвечает
`false`. А кто принимает — переопределяет:

```java
// Chest — берёт что угодно
@Override public boolean accept(Item item) { count++; return true; }

// Furnace — разборчива: только руду и только пока есть место
@Override public boolean accept(Item item) {
    if (item != Item.IRON_ORE || oreBuffer >= BUFFER_MAX) return false;
    oreBuffer++;
    return true;
}
```

Обрати внимание: код приёма НИКУДА не делся — он всегда жил в `Chest` и `Furnace`. Мы лишь
объявили его частью общего договора `Building`, добавив `@Override`. Теперь у зданий единый
интерфейс приёма, и на него можно опереться.

---

## 2. Мир перестаёт знать типы

Раз у каждого здания есть `accept`, мир больше не перебирает сорта. Он просто спрашивает:

```java
// как стало
private boolean offer(int x, int y, Item item) {
    Building building = buildings.get(key(x, y));
    return building != null && building.accept(item);
}
```

Три строки вместо десяти, и — главное — `offer` больше НЕ РАСТЁТ. Появится четвёртое принимающее
здание (скажем, лаборатория, что глотает пластины) — оно переопределит `accept`, и всё
заработает само. Мир не придётся трогать. Вот что значит «заменить условие полиморфизмом»:
ветвление по типу расселилось по самим типам.

```
   БЫЛО                                  СТАЛО
 ┌─────────────────────────┐           ┌──────────────────────────┐
 │ World.offer:            │           │ World.offer:             │
 │   if instanceof Chest   │           │   building.accept(item)  │
 │   if instanceof Furnace │           └──────────────────────────┘
 │   if instanceof …       │                       │ спрашивает
 │   (растёт с каждым)     │              ┌────────┼─────────┐
 └─────────────────────────┘              ▼        ▼         ▼
                                        Miner    Chest    Furnace
                                        false    true    руду/место
                                     каждый отвечает сам за себя
```

---

## 3. Важно: `switch` в отрисовке мы НЕ трогаем

Резонный вопрос: если `instanceof` в `offer` — плохо, то чем лучше `switch` по зданию в
`BuildingRenderer`? Ведь он тоже разбирает типы. Разница принципиальная:

| | `offer` (убрали) | `switch` в отрисовке (оставили) |
|---|---|---|
| Про что | ПОВЕДЕНИЕ: брать ли предмет — знает само здание | ВНЕШНОСТЬ: как здание выглядит на экране |
| Кто отвечает | логично, что здание | логично, что рисующий слой |
| Забудешь ветку | тихо: предмет молча не доставится | шумно: **компилятор не соберёт** (sealed) |
| Растёт молча? | да — вот почему убрали | нет — компилятор ведёт за руку |

Поведение здания — часть самого здания, ему там и место. А как здание НАРИСОВАТЬ — забота
графики, и `sealed`+`switch` делают этот разбор безопасным: забудешь сорт — узнаешь сразу, при
сборке. Мы убрали ПЛОХОЙ, молчаливый перебор и оставили ХОРОШИЙ, проверяемый. Разбор по типу сам
по себе не грех — грешит МОЛЧАЛИВЫЙ разбор поведения, которое объект мог бы взять на себя.

(Придёт урок, где и отрисовку захочется освободить от знания всех зданий поимённо, — но там будет
другой приём: пусть здание само подскажет, чем себя рисовать. Не сегодня.)
