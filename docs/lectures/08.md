# Урок 8 — Здание само знает, как выглядеть

К уроку 7 добавление здания стало «многодельным»: правишь `sealed permits`, `switch` в отрисовке,
`switch` в `World.place`, константу `BuildingType`. Один из этих швов особенно назойлив — **`switch`
в отрисовке**. Там на каждое здание своя логика рисования:

```java
// как было (урок 7)
switch (building) {
    case Miner _ -> batch.draw(textures.miner[0], px, py, tile, tile);
    case Chest chest -> {
        batch.draw(textures.chest, px, py, tile, tile);
        font.draw(batch, Integer.toString(chest.count()), px + 3, py + tile - 3);
    }
    case Furnace furnace -> {
        TextureRegion s = furnace.oreBuffer() > 0 ? textures.furnaceOn : textures.furnaceOff;
        batch.draw(s, px, py, tile, tile);
        if (furnace.oreBuffer() > 0) font.draw(batch, ...);
    }
}
```

Отрисовка знает КАЖДОЕ здание в лицо: где у ящика число, когда печь горячая. Освободим её — пусть
здание само расскажет, как выглядит.

---

## Чему ты научишься

- **Приём «расскажи, не спрашивай» (tell, don't ask).** Вместо «отрисовка выспрашивает у здания
  его потроха» — «здание само отдаёт готовое описание внешности».
- **Держать домен независимым от графики.** Описание внешности будет в домене, но без единого
  упоминания libGDX/текстур. Поймёшь, где проходит граница.
- **Куда переезжает решение.** Выбор «печь горячая или холодная» — это про состояние печи, значит
  жить ему В печи, а не в отрисовке.
- **Хороший остаточный шов.** Увидишь, что кое-какой перевод «имя → картинка» остаётся, и почему
  это нормально.

---

## 1. Описание внешности: `Appearance` и `Sprite`

Что отрисовке НУЖНО от здания? Всего две вещи: какую картинку нарисовать и не подписать ли поверх
число. Опишем ровно это — в домене, без всякой графики:

```java
// com/rustorio/Sprite.java — логическое ИМЯ картинки, не сама картинка
public enum Sprite { MINER, CHEST, FURNACE_HOT, FURNACE_COLD }

// com/rustorio/Appearance.java — что рисовать: спрайт + необязательный бейдж
public record Appearance(Sprite sprite, int badge) {
    public static final int NO_BADGE = -1;
    public static Appearance of(Sprite sprite)            { return new Appearance(sprite, NO_BADGE); }
    public static Appearance of(Sprite sprite, int badge) { return new Appearance(sprite, badge); }
    public boolean hasBadge() { return badge != NO_BADGE; }
}
```

Важнейшее здесь — **чего тут НЕТ**: ни `TextureRegion`, ни `batch`, ни единого класса libGDX.
`Sprite.FURNACE_HOT` — это «я выгляжу как горячая печь», а не конкретные пиксели. Домен рассказывает,
КАК он выглядит, ничего не зная о том, ЧЕМ его рисуют. Граница домен ↔ графика цела.

---

## 2. Каждое здание описывает себя

Добавляем в общий тип обязанность — назвать свою внешность:

```java
// Building — БЕЗ реализации по умолчанию: внешность есть у любого здания
Appearance appearance();
```

`tick` и `accept` мы давали с пустым `default` (не всякое здание тикает/принимает). А внешность
есть у КАЖДОГО — поэтому метод без умолчания, и компилятор заставит реализовать его у любого
нового здания. И каждое отвечает за себя:

```java
// Miner — всегда один спрайт, без числа
public Appearance appearance() { return Appearance.of(Sprite.MINER); }

// Chest — спрайт + число «сколько лежит»
public Appearance appearance() { return Appearance.of(Sprite.CHEST, count); }

// Furnace — САМА решает: горячая (с числом) или холодная
public Appearance appearance() {
    return oreBuffer > 0
        ? Appearance.of(Sprite.FURNACE_HOT, oreBuffer)
        : Appearance.of(Sprite.FURNACE_COLD);
}
```

Смотри, куда переехало РЕШЕНИЕ. Раньше отрисовка сама смотрела `furnace.oreBuffer() > 0` и
выбирала спрайт. Теперь это выбирает печь — там, где живёт буфер. Отрисовке остаётся готовый ответ.
Это и есть «расскажи, не спрашивай»: не выпытывать у объекта его внутренности, чтобы решить за
него, а получить от него уже принятое решение.

## 3. Отрисовка становится тупой и одинаковой

Раз каждое здание отдаёт `Appearance`, слой рисует ВСЕ здания одним и тем же кодом:

```java
world.forEachBuilding((x, y, building) -> {
    Appearance look = building.appearance();
    float px = grid.x(x), py = grid.yBottom(y);
    batch.draw(sprite(look.sprite()), px, py, tile, tile);
    if (look.hasBadge())
        font.draw(batch, Integer.toString(look.badge()), px + 3, py + tile - 3);
});
```

Ни `Miner`, ни `Chest`, ни `Furnace` — отрисовка их больше не импортирует и знать не знает.
Добавишь четвёртое, пятое, десятое здание — **этот код не изменится ни на строку**. Вот ради чего
всё затевалось: назойливый шов из вступления исчез.

---

## 4. Что осталось — и почему это нормально

Одно место всё же переводит логическое имя спрайта в настоящую текстуру:

```java
private TextureRegion sprite(Sprite sprite) {
    return switch (sprite) {
        case MINER        -> textures.miner[0];
        case CHEST        -> textures.chest;
        case FURNACE_HOT  -> textures.furnaceOn;
        case FURNACE_COLD -> textures.furnaceOff;
    };
}
```

«Опять switch! Не от него ли мы бежали?» Нет — он про ДРУГОЕ. Прежний switch разбирал ПОВЕДЕНИЕ
зданий (где число, когда греется) — это чужая для графики забота. Этот же switch — про АССЕТЫ:
«какой файл-картинка соответствует имени `FURNACE_HOT`». Знать, где лежат пиксели, — прямая работа
графики, и больше её негде делать. Вдобавок это `switch`-выражение по enum: забудешь имя —
компилятор не соберёт. Шов маленький, честный и проверяемый.

Правило на будущее: гони из отрисовки знание про ПОВЕДЕНИЕ и СОСТОЯНИЕ зданий; оставляй ей знание
про КАРТИНКИ. Первое — чужое, второе — своё.
