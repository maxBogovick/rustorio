# Урок 9 — Статистика: у завода появляется цель

К уроку 8 завод работает и хорошо развязан внутри, но у ИГРОКА нет обратной связи: числа над
ящиком и печью видны, только пока они стоят на месте, а снесёшь их — и всё, что они наработали,
пропало без следа. Заведём **статистику**: сколько всего добыто руды и выплавлено пластин с
начала игры. Число, которое растёт и никогда не сбрасывается, — первая настоящая ЦЕЛЬ для игрока.

---

## Чему ты научишься

- **Искать состоянию правильное место жительства.** Не всякий счётчик должен жить в объекте,
  который считает. Разберём, почему статистика не может жить в `Miner`/`Chest`/`Furnace`.
- **Использовать готовый шов вместо нового.** В мире уже есть ЕДИНАЯ точка, через которую проходит
  каждый произведённый предмет (`offerToNeighbor`, урок 4). Новая фича сядет на неё и не тронет ни
  строчки в `Miner.java` и `Furnace.java`.
- **Коллекцию, которая строит себя из `enum`.** Тот же приём, что и в панели постройки (урок 7):
  карта `Item → количество` вместо отдельного поля на каждый сорт предмета.
- **Разный доступ на запись и на чтение.** `ProductionStats.record` — package-private (пишет
  только мир), `total` — `public` (читает кто угодно, например HUD).

---

## 1. Где живёт счётчик? Первая мысль — и почему она неверна

Первая идея, что приходит в голову: пусть каждое здание считает само, как ящик уже считает
`count`. Печь могла бы хранить `totalSmelted`, бур — `totalMined`.

Проверим идею на прочность одним вопросом: **что будет со счётчиком, когда игрок снесёт
здание?** У нас уже есть `World.removeBuilding` (урок 7) — снос предусмотрен с самого начала.
Если счётчик живёт В буре, снос бура сотрёт его историю вместе с ним. А нам нужен ИТОГ ЗАВОДА —
число, которое **переживает** отдельные постройки, сколько бы их ни ставили и ни сносили.

Значит, счётчик не может жить в здании. Ему место там, где живёт что-то, что переживает отдельные
здания, — в `World`.

```
   счётчик В ЗДАНИИ                      счётчик В МИРЕ
 ┌───────────────────────┐            ┌───────────────────────┐
 │ Furnace #1: 40 плавок  │            │ World.stats:           │
 │  ← снесли ─╳           │            │   IRON_PLATE: 40       │
 │ Furnace #2: 0 плавок   │            │  (не зависит от того,  │
 │ (новая, старт с нуля)  │            │   сколько печей стоит  │
 │                        │            │   и стоят ли вообще)   │
 │ ИТОГ ЗАВОДА? — теряется│            │                        │
 └───────────────────────┘            └───────────────────────┘
```

## 2. `ProductionStats` — маленький, но отдельный класс

Счётчиков два сейчас (руда, пластина) и станет больше, когда вырастет `Item`. Можно было бы
завести в `World` два поля `long minedTotal, smeltedTotal` — но тогда каждый новый предмет требует
новой пары «поле + строчка кода», совсем как хотбар до урока 7 требовал нового жеста на каждое
здание. Вместо этого — одна карта `Item → количество`, которая обслуживает любой сорт предмета
сама:

```java
// com/rustorio/ProductionStats.java
public final class ProductionStats {

    private final Map<Item, Long> totals = new EnumMap<>(Item.class);

    /** Отметить, что где-то на карте произвели один предмет. */
    void record(Item item) {
        totals.merge(item, 1L, Long::sum);
    }

    /** Сколько всего произведено предметов данного сорта с начала игры. */
    public long total(Item item) {
        return totals.getOrDefault(item, 0L);
    }
}
```

Два метода — и у них разная видимость, не случайно:

- **`record` — пакетный (без модификатора).** Писать в статистику разрешено только миру: это ОН
  знает, когда предмет произведён. Дать `record` любому чужаку — значит разрешить подделывать
  цифры завода откуда угодно.
- **`total` — `public`.** Читать статистику можно всем: HUD, будущий экран результатов, что
  угодно. Чтение безопасно, запись — нет. Это та же логика, что у `getX()` без `setX()`: наружу
  отдаём результат, а не рычаг для его порчи.

`EnumMap` — обычная карта, но заточенная под ключи-`enum`: работает быстрее `HashMap` и явно
говорит читателю «ключи здесь — это весь набор значений одного перечисления». `merge(item, 1L,
Long::sum)` — стандартный приём «увеличить счётчик, а если его ещё не было — завести с нуля»: одна
строка вместо `if (totals.containsKey(item)) … else …`.

## 3. Мир: считаем в уже существующем шве

Самое интересное — КУДА посадить вызов `record`. У нас уже есть единственная точка, через которую
проходит абсолютно каждый произведённый предмет: `offerToNeighbor`. И бур, и печь зовут именно её,
отдавая свою добычу дальше (см. урок 4 и урок 5). Значит, сюда и садим счётчик:

```java
// World.java
public boolean offerToNeighbor(int x, int y, Item item) {
    stats.record(item);
    return offer(x + 1, y, item)
        || offer(x - 1, y, item)
        || offer(x, y + 1, item)
        || offer(x, y - 1, item);
}
```

Одна строка — и статистика уже работает для ОБОИХ производящих зданий. Проверь сам: загляни в
`Miner.java` и `Furnace.java` — там ничего не поменялось. Это и есть выгода от того, что в уроке 4
мы завели `offerToNeighbor` как единую дверь для «отдать предмет соседу»: новая фича встала на
готовый шов, вместо того чтобы просить каждое здание отчитаться о себе отдельно.

```
   Miner.tick()  ──┐
                   │
                   ├──►  World.offerToNeighbor(x, y, item)
                   │            │
   Furnace.tick() ─┘            ├──► stats.record(item)      ← ОДНО место на все здания
                                └──► offer(...соседям...)
```

Обрати внимание на решение: считаем в момент, когда здание ПРОИЗВЕЛО предмет, — до того, как
известно, найдётся ли сосед. Даже если руда потеряется (некому её принять), в статистику она уже
попала. Это осознанный выбор: `ProductionStats` отвечает на вопрос «сколько сделал завод», а не
«сколько успешно доставлено». Задание 3 попросит тебя обдумать, что изменилось бы при другом
выборе.

## 4. HUD: строка статистики строит себя из `Item.values()`

Ровно тем же приёмом, что хотбар в уроке 7 сам собирает список зданий из `BuildingType.values()`,
строка статистики сама собирает список предметов из `Item.values()`:

```java
// HudRenderer
void render(BuildingType selected, ProductionStats stats) {
    ...
    font.draw(batch, hotbar(selected), 20, top - 44);
    font.draw(batch, produced(stats), 20, top - 66);     // ← новая строка
    ...
}

private static String produced(ProductionStats stats) {
    StringBuilder sb = new StringBuilder("Produced:   ");
    for (Item item : Item.values()) {
        sb.append(item.name()).append(' ').append(stats.total(item)).append("    ");
    }
    return sb.toString();
}
```

На экране: `Produced:   IRON_ORE 12    IRON_PLATE 4`. Появится третий предмет в `Item` — строка
покажет и его, без единой правки `HudRenderer`.

Осталось протянуть статистику от мира к HUD. `Renderer.render(World world, ...)` мир уже получает
параметром, так что не пришлось менять ни его сигнатуру, ни `GameScreen` — только одна строка
внутри `Renderer`:

```java
hudRenderer.render(selected, world.stats());
```
