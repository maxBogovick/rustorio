# Урок 10 — Сохранение и загрузка

К уроку 9 у завода появилась цель — растущая статистика. Но закроешь игру, и всё пропадает: и
здания на карте, и сама статистика начинаются с нуля. Заведём **сохранение**: `F5` записывает
мир на диск, `F9` читает его обратно. Впервые состояние игры переживёт закрытие окна.

---

## Чему ты научишься

- **Превращать объекты в текст и обратно.** Каждое здание научится описывать своё состояние
  строкой и воссоздаваться из неё — тот же принцип, что `appearance()` в уроке 8, только результат
  не рисуется, а пишется на диск.
- **Файловый ввод-вывод (`java.nio.file`).** `Files.write`/`Files.readAllLines` — первый раз в
  курсе, когда игра говорит с диском, а не только с экраном.
- **Проверяемое исключение (`IOException`).** Первая встреча курса с исключениями: диск может
  отказать, и Java заставляет это учесть — компилятор не даст забыть `catch`.
- **Switch, который необходим, а не является запашком.** В уроке 6 мы убрали `instanceof`-перебор
  из `offer`. Здесь тоже появится switch по сорту здания — и он ОСТАЁТСЯ, потому что причина
  другая: мы не спрашиваем существующий объект, мы его СОЗДАЁМ, а создать виртуально, не зная
  класса заранее, нельзя в принципе.
- **Доверие к своим данным и недоверие к чужим.** Мир, только что построенный игроком, и мир,
  прочитанный из файла, — разного доверия: одно проверяем, другое короли.

---

## 1. Что должно попасть в файл?

Мир — это карта зданий (`Map<Long, Building>`) и статистика (`ProductionStats`). Всё остальное
(камера, текстуры, ввод) — не состояние ИГРЫ, а состояние ОКНА; сохранять его незачем, оно
пересоздаётся при каждом запуске.

Формат выбираем текстовый и рукописный — без библиотек сериализации. Библиотека сделала бы это в
одну строку, но студент не увидел бы, ЧТО именно превращается в текст и КАК. А ради этого урок и
затевается. Файл выглядит так:

```
# rustorio save v1
STATS IRON_ORE 42
STATS IRON_PLATE 7
MINER 3 5 2
CHEST 4 5 12
FURNACE 5 5 3 1
```

Первая строка — заголовок (при чтении просто пропускается наравне с пустыми строками). Строки
`STATS` — по одной на каждый предмет из `Item.values()`. Строки зданий — `<сорт> <x> <y>
<состояние>`: сорт и координаты одинаковы для всех, а что после них — решает само здание.

## 2. Здание описывает себя строкой: `save()` и `type()`

Тем же приёмом, что и `appearance()` в уроке 8, — здание рассказывает о себе само, вместо того
чтобы кто-то снаружи выспрашивал его потроха. В `Building` добавляются два новых члена, оба БЕЗ
`default` (у любого здания есть и сорт, и состояние — как раньше у `appearance()`):

```java
// Building
BuildingType type();   // какого я сорта — та же метка, что в панели постройки
String save();          // моё состояние текстом — формат решаю сам
```

Реализации короткие — каждое здание просто называет то, что уже хранит:

```java
// Miner
@Override public BuildingType type() { return BuildingType.MINER; }
@Override public String save()       { return Integer.toString(cooldown); }

// Chest
@Override public BuildingType type() { return BuildingType.CHEST; }
@Override public String save()       { return Integer.toString(count); }

// Furnace — двух чисел, поэтому сама решает склеить их пробелом
@Override public BuildingType type() { return BuildingType.FURNACE; }
@Override public String save()       { return oreBuffer + " " + cooldown; }
```

Зачем `type()`, если можно было бы в `SaveGame` написать `if (b instanceof Miner) …`? Это ровно
та болезнь, от которой лечились в уроке 6: перебор чужих типов снаружи. `type()` — тот же рецепт
«расскажи, не спрашивай», просто применённый к новому вопросу: не «как я выгляжу», а «кто я».

## 3. Загрузка: почему нельзя просто позвать `Building.load()`

Симметрично напрашивается метод `load` — но у него другая природа. `save()` — метод ЭКЗЕМПЛЯРА:
у тебя уже есть здание, ты его спрашиваешь. А загрузка ЭКЗЕМПЛЯРА ещё не имеет — она должна его
СОЗДАТЬ. Позвать метод можно только НА объекте; создающий метод обязан знать точный класс заранее,
а значит не может быть виртуальным вызовом через интерфейс `Building`.

Поэтому у каждого класса — свой статический метод `load`, а выбор, какой из них позвать, делает
`switch` по уже знакомому `BuildingType`:

```java
// Miner
static Miner load(String data) {
    Miner miner = new Miner();
    miner.cooldown = Integer.parseInt(data);
    return miner;
}

// Furnace — обратный разбор строки из своего же save()
static Furnace load(String data) {
    String[] fields = data.split(" ");
    Furnace furnace = new Furnace();
    furnace.oreBuffer = Integer.parseInt(fields[0]);
    furnace.cooldown = Integer.parseInt(fields[1]);
    return furnace;
}
```

```java
// SaveGame — единственное место, которое знает про все три класса разом
Building building = switch (type) {
    case MINER   -> Miner.load(data);
    case CHEST   -> Chest.load(data);
    case FURNACE -> Furnace.load(data);
};
```

Сравни с таблицей из урока 6: там был «плохой» `instanceof`-перебор (спрашивает поведение, растёт
молча) и «хороший» exhaustive-`switch` в отрисовке (спрашивает внешность, проверяется компилятором).
Этот `switch` — третий случай: не про «спросить», а про «создать». Такой switch не убрать
полиморфизмом в принципе — зато он, как и рендер, exhaustive: `BuildingType` закрыт по своей
природе (`enum`), забудешь ветку под новый сорт — компилятор откажется собирать.

## 4. `World`: `restore` не переспрашивает правила

Постройка руками и восстановление из файла — разные вещи, и у мира для них разные двери:

```java
// place(...) — решение ИГРОКА, может быть ошибочным, поэтому проверяет правила
public void placeMiner(int x, int y) {
    if (inBounds(x, y) && hasOre(x, y) && isFree(x, y)) buildings.put(key(x, y), new Miner());
}

// restore(...) — решение ПРОШЛОГО, уже было проверено тогда, когда сохранялось
void restore(int x, int y, Building building) {
    buildings.put(key(x, y), building);
}
```

Если бы загрузка звала `place*`, а не `restore`, у неё было бы две проблемы разом: во-первых,
`placeMiner` ожидает пустой конструктор `new Miner()`, а не восстановленное состояние; во-вторых,
если правила постройки когда-нибудь изменятся (например, руда на карте станет другой), старое
сохранение вдруг начнёт молча терять здания при загрузке. `restore` доверяет файлу целиком — какой
мир был, такой и вернётся.

Мир получает ещё `clear()` — снести все здания и обнулить статистику перед загрузкой нового
сохранения:

```java
void clear() {
    buildings.clear();
    stats.clear();
}
```

А у `ProductionStats` рядом с игровым `record` (прибавляет единицу) появляется `set` — задать
итог напрямую, без прибавления. Разные глаголы для разных случаев: `record` — событие в игре,
`set` — восстановление точного числа из файла.

## 5. `SaveGame` — вся оркестрация в одном месте

```java
public static boolean save(World world, String path) {
    List<String> lines = new ArrayList<>();
    lines.add(HEADER);
    for (Item item : Item.values()) {
        lines.add("STATS " + item.name() + " " + world.stats().total(item));
    }
    world.forEachBuilding((x, y, building) ->
            lines.add(building.type().name() + " " + x + " " + y + " " + building.save()));

    try {
        Files.write(Path.of(path), lines);
        return true;
    } catch (IOException e) {
        System.err.println("Save failed: " + e.getMessage());
        return false;
    }
}
```

`Files.write` — метод из `java.nio.file`, современного файлового API Java: отдаёшь путь и список
строк, он сам открывает файл, пишет и закрывает. И тут же — первая в курсе встреча с
**проверяемым исключением**: `IOException` — тем, о котором компилятор ЗАСТАВЛЯЕТ позаботиться
(либо `catch`, либо `throws` дальше). Диск может отказать (нет прав, кончилось место), и Java не
даёт про это забыть, в отличие от привычных нам `NumberFormatException`/`IllegalArgumentException`,
которые компилятор проверять не требует.

```java
public static boolean load(World world, String path) {
    List<String> lines;
    try {
        lines = Files.readAllLines(Path.of(path));
    } catch (IOException e) {
        System.err.println("Load failed: " + e.getMessage());
        return false;
    }

    world.clear();
    for (String line : lines) {
        if (line.isBlank() || line.startsWith("#")) continue;
        if (line.startsWith("STATS ")) {
            String[] parts = line.split(" ", 3);
            world.stats().set(Item.valueOf(parts[1]), Long.parseLong(parts[2]));
        } else {
            loadBuilding(world, line);
        }
    }
    return true;
}
```

Важная деталь порядка: сначала читаем файл ЦЕЛИКОМ (внутри `try`), и только если чтение удалось —
зовём `world.clear()`. Если файла нет или он не читается, `load` вернёт `false`, а игра, которая
уже была на экране, останется как была. Мир стирается только тогда, когда мы точно знаем, что
есть чем его заменить.

`line.split(" ", 4)` для строки здания — не случайное число: ограничение в 4 части означает
«раздели только первые три пробела, а всё, что после третьего, оставь ОДНИМ куском». Для печи
после этого куска — `"3 1"`, две цифры вместе — их дальше разберёт уже `Furnace.load`, которая
знает, что у неё внутри два числа. Мир снаружи об этом не думает.

## 6. Запуск

```
./gradlew run
```

1. Собери цепочку бур → печь → ящик (`1/2/3` + ЛКМ), дай ей потикать, чтобы числа выросли.
2. Нажми **`F5`** — в папке проекта появится `rustorio-save.txt`. Открой его текстовым
   редактором — это ровно то, что описано в разделе 1.
3. Постучи ещё зданий, снеси парочку, дай счётчикам подрасти дальше.
4. Нажми **`F9`** — карта мгновенно вернётся к состоянию на момент `F5`: сохранённые здания на
   месте, лишние (поставленные после сохранения) исчезли, статистика — та, что была при сохранении.
