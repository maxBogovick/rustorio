# Урок 11 — Лента: предмет едет дальше одной клетки

До сих пор предмет мог попасть только к СОСЕДУ — бур кладёт руду в клетку рядом, печь отдаёт
пластину в клетку рядом. Хочешь протянуть завод подальше — не выйдет: соседей всего четыре.
Заведём **ленту** — четвёртое здание, и первое, чья работа — не производить и не копить, а
просто ВЕЗТИ предмет дальше.

Сделаем её настолько просто, насколько получится: лента держит ОДИН предмет и раз в тик
подталкивает его к соседу справа. Ни направлений на выбор, ни очереди из нескольких предметов —
только «занято» или «пусто». Этого достаточно, чтобы завод впервые растянулся больше чем на одну
клетку.

---

## Чему ты научишься

- **Добавлять четвёртое здание — и увидеть, что трогает почти всё, что мы построили.** Sealed-
  список, единая дверь `place`, enum-меню, `appearance`, теперь ещё и `SaveGame` — лента коснётся
  каждого. Хорошая проверка, что архитектура прошлых десяти уроков не выдумана зря.
- **Адресную доставку вместо доставки „куда получится“.** `offerToNeighbor` перебирает всех
  четырёх соседей; лента толкает предмет только ВПЕРЁД — понадобится новый, более прицельный
  способ отдать предмет.
- **Почему порядок обхода зданий иногда важен.** Впервые здание одного тика влияет на здание,
  которое тикнет following за ним в ТОМ ЖЕ тике, — и порядок обхода перестаёт быть безразличным.

---

## 1. Лента как здание — без ничего нового

Всё, что нужно ленте, мы уже писали раньше по кусочкам — сейчас просто собираем:

```java
// com/rustorio/Belt.java
public final class Belt implements Building {

    private Item held;   // что везём, или null, если пусто

    @Override
    public boolean accept(Item item) {
        if (held != null) return false;   // уже что-то везём
        held = item;
        return true;
    }

    @Override
    public void tick(World world, int x, int y) {
        if (held == null) return;                       // везти нечего
        if (world.offerForward(x + 1, y, held)) {
            held = null;                                 // сосед справа принял — освободились
        }
    }

    @Override
    public Appearance appearance() {
        return held == null ? Appearance.of(Sprite.BELT_EMPTY) : Appearance.of(Sprite.BELT_FULL);
    }

    @Override
    public BuildingType type() { return BuildingType.BELT; }

    @Override
    public String save() { return held == null ? "-" : held.name(); }

    static Belt load(String data) {
        Belt belt = new Belt();
        if (!data.equals("-")) belt.held = Item.valueOf(data);
        return belt;
    }
}
```

Сравни с печью (урок 5): та же форма — `accept` разборчив (берёт, только если есть место), `tick`
активен (что-то делает сам, без внешнего толчка). Разница лишь в ЧТО: печь копит и превращает
руду в пластину, лента просто перекладывает предмет на клетку правее. Ни одного нового приёма —
только новая комбинация уже знакомых.

`appearance()` — тем же способом, что печь выбирает горячий/холодный спрайт (урок 8), лента сама
решает, полная она или пустая. И тут повезло: спрайты `belt_1.png`/`belt_2.png` уже лежат в
атласе с самого начала («2 кадра бегущей дорожки») — просто раньше их некому было попросить.
Добавили два имени в `Sprite` (`BELT_EMPTY`, `BELT_FULL`) и две строчки в `BuildingRenderer.sprite`
— по образцу `FURNACE_HOT`/`FURNACE_COLD`. Больше в отрисовке ничего не поменялось: она как не
знала про сорта зданий с урока 8, так и не узнала.

## 2. Направление — сознательно зашито, не выбирается

Настоящие ленты в играх-фабриках можно повернуть в любую сторону. Мы этого делать не будем: лента
ВСЕГДА толкает вправо (`x + 1`). Никакой клавиши поворота, никакого поля «направление» внутри
`Belt`, никакой геометрии под четыре стороны. Чтобы предмет доехал куда нужно, ставь ленты в ряд
слева направо — вот и весь способ управления маршрутом.

Это осознанное упрощение, а не недосмотр: направление и повороты — хорошая тема для отдельного
урока-улучшения ПОТОМ, когда база уже устоялась (как в уроке 1 не заводили `Building` для одного
бура — незачем усложнять то, что пока прекрасно работает и без этого).

## 3. Доставка вперёд — не то же самое, что доставка соседу

`offerToNeighbor` (урок 4) перебирает ВСЕХ четырёх соседей и отдаёт первому, кто согласится, — это
годилось буру и печи: им всё равно, в какую сторону сбросить готовый предмет, лишь бы приняли.
Ленте не всё равно — она обязана толкать СТРОГО вперёд, а не вбок и не назад. Понадобился новый,
адресный способ:

```java
// World
public boolean offerForward(int x, int y, Item item) {
    return offer(x, y, item);   // тот же приватный offer, что и внутри offerToNeighbor
}
```

Заметь важную деталь: `offerForward`, в отличие от `offerToNeighbor`, НЕ пишет в `stats`. Причина
не техническая, а смысловая: `offerToNeighbor` считает статистику, потому что вызывающий её —
ПРОИЗВОДИТЕЛЬ (бур добыл, печь выплавила). Лента ничего не производит — она передаёт предмет,
который уже посчитан на выходе из бура или печи. Если бы каждый шаг по ленте снова считался,
статистика показывала бы кратно больше, чем реально сделал завод. Один и тот же метод (`offer`)
переиспользуется, а вот СЧЁТ — намеренно нет.

## 4. Почему обход зданий пошёл справа налево

Вот здесь пряталась настоящая ловушка, и стоит через неё пройти. Мир обходит здания в `tick()` —
до сих пор было неважно, в каком порядке: бур и печь не зависят от того, тикнул ли уже сосед.
Лента — зависит: если лента A стоит слева от ленты B, и в ОДНОМ и том же тике сначала тикнет A
(толкнёт предмет в B), а потом ЕЩЁ И B (толкнёт ЭТОТ ЖЕ предмет дальше, в C) — предмет за один тик
проедет две клетки вместо одной. Это не гипотеза: именно так проект вёл себя, когда мир хранил
здания в обычной `HashMap` — порядок обхода там ничей не гарантирован, и предмет время от времени
проскакивал сразу несколько лент.

Лечится просто: обходить здания НЕ в случайном порядке `HashMap`, а по координате — и обязательно
СПРАВА НАЛЕВО (от больших `x` к меньшим). Тогда лента справа успевает «сходить» раньше, чем до неё
доберётся толчок от соседа слева, и предмет физически не может сдвинуться дважды за один тик.

```java
// World — вместо HashMap теперь NavigableMap (TreeMap): ключ упорядочен, порядок = порядок по x
private final NavigableMap<Long, Building> buildings = new TreeMap<>();

public void tick() {
    for (Map.Entry<Long, Building> entry : buildings.descendingMap().entrySet()) {
        long k = entry.getKey();
        entry.getValue().tick(this, keyX(k), keyY(k));
    }
}
```

Работает это благодаря тому, что мы уже знаем про упаковку ключа (урок 4): `x` лежит в СТАРШИХ
битах `long`-ключа, значит порядок ключей — это и есть порядок по `x`. `descendingMap()` —
готовый метод `TreeMap`, отдающий записи от большего ключа к меньшему, ничего считать вручную не
нужно.

```
   HashMap (порядок не гарантирован)         TreeMap.descendingMap() (всегда справа налево)

   A ──► B ──► C   один тик:                 A ──► B ──► C   один тик:
   если B тикнет ПОСЛЕ A —                   C тикнет первым (уже освободился
   предмет успевает пройти A→B→C             или ещё занят — неважно),
   за один тик                               потом B, потом A:
                                              каждый толкает ровно один раз
```

## 5. Одна дверь, один enum, один switch — лента проходит по всем them

Реши для себя вопрос из урока 7 и 10: что вообще пришлось тронуть, чтобы завести четвёртое
здание?

- `Building permits Miner, Chest, Furnace, Belt` — список закрытых сортов.
- `World.placeBelt` + ветка `case BELT` в `World.place`.
- `BuildingType.BELT("Belt")` — и хотбар в HUD показал ленту САМ, `HudRenderer` не тронут ни
  строкой (урок 7: панель строится из `values()`).
- `Sprite.BELT_EMPTY/BELT_FULL` + две строки в `BuildingRenderer.sprite`.
- `case BELT` в `SaveGame.loadBuilding` — лента сохраняется и загружается наравне с остальными.
- Клавиша `4` в `InputHandler` — выбор ленты в панели.

Шесть мест, и ни одно не стало неожиданностью — каждое уже было спроектировано именно для этого
момента в уроках 4, 6, 7, 8 и 10. Компилятор, как обычно, показал часть из них сам: добавь `Belt`
в `permits` раньше времени — и `switch` в `BuildingRenderer.sprite` откажется собираться, пока не
допишешь ветки `BELT_EMPTY`/`BELT_FULL`.
