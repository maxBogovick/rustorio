# Урок 12 — Strategy: сортировщик с заменяемым правилом

База из четырёх зданий готова: бур копает, печь плавит, ящик копит, лента везёт. Отсюда курс
сворачивает в блок про **паттерны проектирования** — но не «выучи название», а по-прежнему
код-first: сначала конкретная нужда, потом приём, который её закрывает, и только потом имя,
которым эту связку называют в литературе.

Нужда сегодня такая: лента умеет только одно — везти предмет прямо. А если на развилке завода
руду нужно пустить в одну сторону, а пластины — в другую? Заведём **сортировщик**: одно здание,
два выхода, и решение «куда» — не зашитое намертво, а ЗАМЕНЯЕМОЕ. Это и есть паттерн **Strategy**.

---

## Чему ты научишься

- **Strategy: поведение как отдельное значение, а не как код внутри класса.** Здание не решает
  само, оно СПРАШИВАЕТ решение у объекта, которого держит.
- **Чем это отличается от полиморфизма по типу (урок 6).** Там разное поведение — у разных
  КЛАССОВ (`Chest.accept` vs `Furnace.accept`). Здесь — у ОДНОГО класса, но с разными правилами
  внутри. Разница важна и на неё легко наступить.
- **Лямбда как современная замена классу-стратегии.** В книжках Strategy часто рисуют отдельным
  классом на каждое правило; для однометодного интерфейса в Java давно есть способ короче.
- **Честную границу.** Что мы НЕ стали делать (выбор правила из интерфейса игры, сохранение
  правила в файл) и почему это осознанный, а не забытый кусок.

---

## 1. Почему решение нельзя просто зашить в `tick`

Соблазн — написать прямо внутри сортировщика:

```java
// НЕ так — правило приколочено к коду
public void tick(World world, int x, int y) {
    if (held == Item.IRON_ORE) { /* толкнуть вперёд */ }
    else                       { /* толкнуть вниз */ }
}
```

Работает. Но подумай: что, если ГДЕ-ТО ЕЩЁ на карте нужен сортировщик с ДРУГИМ правилом —
например, пластины вперёд, а всё остальное вниз? `Building` у нас `sealed` (урок 4) — заводить
второй класс `Splitter2` под второе правило означает раздувать закрытый список ради того, что по
сути одно и то же здание с другим решением внутри. А если понадобится третье правило, четвёртое?

Настоящая причина, почему это плохо, — та же, что и в уроке 6: правило спрятано ВНУТРИ кода
метода, а не существует само по себе. Раз мы уже умеем «заменять условие полиморфизмом», раз
достанем тот же приём — но повёрнутый на 90 градусов.

---

## 2. Правило — отдельное значение: `SortRule`

Вместо того чтобы прятать решение в `tick`, вынесем его в свой, крошечный тип:

```java
// com/rustorio/SortRule.java
@FunctionalInterface
public interface SortRule {
    boolean forward(Item item);   // true — вперёд, false — вниз

    SortRule ORE_FORWARD = item -> item == Item.IRON_ORE;
}
```

Один метод, один вопрос: «этот предмет — вперёд?». `ORE_FORWARD` — готовое правило-константа,
записанное ЛЯМБДОЙ. Это и есть современный способ писать Strategy: раньше под каждое правило
заводили отдельный класс с телом метода внутри, а для интерфейса из одного метода лямбда — это
и есть «маленький объект-правило», только без церемонии в виде отдельного файла.

---

## 3. Сортировщик пользуется правилом, а не решает сам

```java
// com/rustorio/Splitter.java
public final class Splitter implements Building {

    private final SortRule rule;   // дали при постройке — раз и навсегда для этого экземпляра
    private Item held;

    public Splitter(SortRule rule) {
        this.rule = rule;
    }

    @Override
    public boolean accept(Item item) {
        if (held != null) return false;
        held = item;
        return true;
    }

    @Override
    public void tick(World world, int x, int y) {
        if (held == null) return;
        boolean forward = rule.forward(held);         // решение НЕ здесь
        int tx = forward ? x + 1 : x;
        int ty = forward ? y : y + 1;
        if (world.offerForward(tx, ty, held)) held = null;
    }
    // appearance/type/save — по образцу прошлых зданий, см. код
}
```

`Splitter.tick` не знает, ПОЧЕМУ руда идёт вперёд, а пластина вниз, — он знает только, что нужно
СПРОСИТЬ `rule` и подчиниться ответу. Захочешь другое поведение для другого сортировщика — не
трогай этот класс:

```java
// World.placeSplitter — единственное место, откуда рождается сортировщик
public void placeSplitter(int x, int y) {
    if (inBounds(x, y) && isFree(x, y)) {
        buildings.put(key(x, y), new Splitter(SortRule.ORE_FORWARD));
    }
}
```

Смени `SortRule.ORE_FORWARD` на любое другое правило (даже написанное на месте лямбдой) — и все
новые сортировщики поведут себя иначе, а `Splitter.java` при этом не откроется НИ РАЗУ. Задание 3
попросит тебя убедиться в этом руками.

---

## 4. Направленная доставка — снова `offerForward`

Как и лента (урок 11), сортировщик толкает предмет в КОНКРЕТНУЮ клетку, а не «куда получится» —
значит, снова адресный `world.offerForward`, а не «раскидай по всем четырём соседям»
`offerToNeighbor`. И, как у ленты, это НЕ производство — статистика в `offerForward` не считается:
сортировщик только пересылает то, что уже посчитано раньше.

---

## 5. Strategy — это не то же самое, что урок 6

Оба приёма убирают ветвление, и оба называются «полиморфизм», но развязывают РАЗНОЕ:

| | Урок 6 (`accept`) | Урок 12 (`SortRule`) |
|---|---|---|
| Что варьируется | Поведение — по КЛАССУ (`Chest` ли это, `Furnace` ли) | Поведение — по ЗНАЧЕНИЮ, вставленному в ОДИН класс |
| Сколько экземпляров одного поведения | Одно поведение = один класс | Одно поведение = один объект `SortRule`, экземпляров `Splitter` с ним может быть сколько угодно |
| Как расширить | Новый класс, реализующий `Building` | Новое правило — без нового класса, иногда без нового файла вовсе |

Полиморфизм по типу отвечает на вопрос «что я за здание?». Strategy отвечает на другой вопрос:
«какое из МОИХ ВОЗМОЖНЫХ решений сейчас применить?» — и решение при этом можно перекладывать
между экземплярами ОДНОГО И ТОГО ЖЕ класса.

## 6. Подключение — уже знакомые швы

Пятое здание проходит по тем же местам, что и лента в уроке 11 (список не меняется четвёртый
урок подряд — это тоже сигнал, что архитектура устоялась): `permits` в `Building`, ветка в
`World.place`, `BuildingType.SPLITTER` (хотбар подхватил сам), `Sprite.SPLITTER` + строка в
`BuildingRenderer.sprite` (спрайт `branch_1.png` уже лежал в атласе неиспользованным, как раньше
лента нашла свои `belt_1/2.png`), ветка в `SaveGame.loadBuilding`, клавиша `5` в `InputHandler`.

Честно: правило (`SortRule`) в файл сохранения НЕ пишется — при загрузке сортировщик всегда
получает `ORE_FORWARD` заново. Раз в игре сейчас в принципе только одно правило в ходу (меняем
его правкой кода, не через интерфейс), это не потеря — а если правил станет несколько
ОДНОВРЕМЕННО на одной карте, сохранение правила будет честной темой отдельного урока.

## 7. Запуск

```
./gradlew run
```

**Шаг A — руда идёт вперёд.** Бур (`1`) на руду, сортировщик (`5`) рядом, ящик (`2`) СПРАВА от
сортировщика и ещё один ящик СНИЗУ. Дай потикать — растёт только правый ящик: руда (`ORE_FORWARD`)
уходит вперёд, нижний остаётся пуст.

**Шаг B — пластины идут вниз.** Снеси сортировщик, поставь между буром и им ПЕЧЬ (`3`) —
сортировщик теперь получает не руду, а пластины. Смотри: растёт уже НИЖНИЙ ящик, а правый стоит —
то же самое здание, то же правило, но другой предмет ведёт себя по-другому, потому что правило
именно ЕГО и разбирает.
