# Урок 13 — Когда повтор уже пять раз: сводим воедино

В конце урока 12 обещался Observer. Прежде чем добавлять НОВЫЙ паттерн, оглянемся на то, что уже
накопилось: пока мы добавляли здание за зданием (уроки 7, 11, 12), в двух местах тихо росло
дублирование. Не гипотетическое — уже случившееся. Посчитаем и уберём его, а Observer подождёт
один урок.

Это не новая идея — тот же приём, что и в уроке 4 («извлечь общий тип, когда дублирование
созрело») и в уроке 6 («заменить условие полиморфизмом»). Разница лишь в том, что в этот раз
дублирование не в поведении зданий, а в коде, который их СТРОИТ и ВЫБИРАЕТ.

---

## Чему ты научишься

- **Замечать дублирование, которое компилятор НЕ защищает.** У `sealed`-switch забудешь ветку —
  сборка упадёт. У копипасты — нет: она просто тихо растёт, и ничего не заставит её остановить.
- **Extract Method с фабрикой вместо копии тела.** `Supplier<Building>` и ссылки на конструктор
  (`Chest::new`) вместо пяти одинаковых `if`.
- **Ещё раз — «пусть список строит себя».** Тот же приём, что уже был в хотбаре (урок 7) и в
  строке статистики (урок 9), теперь — для выбора здания клавишами.
- **Где проходит граница.** Почему одно место мы РАВНЯЕМ (четыре метода в одну фабрику), а другое
  оставляем как есть (бур — по-прежнему отдельно).

## 1. Посчитаем, а не просто скажем «похоже»

Загляни в `World` — четыре метода `place*` рядом:

```java
public void placeChest(int x, int y) {
    if (inBounds(x, y) && isFree(x, y)) { buildings.put(key(x, y), new Chest()); }
}
public void placeFurnace(int x, int y) {
    if (inBounds(x, y) && isFree(x, y)) { buildings.put(key(x, y), new Furnace()); }
}
public void placeBelt(int x, int y) {
    if (inBounds(x, y) && isFree(x, y)) { buildings.put(key(x, y), new Belt()); }
}
```

Замени имена классов на одну букву — и три метода становятся БУКВАЛЬНО одинаковыми, символ в
символ. `placeSplitter` — та же форма, с одним лишним аргументом конструктора. Четыре из пяти
методов постройки — один и тот же текст.

Рядом, в `InputHandler`, — другая версия той же болезни:

```java
private void handleBuildSelection() {
    if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_1)) { selected = BuildingType.MINER; }
    if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_2)) { selected = BuildingType.CHEST; }
    if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_3)) { selected = BuildingType.FURNACE; }
    if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_4)) { selected = BuildingType.BELT; }
    if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_5)) { selected = BuildingType.SPLITTER; }
}
```

Пять веток. Три урока подряд (7, 11, 12) сюда дописывали по строке и ни разу не спросили, не пора
ли остановиться.

Сравни с тем, при скольких повторах курс уже брался за рефакторинг раньше:

| Момент курса | Сколько повторов было |
|---|---|
| Урок 3→4 (`Miner`/`Chest` двумя картами) | 2 |
| Урок 5→6 (`instanceof` в `offer`) | 2 |
| **Сейчас: `place*` в `World`** | **4** |
| **Сейчас: выбор здания в `InputHandler`** | **5, и продолжает расти** |

Оба прошлых рефакторинга случились при ДВУХ повторах. Здесь их вдвое-впятеро больше — момент
давно назрел, курс его просто ещё не назвал вслух.

## 2. Почему это ДРУГОЕ дублирование, не то, что мы хвалили

В `World.place`, `BuildingRenderer.sprite`, `SaveGame` тоже есть switch на одну ветку на здание —
и мы их НЕ трогаем. Разница принципиальная:

| | `switch` (оставляем) | `place*`/выбор клавишей (правим) |
|---|---|---|
| Забудешь ветку | Сборка не пройдёт (`sealed`/exhaustive) | Молча ничего — здание просто не выбирается |
| Тело ветки | У каждого сорта СВОЁ | У четырёх из пяти — ОДНО И ТО ЖЕ |
| Кто следит за полнотой | Компилятор | Никто |

Разбор по сорту сам по себе — не грех (та же мысль, что в уроке 6 про `switch` в отрисовке).
Грех — когда тело ветки не просто «своё для своего сорта», а буквально скопированное.

## 3. Мир: одна фабрика вместо четырёх копий

```java
public void placeChest(int x, int y)    { placeIfFree(x, y, Chest::new); }
public void placeFurnace(int x, int y)  { placeIfFree(x, y, Furnace::new); }
public void placeBelt(int x, int y)     { placeIfFree(x, y, Belt::new); }
public void placeSplitter(int x, int y) { placeIfFree(x, y, () -> new Splitter(SortRule.ORE_FORWARD)); }

private void placeIfFree(int x, int y, Supplier<Building> factory) {
    if (inBounds(x, y) && isFree(x, y)) {
        buildings.put(key(x, y), factory.get());
    }
}
```

`Chest::new` — ссылка на конструктор: то же самое, что `() -> new Chest()`, только короче. Для
`Splitter`, которому нужен ещё и `SortRule`, конструктор одним токеном не собрать — там лямбда
целиком, тоже `Supplier<Building>`, просто чуть длиннее.

Каждый `place*` остался ОТДЕЛЬНЫМ публичным методом — снаружи (в `World.place`, в тестах) ничего
не поменялось, эти четыре двери никуда не делись. Изменилось только то, ЧТО у них внутри: было
скопированное тело, стало — одна строка, зовущая общий приём.

**`placeMiner` мы НЕ трогаем.** У него по-настоящему другое правило — проверка руды. Собрать его
в тот же `placeIfFree` значило бы либо протащить туда лишний параметр «а ещё вот это условие»
(усложнить общий метод ради одного частного случая), либо соврать и убрать проверку руды
незаметно. И то и другое хуже, чем оставить один метод особым — точно тот же вывод, что курс уже
сделал в уроке 4: «дублирование, за которым стоит РЕАЛЬНАЯ разница, — не дублирование».

## 4. Ввод: снова «пусть список строит себя»

```java
private void handleBuildSelection() {
    for (BuildingType type : BuildingType.values()) {
        if (Gdx.input.isKeyJustPressed(Input.Keys.NUM_1 + type.ordinal())) {
            selected = type;
        }
    }
}
```

Работает это благодаря одному факту про libGDX, который стоит проверить, а не поверить на слово:
`Input.Keys.NUM_1`, `NUM_2`, … `NUM_9` — это подряд идущие целые числа. Значит, «клавиша с номером
`N`» — это просто `NUM_1 + (N - 1)`, а порядковый номер здания в перечислении (`type.ordinal()`,
считая от нуля) — уже готовое `N - 1`. Ничего не пришлось изобретать: `BuildingType.MINER`
стоит первым (`ordinal() == 0`) и получает `NUM_1`, `SPLITTER` — пятый (`ordinal() == 4`) —
`NUM_5`.

Это тот же самый приём, который уже дважды был в курсе: хотбар в уроке 7 (`for (BuildingType type
: BuildingType.values())`) и строка статистики в уроке 9 (`for (Item item : Item.values())`).
Тогда он убирал повторение в ОТРИСОВКЕ панели; здесь — в её ВВОДЕ. Тот же список, та же идея,
третье применение.

**Честный предел.** Клавиш `1`–`9` всего девять. Пока зданий пять — с запасом; если их станет
больше девяти, эта схема выбора упрётся в потолок первой. Чинить её сейчас рано — станет больно,
тогда и починим (клавиатура сменится на что-то другое — колесо мыши, список). Момент придёт
своим чередом, ровно как приходил для каждого рефакторинга до этого.
