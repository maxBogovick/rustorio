# Урок 16 — Open/Closed: рецепт как данные

У печи есть ровно одно поведение, зашитое прямо в код: берёт руду, делает пластину, 5 тиков. Хотим
вторую ступень переработки — пластину в шестерёнку. Наивный путь — скопировать `Furnace` в
`GearPress` почти один в один: тот же буфер, тот же таймер, та же форма `accept`/`tick`, другие
константы внутри. Мы уже такое дублирование видели (урок 13) и знаем, чем оно кончается.

Сегодня — принцип **Open/Closed**: класс закрыт для изменений, но открыт для расширения. Мерило
успеха — число: сколько строк КОДА придётся тронуть, чтобы добавить целую новую ступень
переработки. Посчитаем честно, в конце.

---

## Чему ты научишься

- **Превращать поведение в данные.** «Беру только руду», «делаю пластину», «5 тиков» — это не
  код, это ТРИ ЧИСЛА (точнее, два предмета и число). Вынесенные в `record`, они становятся
  конфигурацией, а не логикой.
- **Один класс — много ролей.** Печь и пресс — один и тот же `Furnace.java`, но игрок видит два
  разных пункта меню.
- **Честную опасность двух параметров, которые обязаны совпадать.** Если бы `Furnace` брал
  отдельно рецепт и отдельно `BuildingType`, их можно было бы перепутать при постройке. Разберём,
  как этого избежать.
- **Считать цену расширения.** Не абстрактно «стало гибче», а конкретно — по файлам и строкам.

## 1. Рецепт — три значения, а не код

```java
// com/rustorio/Recipe.java
public record Recipe(Item input, Item output, int time, BuildingType type) {
    public static final Recipe IRON = new Recipe(Item.IRON_ORE, Item.IRON_PLATE, 5, BuildingType.FURNACE);
    public static final Recipe GEAR = new Recipe(Item.IRON_PLATE, Item.GEAR, 8, BuildingType.PRESS);
}
```

Три первых поля — то, что раньше было ЖИВЫМ КОДОМ внутри `Furnace`: сравнение `item !=
Item.IRON_ORE`, константа `Item.IRON_PLATE` в `offerToNeighbor`, константа `SMELT_TIME`. Теперь
это данные, лежащие рядом, а не растворённые в теле трёх разных методов.

Четвёртое поле, `type`, — отдельный разговор (раздел 3).

## 2. Печь спрашивает рецепт, а не решает сама

```java
// Furnace — было
private static final int SMELT_TIME = 5;
public boolean accept(Item item) {
    if (item != Item.IRON_ORE || oreBuffer >= BUFFER_MAX) return false;
    ...
}
public void tick(World world, int x, int y) {
    ...
    world.offerToNeighbor(x, y, Item.IRON_PLATE);
}
```

```java
// Furnace — стало
private final Recipe recipe;

public Furnace(Recipe recipe) {
    this.recipe = recipe;
    this.cooldown = recipe.time();
}

public boolean accept(Item item) {
    if (item != recipe.input() || buffer >= BUFFER_MAX) return false;
    ...
}
public void tick(World world, int x, int y) {
    ...
    world.offerToNeighbor(x, y, recipe.output());
}
```

Ни одного упоминания `IRON_ORE`/`IRON_PLATE` в самом классе не осталось. `Furnace.java` теперь не
знает, что именно она перерабатывает, — и именно поэтому больше НИКОГДА не потребует правки ради
нового рецепта.

Похоже на `SortRule` (урок 12)? По механике — да, тот же приём «поведение снаружи». Но смысл
другой: `SortRule` — это РЕШЕНИЕ («куда толкнуть именно этот предмет»), а `Recipe` — это
НАСТРОЙКА («чем вообще питается это здание и что производит»). Strategy отвечает на вопрос
каждый тик заново; данные рецепта просто лежат и читаются.

## 3. Печь и пресс — один класс, два ответа на «кто я»

Проблема, которую легко не заметить: `Building.type()` должен возвращать РАЗНОЕ для печи и
пресса — иначе сохранение перепутает их при загрузке. Соблазн — дать `Furnace` два параметра
конструктора: `Furnace(Recipe recipe, BuildingType type)`. Опасность в том, что их можно
рассинхронизировать: ничто не мешает написать `new Furnace(Recipe.GEAR, BuildingType.FURNACE)` —
пресс, притворяющийся печью, скомпилируется и будет вести себя необъяснимо.

Решение — не давать двух параметров вообще. `type` живёт ВНУТРИ `Recipe`:

```java
public BuildingType type() {
    return recipe.type();   // печь и пресс отвечают на «кто я» через свой рецепт
}
```

Каждая константа рецепта сама решает, какому пункту меню принадлежит, — рассинхронизировать
нечего, потому что синхронизировать больше нечего по отдельности.

## 4. Подключение — и честная плата за сохранение

```java
// World
public boolean placeFurnace(int x, int y) {
    return placeIfFree(x, y, () -> new Furnace(Recipe.IRON));
}
public boolean placePress(int x, int y) {
    return placeIfFree(x, y, () -> new Furnace(Recipe.GEAR));
}
```

Обе двери зовут ОДИН конструктор с разными данными — не два класса. `BuildingType.PRESS("Press")`
добавился в перечисление, хотбар подхватил его сам (урок 7), клавиша `6` заработала сама (урок 13,
`NUM_1 + ordinal`).

Один нюанс НЕ достался бесплатно — сохранение. `Furnace.save()` пишет только буфер и таймер, без
рецепта:

```java
public String save() { return buffer + " " + cooldown; }
```

А вот загрузка ДОЛЖНА знать рецепт заранее — угадать его по двум числам неоткуда. Решает это
`SaveGame`, у которого рецепт и так под рукой — он же читает ТЕГ здания из файла:

```java
Building building = switch (type) {
    ...
    case FURNACE -> Furnace.load(data, Recipe.IRON);
    case PRESS   -> Furnace.load(data, Recipe.GEAR);
};
```

Сравни с сортировщиком (урок 12): там правило ВООБЩЕ не сохранялось (при загрузке всегда
подставлялось одно и то же `ORE_FORWARD`), потому что все сортировщики в игре и так жили по одному
правилу. Здесь так поступить было бы НЕВЕРНО: печь и пресс — не один и тот же случай с одним
запасным значением, а два РАЗНЫХ, различимых по тегу. Раз тег уже есть — используем его, а не
упрощаем там, где упрощение обманывало бы.

## 5. Счёт: что было тронуто, а что — нет

- `Item.java` — одна новая строка (`GEAR`).
- `Recipe.java` — новый файл (инфраструктура рецептов, пишется РАЗ, а не на каждый рецепт).
- `Furnace.java` — рефакторинг (тоже разовый: сделан один раз для ВСЕХ будущих рецептов).
- `BuildingType.java` — одна новая строка (`PRESS`).
- `World.java` — один новый метод в три строки + одна строка в `switch`.
- `SaveGame.java` — одна строка в `switch`.

Нигде не тронуты: `BuildingRenderer` (пресс рисуется тем же кодом, что и печь — `Sprite` не
менялся ни на одну строку), `InputHandler` (клавиша нашлась сама), `HudRenderer` (хотбар и
`Produced:` строятся из `values()` — уже показывали этот трюк в уроках 7 и 9), `Building.java`
(сортов зданий не прибавилось — прибавилось РЕЦЕПТОВ для уже разрешённого сорта).

Честно: визуально пресс сейчас неотличим от печи — оба рисуются одним и тем же `FURNACE_HOT`/
`FURNACE_COLD`. Это ограничение текущих ассетов (своего спрайта у пресса пока нет), не
архитектуры — рецепт от внешности решил остаться независим специально.

## 6. Запуск

```
./gradlew run
```

1. Бур (`1`) на руду, печь (`3`) рядом — плавит руду в пластины, как раньше.
2. Пресс (`6`) следующей клеткой — берёт пластины, штампует шестерёнки (`GEAR`) 8 тиков за штуку.
3. Ящик (`2`) в конце цепочки — копит уже шестерёнки.
4. Смотри на HUD: `Produced:` сама показала третий предмет — `GEAR N` — без единой правки
   `HudRenderer`.
