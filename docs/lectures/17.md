# Урок 17 — Когда паттерн не нужен: State против обычного флага

Прошлые уроки блока паттернов показывали одно и то же: боль от наивного кода, потом приём — и
боль уходит. Этот урок — про обратную дисциплину. Паттерн — тоже расход: новые типы, косвенность,
лишнее место, которое надо держать в голове. Инженер, который знает только «когда паттерн нужен»,
опасен ровно так же, как тот, кто не знает паттернов вовсе, — просто расставляет их везде.

**В этом уроке ты не откроешь ни одного файла в `src`.** Мы напишем соблазнительный рефакторинг
как черновик, посчитаем его настоящую цену — и решим не применять. Это тоже валидный вывод урока,
причём самый частый в реальной работе.

---

## Чему ты научишься

- **Считать паттерн расходом, а не подарком.** Новые файлы, новая косвенность — цена, которую
  платишь ДО того, как получишь выгоду; выгода должна её окупить, а не просто существовать.
- **Отличать ПРОИЗВОДНОЕ значение от НЕЗАВИСИМОГО факта.** «Горячая ли печь» — это не факт из
  внешнего мира, это чистая функция от `buffer`. Настоящее состояние — то, что нельзя вычислить
  заново, у него есть своя память.
- **Конкретный риск, а не общие слова.** Не «церемония», а воспроизводимый баг: два места, обязанные
  соглашаться друг с другом, разошлись — и один из них никто не заметил.
- **Где именно граница.** Не «паттерны — это сложно», а конкретное условие, при котором тот же
  самый State перестанет быть излишеством.

---

## 1. Искушение

Открой `Furnace.appearance()`:

```java
public Appearance appearance() {
    return buffer > 0
            ? Appearance.of(Sprite.FURNACE_HOT, buffer)
            : Appearance.of(Sprite.FURNACE_COLD);
}
```

Выглядит как «состояние»: печь то горячая, то холодная. Кто-то, только что прошедший курс по
паттернам, увидит здесь ровно один намёк — «State! Заведу `Idle`/`Working`, каждое само знает
свой спрайт». Звучит убедительно. Проверим, что это даёт НА САМОМ ДЕЛЕ, не на словах.

---

## 2. Пишем то, что шепчет шаблон

Черновик — три новых файла и переписанная печь:

```java
interface FurnaceState {
    Sprite sprite();
}
final class Idle implements FurnaceState {
    public Sprite sprite() { return Sprite.FURNACE_COLD; }
}
final class Working implements FurnaceState {
    public Sprite sprite() { return Sprite.FURNACE_HOT; }
}
```

```java
public final class Furnace /* ... */ {
    private FurnaceState state = new Idle();   // ← второй источник истины про "горячая ли я"

    public boolean accept(Item item) {
        if (item != recipe.input() || buffer >= BUFFER_MAX) return false;
        buffer++;
        state = new Working();                 // не забыть обновить здесь
        return true;
    }

    public void tick(World world, int x, int y) {
        if (buffer == 0) return;
        if (--cooldown > 0) return;
        cooldown = recipe.time();
        buffer--;
        world.offerToNeighbor(x, y, recipe.output());
        if (buffer == 0) state = new Idle();   // и ЕЩЁ РАЗ не забыть обновить здесь
    }

    public Appearance appearance() {
        return buffer > 0 ? Appearance.of(state.sprite(), buffer) : Appearance.of(state.sprite());
    }
}
```

## 3. Считаем цену — числами, не ощущениями

| | Было (`buffer > 0`) | Стало (`FurnaceState`) |
|---|---|---|
| Новых типов | 0 | 3 (`FurnaceState`, `Idle`, `Working`) |
| Новых строк | 0 | 83 (посчитано `wc -l` по черновику) |
| Источников истины про «горячая ли печь» | 1 (`buffer`) | 2 (`buffer` И `state`) |
| Мест, обязанных соглашаться друг с другом | 0 | 2 (`accept`, `tick`) |

Последняя строка — самая важная. `buffer` и `state` теперь ДОЛЖНЫ всегда указывать одно и то же
— это не свойство языка, это долг программиста, который надо помнить в двух разных местах кода.

---

## 4. Настоящая цена — не церемония, а конкретный баг

Кто-то один раз забыл вторую синхронизацию — убрал `if (buffer == 0) state = new Idle();` из
`tick`. Компилятор не возразил ни словом: `state` — обычное поле, его можно не трогать сколько
угодно. Вот что происходит:

```
good:  hotWhileWorking=true coldAfterEmpty=true buffer=0
buggy: buffer=0 sprite=FURNACE_HOT (ожидали бы FURNACE_COLD, раз buffer==0)
OK - подтверждён конкретный баг рассинхронизации: buffer==0, но спрайт
всё ещё FURNACE_HOT, потому что забыли обновить state в ОДНОМ из двух мест
```

Буфер пуст — печь ничего не перерабатывает, — а на экране она всё ещё «горячая» и с числом. Игрок
видит вымышленную работу. Ни один тест на `buffer` эту ошибку не поймает: `buffer` как раз в
полном порядке. Ошибка живёт ИСКЛЮЧИТЕЛЬНО в рассинхронизации.

С `buffer > 0` такой баг СТРУКТУРНО невозможен: там одно значение читается напрямую, второму
просто неоткуда взяться и разойтись с первым.

---

## 5. Вердикт: не применяем

`buffer` в печи — не намёк на паттерн, а обычное число, из которого «горячая/холодная» ВЫЧИСЛЯЕТСЯ
за одно сравнение. У этого числа нет собственной памяти, нет истории, нет ничего, что оправдывало
бы отдельный объект. `Furnace.java` остаётся как есть, ни одна строка в `src` не менялась. Это и
есть верный ответ на «нужен ли тут State» — не потому что паттерны плохие, а потому что здесь
нечего инкапсулировать: значение и так живёт в одном месте.

---

## 6. Где та же самая печь заслужила бы State

Граница — не «паттерны сложны», а конкретное условие: State окупается, когда состояние — это
НЕЗАВИСИМЫЙ факт с СОБСТВЕННОЙ памятью, которую нельзя вычислить заново из уже существующих полей,
и это состояние меняет поведение СРАЗУ НЕСКОЛЬКИХ методов не одинаково.

Придумаем (только словами, без кода — сегодня мы код не пишем) сценарий, где это правда: печь
**перегревается**, если отработала без остановки N тиков подряд, и после этого **не принимает
руду вообще** ещё M тиков, пока не остынет — даже если `buffer` позволяет. Для этого нужны ДВА
новых счётчика, которых сейчас нет вообще («сколько тиков подряд без простоя», «сколько ещё
тиков блокировки»), и `accept`, и `tick` должны вести себя по-разному в зависимости от того, в
каком из ТРЁХ состояний печь: обычная работа, перегрев, охлаждение. Здесь `Idle`/`Working`/
`Overheated`, каждый со своим `accept`/`tick`, уже не церемония — они СОБИРАЮТ разбросанные по
двум методам условия в одно место на состояние, вместо `if` внутри `if` внутри `if`.

Разница именно в этом: раньше состояние было ФУНКЦИЕЙ одного поля; в гипотезе выше — оно НЕСЁТ
информацию, которой больше неоткуда взяться.
