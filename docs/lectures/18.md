# Урок 18 — Decorator: апгрейд одной конкретной печи

Рецепты (урок 16) меняют, ЧТО здание производит. Сегодня — ось прогрессии про то, КАК БЫСТРО.
Хотим вставить модуль скорости в ОДНУ конкретную печь — ускорить именно её, а соседнюю не трогать.
И чтобы модули складывались: печь в двух модулях быстрее, чем в одном.

Это последний урок блока паттернов, и он не только про новый приём — **Decorator** — но и про
честное столкновение с решением, которое мы приняли ещё в уроке 4: `Building` у нас `sealed`.
Decorator по своей природе хочет оборачивать что угодно, не спрашивая разрешения. Sealed —
противоположная идея: список того, что разрешено, закрыт заранее. Это трение — не досадная
мелочь, а сердце сегодняшнего урока.

---

## Чему ты научишься

- **Оборачивать объект тем же интерфейсом.** Модуль скорости — здание, которое внутри держит
  ДРУГОЕ здание и подсовывает миру себя вместо него.
- **Складывать обёртки.** Два модуля — это обёртка вокруг обёртки; ни одна не знает, сколько их
  всего снаружи или внутри.
- **Настоящую цену sealed для декоратора.** Не абстрактно «неудобно», а точно — что именно
  приходится сделать, чтобы декоратор появился в закрытом списке.
- **Честную границу.** Что модуль скорости НЕ переживает (сохранение) и почему это осознанный
  предел, а не забытый баг.

---

## 1. Идея: обернуть, а не изменить

Задача звучит как «печь работает быстрее» — соблазн полезть внутрь `Furnace` и завести там
множитель скорости. Но тогда ускорить можно только печь: захочешь ускорить бур или пресс — снова
лезть внутрь другого класса, и так на каждое здание. Вместо этого — обёртка ВОКРУГ любого
`Building`, которая тикает его чаще:

```java
// com/rustorio/SpeedModule.java
public final class SpeedModule implements Building {

    private final Building inner;

    public SpeedModule(Building inner) {
        this.inner = inner;
    }

    @Override
    public void tick(World world, int x, int y) {
        inner.tick(world, x, y);
        inner.tick(world, x, y);   // второй вызов — и есть всё ускорение
    }

    @Override
    public boolean accept(Item item)     { return inner.accept(item); }
    @Override
    public Appearance appearance()       { return inner.appearance(); }
    @Override
    public BuildingType type()           { return inner.type(); }
    @Override
    public String save()                 { return inner.save(); }
}
```

`SpeedModule` не знает и знать не должен, печь внутри или бур, — он лишь дважды зовёт `tick` и
честно передаёт остальные четыре метода дальше без изменений. Здание внутри не подозревает, что
его поторопили: оно просто получает вызов `tick` чаще, чем обычно.

---

## 2. Складывание — бесплатно, само собой

```java
Building x1 = new SpeedModule(furnace);
Building x2 = new SpeedModule(new SpeedModule(furnace));
```

`x2` — обёртка вокруг обёртки. Внешний `SpeedModule` дважды зовёт `tick` у внутреннего
`SpeedModule`, а тот, в свою очередь, у КАЖДОГО своего вызова снова тикает настоящую печь дважды —
итого печь под `x2` получает четыре вызова `tick` за один тик мира. Ни один из двух модулей не
писал код для этого случая специально — сложение получилось из того, что декоратор реализует ТОТ
ЖЕ интерфейс, что и то, что он оборачивает, и потому сам может быть обёрнут снова.

Проверено: обычная печь (рецепт на 5 тиков) выдаёт первую пластину на 5-м тике; в одном модуле —
на 3-м; в двух — на 2-м. Каждый слой честно ускоряет то, что внутри, не зная, сколько слоёв
вокруг него самого.

---

## 3. Настоящая цена sealed — не абстракция, а конкретный список правок

`Building` — `sealed interface Building permits Miner, Chest, Furnace, Belt, Splitter`. Чтобы
`SpeedModule` вообще СКОМПИЛИРОВАЛСЯ как `implements Building`, пришлось вписать его в этот список
явно — иначе ошибка сборки: «class is not allowed to extend sealed class». Никакого способа
обойти это, реализовав интерфейс молча, не существует — sealed для того и придуман.

Стоит проверить факт, а не поверить на слово: раньше (до урока 8) добавление в `permits` ломало
`switch` в отрисовке, и приходилось чинить его тоже. Сейчас — проверено — такого `switch` по
зданиям в проекте больше НЕТ вообще (последний убрали в уроке 8, заменив на `appearance()`).
Значит ли это, что sealed для декоратора теперь бесплатен? Нет: сама СТРОКА в `permits`
по-прежнему обязательна — просто в НАШЕМ конкретном проекте цепочка поломок, которая раньше шла
за ней, уже разомкнута более ранними рефакторингами. Более полная плата — в другом месте:
`SpeedModule` обязан реализовать ВСЕ ПЯТЬ методов `Building`, хотя меняет поведение только у
одного. Четыре из пяти — чистое делегирование, работа, которую декоратор обязан сделать просто
потому, что интерфейс требует. Добавится шестой метод в `Building` завтра — `SpeedModule`
немедленно перестанет компилироваться, пока не допишешь делегирование и для него.

## 4. Подключение: апгрейд — это тоже действие

Обернуть здание в клетке — значит снять его и поставить обратно, уже обёрнутым. Знакомая форма —
`PlayerAction` (урок 15):

```java
// com/rustorio/UpgradeSpeedAction.java
public final class UpgradeSpeedAction implements PlayerAction {
    private final int x, y;
    private Building previous;   // что стояло ДО апгрейда — для отмены

    @Override
    public boolean apply(World world) {
        previous = world.removeBuilding(x, y);
        if (previous == null) return false;
        world.restore(x, y, new SpeedModule(previous));
        return true;
    }

    @Override
    public void undo(World world) {
        world.restore(x, y, previous);   // снимаем обёртку целиком — тот же приём, что RemoveAction
    }
}
```

Отмена апгрейда — не «снести и поставить обычное здание заново», а вернуть НА МЕСТО ровно то, что
там было (уже сколько-то раз обёрнутое или нет — неважно). `World.java` при этом не пришлось
трогать НИ РАЗУ: `removeBuilding`/`restore` уже умели работать с ЛЮБЫМ `Building`, а
`SpeedModule` — просто ещё один. Клавиша `U` под курсором заворачивает клик в это действие и
отдаёт его той же `ActionHistory`, что уже применялась к постройке и сносу.

---

## 5. Честная граница: апгрейд не переживает сохранение

`SpeedModule.save()` и `.type()` делегируют внутреннему зданию БЕЗ следа обёртки — значит, файл
сохранения печи в модуле выглядит ТОЧНО так же, как файл обычной печи. После `F9` апгрейд
пропадает, здание возвращается к своему базовому виду. Это не забытый баг, а сознательно не
решённая сегодня задача: чтобы обёртка переживала перезагрузку, формат сохранения (урок 10)
должен уметь записывать ВЛОЖЕННОСТЬ — «модуль вокруг печи вокруг ещё одного модуля» — а это уже
не одна строка на здание, а рекурсивный формат. Стоит ли это того, если апгрейды в игре — редкое
решение игрока, а не основа экономики? Урок 17 научил задавать этот вопрос вслух, а не решать его
рефлекторно.

## 6. Запуск

```
./gradlew run
```

1. Собери бур → печь → ящик, дай поработать — заметь ритм, с которым растёт число в ящике.
2. Наведи курсор на печь, нажми **`U`** — модуль скорости вставлен. Тот же рецепт, но пластины
   капают заметно чаще.
3. Нажми **`U`** ещё раз на той же печи — вторая обёртка, ритм ускоряется снова.
4. **Ctrl+Z** — снимает последний модуль (печь возвращается к прежней скорости, не исчезает).
5. `F5`, перезапусти, `F9` — печь на месте, но снова в БАЗОВОЙ скорости: апгрейд не сохранился,
   ровно как предупреждал раздел 5.
