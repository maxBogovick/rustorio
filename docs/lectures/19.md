# Урок 19 — Направление ленты: обещание из урока 11 выполнено

Урок 11 честно предупредил: «лента только вправо — направление и повороты будут отдельным
уроком-улучшением». База с тех пор прошла весь блок паттернов и устоялась. Пора.

Задача звучит просто — дать ленте направление на выбор. Но простая задача вскрыла настоящий баг в
уже проверенном коде: механизм «одна клетка за тик» из урока 11 был заточен ИМЕННО под движение
вправо. Сегодняшний урок — не только «добавили фичу», но и «доверяй, но проверяй» — код, который
работал полгода уроков подряд, оказался наполовину неправильным для нового случая использования.

---

## Чему ты научишься

- **Направление как значение, а не зашитая арифметика.** `x + 1` было спрятанным предположением;
  теперь это `x + direction.dx()` — предположение стало явным параметром.
- **Проверять старые гарантии на новых входных данных.** Тест, который годами проходил для одного
  направления, ничего не говорит про остальные три — если их не проверить отдельно.
- **Шестой метод в `Building` — и его настоящую цену.** Урок 18 задавал вопрос «что будет с
  `SpeedModule`, если у `Building` появится шестой метод?» Сегодня он появился по-настоящему —
  и ответ оказался не риторическим.
- **Полиморфизм вместо `instanceof` — даже когда очень хочется срезать.** Мир не должен спрашивать
  «а ты лента?», чтобы решить порядок обхода.

## 1. Направление — значение, не арифметика внутри `tick`

```java
// com/rustorio/Direction.java
public enum Direction {
    RIGHT(1, 0), DOWN(0, 1), LEFT(-1, 0), UP(0, -1);

    private final int dx, dy;
    Direction(int dx, int dy) { this.dx = dx; this.dy = dy; }
    public int dx() { return dx; }
    public int dy() { return dy; }
    public Direction rotate() { return values()[(ordinal() + 1) % values().length]; }
}
```

Лента теперь хранит направление и толкает предмет по нему, а не по зашитому `+1`:

```java
// Belt
private final Direction direction;

public Belt(Direction direction) { this.direction = direction; }

@Override
public void tick(World world, int x, int y) {
    if (held == null) return;
    if (world.offerForward(x + direction.dx(), y + direction.dy(), held)) held = null;
}
```

Постройка получает направление через уже знакомый механизм — клавиша `R` крутит «в какую сторону
буду строить», ЛКМ ставит с текущим направлением:

```java
// InputHandler
private Direction facing = Direction.RIGHT;
...
if (Gdx.input.isKeyJustPressed(Input.Keys.R)) facing = facing.rotate();
...
history.perform(world, new PlaceAction(selected, tile.x(), tile.y(), facing));
```

`World.place`/`placeBelt` получили параметр `Direction`; здания, которым он безразличен (бур,
ящик, печь, пресс, сортировщик), его просто игнорируют — тот же принцип, что уже был с `x`/`y`
в `tick`: параметр есть у всех, пользуется им, кому надо.

## 2. Старая гарантия, проверенная на новом входе, — не подтвердилась

Урок 11 доказывал: обход зданий «с конца» (`descendingMap`, от больших `x` к меньшим) гарантирует
ленте ровно один шаг за тик. Формально утверждение звучало как «обходим справа налево» — но
НАСТОЯЩАЯ причина была уже, чем формулировка: порядок работал, потому что лента толкала именно
ВПРАВО. Стоило проверить это буквально — тем же самым тестом, что и в уроке 11, только для всех
четырёх направлений:

```
RIGHT tick 1: .#...   tick 2: ..#..   tick 3: ...#.   tick 4: ....#   tick 5: ..... chest=1
DOWN  tick 1: .#...   tick 2: ..#..   tick 3: ...#.   tick 4: ....#   tick 5: ..... chest=1
LEFT  tick 1: .....                                                          chest=1  ← !!
UP    tick 1: .....                                                          chest=1  ← !!
```

`RIGHT` и `DOWN` — чисто, по клетке за тик, как и раньше. `LEFT` и `UP` — предмет доехал до
ящика через ВСЮ цепочку из пяти лент за ОДИН тик, будто телепортировался. Старый механизм
защищал только половину направлений, и никто бы не заметил, пока их не завели.

**Почему именно так.** Обход «с конца» ставит соседа с БОЛЬШИМ `x` раньше соседа с меньшим.
Ленте вправо (толкает к большему `x`) это и нужно — цель уже сходила в этом кадре, повторно не
сдвинется. Ленте влево (толкает к МЕНЬШЕМУ `x`) тот же порядок только вредит: цель ещё ВПЕРЕДИ по
ходу обхода, получает предмет и САМА успевает потолкать его дальше в том же кадре — и так по
цепочке.

## 3. Шестой метод — и настоящая проверка урока 18

Единого порядка обхода, который годился бы сразу всем четырём направлениям, не существует —
нужно два прохода: сперва все, кому подходит обход «с конца», потом остальные в обратную сторону.
Кто есть кто — здание отвечает само, не мир его разглядывает:

```java
// Building — шестой метод, с default: почти всем зданиям всё равно
default boolean prefersDescendingTick() { return true; }
```

```java
// Belt
@Override
public boolean prefersDescendingTick() {
    return direction == Direction.RIGHT || direction == Direction.DOWN;
}
```

```java
// World.tick()
public void tick() {
    for (var e : buildings.descendingMap().entrySet())
        if (e.getValue().prefersDescendingTick()) tickEntry(e);
    for (var e : buildings.entrySet())
        if (!e.getValue().prefersDescendingTick()) tickEntry(e);
}
```

Ни одного `instanceof Belt` в мире — та же дисциплина, что и в уроке 6: мир задаёт вопрос
интерфейсу, а не разбирает конкретные классы.

И вот та самая проверка, которую урок 18 задавал как домашнее задание («что будет с
`SpeedModule`, если появится шестой метод?») — теперь не гипотеза. `default` не заставил
компилятор потребовать реализацию у `SpeedModule`, и первая версия декоратора её не получила бы
просто по инерции. Проверено намеренно:

```java
Belt leftBelt = new Belt(Direction.LEFT);
Building wrapped = new SpeedModule(leftBelt);
wrapped.prefersDescendingTick();   // без делегирования — true (default), должно быть false
```

Без явного делегирования апгрейженная лента влево ЗАБЫВАЕТ, что она лента влево, и снова
телепортирует предмет через всю цепочку — ровно тот баг из раздела 2, только спрятанный за
декоратором. Чиним так же, как остальные четыре метода:

```java
// SpeedModule
@Override
public boolean prefersDescendingTick() {
    return inner.prefersDescendingTick();
}
```

## 4. Запуск

```
./gradlew run
```

1. Клавишей `4` выбери ленту, `R` покрути направление — в HUD строка `Facing:` меняется.
2. Построй бур (руда всегда рядом), ленту ВПРАВО от него, потом ещё несколько лент, поворачивая
   `R` перед каждой постройкой, чтобы цепочка сложилась буквой Г или змейкой.
3. Ящик в конце — смотри, как руда едет по клетке за тик через все повороты, включая те, что
   идут ВЛЕВО или ВВЕРХ.

Честно: спрайт ленты одинаковый во все стороны — как и пресс в уроке 16, поворот картинки не
тема этого урока. Куда толкает лента, видно по движению предмета, не по рисунку самой ленты.

## 5. Задание

1. Собери цепочку с поворотом (хотя бы одна лента влево или вверх), проверь на глаз — предмет
   действительно едет по клетке за тик, а не прыгает.
2. Апгрейдни клавишей `U` именно ленту, повёрнутую влево или вверх. Убедись, что предмет по-прежнему
   едет аккуратно (быстрее, но не скачками) — это и есть проверка делегирования из раздела 3.
3. Временно закомментируй `prefersDescendingTick` в `SpeedModule` (пусть наследует `default`),
   пересобери, апгрейдни ленту влево — понаблюдай баг живьём. Верни как было.
4. Ответь письменно: почему нельзя починить эту задачу ОДНИМ порядком обхода на все четыре
   направления сразу? Что случилось бы с лентой, направленной ПРЯМО НА другую ленту, направленную
   ей навстречу?
