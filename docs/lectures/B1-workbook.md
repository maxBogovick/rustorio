# B1 — Рабочая тетрадь: чанки

> **Как этим пользоваться.** Здесь нет ни одной строчки решения — только объяснение,
> **зачем** нужен очередной кусок, **что** он обязан уметь и **как** проверить, что он это
> умеет. Код вы пишете сами.
>
> В конце каждого шага — две ссылки: **💡 Подсказка** (направление, но не ответ) и
> **📄 Решение** (код целиком). Каждая ведёт в **отдельный файл**, поэтому вы видите ровно
> один ответ, а не всю простыню сразу. Пока не перешли — ответ на глаза не попадётся.

> Заглянуть в решение — **не поражение**. Поражение — сидеть три вечера в одном месте. Но
> сначала честно попробуйте сами: код, который вы написали и который не заработал, учит
> больше, чем правильный код, который вы прочитали.

## 0. Что мы делаем — в трёх предложениях

Мир перестаёт быть одним большим массивом клеток и становится **набором кусков 32×32**,
которые создаются, только когда в них впервые заглянули.

Публичный интерфейс мира при этом **не меняется вообще**: снаружи — те же `tile(x, y)`,
`place`, `remove`, `forEachBuilding`.

Главный критерий успеха — **старые тесты пройдут, не изменившись ни на строчку**. Если
пришлось их чинить, значит, устройство мира протекло наружу.

---

## 1. Карта: три кирпича

```
   World  (фасад — снаружи ничего не изменилось)
     │  tile(x,y) · place · remove · forEachBuilding
     │
     ├──► Map<Long, Chunk>          «кусок появляется, когда в него заглянули»
     │        │
     │        ▼
     │      Chunk 32×32             «Tile[1024] внутри»
     │        │
     │        ▼
     └──►  OreMap.hasOre(x, y)      «руда — ФУНКЦИЯ, а не массив»
```

| Класс | Зачем существует (одна причина) |
|-------|--------------------------------|
| `Chunk` | Кусок мира 32×32. Создаётся по требованию — поэтому мир может расти, не занимая память впустую |
| `OreMap` | Ответ на «есть ли руда в (x, y)?» **без создания мира**. Раньше руду раскладывали в массив — с чанками так нельзя |
| `World` | Остаётся **фасадом**. Внутри меняется фундамент, снаружи форма двери прежняя |

**«Почему 32×32?»** Индустриальный стандарт (Factorio, Minecraft): компромисс между «слишком
много мелких кусков» (накладные расходы на каждый) и «в куске слишком много лишнего» (обходим
впустую).

**«Почему руда стала функцией?»** Раньше `generate()` проходил по всем клеткам и расставлял
залежи. С чанками «пройти по всем клеткам» **невозможно** — их ещё нет. Значит, вопрос «есть
ли руда в (x, y)?» должен иметь ответ **до** того, как клетка создана. Функция от координат —
ровно такой ответ, и она детерминирована: одна клетка всегда даёт один ответ, в каком бы
порядке ни создавались куски.

## 2. Порядок работы

| Шаг | Что появляется | Что уже можно проверить |
|-----|----------------|-------------------------|
| 1 | `OreMap` — руда как функция | старый тест «бур знает про руду» зелёный |
| 2 | `Chunk` | — |
| 3 | `World` внутри — карта кусков | **все старые тесты зелёные, БЕЗ правок** |

| 5 | Новые тесты на чанки | «пустой мир не создаёт кусков» |

## ШАГ 2. `Chunk`

### Что должно уметь

```java
final class Chunk {
    static final int SIZE = 32;
    static final int MASK = SIZE - 1;   // x & MASK  == x % 32, но быстрее
    static final int SHIFT = 5;         // x >> SHIFT == x / 32, но быстрее

    Chunk(int chunkX, int chunkY);      // создаёт свои 1024 клетки (с рудой из OreMap)
    Tile tile(int localX, int localY);  // ЛОКАЛЬНЫЕ координаты 0..31
}
```

### Про `>>` и `&` вместо `/` и `%`

Для степеней двойки это одно и то же, но короче и быстрее. Не самоцель, но приём стоит знать:
32 = 2⁵, поэтому `x / 32` = `x >> 5`, а `x % 32` = `x & 31`. Именно поэтому размер куска —
степень двойки, а не «круглое» число вроде 30.

### Класс — пакетно-приватный

Наружу устройство мира **не торчит**. В этом весь смысл задачи: `sim`, `render` и `input`
даже не узнают, что появились какие-то куски.

💡 Подсказка: [П2](answers/B1-hint-2.md) · 📄 Решение: [Р2](answers/B1-solution-2.md)

## ШАГ 3. `World`: фасад держит удар

### Что меняется внутри

```java
    private final Map<Long, Chunk> chunks = new HashMap<>();

    public Tile tile(int x, int y);          // сигнатура ТА ЖЕ
    private Chunk chunk(int chunkX, int chunkY);   // создаёт по требованию
    private static long key(int chunkX, int chunkY);  // упаковать две координаты в long
```

### Ключ — упакованные координаты

Две координаты `int` умещаются в один `long`: старшие 32 бита — X, младшие — Y.
`((long) chunkX << 32) | (chunkY & 0xFFFFFFFFL)`. Маска нужна, чтобы отрицательный Y не
«залил» единицами старшую половину (это классическая ловушка знакового расширения).

### Как проверить — и это главный критерий задачи

**Старые тесты `WorldTest` проходят, не изменившись ни на строчку.** Они написаны через
координаты и ничего не знают о хранении. Зелёные — значит, фундамент заменён незаметно.

Если пришлось их править — остановитесь: где-то устройство мира протекло наружу, и это надо
чинить сейчас, а не потом.

💡 Подсказка: [П3](answers/B1-hint-3.md) · 📄 Решение: [Р3](answers/B1-solution-3.md)

## ШАГ 4. Обход: ловушка, о которой легко не подумать

### Задача

`forEachBuilding` должен обойти все здания. Куски лежат в `HashMap`. Соблазн: пройтись по
`chunks.values()`.

### Почему так делать НЕЛЬЗЯ

Порядок обхода `HashMap` **произволен** и может отличаться между запусками. А симуляция
обязана быть **воспроизводимой**: одинаковые действия — одинаковый мир. Если порядок обхода
зданий плавает, то плавает и порядок передачи предметов — и мир становится
невоспроизводимым. Сохранения сломаются, тесты начнут падать через раз.

### Как правильно

Идти по **координатной сетке кусков** (`for cy … for cx …`), а карту только **спрашивать**.
Пустые куски пропускаются целиком — на разреженном мире обход почти бесплатен.

> Это ровно то, что стережёт правило детерминизма из задачи C6. Здесь видно, зачем оно.

💡 Подсказка: [П4](answers/B1-hint-4.md) · 📄 Решение: [Р4](answers/B1-solution-4.md)

## ШАГ 5. Новые тесты и замер

### Тесты

- **Пустой мир не создаёт ни одного куска.** Заглянули в угол — создался один. Заглянули
  далеко — второй, а не весь мир.
- **Далёкая клетка работает как любая другая.**

### Замер: честный результат

Прогоните бенчмарк (C1) до и после. У меня вышло:

```
до  B1 (плоский массив): среднее 0,504 мс
после B1 (чанки):        среднее 0,593 мс
```

**Стало медленнее примерно на 18%.** И это нормально — вот почему.

На **плотно застроенном** мире чанки ничего не дают: клетки те же, а к каждому обращению
добавился поиск куска в карте. Выигрыш чанков — в другом: мир может **расти**, а пустое
место **ничего не стоит**. Мы разменяли немного скорости на возможность иметь мир, который не
влезал в память.

Главное — мы **знаем** цену, потому что померили. Бюджет 8 мс, у нас 0.6 — платить можно.

## 7. Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|------------|---------------|
| Пришлось править старые тесты | Устройство мира протекло наружу — ищите новый публичный метод, который выдаёт куски |
| Симуляция ведёт себя по-разному между запусками | Обход по `HashMap` вместо сетки кусков (шаг 4) |
| Клетки с отрицательными координатами ломаются | Знаковое расширение в ключе: забыта маска `& 0xFFFFFFFFL` |
| Мир занимает память сразу | `generate()` создаёт куски заранее вместо «по требованию» |
| Руда пропала | `OreMap` вызывается с локальными координатами куска вместо мировых |
| Стало медленнее | **Так и должно быть** на плотном мире. Смотрите, укладываетесь ли в бюджет |

## 8. Если совсем застряли

1. Проверьте перевод координат: мировая `x` → кусок `x >> 5`, локальная `x & 31`. Обратно:
   `(chunkX << 5) + localX`. Половина ошибок в этой задаче — именно здесь.
2. Напечатайте `chunkCount()` после каждой операции: создаётся ли лишнее?
3. Идите с падающим **старым** тестом — он точно указывает, где протекло.
