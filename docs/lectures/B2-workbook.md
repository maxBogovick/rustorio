# B2 — Рабочая тетрадь: симуляция обзаводится буферами

> **Как этим пользоваться.** Здесь нет ни одной строчки решения — только объяснение,
> **зачем** нужен очередной кусок, **что** он обязан уметь и **как** проверить, что он это
> умеет. Код вы пишете сами.
>
> В конце каждого шага — две ссылки: **💡 Подсказка** (направление, но не ответ) и
> **📄 Решение** (код целиком). Каждая ведёт в **отдельный файл**, поэтому вы видите ровно
> один ответ, а не всю простыню сразу. Пока не перешли — ответ на глаза не попадётся.
>
> Заглянуть в решение — **не поражение**. Поражение — сидеть три вечера в одном месте. Но
> сначала честно попробуйте сами: код, который вы написали и который не заработал, учит
> больше, чем правильный код, который вы прочитали.

>

## 0. Что мы делаем — в трёх предложениях

Симуляция перестаёт быть «набором статических функций» и становится **объектом**, который
живёт всю игру и владеет своими рабочими буферами.

Заодно исчезает массив отметок «в эту клетку уже кладут предмет», который каждый тик
создавался заново, — его заменяет приём **«штамп версии»**.

Звучит как мелкая уборка, но без неё **не поедет задача B1** (чанки), и это, а вовсе не
скорость, — настоящая причина делать её сейчас.

## 1. Карта: что меняется и зачем

```
   БЫЛО                                  СТАЛО
   ┌────────────────────────┐            ┌────────────────────────┐
   │ Systems                │            │ Simulation             │
   │ (статические методы,   │   ───►     │ (ОБЪЕКТ, живёт всю     │
   │  без состояния)        │            │  игру, владеет         │
   │                        │            │  буферами)             │
   │ каждый тик:            │            │ каждый тик:            │
   │  new ArrayList<>()     │            │  moves.clear()         │
   │  new boolean[всеКлетки]│            │  tick++                │
   └────────────────────────┘            └───────────┬────────────┘
                                                     │ вместо массива отметок
                                                     ▼
                                         ┌────────────────────────┐
                                         │ Tile.claimedTick       │
                                         │ «клетка занята ⇔       │
                                         │  claimedTick == тик»   │
                                         └────────────────────────┘
```

| Что | Зачем существует (одна причина) |
|-----|--------------------------------|
| `Simulation` (новый) | Хранить буферы **между** тиками, чтобы не создавать их заново каждый шаг |
| `Simulation.moves` | Переиспользуемый список запланированных передач: `clear()` вместо `new` |
| `Simulation.tick` | Счётчик тиков — он и есть «штамп», которым метятся занятые клетки |
| `Tile.claimedTick` | Клетка сама помнит, на каком тике её заняли. Заменяет массив отметок, которого в чанковом мире не построить |
| `World.claimNeighbor(...)` | Дать симуляции застолбить соседнюю клетку, не зная, как мир хранит клетки внутри |
| `Systems` (старый) | **Удаляется.** |

**«Зачем плодить сущности — был же простой класс с функциями?»** Он и правда был лучше:
класс без состояния невозможно испортить, он не может «протечь» между вызовами. Мы меняем
его на объект **не ради красоты, а вынужденно** — и в §3 честно называем цену.

## ШАГ 1. `Systems` → `Simulation`

### Как сейчас

Фаза передачи предметов работает в два прохода: сначала **планирует** передачи, только
читая мир, потом **применяет** их. Для этого ей нужны две временные вещи — **список
передач** и **отметки «в эту клетку уже кладут»**, — и обе она создаёт заново **на каждом
тике**, а в конце выбрасывает.

### В чём беда — и здесь я должен извиниться

В первой редакции плана я написал, что из-за этого «сборщик мусора заставит игру
подёргиваться», и нарисовал драматичную картину. Потом **сел и посчитал**.

Массив отметок на поле 250×250 — это 62 500 байт. Тиков — пять с половиной в секунду.
Итого около **340 килобайт в секунду**. Для JVM это **вообще ничто**.

Я пугал вместо того, чтобы считать. Извините — и запомните этот эпизод: **интуиция про
производительность врёт, и врёт постоянно.** Ровно поэтому в проекте есть правило
«оптимизация без замера запрещена», а бенчмарк (C1) стоит первой задачей.

### А настоящая причина сильнее

Посмотрите, **как** создаётся массив отметок: его размер — «сколько всего клеток в мире».

В задаче B1 мир станет набором **чанков**, которые появляются по мере надобности. У такого
мира **нет общего числа клеток** и нет сплошной нумерации от нуля. Массив отметок не по
чему создавать и не по чему адресовать.

> **B2 — это не оптимизация. Это условие, без которого не поедет B1.**
> Поэтому она стоит **перед** чанками, а не после.

### Что должно уметь

```java
public final class Simulation {

    public Simulation(World world);      // создаётся ОДИН раз, в GameState

    /** ОДИН шаг симуляции = конвейер систем по порядку. */
    public void step(TickContext ctx);

    // внутри:
    //   private final List<Move> moves = new ArrayList<>();  ← буфер живёт между тиками
    //   private int tick;                                    ← понадобится на шаге 2
}
```

### Размен, который надо назвать вслух

Мы **теряем красоту**. `Systems` был классом без состояния: только статические функции, его
невозможно испортить. `Simulation` — объект с изменяемыми полями, и теперь возможна целая
категория ошибок, которой раньше не было: «буфер не очистили как следует».

Это **осознанная плата** за то, чтобы пережить чанки. Напишите про это в javadoc класса.
Через месяц никто не вспомнит, почему красивый класс стал некрасивым, и кто-нибудь
«исправит» обратно.

*Аналогия:* сейчас мы на каждый обед достаём новую одноразовую тарелку. Станет — одна
тарелка, которую моют. Мыть надо аккуратно — вот и вся цена.

### Как проверить

`MovementTest` проходит после переименования. И **новый тест на главный риск
переиспользования**: два тика подряд дают тот же результат, что и раньше. Если буфер очищен
небрежно, «хвост» прошлого тика протечёт в следующий, и предмет поедет не туда.

💡 Подсказка: [П1](answers/B2-hint-1.md) · 📄 Решение: [Р1](answers/B2-solution-1.md)

## ШАГ 2. «Штамп версии» вместо массива отметок

### Зачем

Симуляции нужно уметь отвечать: «в эту клетку **на этом тике** уже кладут предмет?» Иначе
две ленты, смотрящие в одну клетку, пропихнут туда два предмета за один тик.

Наивно это делается массивом `boolean` на все клетки: в начале тика обнулить, при захвате —
поставить `true`. Две беды: такого массива **не построить в чанковом мире**, и обнулять
миллион ячеек каждый тик — работа на ровном месте.

### Идея

Пусть **клетка сама помнит номер тика**, на котором её заняли:

```
клетка занята  ⇔  claimedTick == текущийТик
```

Наступил новый тик, счётчик увеличился — и **все прошлые отметки автоматически стали
«старыми»**. Ничего обнулять не нужно.

> Обнуление миллиона ячеек заменилось **увеличением одного числа**.

Приём называется «штамп версии» и встречается всюду — от игровых движков до баз данных.
Он стоит того, чтобы его знать.

### Вопрос на понимание (задайте его себе до того, как писать код)

*Почему нельзя просто хранить `boolean claimed` и обнулять его в конце тика — мы ведь и так
проходим по всем зданиям?*

Потому что мы проходим по **зданиям**, а занимать можно и **пустую** клетку — например,
когда сосед хотел бы туда отдать, но приёмника там нет. До пустой клетки обход не дойдёт, и
её отметка останется висеть навсегда.

### Что должно уметь

```java
// Tile
    private int claimedTick = -1;

    /** @return true, если клетку в этом тике ещё не занимали */
    boolean claim(int tick);

// World
    /** Застолбить соседнюю клетку на этот тик. Границы поля проверяет сам. */
    public boolean claimNeighbor(int x, int y, Direction dir, int tick);
```

### Цена, которую надо назвать

Поле `claimedTick` живёт в `Tile` — то есть в **данных мира** поселилось поле, нужное
**только симуляции**. Чистюля скажет, что это протечка слоя, и будет отчасти прав. Мы делаем
это сознательно (так же поступают графические движки со своими «грязными флагами») и пишем
об этом в javadoc.

### Порядок вызовов, на котором легко ошибиться

Сначала убедитесь, что приёмник **существует** и **принимает** предмет, и **только потом**
столбите клетку. Застолбите раньше — и клетка окажется занята впустую, а сосед, который мог
бы туда отдать, останется ни с чем.

### Как проверить

Тест «две ленты в одну клетку пропихнут ровно один предмет» из `MovementTest` **обязан**
остаться зелёным — он и стережёт всю эту логику.

💡 Подсказка: [П2](answers/B2-hint-2.md) · 📄 Решение: [Р2](answers/B2-solution-2.md)

## ШАГ 4. Измерьте, что получилось

### Зачем

**Это обязательная часть задачи, а не украшение.** Прогоните бенчмарк (C1) **до** и
**после**, оба числа впишите в PR.

### Что получилось у меня

```
до  B2:   среднее 0,558 мс   ·   99-й процентиль 0,723 мс
после B2: среднее 0,492 мс   ·   99-й процентиль 0,646 мс
```

Выигрыш — процентов двенадцать. **Не «в разы».** И это правильный, честный результат:
задача делалась не ради скорости, а чтобы пережить чанки. Двенадцать процентов — приятный
бонус, который мы **измерили**, а не выдумали.

Напиши я в отчёте «оптимизация ускорила симуляцию» без чисел — это было бы почти враньём.
С числами — это факт, который можно проверить.

## 6. Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|------------|---------------|
| Предмет через несколько тиков «поехал не туда» | Буфер `moves` не очищается в начале тика (шаг 1) |
| Две ленты пропихнули два предмета в одну клетку | Штамп не проверяется — или клетка столбится не в том порядке (шаг 2) |
| Клетка навсегда осталась «занятой» | Пытаетесь обнулять флаг вручную вместо штампа тика (шаг 2) |
| Передача не состоялась, хотя приёмник свободен | Столбите клетку **до** проверки `canAccept` — она занята впустую (шаг 2) |
| Тесты зелёные, но бенчмарк почти не изменился | **Так и должно быть.** Задача не про скорость, а про совместимость с чанками |
| Буферы всё равно создаются каждый кадр | `GameState` создаёт `Simulation` не в конструкторе, а в `update()` (шаг 3) |

## 8. Чему эта задача учит

Трём вещам, и все три важнее самого кода.

**Интуиция про производительность врёт.** Я сам, планируя эту задачу, нарисовал страшную
картину — а расчёт показал, что бояться было нечего. Считайте. Меряйте. Не верьте себе.

**У правильного решения часто не та причина, которую называют первой.** B2 нужна — но не
из-за мусора, а потому что старый код физически не переживёт чанки. Найдя настоящую причину,
вы и место задачи в плане определите верно (перед B1, а не после).

**Красоту иногда приходится менять на другое — но только вслух.** Молчаливое ухудшение кода
— это долг, о котором через месяц никто не помнит. Названное и объяснённое — это решение.
