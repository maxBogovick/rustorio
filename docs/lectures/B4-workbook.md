## 0. Что мы делаем — в трёх предложениях

Наполняем поведением две заглушки, заведённые ещё в спринте 0: **развилку** (раздаёт поток по
нескольким направлениям) и **подземную ленту** (проносит предметы под постройками).

Обе — не просто «ещё два здания»: каждая ломает какое-то удобное предположение, на котором
держался прежний код, и в этом вся ценность задачи.

После неё в игру становится **интересно** играть: появляются задачи маршрутизации, а не просто
«протяни ленту от А до Б».

## 1. Карта: что появляется и почему именно так

```
   Splitter                          UndergroundBelt
     │ держит 1 предмет                │ вход:  очередь с таймерами
     │ outputsInOrder(): прямо,        │ выход: очередь доехавших
     │   направо, налево — по кругу    │ роль (вход/выход) задаёт СИМУЛЯЦИЯ
     ▼                                 ▼
   Simulation.moveSplitters()        Simulation.moveUnderground()
     «перебрать выходы, пропустить      «найти пару, крутить таймеры,
      занятые — в ОДНОМ тике»            передать доехавшее выходу»
```

| Что | Зачем существует (одна причина) |
|-----|--------------------------------|
| `Splitter.held` / `take(dir)` | Развилка **не может** пользоваться общим `output()` — он отдаёт **одно** направление |
| `Simulation.moveSplitters()` | Только здесь есть **мир**: можно спросить каждого соседа по очереди и пропустить занятого |
| `UndergroundBelt.transit` | Предмет обязан **ехать** под землёй, а не телепортироваться |
| `UndergroundBelt.setRole(...)` | Роль (вход/выход) — свойство **места**, а не здания. Здание не знает своих координат |
| `Simulation.moveUnderground()` | Здесь есть мир — значит, здесь ищется пара |

### Два ключевых «почему»

**Почему развилка не пользуется `output()`.** Тот отдаёт один `Handoff` — одно направление. А
суть развилки: «левый выход занят → отдаю в правый **в этом же тике**». Через `output()` она
могла бы назвать лишь одно направление и узнала бы об отказе только на следующем тике — то
есть **теряла бы тик** на каждом переключении, а при забитом выходе просела бы вдвое.
Необъяснимо для игрока.

Расширять `Handoff` **нельзя**: он заморожен, его знают все здания. Значит, движение развилки
живёт в **отдельной фазе симуляции**, где мир доступен. Поймали себя на желании «чуть-чуть»
поправить `Building` — вы свернули не туда.

**Почему подземка — не телепорт.** Соблазн: принял на входе — сразу выдал на выходе. Тогда
четыре клетки преодолеваются за один тик вместо четырёх, подземка становится **строго быстрее**
обычной ленты, и вся игра уезжает под землю. Механика ломается.

Значит, предмет обязан **ехать**: несколько тиков, со своим отсчётом, не обгоняя соседей.
Узнаёте? Это дословное определение транспортной линии. **Подземка не обходит B3 — она её
требует.**

## ШАГ 1. `Splitter`

### Что должно уметь

```java
public final class Splitter implements Building {

    @Override public Optional<Handoff> output();   // ВСЕГДА пусто! см. выше
    @Override public boolean canAccept(Item item); // свободна, если буфер пуст
    @Override public void accept(Item item);

    /** Предмет, ждущий отправки. */
    public Optional<Item> held();

    /** Куда пробовать отдать — по кругу, начиная с текущего. */
    public List<Direction> outputsInOrder();

    /** Предмет ушёл туда-то: убрать его и сдвинуть очередь. */
    public void take(Direction taken);
}
```

### Куда отдаёт

Прямо (своё направление), направо, налево — **по кругу**, пропуская занятые. Это «мягкая»
очередь, а не честный балансировщик: так делает большинство игр жанра, и это предсказуемо для
игрока — наш столп дизайна «никакой магии».

### Тонкость в `take()`, которую легко проглядеть

Очередь сдвигается на выход, **следующий за использованным**, — а не «на один вперёд от
прошлого». Разница вылезает, когда выход был пропущен как занятый: если считать от прошлого,
круг сбивается, и поток перестаёт делиться поровну.

💡 Подсказка: [П1](B4-solutions.md#п1--splitter) · 📄 Решение: [Р1](B4-solutions.md#р1--splitter)

## ШАГ 2. Фаза развилок

### Что должно уметь

```java
    /** Перебрать выходы по кругу, пропуская занятых. Всё — в одном тике. */
    private void moveSplitters();
```

### Алгоритм

Для каждой развилки с предметом: пройти `outputsInOrder()`; для каждого направления —
спросить соседа (`canAccept`), застолбить клетку (`claimNeighbor` — тот самый штамп из B2) и
передать. Успех — `take(dir)` и выходим. Все выходы заняты — **предмет остаётся**, и это
правильно: затор виден игроку.

### Как проверить

- Три ящика вокруг развилки → шесть предметов делятся **2 / 2 / 2**.
- Один ящик, остальные стороны пусты → все предметы уходят в него, **без потери тиков**.
- Соседей нет вовсе → предмет **остаётся** в развилке, и второй она не принимает.

💡 Подсказка: [П2](B4-solutions.md#п2--фаза-развилок) · 📄 Решение: [Р2](B4-solutions.md#р2--фаза-развилок)

## ШАГ 3. `UndergroundBelt`

### Что должно уметь

```java
public final class UndergroundBelt implements Building {

    public enum Role { NONE, ENTRANCE, EXIT }

    /** Симуляция сообщает: кто ты и как далеко пара. */
    public void setRole(Role role, int distance, int slotsPerTick);

    /** Продвинуть предметы под землёй; вернуть доехавших. */
    public List<Item> advance();

    /** Предмет доехал: положить его на выход. */
    public void deliver(Item item);
}
```

### Роль — свойство МЕСТА, а не здания

Одна и та же подземка может быть входом, выходом или бесполезной — в зависимости от того, что
стоит рядом. А здание **не знает своих координат**. Значит, пару ищет симуляция (у неё есть
мир) и каждый тик сообщает подземке её роль.

Это та же схема, что с буром и рудой: **всё, что зависит от места, приходит снаружи**.

### Сколько тиков ехать — цифра, которую надо вывести, а не угадать

Предмет должен добраться от входа до выхода **ровно за столько же**, за сколько проехал бы по
земле на том же отрезке. Иначе подземка станет быстрее ленты (или медленнее — тогда её никто
не будет строить).

Считайте в **слотах** (см. B3): от входного слота первой клетки до последнего слота
клетки-выхода. Ошибётесь на единицу — и тест «подземка не быстрее ленты» это поймает. У меня
поймал.

💡 Подсказка: [П3](B4-solutions.md#п3--undergroundbelt) · 📄 Решение: [Р3](B4-solutions.md#р3--undergroundbelt)

## ШАГ 4. Фаза подземок

### Алгоритм

Для каждой подземки: искать вперёд (до `balance.undergroundReach()` клеток) подземку **того же
направления**. Нашли — я **вход**, она **выход**, расстояние известно. Крутим таймеры;
доехавшее передаём выходу. Не нашли — роль `NONE`, и я не принимаю ничего.

### Как проверить

- Вход на (0,0), выход на (4,0), ящик на (5,0) → предмет **доезжает**.
- Одинокая подземка → роль `NONE`, предметы **не принимает**.
- **Подземка не быстрее ленты** — сравните с обычной лентой на том же отрезке.

💡 Подсказка: [П4](B4-solutions.md#п4--фаза-подземок) · 📄 Решение: [Р4](B4-solutions.md#р4--фаза-подземок)

## ШАГ 5. Ловушка, которую поймали мои тесты (и это был НАСТОЯЩИЙ баг)

Три теста упали сразу. Два — из-за одного дефекта, и он оказался **не в новом коде**.

**Что было.** Счётчик тиков (тот самый «штамп версии» из B2) жил полем в `Simulation`. А сами
штампы — на клетках, то есть **в мире**. Пока симуляция одна, всё сходится. Но стоило тесту
создать **новую** симуляцию над тем же миром — и счётчик начинался заново, с единицы, натыкаясь
на штампы, оставшиеся от прошлой. Клетки выглядели «уже занятыми», передачи **молча** не
происходили.

**Вывод, который стоит унести:** **счётчик и штампы, которые им метятся, обязаны жить в одном
месте.** Штампы — на клетках, значит и счётчик — в мире. Разнеся их, вы получаете дефект,
который проявляется не всегда и не сразу, — худший вид.

Это к вопросу о том, зачем в B4 вообще писать тесты на «поток делится поровну»: они поймали
ошибку **в задаче B2**, а не в развилке.

## 6. Что считается «сделано»

- [ ] Развилка **не пользуется** `output()`; `Handoff` и `Building` **не тронуты**.
- [ ] Поток делится поровну; занятый выход пропускается **в том же тике**.
- [ ] Все выходы заняты → предмет остаётся (затор виден).
- [ ] Подземка **не быстрее** обычной ленты (есть тест).
- [ ] Одинокая подземка ничего не принимает.
- [ ] Руками: развёл руду на две печи и свёл результат обратно в ящик — **это DoD вехи M3**.

## 7. Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|------------|---------------|
| Развилка теряет тик на каждом переключении | Вы делаете её через `output()` — а надо отдельной фазой (шаг 2) |
| Поток делится неравномерно | `take()` сдвигает очередь «от прошлого», а не от использованного выхода (шаг 1) |
| Предметы исчезают в развилке | `accept()` вызывается, когда буфер занят: проверяйте `canAccept` |
| Подземка быстрее ленты | Ошибка на единицу в расчёте слотов (шаг 3) |
| Подземка не принимает предметы | Роль не назначена: фаза подземок должна идти **до** передач |
| Предметы не передаются вообще, тесты «мигают» | Счётчик тиков и штампы живут в разных местах (шаг 5!) |

## 8. Если совсем застряли

1. Напечатайте роль каждой подземки и содержимое развилки после каждого тика.
2. Проверьте порядок фаз в `step()`: подземки — **до** передач (иначе роль ещё не назначена),
   развилки — **после** (иначе им нечего раздавать).
3. Идите с падающим тестом и числами: «делится 3/2/1 вместо 2/2/2».
