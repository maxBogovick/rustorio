> **Сложность:** 🟡 · **Зависит от:** C4 (дерева технологий) и S0.2 (`Balance`) ·

## 0. Что мы делаем — в трёх предложениях

Механизм прогрессии готов: очки копятся, технологии открываются, эффекты меняют `Balance`.
Но игрок этого **не видит** — в интерфейсе нет ни очков, ни технологий, и нажать нечего.

Мы выводим прогрессию на экран, даём клавиши и — главное — **доказываем тестом**, что
апгрейд действительно ускоряет машину, а не просто зажигает галочку.

И вот тут вас ждёт сюрприз: **в зданиях не придётся менять ни строчки.**

---

## 1. Карта: что трогаем

```
   Research (готово)  ──► HUD: очки + список технологий (F1..F4)
        ▲                       ▲
        │                       │
   InputHandler: F1..F4 ────────┘
        │
        └──► research(tech) → Balance изменился
                                  │
                                  ▼
                        TickContext → печь, бур, лента
                        (ничего не меняем: они уже читают Balance)
```

| Что | Зачем существует (одна причина) |
|-----|--------------------------------|
| Клавиши F1..F4 в `InputHandler` | Игрок должен уметь **нажать** — иначе прогрессия существует только в тестах |
| Строка исследований в HUD | Игрок должен **видеть**: сколько очков, что стоит сколько, что уже открыто |
| Сквозной тест «печь стала быстрее» | Единственное доказательство, что эффект **дошёл** до машины |

## 2. Порядок работы

| Шаг | Что появляется | Что уже можно проверить |
|-----|----------------|-------------------------|
| 1 | Клавиши F1..F4 | нажал — технология открылась |

| 3 | Сквозной тест | «печь плавит за МЕНЬШЕЕ число тиков» |

## ШАГ 1. Клавиши

### Зачем

Открыть технологию должен игрок, а не тест.

### Что должно уметь

```java
// InputHandler
for (Tech tech : Tech.values()) {
    if (Gdx.input.isKeyJustPressed(Input.Keys.F1 + tech.ordinal())) {
        game.research().research(tech);   // сам проверит: очки, предпосылки
    }
}
```

### Обратите внимание на то, чего здесь НЕТ

Нет проверок. Не нужно писать «если очков хватает и предпосылки открыты — тогда…»:
`research()` **сам** проверяет и возвращает `false`, если нельзя (мы так решили в C4 —
«делать неправильное невозможно»). Вызывающему остаётся просто попросить.

И нет лесенки `if (F1) … if (F2) …` — цикл по данным. Появится пятая технология — клавиша
возникнет **сама**.

💡 Подсказка: [П1](C5-solutions.md#п1--клавиши) · 📄 Решение: [Р1](C5-solutions.md#р1--клавиши)

## ШАГ 2. Строка исследований в HUD

### Зачем

Игрок должен видеть три вещи: **сколько очков**, **что можно открыть** и **что уже открыто**.
Без этого прогрессия — секрет, известный только коду.

### Что показываем

```
Science: 24    F1 Быстрая лента [OK]   F2 Быстрая печь [ready]   F3 Быстрый бур [20]   …
```

- `[OK]` — уже открыто;
- `[ready]` — можно открыть **прямо сейчас** (`canResearch`);
- число — сколько **стоит** (то есть пока нельзя).

### Собирается из данных, а не из строки

Как и панель инструментов, строка строится циклом по `Tech.values()` + таблице
`Technology`. Захардкодить её текстом — значит завести **второй источник правды**, который
разойдётся с первым при первой же правке дерева.

💡 Подсказка: [П2](C5-solutions.md#п2--hud) · 📄 Решение: [Р2](C5-solutions.md#р2--hud)

## ШАГ 3. Сквозной тест: апгрейд **дошёл** до машины

### Зачем именно такой тест

Проверить `balance.speed(FURNACE) == 1.5` — **недостаточно**. Это проверка того, что число в
объекте изменилось. А вопрос другой: **дошло ли это число до печи?**

Тест обязан мерить **поведение**: сколько тиков печь плавит руду до апгрейда и после.

### Что должно уметь

```java
    /** Сколько тиков печь плавит одну руду при данном балансе. */
    private static int ticksToSmelt(GameState game, World world, int x, int y);

    @Test void fastFurnaceActuallySpeedsUpSmelting();
```

### И вот теперь — момент истины

**Чтобы апгрейд заработал, в печи не меняется ничего.** Ни строчки. Она уже получает
`Balance` через `TickContext` — это сделали в спринте 0, когда убирали уродливый параметр
`hasOre`.

Если вам кажется, что фича появилась **бесплатно** — значит, архитектура была спроектирована
правильно. Хорошая архитектура ощущается именно так: не «сегодня стало красиво», а «завтра
фича приехала сама».

А если бы `Config` и `Balance` не разделили в спринте 0, вы бы сейчас правили все машины и
переписывали константы. Вот отсроченная цена архитектурных решений — и вот отсроченная
выгода.

### Как проверить

```
до апгрейда:  N тиков
после:        меньше N
```

Числа в сообщении об ошибке — обязательно. Тест, который говорит «expected true», при падении
бесполезен.

💡 Подсказка: [П3](C5-solutions.md#п3--сквозной-тест) · 📄 Решение: [Р3](C5-solutions.md#р3--сквозной-тест)

## 4. Что считается «сделано»

- [ ] F1..F4 открывают технологии; лесенки `if` нет — цикл по `Tech.values()`.
- [ ] HUD показывает очки и состояние каждой технологии; собирается **из данных**.
- [ ] Сквозной тест: после «быстрой печи» плавка занимает **меньше тиков**.
- [ ] **В зданиях не изменилось ни строчки** — если пришлось править, ищите ошибку в S0.2.
- [ ] Руками: построил лабораторию → скормил шестерёнки → нажал F2 → печь **видимо** быстрее.

## 5. Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|------------|---------------|
| Нажал F2 — ничего | Очков не хватает или предпосылка закрыта. HUD должен это показывать (шаг 2) |
| Галочка зажглась, скорость та же | Эффект применён к `Config`, а не к `Balance` — там менять нечего |
| Скорость та же, `Balance` изменился | Машина читает `Config` напрямую, а не `ctx.balance()` (ошибка S0.1) |
| Пришлось править печь и бур | Значит, `TickContext` не довели до машин в спринте 0 |
| HUD показывает не те технологии | Строка захардкожена вместо цикла по `Tech.values()` |

## 6. Если совсем застряли

1. Проверьте `balance.speed(Tool.FURNACE)` **до** и **после** `research()`. Изменился?
   Значит, проблема не в C4, а в том, как печь читает баланс.
2. Напечатайте в `ProcessKernel.update` эффективное время цикла. Оно должно уменьшиться.
3. Идите с числами «было N тиков, стало M».
