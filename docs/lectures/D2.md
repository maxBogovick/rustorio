# D2 — Шаблон Observer: статистика производства

Цель урока — шаблон **Observer**: развязать источник события и его потребителей. Попутно —
сравнение двух моделей связи, **pull** (потребитель опрашивает) и **push** (источник
уведомляет): в проекте уже есть pull (`Research.collect`), и видно, где он не подходит.

**Что строим.** Счётчик суммарного производства по каждому предмету. Требование: счётчик не
должен лезть в машины, а машина — знать про счётчик; счётчиков может быть несколько.

**Зависит от:** [D1](D1.md). Код урока — в `core`, `model`, `game`. `render` не затрагивается.

---

## 1. Как это уже сделано для очков: pull

Очки исследований копятся на лаборатории, а `Research` раз в тик их **забирает** —
опрашивает мир (pull):

```java
// game/Research.java (существующий код)
public void collect(World world) {
    world.forEachBuilding((x, y, building) -> {
        if (building instanceof Lab lab) {
            points += lab.drainPoints();
        }
    });
}
```

Это работает, потому что очки **хранятся** на лаборатории: их можно опросить в любой момент.
Попробуем так же посчитать производство — и увидим, где модель ломается.

## 2. Прямолинейная версия производства: тоже pull

Произведённый предмет на машине не задерживается — его сразу забирает сосед. Хранимого
счётчика, как у лаборатории, нет. Чтобы опрашивать, придётся его завести: в каждую машину
добавить накопитель произведённого и «сливать» его тик за тиком.

```java
// В ProcessKernel — новое поле только ради статистики:
private final Map<Item, Integer> producedSinceDrain = new EnumMap<>(Item.class);

private void complete(Recipe recipe) {
    // ... списание сырья и выкладка продукции ...
    recipe.outputs().forEach((item, count) ->
            producedSinceDrain.merge(item, count, Integer::sum));
}

Map<Item, Integer> drainProduced() {
    Map<Item, Integer> out = new EnumMap<>(producedSinceDrain);
    producedSinceDrain.clear();
    return out;
}
```

```java
// Сборщик статистики опрашивает мир и разбирает типы производителей:
public void collect(World world) {
    world.forEachBuilding((x, y, building) -> {
        switch (building) {
            case Furnace f   -> add(f.drainProduced());
            case Assembler a -> add(a.drainProduced());
            case Miner m     -> add(m.drainProduced());
            default -> { }   // остальные не производят
        }
    });
}
```

Три конкретных следствия:

1. **Связанность с типами.** `collect` разбирает виды зданий (`switch`). Каждый новый
   производитель — правка сборщика. Это та же связь, что мы убирали в A8/D1.
2. **Загрязнение домена.** Печь, сборщик и бур несут поле-накопитель и метод `drainProduced`
   ради чужой задачи (статистики), которая их не касается.
3. **Второй потребитель — вторая копия работы.** Понадобился журнал «каждые 100 штук» —
   либо второй полный обход мира, либо логика лога вмешивается в сборщик.

Причина всех трёх — потребитель **опрашивает** производителей, поэтому обязан их знать.
Развернём направление: пусть производитель **уведомляет**, не зная потребителей.

## 3. Решение: издатель — подписчик (Observer)

### 3.1. Наблюдатель и шина

Наблюдатель — интерфейс с одним методом. Шина хранит подписчиков и рассылает событие. Оба в
`core`: их видят и издатели (`model`), и подписчики (`game`).

```java
package com.rustorio.core;

/** Наблюдатель производства (шаблон Observer). */
public interface ProductionObserver {
    void onProduced(Item item, int amount);
}
```

```java
package com.rustorio.core;

import java.util.ArrayList;
import java.util.List;

/** Шина: связывает издателей и подписчиков. «Субъект» в шаблоне Observer. */
public final class ProductionBus {

    private final List<ProductionObserver> observers = new ArrayList<>();

    public void subscribe(ProductionObserver observer) {
        observers.add(observer);
    }

    public void publish(Item item, int amount) {
        for (ProductionObserver observer : observers) {
            observer.onProduced(item, amount);
        }
    }
}
```

Порядок рассылки — порядок подписки, то есть детерминированный. Событие транзиентное: шина
его не хранит, только передаёт.

### 3.2. Шина доезжает до машин через контекст тика

Машина публикует событие в своём `update(ctx)`. Значит, шина должна лежать в `TickContext`.
Это ровно та причина, ради которой контекст сделан «коробкой»: добавляем поле, сигнатуры
`update` у зданий не меняются. Вторичный конструктор оставляет старые вызовы (тесты,
бенчмарк) рабочими — им события не нужны.

```java
package com.rustorio.core;

public record TickContext(float dt, Balance balance, ProductionBus events) {

    /** Без подписчиков — для тестов и бенчмарка. publish по такой шине никого не зовёт. */
    public TickContext(float dt, Balance balance) {
        this(dt, balance, new ProductionBus());
    }
}
```

### 3.3. Производители публикуют

Машина сообщает о продукции и не знает, кто слушает. Поля-накопителя из шага 2 нет — «выстрелил
и забыл».

```java
// ProcessKernel.update(), в момент завершения цикла:
if (progress >= cycleTime) {
    Recipe finished = active;
    complete(finished);
    finished.outputs().forEach(ctx.events()::publish);   // печь/сборщик; у лаборатории outputs пуст
    active = null;
    progress = 0f;
}
```

```java
// Miner.update(), в момент добычи:
if (cooldown <= 0f) {
    output = Item.IRON_ORE;
    cooldown = cycleTime;
    ctx.events().publish(Item.IRON_ORE, 1);              // бур и печь шлют в одну шину, не зная друг о друге
}
```

### 3.4. Потребители подписываются

Каждый потребитель — отдельный класс, независимый от машин и от других потребителей.

```java
package com.rustorio.game;

import com.rustorio.core.Item;
import com.rustorio.core.ProductionObserver;

import java.util.EnumMap;
import java.util.Map;

/** Суммарное производство по каждому предмету. */
public final class ProductionStats implements ProductionObserver {

    private final Map<Item, Long> totals = new EnumMap<>(Item.class);

    @Override public void onProduced(Item item, int amount) {
        totals.merge(item, (long) amount, Long::sum);
    }

    public long total(Item item) { return totals.getOrDefault(item, 0L); }
    public Map<Item, Long> snapshot() { return new EnumMap<>(totals); }
}
```

```java
package com.rustorio.game;

import com.rustorio.core.Item;
import com.rustorio.core.ProductionObserver;

import java.util.EnumMap;
import java.util.Map;

/** Второй, независимый подписчик: печатает веху на каждой сотне. */
public final class ProductionLog implements ProductionObserver {

    private static final int STEP = 100;
    private final Map<Item, Long> running = new EnumMap<>(Item.class);

    @Override public void onProduced(Item item, int amount) {
        long prev = running.getOrDefault(item, 0L);
        long now = prev + amount;
        running.put(item, now);
        if (now / STEP != prev / STEP) {
            System.out.println("Производство: " + item + " ×" + (now / STEP * STEP));
        }
    }
}
```

Одно событие от машины — две реакции. Добавить третью (за минуту, на график) — новый класс
и одна строка подписки; машины и другие подписчики не трогаются.

### 3.5. Связывание

Шина и подписчики создаются один раз в `GameState`; шина передаётся в контекст каждого тика.

```java
// game/GameState.java
private final ProductionBus production = new ProductionBus();
private final ProductionStats stats = new ProductionStats();

public GameState(World world) {
    this.world = world;
    this.simulation = new Simulation(world);
    production.subscribe(stats);
    production.subscribe(new ProductionLog());
}

public void update(float deltaTime) {
    // ...
    TickContext ctx = new TickContext(Config.TICK, balance, production);
    // ... simulation.step(ctx) в цикле ...
}

public ProductionStats stats() { return stats; }
```

## 4. Pull или push — когда что

| | pull (опрос) | push (уведомление) |
|---|---|---|
| Кто кого знает | потребитель знает производителей | производитель не знает потребителей |
| Где живёт значение | **хранится** на производителе | **транзиентное** событие, нигде не лежит |
| Число потребителей | мало, фиксировано | много, заранее неизвестно |
| Пример в проекте | `Research.collect` (очки на лаборатории) | производство (предмет ушёл сразу) |

Правило: значение хранится и потребитель один — **pull** проще (никакой шины). Значение
транзиентное или потребителей много и они независимы — **push** (Observer). Очки честно
оставлены на pull: у лаборатории они лежат, а `Research` — единственный, кому они нужны.

---

## 5. Детерминизм

Событие рассылается в фазе симуляции, поэтому наблюдатели обязаны быть детерминированными:
без случайности и «настенных часов» (это проверяет `ArchitectureTest`). Порядок событий
задаёт обход мира (фиксированная сетка), порядок реакций — порядок подписки. `ProductionStats`
суммирует (от порядка не зависит), `ProductionLog` сравнивает пороги — тоже детерминированно.
