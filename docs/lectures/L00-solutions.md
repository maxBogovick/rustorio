## П1 — Что держит камеру у карты

Метод `GameCamera.clampAndUpdate()` (его зовут `pan`, `zoomAt` и `resize` — каждый
раз, когда камера могла сдвинуться). Он зажимает центр камеры так, чтобы видимая
область не выходила за мир: `axisClamp` держит позицию в пределах
`[полэкрана … мир − полэкрана]`. Отдельный случай: если при сильном отдалении вид
ШИРЕ карты, зажимать не во что — тогда карта просто центрируется
(`return worldSpan / 2f`). Поэтому на максимальном зуме карта стоит по центру окна
с полями.

## П2 — Почему рендер не спрашивает мышь сам

Технически `Gdx.input.getX()` в рендере сработал бы. Цены две:

1. **Рушится золотое правило как ГАРАНТИЯ.** Сейчас «рендер только читает состояние»
   — свойство, которое видно по сигнатурам: в рендер приходит `GameState`, и всё.
   Как только рендер сам полез в устройство ввода, у него появился второй источник
   данных, и каждый следующий программист (включая вас через месяц) уже не может
   доверять правилу — надо перечитывать весь рендер.
2. **Рендер перестаёт быть функцией от состояния.** Сейчас «одно состояние → одна
   картинка»; это позволяет когда-нибудь тестировать отрисовку и, что важнее,
   рассуждать о багах: картинка неверна ⇒ неверно состояние ⇒ смотреть в input/update.
   С мышью внутри рендера этот способ думать ломается.

Мелкая деталь каркаса — а перед вами главный урок архитектуры всего курса.

## П3 — Трассировка аккумулятора

`TICK = 0.18`, кадры по `deltaTime = 0.1`:

| Кадр | accumulator ДО while | тиков | accumulator ПОСЛЕ |
|---|---|---|---|
| 1 | 0.1 | 0 (0.1 < 0.18) | 0.1 |
| 2 | 0.2 | 1 | 0.02 |
| 3 | 0.12 | 0 | 0.12 |

Итого: три кадра — один тик. Проверка здравым смыслом: 0.3 наигранной секунды —
это 0.3 / 0.18 ≈ 1.67 тика; один сделан, 0.12 «сдачи» ждёт в аккумуляторе. Время
не теряется и не выдумывается — оно только копится и тратится порциями по 0.18.

## П4 — Заморозка на 2 секунды

Тиков будет **один**, а не одиннадцать. Строка-ответ:

```java
accumulator = Math.min(accumulator + deltaTime, Config.MAX_FRAME_TIME);
```

Аккумулятор зажат сверху 0.25 c — влезает один тик (0.25 − 0.18 = 0.07 остатка).
Беда, от которой это защищает, — «спираль смерти»: если после лага честно
отрабатывать все накопленные тики, кадр становится ЕЩЁ дольше, к следующему кадру
накапливается ЕЩЁ больше тиков — и игра уже никогда не догоняет реальное время.
Размен осознанный: после заморозки мир чуть «замедлился» (потерял наигранное
время), зато остался живым.

## П5 — Клетка (40, 50) в чанках

- чанк X: `40 >> 5` = 40 / 32 = **1**
- чанк Y: `50 >> 5` = 50 / 32 = **1**
- локально X: `40 & 31` = 40 − 32 = **8**
- локально Y: `50 & 31` = 50 − 32 = **18**

Клетка (40, 50) — это чанк **(1, 1)**, позиция **(8, 18)** внутри него.
(Трюк работает только потому, что 32 — степень двойки: сдвиг и маска заменяют
деление и остаток. Потому `SIZE`, `SHIFT` и `MASK` объявлены рядом — это одно
знание в трёх формах.)

## П6 — Сколько чанков

```java
World world = World.generate(96, 64);  // 0 — генерация НЕ создаёт ни одного куска
world.tile(0, 0);    // 1 — родился чанк (0, 0)
world.tile(5, 7);    // 1 — та же клетка 32×32, кусок уже есть
world.tile(32, 0);   // 2 — x=32 это уже чанк (1, 0)
world.tile(31, 31);  // 2 — (31, 31) — дальний угол чанка (0, 0), он давно создан
```

Границы — на числах, кратных 32: клетки 0…31 в чанке 0, клетка 32 — первая в чанке 1.

## П7 — Руда в (8, 13) и (9, 9)

Формула: руда есть, если `dx² + dy² ≤ r²` хотя бы для одной залежи.

**(8, 13):** ближайшая залежь `{9, 14, 3}`: dx = 8−9 = −1, dy = 13−14 = −1;
1 + 1 = 2 ≤ 9. **Руда есть.**

**(9, 9):** залежь `{6, 5, 3}`: dx = 3, dy = 4; 9 + 16 = 25 > 9 — мимо.
Залежь `{9, 14, 3}`: dx = 0, dy = −5; 25 > 9 — мимо. Остальные далеко.
**Руды нет.** (Знакомые числа? 3-4-5 — египетский треугольник: клетка лежит ровно
на расстоянии 5 от центра залежи радиуса 3.)

## М2 — Почему тест остался зелёным

`oreIsDeterministic` проверяет не «где лежит руда», а что **два независимых мира
согласны друг с другом**. Ваша новая залежь — часть функции `hasOre`, поэтому оба
мира увидели её одинаково: детерминизм не пострадал. А вот М3 валит другую проверку
того же теста — `assertTrue(a.tile(6, 5).hasOre())`: она стережёт конкретный факт
«стартовая залежь существует», на который будут полагаться первые лекции про бур.
