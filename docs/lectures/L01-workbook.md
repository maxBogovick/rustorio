## 0. Что мы делаем — в трёх предложениях

Прежде чем ставить здания, игре нужен **словарь**: что такое «направление», «предмет»,
«инструмент». Мы создадим три перечисления (`enum`) — от самого простого к самому
насыщенному — и подключим их к состоянию игры, вводу и HUD. В конце лекции клавиши
**1–4** будут переключать инструмент, **R** — крутить направление, и всё это будет
видно на экране — хотя ни одного здания в игре ещё нет.

---

## 1. Карта: четыре вида «типов с данными»

В Java есть несколько способов сказать «вот данные». В этой лекции вы потрогаете все
четыре — три напишете, один прочитаете:

| Тип | Что это | Когда выбирать |
|---|---|---|
| `enum Item` | фиксированный список БЕЗ данных | «одно из: руда, пластина» — и всё |
| `enum Direction`, `enum Tool` | фиксированный список, у каждого элемента — данные и методы | список замкнут, но у элементов есть свойства |
| `record Cell` *(уже написан — читаем)* | неизменяемый «носитель данных» | пара чисел/полей, равенство по значению |
| `class Tile` *(уже написан — читаем)* | изменяемое состояние | данные, которые живут и меняются |

| Новый файл | Одна причина существования |
|---|---|
| `core/Item.java` | предметы, которые будут ездить по лентам |
| `core/Direction.java` | куда «смотрит» здание; смещение на соседнюю клетку |
| `core/Tool.java` | что выбрано в панели строительства + номер клавиши |

**Почему всё это в `core`?** Это словарь — им пользуются и модель, и ввод, и
отрисовка. `core` — нижний слой: он не знает НИ ПРО КОГО, а знают все про него.
За этим следит `ArchitectureTest` — в шаге 6 вы убедитесь, что он не спит.

|---|---|---|

## ШАГ 1. `Item`: перечисление без всего

### Зачем

По лентам скоро поедут предметы. «Предмет» — это выбор из фиксированного списка:
идеальная работа для `enum`. Начинаем с двух: руда и то, во что печь её переплавит.

### Что должно уметь

```java
// core/Item.java
public enum Item {
    IRON_ORE,
    IRON_PLATE
}
```

Да, это весь файл (плюс javadoc — напишите в двух строках, ЗАЧЕМ тип существует;
привыкайте: файл без ответа «зачем я существую» в этом проекте не появляется).

### Почему enum, а не константы-строки или int

`Item.IRON_ORE` невозможно написать с опечаткой (не скомпилируется), невозможно
передать туда «посторонний» предмет, а `switch` по enum умеет проверять полноту —
когда в лекции про сборщик появится `GEAR`, компилятор сам покажет все места,
которые надо дописать. Строка `"iron_ore"` не умеет ничего из этого.

### Как проверить

`./gradlew test` — компилируется, всё зелёное. Теста на `Item` нет: проверять
в нём пока нечего, а тест ради теста — это шум.

💡 Подсказка: [П1](L01-solutions.md#п1) · 📄 Решение: [Р1](L01-solutions.md#р1)

## ШАГ 2. `Direction`: enum с данными и поведением

### Зачем

Бур отдаёт руду «вперёд», лента везёт «вперёд» — зданиям нужно направление.
А направление — это не просто имя: это ещё и **смещение на соседнюю клетку**
(куда прибавить единицу, чтобы попасть «вперёд»).

### Сначала — тест (он же спецификация)

Создайте `src/test/java/com/rustorio/core/DirectionTest.java` и вставьте ЦЕЛИКОМ:

```java
package com.rustorio.core;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

/** Направление — чистые данные: проверяется без окна и движка. */
class DirectionTest {

    @Test
    void rotateCwGoesClockwise() {
        assertEquals(Direction.EAST, Direction.NORTH.rotateCw());
        assertEquals(Direction.SOUTH, Direction.EAST.rotateCw());
        assertEquals(Direction.WEST, Direction.SOUTH.rotateCw());
        assertEquals(Direction.NORTH, Direction.WEST.rotateCw());
    }

    @Test
    void offsetsPointToNeighbours() {
        // Ось Y растёт ВНИЗ (строки поля считаются сверху) — поэтому North = -1.
        assertEquals(0, Direction.NORTH.dx());
        assertEquals(-1, Direction.NORTH.dy());
        assertEquals(1, Direction.EAST.dx());
        assertEquals(0, Direction.EAST.dy());
        assertEquals(0, Direction.SOUTH.dx());
        assertEquals(1, Direction.SOUTH.dy());
        assertEquals(-1, Direction.WEST.dx());
        assertEquals(0, Direction.WEST.dy());
    }
}
```

Запустите: он **красный** (не компилируется — `Direction` не существует). Это
нормальный старт шага: тест уже сказал вам ВСЁ, что нужно написать. Дальше вы
работаете, пока он не станет зелёным. Этот ритм называется red → green, и он
останется с вами до конца курса.

### Что должно уметь

```java
public enum Direction {
    NORTH(...), EAST(...), SOUTH(...), WEST(...);

    public int dx()            // смещение по X на соседнюю клетку
    public int dy()            // смещение по Y (ось вниз: North = -1)
    public String shortName()  // "N"/"E"/"S"/"W" — для HUD
    public Direction rotateCw() // поворот по часовой (клавиша R)
}
```

### Предскажи-1: почему у NORTH `dy = -1`, а не `+1`?

Вспомните L0 (шаг 5): в модели строки считаются **сверху**, клетка (0, 0) — левый
верхний угол. Запишите ответ, сверьтесь: [П2](L01-solutions.md#п2).

### Два приёма, на которые стоит посмотреть внимательно

1. **Данные — прямо в элементах enum.** `NORTH(0, -1, "N")` — у каждого элемента
   свой конструктор. Тогда `dx()` — это чтение поля, и никакого `switch` с
   дублированием списка направлений.
2. **`rotateCw` без `switch`.** Объявите элементы в порядке по часовой стрелке —
   и поворот станет «следующий по кругу»: `values()[(ordinal() + 1) % 4]`.
   Порядок объявления — тоже данные.

### Как проверить

`DirectionTest` зелёный. Заодно прогоните ВСЕ тесты — привычка.

💡 Подсказка: [П2](L01-solutions.md#п2) · 📄 Решение: [Р2](L01-solutions.md#р2)

## ШАГ 3. `Tool`: enum + тест на то, чего компилятор не видит

### Зачем

Игрок выбирает, ЧТО строить. Выбор из списка — снова enum. Но у инструмента два
свойства: имя для HUD и **номер клавиши-слота** (1..9).

### Что должно уметь

```java
public enum Tool {
    MINER(...),   // слот 1
    BELT(...),    // слот 2
    FURNACE(...), // слот 3
    CHEST(...);   // слот 4

    public String displayName() // человекочитаемое имя для HUD
    public int hotkeySlot()     // номер слота панели (1..9)
}
```

Зданий этих ещё нет — и не должно быть. Словарь пишется раньше предложений.
(Сборщик, развилка, подземка и лаборатория добавятся в своих лекциях — по одной
строке сюда.)

### Почему слот живёт в `Tool`, а не в слое ввода

Раньше в таких проектах пишут лесенку `if (нажата 1) … if (нажата 4)` в обработчике
ввода. Добавили пятое здание — компилятор промолчал, лесенку забыли, здание молча
недоступно. Когда слот — **часть самого инструмента**, забыть его нельзя: новый
элемент enum без слота не скомпилируется. Это называется «данные ведут поведение».

### Предскажи-2: а что компилятор всё-таки НЕ поймает?

Слот объявить обязательно — это стережёт компилятор. Придумайте ошибку со слотами,
которую компилятор пропустит молча. Потом вставьте тест-ворота шага —
`src/test/java/com/rustorio/core/ToolTest.java`:

```java
package com.rustorio.core;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.util.HashSet;
import java.util.Set;

import static org.junit.jupiter.api.Assertions.assertTrue;

/**
 * Последняя щель в «карте задач от компилятора».
 *
 * <p>Компилятор заставит новый инструмент объявить номер слота — забыть его нельзя.
 * Но он НЕ заметит, если вы напишете чужой номер: два здания на одной клавише
 * скомпилируются прекрасно, а в игре второе окажется недоступным. Ловится это
 * только тестом.
 */
class ToolTest {

    @Test
    @DisplayName("Слоты инструментов уникальны и помещаются на клавиатуру (1..9)")
    void hotkeySlotsAreUniqueAndValid() {
        Set<Integer> used = new HashSet<>();
        for (Tool tool : Tool.values()) {
            int slot = tool.hotkeySlot();
            assertTrue(slot >= 1 && slot <= 9,
                    tool + ": слот " + slot + " вне диапазона 1..9 — на клавиатуре его нет");
            assertTrue(used.add(slot),
                    tool + " занял слот " + slot + ", который уже занят другим инструментом");
        }
    }
}
```

— он и есть ответ на «Предскажи-2». Разделение труда запомните: **компилятор ловит
«забыл», тест ловит «написал не то»**.

### Как проверить

`ToolTest` зелёный. Для верности сломайте: дайте `CHEST` слот 1 — тест обязан
упасть с внятным сообщением. Верните.

## ШАГ 4. Словарь — в состояние игры

### Зачем

Выбранный инструмент и направление — это **состояние между кадрами** (нажал «3» —
и до следующего нажатия строишь печи). Всё такое состояние живёт в `GameState`.

### Что должно уметь

В `game/GameState.java` добавьте:

```java
private Tool tool = ...;            // стартовый инструмент — MINER
private Direction direction = ...;  // стартовое направление — EAST

public Tool tool()
public Direction direction()
public void selectTool(Tool tool)
public void rotateDirection()       // direction = direction.rotateCw()
```

### Предскажи-3: почему поля приватные, а не `public Tool tool;`?

Кода стало бы меньше. Что стало бы хуже? Ответ: [П4](L01-solutions.md#п4).

### Как проверить

Компилируется, все тесты зелёные. В игре пока ничего не видно — норма: состояние
есть, но его никто не пишет (шаг 5) и не показывает (шаг 6).

💡 Подсказка: [П4](L01-solutions.md#п4) · 📄 Решение: [Р4](L01-solutions.md#р4)

## ШАГ 5. Горячие клавиши: цикл по данным вместо лесенки

### Зачем

Ввод переводит клавиши в изменения состояния. Слоты уже объявлены в `Tool` —
слою ввода осталось пройтись по списку.

### Что должно уметь

В `input/InputHandler.handle` (после блока паузы):

- для каждого `Tool` из `Tool.values()`: если нажата клавиша его слота —
  `game.selectTool(tool)`;
- если нажата `R` — `game.rotateDirection()`.

И вспомогательный перевод «номер слота → код клавиши libGDX»:

```java
private static int keyForSlot(int slot)   // Input.Keys.NUM_0 + slot
```

### Почему перевод «слот → клавиша» именно ЗДЕСЬ, а не в `Tool`

`Tool` лежит в `core`, которому запрещено знать про движок. `Input.Keys` — это
libGDX. Слой ввода про движок знать обязан — вот он и переводит. Не верите, что
запрет настоящий? Шаг 6 покажет.

### Как проверить

Запустите игру. Глазами пока ничего (HUD ещё не показывает инструмент) — но
нажатия уже работают. Хотите убедиться прямо сейчас — временный
`System.out.println(game.tool())` после цикла (и удалить после проверки).

💡 Подсказка: [П5](L01-solutions.md#п5) · 📄 Решение: [Р5](L01-solutions.md#р5)

## ШАГ 6. HUD: показать словарь игроку

### Зачем

Состояние, которого не видно, для игрока не существует. HUD — витрина состояния.

### Что должно уметь

В `render/HudRenderer.render` перестройте верхнюю строку:

```
Tool: Miner   Dir: E   Cell: (12, 7)   [PAUSED]
```

а строку-подсказку соберите **из списка инструментов** (`Tool.values()`), а не
руками: `1 Miner  2 Belt  3 Furnace  4 Chest  | R rotate ...`. Добавится пятый
инструмент — подсказка обновится сама. Захардкоженная строка врала бы уже через
две лекции.

### Как проверить (видимый результат лекции)

`./gradlew run`: клавиши **1–4** меняют `Tool:` в HUD, **R** гоняет `Dir:` по
кругу `E → S → W → N → E`. Подсказка перечисляет все четыре инструмента.

### Эксперимент: убедитесь, что архитектурная стража не спит

Добавьте в `Tool.java` поле с типом из движка:

```java
final com.badlogic.gdx.math.Vector2 tmp = new com.badlogic.gdx.math.Vector2();
```

Запустите тесты: упадёт `ArchitectureTest.domain_does_not_depend_on_libgdx` — ядро
не имеет права знать про движок, и это проверяется на каждой сборке, а не «на
словах». Уберите правку.

> Честное признание: первый вариант этого эксперимента был
> `int key = Input.Keys.NUM_1;` — и стража его **не поймала**. Почему: `NUM_1` —
> компайл-тайм константа (`static final int`), компилятор подставляет её ЧИСЛО
> прямо в ваш класс, и в байткоде зависимости на libGDX не остаётся — а ArchUnit
> читает байткод. Запомните эту щель: у любой автоматической проверки есть
> граница применимости, и знать её — часть профессии.

## Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|---|---|
| `cannot find symbol: Direction` в тесте | тест лежит в `src/test/java/com/rustorio/core/`? Пакет файла совпадает с папкой? |
| `rotateCw` возвращает не то | порядок объявления элементов — это и есть порядок поворота; N, E, S, W — по часовой |
| нажатия 1–4 не работают | `keyForSlot`: `Input.Keys.NUM_0 + slot`, не `Input.Keys.NUM_1 + slot`; и клавиши проверяются в `handle`, который зовётся каждый кадр |
| HUD не обновился | HUD читает `game.tool()` каждый кадр или вы сохранили строку один раз в поле? |
| `ArchitectureTest` красный | читаем, КАКОЕ правило упало и КАКОЙ класс назван — там и нарушение; чаще всего лишний импорт |
