## 0. Что мы делаем — в трёх предложениях

Сегодня в мире появится первое здание — ящик: ЛКМ ставит его на клетку, ПКМ сносит,
и на экране рисуется настоящий спрайт из атласа. По дороге вы напишете **главный
тип всей игры** — sealed-интерфейс `Building`: замкнутый список «всего, что можно
поставить на клетку», за полноту которого отвечает компилятор. Каждое следующее
здание курса (бур, лента, печь…) будет входить в игру через этот интерфейс — по
одному и тому же рецепту, который вы сегодня пройдёте первым.

## 1. Карта: кирпичи

```
        InputHandler                    BuildingRenderer
     ЛКМ → place, ПКМ → remove          switch по sealed-типу → спрайт
              │                                   ▲ (только читает)
              ▼                                   │
            World.place / World.remove ───► Tile.building
              │  (правила постановки —           хранит здание клетки
              │   в ОДНОМ месте)
              ▼
        Building (sealed) ◄── permits ── Chest
        «что можно поставить»            первая реализация
```

| Файл | Одна причина существования |
|---|---|
| `model/Building.java` | замкнутый список видов зданий + фабрика «инструмент → здание» |
| `model/Chest.java` | первое здание: пассивная коробка, конечная точка будущих цепочек |
| `model/Tile.java` *(правим)* | клетка обзаводится слотом под здание |
| `model/World.java` *(правим)* | `place`/`remove` — правила постановки в одном месте |
| `input/InputHandler.java` *(правим)* | ЛКМ/ПКМ → вызовы мира |
| `render/BuildingRenderer.java` | слой спрайтов зданий (первое применение атласа) |

## ШАГ 1. `Building` + `Chest`: sealed-интерфейс и первая реализация

### Зачем

«Здание» — это выбор из фиксированного списка, как `Item` или `Tool`. Но enum здесь
НЕ подходит, и понять почему — половина пользы лекции.

### Предскажи-1

Каждая константа enum существует **в одном экземпляре** (`Tool.CHEST` — один объект
на всю программу). Почему это убивает идею «здание = элемент enum»? Подсказка:
представьте два ящика на карте и счётчик предметов внутри каждого.
Ответ: [П1](L02-solutions.md#п1).

### Что такое sealed (одним абзацем)

`sealed interface Building permits Chest` — интерфейс, реализовать который могут
**только классы из списка `permits`**. Это Java-аналог алгебраического типа-суммы:
список видов зданий замкнут, и компилятор его знает. Отсюда два подарка:
`switch` по зданию не требует `default` (все случаи известны), а новый вид здания
**обязан** быть вписан в список — тайком не добавишь и не забудешь.

### Что должно уметь

```java
// model/Building.java
public sealed interface Building permits Chest {

    Optional<Direction> direction(); // у ящика — empty; у будущего бура — сторона выдачи

    /** «Такое же» здание: тот же тип и то же направление? (см. Предскажи-2 в шаге 2) */
    default boolean sameKind(Building other)

    /**
     * Фабрика «инструмент → новое здание». Optional, потому что зданий пока
     * меньше, чем инструментов: для MINER/BELT/FURNACE возвращаем empty —
     * их лекции заполнят эти ветки.
     */
    static Optional<Building> create(Tool tool, Direction dir)
}
```

```java
// model/Chest.java
public final class Chest implements Building {
    // направления нет; больше пока НИЧЕГО — счётчик предметов появится,
    // когда появятся предметы
}
```

Два файла пишутся **парой**: sealed-интерфейс не скомпилируется, пока не существует
класс из `permits`, — не пугайтесь красного между двумя файлами.

### Почему отрисовки в `Building` нет

Могли бы добавить метод `draw()`? Могли бы — и намертво привязали бы домен к
libGDX (`ArchitectureTest` бы это тут же поймал). Здание умеет «быть» и (позже)
«жить в симуляции»; «как оно выглядит» — забота слоя `render`. Шаг 4 покажет,
как рендер разбирает здания без единого метода в них.

### Как проверить

`./gradlew test` — компилируется, всё старое зелёное.

## ШАГ 2. `Tile` и `World`: куда ставим и по каким правилам

### Сначала — тест-ворота шага

Новый файл `src/test/java/com/rustorio/model/WorldPlaceRemoveTest.java` — вставьте
целиком, он красный, дальше работаете до зелёного:

```java
package com.rustorio.model;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertSame;

/** Правила постановки и сноса зданий. Чистая модель — без окна и движка. */
class WorldPlaceRemoveTest {

    private final World world = World.generate(10, 8);

    @Test
    void placePutsBuildingOnTile() {
        world.place(3, 4, new Chest());
        assertNotNull(world.tile(3, 4).building());
    }

    @Test
    void placeAndRemoveOutsideWorldAreSafe() {
        world.place(-1, 0, new Chest());
        world.place(10, 99, new Chest());
        world.remove(-5, -5); // ничего из этого не должно упасть
    }

    @Test
    void placingSameKindKeepsExistingBuilding() {
        Chest first = new Chest();
        world.place(3, 4, first);
        world.place(3, 4, new Chest());
        // Ставим «такой же» — мир обязан ОСТАВИТЬ старое здание, а не пересоздать.
        assertSame(first, world.tile(3, 4).building());
    }

    @Test
    void removeClearsTileAndIsIdempotent() {
        world.place(3, 4, new Chest());
        world.remove(3, 4);
        assertNull(world.tile(3, 4).building());
        world.remove(3, 4); // повторный снос пустого — тоже безопасен
    }
}
```

Обратите внимание на `assertSame` (не `assertEquals`): нам важно, что это **тот же
объект в памяти**, а не «равный». Разница выстрелит в Предскажи-2.

### Что должно уметь

`Tile` — слот под здание:

```java
private @Nullable Building building;   // изменяемое: игрок ставит и сносит

public @Nullable Building building()
void setBuilding(@Nullable Building building)   // ПАКЕТНО-приватный — см. ниже
```

`World` — правила постановки:

```java
public void place(int x, int y, Building building)
public void remove(int x, int y)
```

Оба безопасны к координатам вне поля (молча ничего не делают: протащили мышь за
край — не падать же). В `place` два правила защиты:

1. на клетке здание **другого типа** — не трогаем (протаскивая линию, не сносим
   чужое);
2. на клетке **такое же** здание (`sameKind`) — не пересоздаём.

### Предскажи-2

В шаге 3 ЛКМ будет ставить здание **каждый кадр**, пока кнопка зажата (60 раз в
секунду). Без правила 2 на клетке 60 раз в секунду появлялся бы новый `Chest`.
Сегодня это незаметно (ящики пусты и одинаковы). Опишите, какой баг это правило
предотвращает через пару лекций — когда у ящика будет счётчик предметов, а у ленты
груз. Ответ: [П2](L02-solutions.md#п2).

### Почему `setBuilding` — пакетно-приватный

Снаружи пакета `model` здание можно поставить ТОЛЬКО через `World.place` — вместе
с правилами. Если бы `setBuilding` был `public`, любой слой мог бы обойти правила,
и через месяц кто-нибудь обошёл бы. Модификаторы доступа — это не бюрократия, а
способ сделать неправильное **непишущимся**.

### Как проверить

`WorldPlaceRemoveTest` зелёный. Старые тесты тоже (устройство мира не менялось —
только выросло).

💡 Подсказка: [П3](L02-solutions.md#п3) · 📄 Решение: [Р3](L02-solutions.md#р3)

## ШАГ 3. Ввод: ЛКМ ставит, ПКМ сносит

### Что должно уметь

В `InputHandler.handle`, после блока горячих клавиш:

- зажата **ЛКМ** и курсор над полем → создать здание фабрикой
  (`Building.create(game.tool(), game.direction())`) и, если фабрика вернула
  здание, — `world.place(...)`;
- зажата **ПКМ** → `world.remove(...)`.

Именно `isButtonPressed` (зажата), а не `isButtonJustPressed`: тогда, ведя зажатую
мышь, вы «рисуете» линию зданий — а от 60-кратного пересоздания на месте защищает
правило 2 из шага 2. Ввод прост ровно потому, что правила лежат в мире.

### Как проверить

Компилируется. Игра запускается, клики пока «в пустоту» — здание ставится, но
рисовать его нечем (проверьте через временный `System.out.println` в `place`,
если не терпится; удалите после).

## ШАГ 4. `BuildingRenderer`: первый спрайт из атласа

### Зачем

Слой отрисовки зданий — отдельный класс с одной работой: пройти по видимым клеткам
и нарисовать спрайт каждого здания. Помните «спящее» поле `textures` в `Renderer`
из L0? Просыпается.

### Что должно уметь

```java
// render/BuildingRenderer.java (пакетно-приватный, как соседи)
final class BuildingRenderer {

    BuildingRenderer(SpriteBatch batch, Textures textures, Grid grid)

    /** Спрайты зданий в видимом диапазоне клеток. */
    void renderSprites(World world, TileRange range)
}
```

Внутри `renderSprites` — обход `range` (как в `WorldRenderer`), и для каждой клетки
со зданием — **исчерпывающий switch по sealed-типу**:

```java
switch (b) {
    case Chest _ -> batch.draw(textures.chest, px, py, TILE, TILE);
}
```

`case Chest _` — сопоставление по типу; `_` значит «сам объект не нужен, только
тип». И никакого `default`!

### Предскажи-3

Через лекцию в `permits` добавится `Miner`. Что скажет компилятор про этот
`switch`? А что бы он сказал, будь здесь ветка `default -> {}`? Какая из двух
ситуаций — молчаливая пропажа бура с экрана — вам милее? Ответ:
[П5](L02-solutions.md#п5).

### Подключение в `Renderer`

- поле `buildingRenderer`, создать в конструкторе (туда и уходит `textures` —
  «спящее» поле и комментарий про него удалите);
- в `render(...)`: вызов `buildingRenderer.renderSprites(world, visible)` —
  **после** земли, **до** HUD (порядок вызовов = порядок слоёв картинки).

### Как проверить (видимый результат лекции)

`./gradlew run` → клавиша **4** (Chest) → клики и протаскивание ЛКМ рисуют ящики,
ПКМ сносит. Ящик — настоящий спрайт `chest.png`, а не квадратик. Инструменты 1–3
пока ничего не ставят — их фабричные ветки вернут здания в своих лекциях.

## ШАГ 5. Эксперименты: что именно стережёт sealed

Все правки — временные, в конце `git restore .`.

### Э1. Вломиться в замкнутый список

Создайте в `model` файл `Tower.java`:

```java
package com.rustorio.model;

public final class Tower implements Building {
    // ...реализуйте direction() как Optional.empty()
}
```

Компилятор откажет: `Tower` не в списке `permits`. Впишите его в `permits` — теперь
откажет `switch` в `BuildingRenderer`: «не все случаи разобраны». Вот он, рецепт
добавления здания, которым вы будете пользоваться до конца курса: **вписал в
permits → пошёл по ошибкам компилятора, как по чек-листу**. Удалите `Tower` и
верните `permits`.

### Э2. Саботаж guard'а

Закомментируйте в `World.place` правило «sameKind — не пересоздаём» и запустите
тесты. `placingSameKindKeepsExistingBuilding` падает и **называет** сломанное
правило по имени. Тест здесь — страховка от «оптимизировали лишнюю проверку»
через полгода. Верните.

## Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|---|---|
| `class is not allowed to extend sealed class: Building` (компилятор говорит «class» даже про интерфейс) | класс не вписан в `permits` (или пишете его не в пакете `model`) |
| `the switch statement does not cover all possible input values` | в `permits` есть здание без ветки `case` — это не ошибка, это ваш чек-лист |
| клик ставит, но ящик не виден | `renderSprites` вызван в `Renderer.render`? После земли? `batch.begin()/end()` вокруг рисования есть? |
| ящик рисуется не в той клетке (зеркально по вертикали) | для Y использован `grid.x(y)` или свой расчёт вместо `grid.yBottom(y)` — переворот оси живёт ТОЛЬКО в `Grid` |
| `assertSame` падает, хотя «всё то же самое» | мир пересоздал здание: проверьте порядок guard'ов в `place` — `sameKind` проверяется ДО `setBuilding` |
| ПКМ сносит, а ЛКМ тут же ставит обратно | так и задумано: обе кнопки опрашиваются каждый кадр; сносите, отпустив ЛКМ |
