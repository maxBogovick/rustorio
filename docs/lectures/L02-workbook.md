## 0. Что мы делаем — в трёх предложениях

## 🆕 Новое в языке — прочитать ДО шагов

Пять вещей, которые встретятся впервые. Здесь — что это и зачем; в шагах — только
использование. Возвращайтесь сюда, когда встретите незнакомую запись.

### 1. Лямбда: функция без имени

```java
cell -> world.remove(cell.x(), cell.y())
```

Читается: «дай мне `cell` — я выполню `world.remove(...)`». Слева параметр, справа
тело. Лямбду передают как аргумент — «вот что сделать, когда/если…». До Java 8 то
же самое писали анонимным классом, сравните:

```java
// лямбда (сегодня):
game.hover().ifPresent(cell -> System.out.println(cell));

// то же самое до Java 8 — 5 строк церемонии вместо одной:
game.hover().ifPresent(new Consumer<Cell>() {
    @Override
    public void accept(Cell cell) {
        System.out.println(cell);
    }
});
```

Подробнее: [dev.java: Lambda Expressions](https://dev.java/learn/lambdas/).

### 2. `Optional<T>`: коробка, в которой может не быть значения

`Optional<Direction>` — это коробка: внутри либо `Direction`, либо пусто. Три
операции, которые нужны сегодня:

| Запись | Смысл |
|---|---|
| `Optional.empty()` | пустая коробка |
| `Optional.of(x)` | коробка с `x` внутри |
| `box.ifPresent(v -> ...)` | «если в коробке что-то есть — сделай с ним вот это» |

**Зачем, если есть `null`?** Сигнатура `Optional<Direction> direction()` честно
кричит: «направления может не быть, обработай это». Сигнатура
`Direction direction()`, возвращающая иногда `null`, молчит — и однажды взорвётся
`NullPointerException` в чужом коде, далеко от причины.

**Политика проекта — и null, и Optional, каждый на своём месте:**

| Где | Что используем | Почему |
|---|---|---|
| возвращаемые значения публичных методов домена (`direction()`, `hover()`) | `Optional` | явность + удобные цепочки `ifPresent` |
| поля и «горячие» методы, вызываемые в цикле на каждую клетку каждый кадр (`Tile.building()`) | `@Nullable` + `null` | `Optional` — это объект; создавать ~54 000 коробок в секунду (60 кадров × ~900 клеток) ради красоты — плохой размен |

Эта таблица — ответ на вопрос, который у вас возникнет в шаге 2: «почему
`Tile.building()` возвращает null, а `Building.direction()` — Optional?» Не
непоследовательность, а осознанный выбор в каждом месте.
Подробнее: [dev.java: Optional](https://dev.java/learn/api/streams/optionals/).

### 3. `@Nullable` (JSpecify): машинно-проверяемое «может быть null»

Все пакеты проекта помечены `@NullMarked` (загляните в любой `package-info.java`):
null **запрещён по умолчанию**. Там, где null законен, пишется явное разрешение —
`@Nullable Building building()`. Это контракт, который видит IDE: забудете
проверить на null — получите предупреждение. Подробнее: [jspecify.dev](https://jspecify.dev/).

### 4. `sealed` / `permits`: замкнутая иерархия

```java
public sealed interface Building permits Chest { ... }
```

Реализовать `Building` могут **только классы из списка `permits`** — компилятор
отвергнет любой другой. Каждая реализация обязана объявить себя `final` (или
`sealed`/`non-sealed`) — замкнутость распространяется вглубь. Введено в Java 17:
[JEP 409](https://openjdk.org/jeps/409).

### 5. `switch` по типам и `_`

```java
switch (b) {
    case Chest _ -> batch.draw(textures.chest, px, py, TILE, TILE);
}
```

`case Chest _` — сопоставление по **типу**: «если `b` — это `Chest`». `_` значит
«сам объект не нужен, важен только тип» (если нужен — пишете `case Chest c` и
пользуетесь `c`). Когда `b` — sealed-тип, компилятор знает ВСЕ варианты и требует
разобрать каждый — поэтому `default` не нужен и **вреден** (шаг 4 покажет почему).
Введено в Java 21: [JEP 441](https://openjdk.org/jeps/441); `_` — Java 22,
[JEP 456](https://openjdk.org/jeps/456).

## 🧠 Теория: тип-сумма — шаблон крупным планом

*15 минут чтения. Это ядро лекции: не пропускайте.*

### Проблема, которую решаем

В игре есть **закрытый набор вариантов** (виды зданий) и **набор операций** над
ними (нарисовать; позже — обновить за тик, принять предмет…). Классическая
развилка проектирования: как разложить «варианты × операции» по коду? Это
известная дилемма (в литературе — *expression problem*), и у неё четыре решения.

### Решение 1: наследование — операции внутри вариантов

```java
interface Building {
    void draw(SpriteBatch batch);   // ← отрисовка ВНУТРИ домена
    void update(TickContext ctx);
}
```

Каждое здание само себя рисует. Звучит «объектно-ориентированно», но: домен
теперь **зависит от libGDX** (`SpriteBatch` в сигнатуре — наш `ArchitectureTest`
упал бы немедленно); логика одной операции размазана по всем классам («как
рисуются здания?» — открой восемь файлов); добавить операцию = править каждый
класс. Так пишут, когда вариантов много и они открыты для расширения, а операций
мало и они стабильны. У нас — наоборот.

### Решение 2: instanceof-лесенка — операции снаружи, без гарантий

```java
if (b instanceof Chest) {
    batch.draw(textures.chest, px, py, TILE, TILE);
} else if (b instanceof Miner) {
    ...
}
// нет ветки? — молча ничего не нарисуем
```

Операция собрана в одном месте (уже лучше), но список веток — на совести
программиста. Добавили здание и забыли ветку — **компилятор молчит**, здание
просто исчезает с экрана, и вы ищете это глазами. Так выглядел почти весь
Java-код такого рода до 2021 года.

### Решение 3: Visitor (GoF) — исчерпывающесть ценой церемонии

До sealed-типов гарантию полноты добывали паттерном «Посетитель»: интерфейс
`BuildingVisitor` с методом на каждый вариант + метод `accept(visitor)` в каждом
здании. Добавишь здание — обязан добавить метод в интерфейс посетителя — все
операции не скомпилируются, пока не разберут новый случай. Работает! Но: два
интерфейса, двойная диспетчеризация, ~30 строк обвязки, и читать это новичку —
боль. Знайте, что он существует (встретите в старых кодовых базах), но сегодня
для закрытых иерархий он вытеснен решением 4.

### Решение 4 (наше): sealed-тип + switch по типам

Список вариантов замкнут в `permits` — и `switch` обязан разобрать все случаи.
Гарантия Visitor'а без его церемонии: варианты — просто классы, операции — просто
`switch` в том слое, которому операция принадлежит (отрисовка — в `render`,
симуляция — в `sim`). Это Java-версия **алгебраического типа-суммы** — конструкции,
вокруг которой построены Rust (`enum` + `match`), Kotlin (`sealed class`), Scala,
Haskell. В нашем же репозитории лежит Rust-версия этой игры — сравните сами:

```bash
git log --all --oneline -- src/building.rs   # найдите хеш начального коммита
git show <хеш>:src/building.rs | head -30     # enum Building { Miner {...}, Belt {...} }
```

Наш `sealed interface Building permits ...` — дословный перевод этого `enum` на Java.

### Где так делают

- **JDK сам**: API `java.lang.classfile` (JDK 24+) — sealed-иерархии на десятки
  типов; узлы в компиляторе `javac`.
- **Rust-экосистема**: любой уважающий себя парсер/игра/компилятор — enum + match.
- **Kotlin**: `sealed class` + `when` — тот же приём, те же гарантии.

### Границы применимости (когда sealed НЕ подходит)

Sealed требует, чтобы список вариантов был **закрыт и известен при компиляции**.
Если варианты должны добавляться извне — плагинами, модами, DLC без перекомпиляции
ядра — нужен открытый механизм: реестр. Так устроены блоки в Minecraft: `Block`
регистрируются в `Registry` строковыми ключами, потому что моды добавляют свои.
Цена открытости: никакой проверки полноты, все ошибки — в рантайме. Наш список
зданий закрыт (это учебная игра, а не платформа для модов) — поэтому sealed, и
компилятор работает на нас.

**Куда почитать дальше:** [JEP 409](https://openjdk.org/jeps/409) (мотивация от
авторов Java), R. Nystrom, [Game Programming Patterns](https://gameprogrammingpatterns.com/)
(гл. «Type Object» — как та же задача решается в динамических играх).

## ШАГ 1. `Building` + `Chest` (⏱ 35 мин)

### Зачем

«Здание» — выбор из фиксированного списка, как `Item` или `Tool`. Но enum здесь
НЕ подходит — и понять почему обязательно.

### Предскажи-1

Каждая константа enum существует **в одном экземпляре** (`Tool.CHEST` — один
объект на всю программу). Почему это убивает идею «здание = элемент enum»?
Подсказка: представьте два ящика на карте и счётчик предметов внутри каждого.
Запишите ответ, сверьтесь: [П1](L02-solutions.md#п1).

### Что должно уметь

```java
// model/Building.java
public sealed interface Building permits Chest {

    Optional<Direction> direction(); // у ящика — empty; у будущего бура — сторона выдачи

    /** «Такое же» здание: тот же тип и то же направление? (зачем — в шаге 2) */
    default boolean sameKind(Building other)

    /** Фабрика «инструмент → новое здание». Optional: зданий пока меньше, чем инструментов. */
    static Optional<Building> create(Tool tool, Direction dir)
}
```

```java
// model/Chest.java
public final class Chest implements Building {
    // направления нет; больше пока НИЧЕГО — счётчик появится вместе с предметами
}
```

### 🧠 Приём шага: статическая фабрика

`create` — это **статическая фабрика** (Дж. Блох, «Effective Java», правило №1:
*consider static factory methods instead of constructors*). Не путайте с «Factory
Method» из книги GoF — тот про переопределение создания в подклассах, а здесь
просто статический метод, который создаёт объекты. Что она даёт против «голых»
конструкторов:

- **одна точка создания**: «инструмент → здание» решается в одном месте, а не в
  каждом обработчике ввода;
- **право вернуть не-объект**: конструктор обязан вернуть объект, фабрика может
  вернуть `Optional.empty()` — ровно наш случай (инструментов 4, здание пока 1);
- **исчерпывающий switch по Tool**: добавите инструмент — компилятор потребует
  ветку здесь.

### 🚫 Как выглядел бы код без неё

```java
// InputHandler без фабрики — создание размазано по вводу:
if (game.tool() == Tool.CHEST) {
    world.place(cell.x(), cell.y(), new Chest());
} else if (game.tool() == Tool.MINER) {
    world.place(cell.x(), cell.y(), new Miner(game.direction()));
} // ...и так далее; ввод знает про ВСЕ классы зданий,
  // а забытая ветка — молчаливо мёртвая клавиша
```

Каждое новое здание — правка слоя ввода. С фабрикой ввод не меняется вообще —
проверите в лекции про бур.

### ⚙️ Алгоритм

Два файла пишутся **парой** — компилятор будет красным между ними, и это
запланировано. Идите по ошибкам:

1. Создайте `model/Building.java`: объявите
   `public sealed interface Building permits Chest`, добавьте метод
   `Optional<Direction> direction();`.
   → Компилятор: `cannot find symbol: class Chest` — **это не ошибка, это ваша
   следующая задача.**
2. Создайте `model/Chest.java`: `public final class Chest implements Building`.
   → Компилятор: `Chest is not abstract and does not override abstract method
   direction()` — интерфейс требует реализацию.
3. Реализуйте `direction()` в `Chest`: верните `Optional.empty()`.
   → Зелёно. Первая пара «интерфейс + реализация» готова.
4. В `Building` добавьте `default`-метод `sameKind` (сравнить `getClass()` и
   `direction()`). Почему `default`: реализация одинакова для ВСЕХ зданий —
   дублировать её в каждом классе глупо. (Границу знайте: default-методы хороши
   для таких «общих формул»; прятать в них состояние или сложную логику — запах.)
5. Добавьте статическую фабрику `create` со `switch (tool)`: ветка `CHEST` →
   `Optional.of(new Chest())`, остальные → `Optional.empty()` с комментарием,
   какая лекция их заполнит.
   → Попробуйте нарочно удалить ветку `MINER` из switch — компилятор: `the switch
   expression does not cover all possible input values`. Верните. Вот она,
   исчерпывающесть по enum.
6. `./gradlew test` — всё зелёное.

### Как проверить

Компилируется; старые тесты зелёные. Видимого результата нет — модель без
представления. Терпение: шаг 4.

## ШАГ 2. `Tile` и `World`: куда ставим и по каким правилам (⏱ 40 мин)

### Сначала — тест-ворота шага

Новый файл `src/test/java/com/rustorio/model/WorldPlaceRemoveTest.java` — вставьте
целиком, он красный, работаете до зелёного. Обратите внимание на комментарии
`// дано / когда / тогда` — это классическая структура теста
(*arrange-act-assert*): подготовили мир → сделали одно действие → проверили
результат. Все тесты курса устроены так.

```java
package com.rustorio.model;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertSame;

/** Правила постановки и сноса зданий. Чистая модель — без окна и движка. */
class WorldPlaceRemoveTest {

    private final World world = World.generate(10, 8);

    @Test
    void placePutsBuildingOnTile() {
        world.place(3, 4, new Chest());          // когда
        assertNotNull(world.tile(3, 4).building()); // тогда
    }

    @Test
    void placeAndRemoveOutsideWorldAreSafe() {
        world.place(-1, 0, new Chest());
        world.place(10, 99, new Chest());
        world.remove(-5, -5); // ничего из этого не должно упасть
    }

    @Test
    void placingSameKindKeepsExistingBuilding() {
        Chest first = new Chest();               // дано: ящик уже стоит
        world.place(3, 4, first);
        world.place(3, 4, new Chest());          // когда: ставим «такой же»
        // тогда: мир ОСТАВИЛ старый объект, а не заменил новым
        assertSame(first, world.tile(3, 4).building());
    }

    @Test
    void removeClearsTileAndIsIdempotent() {
        world.place(3, 4, new Chest());
        world.remove(3, 4);
        assertNull(world.tile(3, 4).building());
        world.remove(3, 4); // повторный снос пустого тоже безопасен
    }

    // TODO(L3): «place НЕ затирает здание ДРУГОГО типа» — сегодня непроверяемо:
    // в игре ровно один тип здания. Допишем, как только появится второй (бур).
}
```

Две детали, мимо которых нельзя пройти:

- **`assertSame`, а не `assertEquals`**: нам важно, что это **тот же объект в
  памяти** (`==`), а не «равный по содержимому». Пересозданный пустой ящик был бы
  *equals*-неотличим от старого — а баг именно в пересоздании.
- **«идемпотентность»** (последний тест): операция идемпотентна, если повторное
  применение ничего не меняет — снос пустой клетки безопасен. Слово из
  профессионального словаря; запомните, оно всплывает везде — от HTTP до баз данных.

### Что должно уметь

`Tile` — слот под здание:

```java
private @Nullable Building building;      // изменяемое: игрок ставит и сносит

public @Nullable Building building()
void setBuilding(@Nullable Building b)    // ПАКЕТНО-приватный — ниже о том, почему
```

(Почему тут `@Nullable`, а не `Optional` — см. таблицу политики в
[«Новом в языке»](#2-optionalt-коробка-в-которой-может-не-быть-значения): это
горячий путь отрисовки.)

`World` — правила:

```java
public void place(int x, int y, Building building)
public void remove(int x, int y)
```

Оба безопасны к координатам вне поля. В `place` два правила защиты:

1. на клетке здание **другого типа** — не трогаем (протаскивая линию, не сносим
   чужое);
2. на клетке **такое же** (`sameKind`) — не пересоздаём.

### Предскажи-2

В шаге 3 ЛКМ будет ставить здание **каждый кадр** (60 раз в секунду), пока кнопка
зажата. Без правила 2 на клетке 60 раз в секунду появлялся бы новый `Chest`.
Сегодня это незаметно. Опишите, какой баг это правило предотвращает через пару
лекций — когда у ящика будет счётчик, а у ленты груз. Ответ:
[П2](L02-solutions.md#п2).

### 🧠 Приём шага: инвариант за одной дверью

**Инвариант** — правило, которое обязано быть истинным всегда («на клетке не
пересоздаётся такое же здание»). Классический способ его гарантировать — впустить
все изменения через **одну дверь** и повесить проверки на неё: дверь — `place`,
проверки — правила 1 и 2. А чтобы дверь была единственной, «окно» заколачивается
модификатором доступа: `setBuilding` — пакетно-приватный, снаружи пакета `model`
его не существует. Это и есть практический смысл слова «инкапсуляция» из L1:
**неправильный код не запрещён комментарием — он не компилируется.**

### 🚫 Как выглядел бы код без этого

Представьте `setBuilding` публичным. Через месяц кто-то (вы же) пишет в обработчике
ввода «быстрый фикс»:

```java
// InputHandler, «ну мне же только на минутку»:
game.world().tile(cell.x(), cell.y()).setBuilding(new Chest());
```

Скомпилировалось. Работает. Правила постановки — молча обойдены: этот код затирает
чужие здания и пересоздаёт одинаковые. Тест `placingSameKindKeepsExistingBuilding`
при этом **зелёный** — он же проверяет `place`, а не эту дыру. Баг всплывёт через
неделю как «лента иногда теряет предметы» — и попробуйте её найти. Пакетная
приватность делает такой «фикс» невозможным: строка просто не скомпилируется.

### ⚙️ Алгоритм

1. Вставьте тест-ворота. → Красный: `cannot find symbol: method building()`.
2. `Tile`: добавьте поле `private @Nullable Building building;` (импорт
   `org.jspecify.annotations.Nullable`), геттер `building()`, пакетно-приватный
   `setBuilding` (просто без модификатора — это и есть package-private).
3. `World.place`: сначала guard `if (!inBounds(x, y)) return;` — потом всё
   остальное. Прочитайте клетку, возьмите `existing = tile.building()`.
4. Правила: если `existing != null` — сравните классы (`existing.getClass() !=
   building.getClass()` → `return`), затем `existing.sameKind(building)` →
   `return`. Только после guard'ов — `tile.setBuilding(building)`.
5. `World.remove`: guard `inBounds` → `tile(x, y).setBuilding(null)`.
6. Тесты. Если `placingSameKindKeepsExistingBuilding` красный — правила стоят
   ПОСЛЕ `setBuilding` или сравнение написано через `equals` вместо `==` у классов.

### Как проверить

`WorldPlaceRemoveTest` зелёный, старые тесты зелёные.

## ШАГ 3. Ввод: ЛКМ ставит, ПКМ сносит (⏱ 20 мин)

### Что должно уметь

В `InputHandler.handle`, после блока горячих клавиш: зажата ЛКМ и курсор над
полем → фабрика → `place`; зажата ПКМ → `remove`.

### ⚙️ Алгоритм — сначала многословно, потом красиво

Напишите «в лоб», чтобы увидеть каждое движение (это компилируется и работает):

```java
if (Gdx.input.isButtonPressed(Input.Buttons.LEFT)) {
    Optional<Cell> hover = game.hover();
    if (hover.isPresent()) {
        Cell cell = hover.get();
        Optional<Building> created = Building.create(game.tool(), game.direction());
        if (created.isPresent()) {
            game.world().place(cell.x(), cell.y(), created.get());
        }
    }
}
```

Работает — но лесенка `isPresent()/get()` возвращает нас к стилю «проверь null
руками», от которого Optional и уходил. Теперь сверните её в цепочку `ifPresent`
с лямбдами (см. [«Новое в языке»](#1-лямбда-функция-без-имени)):

```java
if (Gdx.input.isButtonPressed(Input.Buttons.LEFT)) {
    game.hover().ifPresent(cell ->
            Building.create(game.tool(), game.direction())
                    .ifPresent(b -> game.world().place(cell.x(), cell.y(), b)));
}
```

Прочитайте вслух: «если ЛКМ зажата — если есть клетка под курсором — если фабрика
дала здание — поставить». Обе версии равнозначны; в решении оставлена вторая, но
если пока комфортнее первая — оставьте первую и вернитесь к свёртке после шага 4.
ПКМ — по тому же образцу, только `remove` и без фабрики.

**Почему `isButtonPressed` (зажата), а не `isButtonJustPressed` (нажата только
что)?** Чтобы, ведя зажатую мышь, «рисовать» линию зданий. От 60-кратного
пересоздания на месте защищает правило 2 из шага 2 — ввод может позволить себе
быть простым, потому что правила лежат в мире.

### Как проверить

Компилируется; игра запускается; клики пока «в пустоту» — рисовать нечем. Если не
терпится: временный `System.out.println("place " + x + "," + y)` в `World.place` —
кликните, посмотрите в консоль, удалите.

## ШАГ 4. `BuildingRenderer`: первый спрайт из атласа (⏱ 30 мин)

### Зачем

Слой отрисовки зданий — отдельный класс с одной работой: пройти по видимым
клеткам и нарисовать спрайт каждого здания. «Спящее» поле `textures` из L0
просыпается.

### Что должно уметь

```java
// render/BuildingRenderer.java (пакетно-приватный, как соседи по пакету)
final class BuildingRenderer {

    BuildingRenderer(SpriteBatch batch, Textures textures, Grid grid)

    /** Спрайты зданий в видимом диапазоне клеток. */
    void renderSprites(World world, TileRange range)
}
```

Внутри — обход `range` (образец: `WorldRenderer`) и **исчерпывающий switch по
sealed-типу** для каждой клетки со зданием:

```java
switch (b) {
    case Chest _ -> batch.draw(textures.chest, px, py, TILE, TILE);
}
```

### 🚫 Как без этого — и почему `default` здесь саботаж

Вариант «до Java 21» (решение 2 из теории):

```java
if (b instanceof Chest) {
    batch.draw(textures.chest, px, py, TILE, TILE);
}
// добавили Miner → забыли ветку → бур НЕВИДИМ, компилятор молчит,
// вы полчаса дёргаете камеру и «чинте» рендер наугад
```

И «испорченный» вариант switch:

```java
switch (b) {
    case Chest _ -> batch.draw(textures.chest, px, py, TILE, TILE);
    default -> {} // «на всякий случай» — И ВСЁ СЛОМАНО:
}                 // компилятор больше НИКОГДА не потребует новых веток
```

`default` в switch по sealed-типу — это добровольный отказ от главного подарка
компилятора. Правило курса: **в switch по sealed-типам `default` запрещён.**
Ошибка компиляции при добавлении здания — не неудобство, а фича: она называет
файл и строку, где вы ещё не решили, как здание выглядит.

### Предскажи-3

Через лекцию в `permits` добавится `Miner`. Проговорите заранее: что и в каких
файлах скажет компилятор? Ответ: [П5](L02-solutions.md#п5).

### ⚙️ Алгоритм

1. Создайте класс по сигнатурам выше; поля `batch`, `textures`, `grid` — из
   конструктора; константа `TILE = Config.TILE`.
2. `renderSprites`: `batch.begin()` → двойной цикл по `range` (скопируйте форму
   циклов из `WorldRenderer` — да, это нормально) → `Building b =
   world.tile(x, y).building(); if (b == null) continue;` → координаты
   `grid.x(x)`, `grid.yBottom(y)` → switch → `batch.end()`.
3. Подключение в `Renderer`: удалите «спящее» поле `textures` вместе с
   `@SuppressWarnings` и комментарием; поле `buildingRenderer`; в конструкторе —
   `new BuildingRenderer(batch, textures, grid)`; в `render(...)` — вызов
   **после** земли, **до** HUD.
   → Порядок вызовов = порядок слоёв картинки: земля → здания → (позже предметы)
   → HUD поверх.
4. `./gradlew run` → **4** → кликайте.

### 🔍 Трасса одного кадра (свяжите с циклом из L0)

Вы зажали ЛКМ над клеткой (12, 7). Что происходит в ближайшие 16 миллисекунд:

```
GameScreen.render(delta)
 ├─ input.handle(game, delta)
 │    ├─ camera.pickTile(...) → Cell(12,7) → game.setHover(...)
 │    └─ ЛКМ зажата → фабрика → world.place(12, 7, chest)
 │         └─ Tile(12,7).building = chest      ← мир ИЗМЕНЁН фазой ввода
 ├─ game.update(delta)                          ← тиков нет, мир не меняется
 └─ renderer.render(game, delta)
      ├─ worldRenderer: земля, сетка, рамка hover
      ├─ buildingRenderer: tile(12,7).building() != null → батч рисует спрайт
      └─ hudRenderer: «Tool: Chest  Cell: (12, 7)»
```

Один кадр — и на экране ящик. Заметьте: рендер узнал о ящике не по «событию», а
просто **прочитав мир заново**. Состояние — единственный источник правды; никто
никому ничего не «сообщает». Это следствие золотого правила из L0.

### Как проверить (видимый результат лекции)
