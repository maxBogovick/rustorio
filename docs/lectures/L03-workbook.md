## 🆕 Новое в языке — прочитать ДО шагов

Три вещи встретятся впервые. Здесь — что это и зачем; в шагах — использование.

### 1. `instanceof` с привязкой переменной

В L2 вы видели «голый» `instanceof` в теории (плохой пример-лесенка):

```java
if (b instanceof Miner) {          // проверили тип...
    Miner m = (Miner) b;           // ...и ОТДЕЛЬНО привели — два шага, руками
    m.setOnOre(true);
}
```

С Java 16 проверка и приведение — **один шаг**: имя переменной пишется прямо в
`instanceof`, и внутри `if` она уже нужного типа:

```java
if (b instanceof Miner m) {        // проверил И привязал m: Miner — сразу
    m.setOnOre(true);
}
```

`m` существует только там, где проверка истинна (внутри `if`). Это то же «сопоставление
с образцом», что и `case Miner m ->` в `switch` из L2, только в форме `if`. Введено в
Java 16: [JEP 394](https://openjdk.org/jeps/394).

### 2. Свой функциональный интерфейс: лямбда к вашему методу

Лямбду можно передать не только в чужой `ifPresent` — но и в **свой** метод. Правило:
если у интерфейса **ровно один** абстрактный метод, вместо реализации-класса можно
передать лямбду с той же формой параметров.

```java
// Объявляем интерфейс с одним методом — «что сделать с каждым зданием»:
@FunctionalInterface   // обещание: абстрактный метод всегда ровно один (объяснение ниже)
public interface BuildingVisitor {
    void visit(int x, int y, Building building);
}

// Метод принимает его:
public void forEachBuilding(BuildingVisitor visitor) { ... visitor.visit(x, y, b); ... }

// Вызывающий передаёт ЛЯМБДУ — компилятор видит: «форма совпала с visit(int,int,Building)»:
world.forEachBuilding((x, y, b) -> b.update(ctx));
```

Три параметра лямбды `(x, y, b)` встают на `(int x, int y, Building building)` метода
`visit`. Никакого `new BuildingVisitor() { ... }` — компилятор строит его за вас. Это
тот же механизм, что стоит за `Consumer`/`Runnable` из стандартной библиотеки, просто
интерфейс теперь ваш. Подробнее:
[dev.java: Functional Interfaces](https://dev.java/learn/lambdas/functional-interfaces/).

Два примечания к такому интерфейсу:

- **Аннотация `@FunctionalInterface`** над объявлением — обещание компилятору: «здесь
  всегда ровно один абстрактный метод». Без неё интерфейс тоже работает с лямбдами,
  но если кто-то потом допишет второй метод, сломаются все лямбды по всему коду — с
  аннотацией сломается только само объявление, с понятной ошибкой в одном месте. Так
  помечены `Runnable`, `Consumer` и все их родственники в JDK; пометим и мы.
- **Имя `BuildingVisitor` — не паттерн Visitor из GoF.** В L2 вы видели «Решение 3:
  Visitor» — тяжёлый паттерн с двойной диспетчеризацией, который мы отвергли. Здесь
  слово «visitor» используется в бытовом смысле «загляни к каждому»: это обычный
  колбэк для обхода, как у `Iterable.forEach`. Совпадение имён случайно; не путайте на защите.

### 3. Полиморфизм: одна строка — разный код

Синтаксически нового здесь нет, но сегодня мы впервые **опираемся** на главный
механизм ООП, и у него должно быть имя. Посмотрите на строку, вокруг которой
построена вся лекция:

```java
Building b = ...;   // тип ПЕРЕМЕННОЙ — Building; какой ОБЪЕКТ в ней — решается на бегу
b.update(ctx);      // вызовется Miner.update ИЛИ Chest.update — по фактическому объекту
```

Компилятор проверяет только одно: у типа `Building` есть метод `update` — значит,
вызов законен. А вот **какая реализация** выполнится, решает JVM в момент вызова,
посмотрев на настоящий класс объекта в переменной. Это называется **полиморфизм**
(«много форм»: одна запись `b.update(ctx)` — много вариантов поведения), а сам
механизм выбора — **динамическая диспетчеризация** (dynamic dispatch).

Сравните с `switch (b)` из L2: там ветвление по типу пишете **вы**, глазами видно все
случаи. Здесь ветвление делает **JVM**, и в коде его не видно вообще — поэтому
`Simulation` сможет работать со зданиями, не зная ни одного конкретного класса.
Оба инструмента останутся в проекте: `switch` — где важна исчерпывающая карта случаев
(отрисовка), полиморфизм — где важно «не знать и не хотеть знать» (симуляция).
Подробнее: [dev.java: Polymorphism](https://dev.java/learn/inheritance/polymorphism/).

## 🧠 Теория: Update Method — шаблон крупным планом

*15 минут чтения. Это ядро лекции.*

### Проблема, которую решаем

В мире много зданий разных видов, и каждый тик каждое должно сделать «свою работу»:
бур — копнуть, печь — подплавить, лаборатория — исследовать. Вопрос
проектирования: **где живёт эта работа и кто её запускает?**

### Решение 1: божественный цикл — вся работа в одном месте

Пусть `GameState` (или симуляция) сам знает, что делать с каждым типом:

```java
// тело тика — один большой обработчик на все здания:
world.forEachBuilding((x, y, b) -> {
    if (b instanceof Miner m) {
        // ...вся логика добычи прямо здесь: кулдаун, выдача руды...
    } else if (b instanceof Furnace f) {
        // ...вся логика плавки здесь...
    }
    // забыл ветку у нового здания — оно молча мёртвое (instanceof-лесенка не проверяется)
});
```

Работает. Но: **поведение здания живёт НЕ в здании**, а в чужом цикле, который
знает внутренности всех восьми классов; добавить здание — редактировать этот цикл;
цикл растёт без предела; проверить логику ОДНОГО бура нельзя, не подняв весь
`GameState`. И та самая instanceof-лесенка без гарантий полноты, от которой вы
ушли в L2.

### Решение 2 (наше): Update Method — каждый обновляет себя сам

Дадим каждому зданию метод «сделай свою работу за тик». Тогда запускающему коду не
нужно знать НИ ОДНОГО конкретного типа:

```java
// в каждом здании — своя реализация:
public void update(TickContext ctx) { /* моя внутренняя работа за один тик */ }

// в симуляции — ни одного instanceof, ни одного switch:
world.forEachBuilding((x, y, b) -> b.update(ctx));
```

Выбор реализации делает полиморфизм («Новое в языке», п. 3): `b.update(ctx)` вызовет
`Miner.update` для бура и `Furnace.update` для печи — ветвление по типу выполняет
JVM, в коде симуляции его нет. Добавите здание — оно обязано реализовать
`update` (интерфейс требует), а симуляция **не меняется вообще**. Это шаблон
**Update Method** (Р. Нистром, *Game Programming Patterns*), и он в паре с «игровым
циклом» из L0: цикл решает *когда* тикать, Update Method — *что* делает каждый на тике.

### Решение 3 (и граница): ECS — когда поведение отвязано от типа

Есть более радикальный подход — **ECS** (Entity-Component-System): у сущности нет
типа-класса, есть набор «компонентов»-данных, а поведение — в «системах», которые
обходят компоненты. Его берут, когда поведение комбинируется независимо от «вида» и
нужен кэш-дружелюбный обход десятков тысяч сущностей. Для учебной игры с **закрытым**
списком зданий это молоток не по гвоздю: Update Method + чанковый обход уже дают
хорошую локальность (замерим в L11). Знать, что ECS есть, — полезно; тащить его
сюда — переусложнение.

### Границы применимости (когда Update Method НЕ подходит)

Update Method предполагает, что каждое здание обновляется **независимо**, читая
общий контекст только на чтение. Но как только буру нужно **передать руду соседу** —
per-object `update` ломается: здание не знает своих координат и соседей, а порядок
обхода сделал бы передачу нечестной и невоспроизводимой. Такая работа — не метод
здания, а **отдельная система**: функция над всем миром, у которой есть карта и
порядок. Ровно её L4 добавит второй фазой в `Simulation.step`. Запомните разделение:
**внутренняя работа → `update`; работа между зданиями → система.**

### Где так делают

- **Unity**: `MonoBehaviour.Update()` — движок каждый кадр зовёт `Update` у каждого
  объекта сцены.
- **Unreal**: `AActor::Tick(float DeltaTime)` — тот же контракт, тот же `DeltaTime`
  в роли нашего `ctx.dt()`.
- Практически любой игровой движок: «дай каждому шанс обновиться на этом шаге».

**Куда почитать:** R. Nystrom, [Game Programming Patterns](https://gameprogrammingpatterns.com/update-method.html)
(глава «Update Method», и рядом «Game Loop»).

## ШАГ 1. `TickContext` и метод `update` (⏱ 25 мин)

### Зачем

Чтобы здание могло «работать за тик», нужен, во-первых, **контракт** — метод
`update`, который каждое здание реализует, — и, во-вторых, **что ему передать**:
сколько длится тик. Мы заведём метод и «коробку»-параметр под данные тика.

### Предскажи-1

`Building` — sealed-интерфейс с единственной реализацией `Chest` (из L2). Вы
добавляете в интерфейс новый абстрактный метод `void update(TickContext ctx)`. Что
скажет компилятор про `Chest` ДО того, как вы его тронете? Запишите дословную
догадку, сверьтесь: [П1](L03-solutions.md#п1).

### Что должно уметь

```java
// core/TickContext.java — «коробка» данных одного тика
public record TickContext(float dt) { }   // dt — длительность тика в секундах
```

```java
// model/Building.java — добавка к контракту:
void update(TickContext ctx);   // «внутренняя работа здания за один тик»
```

```java
// model/Chest.java — реализация:
@Override public void update(TickContext ctx) { /* ящик пассивен: ничего */ }
```

### 🧠 Приём шага: параметр-объект (Parameter Object)

Почему `update(TickContext ctx)`, а не `update(float dt)`? Сейчас нужен только `dt` —
казалось бы, лишняя обёртка. Но **коробка-параметр** (М. Фаулер, *Refactoring*,
«Introduce Parameter Object») страхует от будущего: когда зданиям понадобится ещё
что-то общее на тик (в L13 — баланс апгрейдов), это поле добавится **в `TickContext`**,
а сигнатура `update` не изменится ни в одном из восьми зданий. Контракт, который не
переписывают, — контракт, за который не страшно.

### 🚫 Как выглядел бы код без коробки

```java
void update(float dt, boolean hasOre) {   // ← hasOre нужен ТОЛЬКО буру,
    ...                                    //   а принимать обязаны ВСЕ, включая ящик
}
// Понадобился баланс? → update(float dt, boolean hasOre, Balance balance) —
// и правка сигнатуры во ВСЕХ зданиях разом, каждый раз. Коробка это гасит:
// новое общее данное — одно поле в TickContext, ни одной правки в зданиях.
```

(`hasOre` мы к тому же вообще уберём из тика — шаг 2 покажет куда.)

### ⚙️ Алгоритм

1. Создайте `core/TickContext.java`: `public record TickContext(float dt) { }`.
   Это `record` — тот же вид «носителя данных», что `Cell` из L0: одно поле,
   готовые `dt()`, `equals`, `toString`.
2. В `Building` добавьте строку `void update(TickContext ctx);` (импорт
   `com.rustorio.core.TickContext`).
   → Компилятор: `Chest is not abstract and does not override abstract method
   update(TickContext)` — интерфейс требует реализацию, как в L2 с `direction()`.
3. В `Chest` реализуйте `update` с **пустым** телом и комментарием «ящик пассивен».
   → Зелёно.

### Как проверить

Компилируется, старые тесты зелёные. Видимого результата нет — механизм, а не
поведение.

## ШАГ 2. `Miner`: здание, которое живёт (⏱ 45 мин)

### Зачем

Первое здание с поведением. Бур стоит на руде и раз в `Config.MINER_TIME` кладёт
руду в свой «выход». Отдавать её соседу он пока не умеет (это L4) — сегодня он
**копает и держит**, а вы видите работу по анимации.

### Сначала — тест-ворота шага

Новый файл `src/test/java/com/rustorio/model/MinerTest.java` — вставьте целиком,
он красный, работаете до зелёного. Структура `// дано / когда / тогда`
(*arrange-act-assert*) — как в L2.

```java
package com.rustorio.model;

import com.rustorio.core.Config;
import com.rustorio.core.Direction;
import com.rustorio.core.Item;
import com.rustorio.core.TickContext;
import org.junit.jupiter.api.Test;

import java.util.Optional;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

/** Поведение бура за тики. Чистая модель — без окна, без симуляции. */
class MinerTest {

    /** Контекст одного тика — длительностью ровно в TICK. */
    private static TickContext tick() {
        return new TickContext(Config.TICK);
    }

    @Test
    void minerOnOreDigsAfterEnoughTicks() {
        Miner miner = new Miner(Direction.EAST);
        miner.setOnOre(true);                        // дано: бур на руде, выход пуст
        assertTrue(miner.outputItem().isEmpty());
        for (int i = 0; i < 10; i++) {               // когда: тиков с запасом (MINER_TIME / TICK ≈ 5)
            miner.update(tick());
        }
        assertEquals(Optional.of(Item.IRON_ORE), miner.outputItem()); // тогда: руда добыта
    }

    @Test
    void minerOffOreNeverDigs() {
        Miner miner = new Miner(Direction.EAST);
        miner.setOnOre(false);                       // не на руде
        for (int i = 0; i < 10; i++) {
            miner.update(tick());
        }
        assertTrue(miner.outputItem().isEmpty(), "без руды копать нечего");
    }

    @Test
    void progressGrowsWithTicks() {
        Miner miner = new Miner(Direction.EAST);
        miner.setOnOre(true);
        assertEquals(0f, miner.progressFraction(), 1e-6f); // дано: только поставлен
```

### 🧠 Приём шага: кэшировать факт, а не спрашивать каждый тик

Буру нужно знать «стою ли я на руде». Наивно — спрашивать мир каждый тик. Но
**здание не знает своих координат** (и не должно: оно живёт в клетке, а не «в точке
(6,5)»). Поэтому факт узнаётся ОДИН раз, при постройке, и **кэшируется** в поле
`onOre`: мир, который координаты знает, сообщает их следствие буру через `setOnOre`.
Кэш безопасен, пока факт не меняется, — руда сегодня не иссякает. Правило кэша: **если
факт однажды станет меняться (истощение руды), мир ОБЯЗАН сообщить об изменении** —
иначе бур будет копать из пустоты. Это записывается в javadoc, чтобы будущий автор
не забыл (см. решение).

### 🚫 Как без этого

```java
// «пусть тик приносит руду параметром» — и вот hasOre снова в сигнатуре ВСЕХ:
void update(float dt, boolean hasOre) { if (hasOre) { ... } }
// Ящику hasOre не нужен, печи не нужен — но принимать обязаны все.
// А чтобы его вычислить, кто-то на каждом тике должен знать координаты каждого
// здания и звать OreMap — работа на ровном месте каждый кадр. Кэш при постройке
// делает это ОДИН раз за всю жизнь бура.
```

чтобы `outputItem()` перестал быть пустым? А что вернёт `update` на **шестом** тике
(когда руда уже на выходе)? Ответ: [П2](L03-solutions.md#п2).

### ⚙️ Алгоритм

1. В `Config`, в конце (после `MAX_FRAME_TIME`), заведите баланс бура — этой
   константы в каркасе ещё нет:

3. Создайте `Miner implements Building`. Поля: `private final Direction dir;`

## ШАГ 4. `Simulation` и `forEachBuilding`: конвейер систем (⏱ 35 мин)

### Зачем

Кто-то должен раз в тик обойти все здания и дать каждому `update`. Это работа
**симуляции** — нового объекта в пакете `sim`. Обходить здания она будет через
`World.forEachBuilding`: мир знает, как он хранит клетки, — симуляция знать не должна
(тот же фасад, что в L2).

### Что должно уметь

```java
// model/World.java — добавка:
public void forEachBuilding(BuildingVisitor visitor)   // обход всех зданий по координатной сетке
@FunctionalInterface
public interface BuildingVisitor {                     // «что сделать с каждым зданием»
    void visit(int x, int y, Building building);
}
```

```java
// sim/Simulation.java
public final class Simulation {
    public Simulation(World world)
    public void step(TickContext ctx)     // ОДИН шаг мира = конвейер систем
}
```

### 🧠 Приём крупным планом здесь — Update Method (см. теорию)

`Simulation.step` вызывает приватную «систему» `runMachines`, а та —
`world.forEachBuilding((x, y, b) -> b.update(ctx))`. **Ни одного `instanceof`, ни
одного `switch`**: полиморфизм сам выберет `Miner.update` или `Chest.update`. Новое
здание встроится в симуляцию, не изменив в ней ни строки. «Система» — это просто
приватный метод-функция над миром; L4 добавит рядом вторую (`moveItems`), L5 —
третью. Один шаг мира = вызвать системы по порядку.

### 🚫 Как без этого

```java
// Без Simulation логика тика переезжает в GameState.update, и он становится
// «богом»: знает про World, про обход, про каждое здание. Тестировать шаг мира
// без окна и без GameState нельзя; добавить систему — раздуть GameState.
// Simulation — отдельный тестируемый объект «как мир идёт на тик», и только.
```

Почему объект, а не набор `static`-методов? Пока разницы нет — но в L4 у симуляции
появятся переиспользуемые буферы (список передач), которым нужно жить между тиками.
Поле объекта для этого есть, у статического метода — нет. Закладываемся сейчас.

### ⚙️ Алгоритм

1. В `World` добавьте вложенный `public interface BuildingVisitor` с одним методом
   `void visit(int x, int y, Building building);` и аннотацией `@FunctionalInterface`
   над объявлением (зачем — «Новое в языке», п. 2).
2. Напишите `forEachBuilding(BuildingVisitor visitor)`: обход идёт **по координатной
   сетке кусков** (не по `chunks.values()` — порядок карты произволен, а симуляция
   обязана быть воспроизводимой). Форму двойного цикла по кускам и по клеткам внутри
   куска возьмите из решения — это чистая механика чанков из L0.
3. Создайте `sim/Simulation.java`: поле `world`, конструктор, `step(ctx)` зовёт
   приватный `runMachines(ctx)`, а тот —
   `world.forEachBuilding((x, y, building) -> building.update(ctx));`.
   → Компилируется. Само по себе ничего не делает — зовущего ещё нет (шаг 5).

### Как проверить

Компилируется, тесты зелёные. Бур всё ещё «спит»: `Simulation.step` никто не зовёт.

```
GameScreen.render(delta)
 ├─ input.handle(...)                      ← игрок, может быть, поставил бур
```

## ШАГ 6. Рендер бура: спрайт, стрелка, рамка (⏱ 40 мин)

### Зачем

Видимый результат лекции. Спящий массив `textures.miner` (три кадра, готов с L0)
просыпается. Плюс две **накладки** поверх спрайта: стрелка направления выдачи и
красная рамка «бур стоит не на руде» — обе рисуются `ShapeRenderer`, поэтому у
`BuildingRenderer` появляется второй инструмент рисования и отдельные проходы.

### Что должно уметь

`BuildingRenderer` (из L2 у него только `renderSprites` со `SpriteBatch`) получает
`ShapeRenderer` в конструктор и два новых прохода:

```java
BuildingRenderer(SpriteBatch batch, ShapeRenderer shapes, Textures textures, Grid grid)

void renderSprites(World world, TileRange range)     // + ветка Miner (3 кадра)
void renderOverlays(World world, TileRange range)    // стрелки направлений
void renderOutlines(World world, TileRange range)    // рамка «не на руде»
```

Почему три прохода, а не один: `SpriteBatch` (спрайты) и `ShapeRenderer` (фигуры)
нельзя рисовать вперемешку без переоткрытия — дешевле сгруппировать все спрайты, потом
все фигуры.

### 🚫 Напоминание из L2: `default` в switch по sealed — саботаж

Ветку `Miner` вы добавляете в `switch (b)` **без** `default`. Если поставите
`default -> {}` «на всякий случай» — компилятор навсегда перестанет требовать ветки
для новых зданий, и лента из L5 просто не нарисуется молча. Правило курса в силе:
**в switch по sealed-типам `default` запрещён.**

### ⚙️ Алгоритм

1. В `renderSprites`, в `switch (b)`, добавьте ветку бура **перед** `Chest`:
   ```java
   case Miner m -> {
       int frame = (int) (Math.clamp(m.progressFraction(), 0f, 0.999f) * 3);
       batch.draw(textures.miner[frame], px, py, TILE, TILE);
   }
   ```
   `* 3` и потолок `0.999f` дают индекс кадра 0, 1 или 2 (никогда 3 — вышли бы за
   массив). → Запустите игру: клавиша `1` выбирает бур (слоты панели — из L1), ЛКМ
   ставит его (фабрика возвращает бур с шага 3) — виден спрайт, меняющий кадр по
   мере добычи.
2. Добавьте в конструктор параметр `ShapeRenderer shapes`, сохраните в поле.
3. Напишите `renderOverlays`: `shapes.begin(Filled)` → обход `range` → для клетки со
   зданием `switch (b)` с ветками `case Miner m -> drawArrow(...)` и `case Chest _ ->
   { }` → `shapes.end()`. Приватный `drawArrow` (геометрия треугольника) возьмите из
   решения — это чистая тригонометрия, не приём; разберитесь потом.
4. В `Palette` добавьте два цвета — `WORKING = Color.GREEN` и `IDLE = Color.RED`
   (стрелка зелёная, когда бур работает; красная — простаивает; ею же рамка). До L3
   их в палитре не было.
5. Напишите `renderOutlines`: `shapes.begin(Line)` → обход `range` → `if
   (tile.building() instanceof Miner && !tile.hasOre())` рисуем красную рамку
   (`Palette.IDLE`) → `shapes.end()`.
6. Подключение в `Renderer`: передайте `shapes` в конструктор `BuildingRenderer`
   (объект `shapes` там уже есть — им рисует `worldRenderer`); в `render(...)`, после
   `renderSprites`, добавьте вызовы `renderOverlays` и `renderOutlines`.
   → `./gradlew run`.

### Как проверить (видимый результат лекции)

Клавиша **1** (бур) → ЛКМ по клетке с рудой (тёмные точки на земле): бур рисуется и
**анимируется тремя кадрами**, пока копает; стрелка показывает направление выдачи.
Поставьте бур на пустую землю — вокруг него **красная рамка**, кадр не меняется:
копать нечего.

**Честная граница лекции:** отдавать руду бур ещё не умеет (это L4). Поэтому, добыв
одну руду (~0.9 с, пять тиков), он останавливается с полной «загрузкой» и больше не
анимируется — потребителя нет. **Стрелка при этом станет красной, даже на руде**:
условие `active` включает «выход пуст», а выход теперь занят навсегда. Это не баг, а
честное состояние «простаиваю». В L4 соседний ящик начнёт забирать руду — бур
зациклится, стрелка снова зазеленеет. Сегодня видимый результат — **один** цикл
добычи и накладки; этого достаточно, чтобы увидеть, что мир пошёл.

💡 Подсказка: [П6](L03-solutions.md#п6) · 📄 Решение: [Р6](L03-solutions.md#р6)

## ШАГ 7. Эксперименты (⏱ 15 мин)

Правки временные — в конце `git restore .`.

### Э1. Выдернуть тик

В `GameState.update` закомментируйте `simulation.step(ctx)`. Запустите, поставьте
бур на руду. Кадр не меняется, стрелка сразу «рабочая», но прогресс стоит: без вызова

решает «когда», `step` — «что»; без второго время идёт, а мир стоит.** Верните.

### Э2. Сломать кэш руды

В `World.place` замените `miner.setOnOre(tile.hasOre())` на `miner.setOnOre(false)`.
Запустите `MinerTest` — `minerOnOreDigsAfterEnoughTicks` падает: бур на руде теперь

`hasOre` внутри `update` — откуда бур возьмёт свои `x, y`?)

### Э3. Убить исчерпывающесть (напоминание из L2)

В `renderSprites` добавьте `default -> {}` в `switch (b)`. Проект соберётся. Теперь
удалите ветку `case Chest _` — компилятор **молчит** (его затыкает `default`), а
ящики исчезают с экрана. Уберите `default` — сразу `the switch statement does not
cover all possible input values` с указанием места. Верните обе правки. Мораль та же,
что в L2: `default` в sealed-switch — добровольный отказ от карты задач.
