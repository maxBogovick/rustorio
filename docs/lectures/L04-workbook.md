## 0. Что мы делаем — в трёх предложениях

Бур наконец **отдаёт** добытую руду соседнему ящику, и на ящике растёт счётчик.
Чтобы передача была честной — «одновременной» и не зависящей от того, в каком порядке
симуляция обходит здания, — вы напишете приём **двухфазного тика**: сначала СОБРАТЬ
все передачи, только читая мир, потом ПРИМЕНИТЬ их. Попутно — «штамп версии»
(`Tile.claim`), который за один тик отдаёт клетку ровно одному отправителю: без него
два соседа пропихнули бы два предмета в один слот.

Заодно это закрывает клиффхэнгер L3: как только ящик заберёт руду, бур освободит выход
и закрутится снова.

## 🧠 Теория: двухфазный тик — шаблон крупным планом

*15 минут чтения. Это ядро лекции.*

### Проблема, которую решаем

Бур хочет отдать руду ящику справа. Ящик хочет отдать… ничего (он конечный). Но
представьте цепочку из трёх лент: A → B → C, и на A лежит предмет. Мы обходим здания
и сразу двигаем предмет соседу. Что получится за ОДИН тик?

- Обошли в порядке **A, B, C**: A отдал в B (теперь предмет в B), доходим до B — B
  отдаёт в C. Предмет проехал **две** клетки за тик.
- Обошли в порядке **C, B, A**: C пуст, B пуст, A отдал в B. Предмет проехал **одну**
  клетку.

Один и тот же мир, один тик — **разный результат**, зависящий от порядка обхода. А
порядок у нас — по сетке кусков, деталь хранения. Симуляция обязана быть
воспроизводимой (это стережёт `ArchitectureTest`): недопустимо, чтобы поведение
зависело от того, как мир разложен по чанкам.

### Решение 1: двигать по месту в один проход

```java
world.forEachBuilding((x, y, b) -> {
    b.output().ifPresent(h -> {
        Building n = world.neighborBuilding(x, y, h.direction());
        if (n != null && n.canAccept(h.item())) {
            b.removeOutput();
            n.accept(h.item());   // ← меняем мир ПРЯМО во время обхода
        }
    });
});
```

Компилируется, «работает» на одиночном буре. Но на цепочке даёт тот самый
порядко-зависимый результат: предмет то «телепортируется» на несколько клеток за
тик, то ползёт по одной. Невоспроизводимо.

### Решение 2 (наше): две фазы — собрать, потом применить

```java
// Фаза 1: только ЧИТАЕМ, собираем список того, что надо сделать.
moves.clear();
world.forEachBuilding((x, y, source) -> {
    source.output().ifPresent(h -> {
        Building n = world.neighborBuilding(x, y, h.direction());
        if (n != null && n.canAccept(h.item())) {
            moves.add(new Move(source, n, h.item()));
        }
    });
});
// Фаза 2: МЕНЯЕМ мир по собранному плану.
for (Move m : moves) {
    m.source().removeOutput();
    m.target().accept(m.item());
}
```

Планирование смотрит на мир в состоянии «начало тика» — до единой правки. Поэтому
каждый предмет двигается ровно на одну клетку, независимо от порядка обхода. Это
двухфазное обновление: **разделить решение (что делать) и действие (сделать)**.

### Решение 3 (и граница): полная копия мира (двойной буфер)

Радикальный способ той же честности — держать ДВЕ копии мира: читаем из «текущей»,
пишем в «следующую», в конце тика меняем их местами. Так устроен классический
клеточный автомат. Верно и просто рассуждать, но копировать весь мир каждый тик —
дорого, а в чанковом мире «весь мир» ещё и не собрать в один массив. Нам хватает
списка передач: изменения точечные, а не «каждая клетка». Двухфазность мы берём, а
двойной буфер — нет: он избыточен для редких точечных передач.

### Границы применимости

Двухфазность нужна там, где результат обязан быть **независимым от порядка обхода**
и «одновременным». Если действия и так независимы (как `update` каждого здания в L3 —
бур копает сам по себе), фаза сбора не нужна, она была бы лишней церемонией. И одного
разделения фаз мало: когда на одну клетку претендуют ДВА отправителя, нужен арбитр —
«кто первый застолбил». Это следующий приём (штамп версии, шаг 4).

### Где так делают

- **Игра «Жизнь» Конвея** и любой клеточный автомат: нельзя читать уже обновлённые
  клетки — сначала считаем новое поколение, потом заменяем.
- **React**: фаза *render* (вычислить, каким должен быть UI, ничего не трогая) и фаза
  *commit* (применить к DOM) — то же разделение «решить / сделать».
- Дискретно-событийные симуляции, планировщики: собрать план шага, затем исполнить.

**Куда почитать:** R. Nystrom, [Game Programming Patterns](https://gameprogrammingpatterns.com/double-buffer.html)
(глава «Double Buffer» — про ту же честность «читать старое, писать новое»).

## ШАГ 1. `Handoff` и протокол передачи (⏱ 25 мин)

### Зачем

Чтобы здания могли передавать предметы, им нужен общий **язык**: «что я готов отдать
и куда» (`output`), «примешь ли ты вот это» (`canAccept`), «прими» (`accept`), «я
отдал, убери из выхода» (`removeOutput`). Это четыре метода контракта `Building` —
их реализуют ВСЕ здания.

### Предскажи-1

Вы добавляете в `sealed interface Building` четыре абстрактных метода. Сколько ошибок
компиляции и в каких файлах вы получите ДО того, как тронете `Miner` и `Chest`?
Запишите догадку, сверьтесь: [П1](L04-solutions.md#п1).

### Что должно уметь

```java
// model/Handoff.java — пара «предмет + куда»
public record Handoff(Item item, Direction direction) { }
```

```java
// model/Building.java — добавка к контракту:
Optional<Handoff> output();       // что готов отдать соседу (и в какую сторону)
boolean canAccept(Item item);     // приму ли это прямо сейчас
void accept(Item item);           // принять в себя
void removeOutput();              // убрать отданное из выхода
```

### 🧠 Приём шага: узкий протокол вместо «толстых» зданий

Четыре маленьких метода — это **протокол**: минимальный набор операций, которого
достаточно симуляции, чтобы двигать предметы, ничего не зная о конкретном здании.
Бур, ящик, будущая печь — все разные внутри, но снаружи говорят на одном языке
`output/canAccept/accept`. Симуляция работает с интерфейсом, а не с классами
(«программируй к интерфейсу» — GoF). Добавите печь в L8 — `moveItems` не изменится ни
на строку: печь просто реализует тот же протокол.

### 🚫 Как без этого

```java
// «Пусть симуляция сама разбирается, кто что умеет»:
world.forEachBuilding((x, y, b) -> {
    if (b instanceof Miner m) { /* достать руду из бура руками */ }
    else if (b instanceof Chest c) { /* положить в ящик руками */ }
    else if (b instanceof Furnace f) { /* ... */ }
});
// Симуляция знает внутренности КАЖДОГО здания; добавили печь — правим симуляцию;
// instanceof-лесенка без гарантий полноты. Протокол переворачивает это: знание
// живёт в здании, симуляция знает лишь четыре метода.
```

### ⚙️ Алгоритм

1. Создайте `model/Handoff.java`: `public record Handoff(Item item, Direction direction) { }`.
2. В `Building` добавьте четыре метода протокола (сигнатуры выше). `Handoff` лежит
   в том же пакете `model` — импорт не нужен; добавьте только `com.rustorio.core.Item`.
   → Компилятор: `Miner is not abstract and does not override abstract method
   output()` (и то же про `Chest`) — список задач на шаги 2–3.

### Как проверить

Пока не компилируется — и это правильно: `Miner`/`Chest` доделаете в шагах 2–3.
Компилятор держит «карту задач».

💡 Подсказка: [П1](L04-solutions.md#п1) · 📄 Решение: [Р1](L04-solutions.md#р1)

## ШАГ 2. `Miner` отдаёт руду (⏱ 25 мин)

### Зачем

Бур из L3 добывал и держал. Теперь он **отдаёт**: `output()` показывает готовую руду
с направлением, `removeOutput()` очищает выход — и, освободившись, бур копает снова
(вот и конец клиффхэнгера L3).

### Тест-ворота шага

Протокол бура проверяем в **существующем** `MinerTest` из L3 — допишите хелпер и два
теста (`Handoff` в том же пакете, импорт не нужен):

```java
    // ── Протокол передачи (L4) ────────────────────────────────────────

    /** Прогнать бур на руде до готовой руды на выходе. */
    private static Miner minerWithOre() {
        Miner miner = new Miner(Direction.EAST);
        miner.setOnOre(true);
        for (int i = 0; i < 10; i++) {
            miner.update(tick());
        }
        return miner;
    }

    @Test
    void minerExposesDugOreAsHandoff() {
        Miner miner = minerWithOre();                // дано: руда добыта
        assertEquals(Optional.of(new Handoff(Item.IRON_ORE, Direction.EAST)),
                miner.output(), "выход — руда в сторону взгляда бура");
    }

    @Test
    void minerDigsAgainAfterOutputRemoved() {
        Miner miner = minerWithOre();                // дано: выход занят, бур застыл
        miner.removeOutput();                        // когда: потребитель забрал руду
        assertTrue(miner.outputItem().isEmpty(), "выход освободился");
        for (int i = 0; i < 10; i++) {
            miner.update(tick());
        }
        assertEquals(Optional.of(Item.IRON_ORE), miner.outputItem(),
                "тогда: бур закрутился снова — это конец клиффхэнгера L3");
    }
```

Запустить их прямо сейчас не выйдет: проект не компилируется, пока `Chest` не закроет
контракт (шаг 3). Это нормально — тесты подождут два шага.

### Что должно уметь

```java
@Override public Optional<Handoff> output()      // Handoff(руда, dir), если выход не пуст
@Override public boolean canAccept(Item item)    // false: бур — источник, не принимает
@Override public void accept(Item item)          // ничего: буру нельзя ничего отдать
@Override public void removeOutput()             // выход пуст (output = null)
```

### Предскажи-2

Бур добыл руду (`output != null`). В L3 его `update` на следующем тике сразу выходил
(`if (output != null ...) return;`) и больше не копал. Что теперь позволит ему копать
снова — и КТО вызовет нужный метод? Ответ: [П2](L04-solutions.md#п2).

### ⚙️ Алгоритм

1. `output()`: если `output == null` → `Optional.empty()`, иначе
   `Optional.of(new Handoff(output, dir))`.
2. `canAccept` → `false`; `accept` → пустое тело с комментарием; `removeOutput` →
   `output = null;`.
   → Ошибка компиляции про `Miner` ушла — осталась только про `Chest` (шаг 3).
   Поле `output` у вас с L3, метод `update` не трогаем.

### Как проверить

Компилятор больше не ругается на `Miner` (только на `Chest`). Передачи ещё нет
(систему пишем в шаге 5), но контракт бур теперь выполняет полностью — новые тесты
подтвердят это в конце шага 3.

💡 Подсказка: [П2](L04-solutions.md#п2) · 📄 Решение: [Р2](L04-solutions.md#р2)

## ШАГ 3. `Chest` принимает и считает (⏱ 20 мин)

### Зачем

Ящику из L2/L3 было нечего делать. Теперь он — приёмник: `accept` увеличивает
счётчик, `items()` отдаёт его отрисовке.

### Тест-ворота шага

Новый файл `src/test/java/com/rustorio/model/ChestTest.java` — вставьте целиком:

```java
package com.rustorio.model;

import com.rustorio.core.Item;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

/** Протокол передачи у ящика: принимает всё, считает, наружу не отдаёт. */
class ChestTest {

    @Test
    void acceptCountsItems() {
        Chest chest = new Chest();                   // дано: пустой ящик
        assertEquals(0, chest.items());
        chest.accept(Item.IRON_ORE);                 // когда: принял два предмета
        chest.accept(Item.IRON_PLATE);
        assertEquals(2, chest.items());              // тогда: счётчик равен двум
    }

    @Test
    void chestAcceptsAnythingAndNeverOutputs() {
        Chest chest = new Chest();
        assertTrue(chest.canAccept(Item.IRON_ORE));
        chest.accept(Item.IRON_ORE);
        assertTrue(chest.canAccept(Item.IRON_PLATE), "ящик бездонный: принимает всегда");
        assertTrue(chest.output().isEmpty(), "ящик — конечная точка: наружу не отдаёт");
    }
}
```

### Что должно уметь

```java
private int items;

@Override public Optional<Handoff> output()     // empty: ящик наружу не отдаёт
@Override public boolean canAccept(Item item)   // true: примет что угодно
@Override public void accept(Item item)         // items++
@Override public void removeOutput()            // ничего: отдавать нечего
public int items()                              // для счётчика на экране
```

### ⚙️ Алгоритм

1. Добавьте поле `private int items;`.
2. Реализуйте четыре метода протокола: `output` → empty; `canAccept` → true;
   `accept` → `items++`; `removeOutput` → пусто. Плюс геттер `items()`.
   → Теперь `Building` компилируется целиком: обе реализации закрыли контракт.

### Как проверить

`./gradlew test` — проект снова собирается, `ChestTest` (2 теста) и пополневший
`MinerTest` (5 тестов) зелёные. Протокол обоих зданий подтверждён ещё до того, как
написана система, которая им пользуется.

💡 Подсказка: [П3](L04-solutions.md#п3) · 📄 Решение: [Р3](L04-solutions.md#р3)

## ШАГ 4. Штамп версии: `Tile.claim` и методы `World` (⏱ 30 мин)

### Зачем

Прежде чем писать передачу, нужен арбитр на случай, когда в одну клетку целятся двое.
Наивный способ — массив «занятых клеток», который каждый тик создают и обнуляют. В
чанковом мире такого массива не построить (нет общего числа клеток). Приём **штамп
версии** решает это одним числом.

### Тест-ворота шага

Новый файл `src/test/java/com/rustorio/sim/TransferTest.java` — пока вставьте только
каркас и тест штампа (остальные два теста добавите в шаге 5). Он красный, работаете
до зелёного.

```java
package com.rustorio.sim;

import com.rustorio.core.Direction;
import com.rustorio.model.World;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

class TransferTest {

    @Test
    @DisplayName("Штамп версии: за один тик клетку столбит ровно один сосед")
    void claimAllowsOnlyOneClaimPerCellPerTick() {
        World world = World.generate(5, 5);
        world.beginTick();
        // Оба претендуют на клетку (2,1): слева-направо и справа-налево.
        assertTrue(world.claimNeighbor(1, 1, Direction.EAST), "первый сосед столбит (2,1)");
        assertFalse(world.claimNeighbor(3, 1, Direction.WEST), "второй в тот же тик — уже занято");
        world.beginTick(); // новый тик — прошлые штампы устарели
        assertTrue(world.claimNeighbor(3, 1, Direction.WEST), "на новом тике клетка снова свободна");
    }
}
```

### 🧠 Приём шага: штамп версии вместо массива отметок

Клетка помнит **номер тика**, на котором её заняли (`claimedTick`). «Занята» ⇔
`claimedTick == текущий тик`. Наступил новый тик (`beginTick` увеличил счётчик) — и
все прошлые отметки автоматически «протухли», обнулять миллион клеток не нужно.
Счётчик тика живёт в `World` (рядом со штампами на клетках), а не в `Simulation`:
иначе новая симуляция над тем же миром начала бы счёт с нуля и наткнулась на чужие
штампы. Цену приёма назовём вслух: в данных клетки поселилось поле, нужное только
симуляции, — осознанный размен (как «грязный флаг» в графике).

**Где так делают.** Это не наша выдумка, приём живёт в самом JDK: у `ArrayList` есть
поле `modCount` — счётчик модификаций списка. Итератор запоминает его при создании и
на каждом шаге сверяет: число изменилось — список трогали в обход итератора, лети
[`ConcurrentModificationException`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/ConcurrentModificationException.html).
Та же идея «версия вместо отметок»: одно увеличенное число разом обесценивает все
прошлые снимки. В кэшах и рендерах это зовут generation counter — «поколение» данных:
вместо инвалидации каждого элемента поштучно увеличивают номер поколения.

### 🚫 Как без этого

```java
// Массив отметок «в эту клетку уже кладут», создаём заново каждый тик:
boolean[][] claimed = new boolean[width][height];   // а в чанковом мире width×height
// ...обнулять каждый тик, миллион ячеек...          // не собрать: клетки ленивые!
```

Штамп заменяет создание-и-обнуление целого массива на `tick++`.

### ⚙️ Алгоритм

1. В `Tile` добавьте поле `private int claimedTick = -1;` и пакетно-приватный
   `boolean claim(int tick)`: если `claimedTick == tick` → `false`; иначе
   `claimedTick = tick; return true;`.
2. В `World` добавьте поле `private int tick;`, публичный `beginTick()` (`tick++`),
   `claimNeighbor(x, y, dir)` (сосед в пределах поля → `tile(nx, ny).claim(tick)`) и
   `neighborBuilding(x, y, dir)` (возвращает `@Nullable Building`, без `Optional` —
   это горячий путь). Импорты `Direction`, `Nullable`.
   → Тест штампа зелёный.

### Как проверить

`TransferTest.claimAllowsOnlyOneClaimPerCellPerTick` зелёный.

💡 Подсказка: [П4](L04-solutions.md#п4) · 📄 Решение: [Р4](L04-solutions.md#р4)

## ШАГ 5. `Simulation.moveItems`: двухфазная передача (⏱ 40 мин)

### Зачем

Ядро лекции: вторая система симуляции. Она собирает передачи (фаза 1, только чтение),
потом применяет (фаза 2). Штамп из шага 4 гарантирует «один предмет в клетку за тик».

### Тест-ворота шага

Допишите в `TransferTest` два теста (импорты `Config`, `TickContext`, `Tool`,
`Building`, `Chest`, `assertEquals`):

```java
    /** Прогнать N тиков симуляции над этим миром. */
    private static void stepTimes(World world, int n) {
        Simulation simulation = new Simulation(world);
        TickContext ctx = new TickContext(Config.TICK);
        for (int i = 0; i < n; i++) {
            simulation.step(ctx);
        }
    }

    @Test
    @DisplayName("Бур наполняет соседний ящик")
    void minerFillsAdjacentChest() {
        World world = World.generate(20, 20);
        assertTrue(world.tile(6, 5).hasOre(), "предусловие: под (6,5) руда");
        world.place(6, 5, Building.create(Tool.MINER, Direction.EAST).orElseThrow());
        world.place(7, 5, Building.create(Tool.CHEST, Direction.EAST).orElseThrow());
        stepTimes(world, 60);
        assertTrue(((Chest) world.tile(7, 5).building()).items() >= 1,
                "ящик должен получить хотя бы один предмет");
    }

    @Test
    @DisplayName("Бур без руды под собой ничего не отдаёт")
    void minerWithoutOreProducesNothing() {
        World world = World.generate(20, 20);
        assertFalse(world.tile(0, 0).hasOre(), "предусловие: под (0,0) руды нет");
        world.place(0, 0, Building.create(Tool.MINER, Direction.EAST).orElseThrow());
        world.place(1, 0, Building.create(Tool.CHEST, Direction.EAST).orElseThrow());
        stepTimes(world, 60);
        assertEquals(0, ((Chest) world.tile(1, 0).building()).items());
    }
```

### ⚙️ Алгоритм

1. В `Simulation` добавьте поле-буфер `private final List<Move> moves = new
   ArrayList<>();` и приватный `private record Move(Building source, Building target,
   Item item) { }`. Буфер живёт между тиками и чистится в начале — не создаём список
   заново каждый шаг.
2. `step(ctx)`: сначала `world.beginTick();`, затем `runMachines(ctx);` (из L3),
   затем новый `moveItems();`.
3. `moveItems()`:
   - `moves.clear();`
   - **Фаза 1** — `world.forEachBuilding((x, y, source) -> { ... })`: взять
     `source.output()`; если пусто — выйти; достать `item` и `neighborBuilding` по
     `handoff.direction()`; если сосед `null` или `!canAccept(item)` — выйти; и только
     потом `if (world.claimNeighbor(x, y, dir)) moves.add(new Move(source, receiver, item));`.
     **Столбим клетку ПОСЛЕДНЕЙ**: если сосед успел раньше, права занимать её нет.
   - **Фаза 2** — `for (Move m : moves) { m.source().removeOutput(); m.target().accept(m.item()); }`.
   → Оба теста передачи зелёные.

### 🔍 Трасса одного тика (свяжите с L3)

```
Simulation.step(ctx)
 ├─ world.beginTick()                 ← tick++, клетки «разштампованы»
 ├─ runMachines(ctx)                  ← бур: cooldown дозрел → output = IRON_ORE
 └─ moveItems()
      фаза 1 (только чтение):
        бур(6,5).output() = Handoff(IRON_ORE, EAST)
        neighborBuilding(6,5,EAST) = ящик(7,5); canAccept? да
        claimNeighbor(6,5,EAST) → (7,5).claim(tick)=true → moves += Move(бур, ящик, руда)
      фаза 2 (запись):
        бур.removeOutput()  → выход пуст → на следующем тике бур копает снова
        ящик.accept(руда)   → items++
```

### Как проверить

`TransferTest` целиком зелёный (3 теста). Игра запускается без исключений.
