## 0. Что мы делаем — в трёх предложениях

Появляется лента — здание, которое **несёт** предмет: держит один груз и толкает его
вперёд. Всё движение вы получаете **бесплатно**, реализовав уже знакомый протокол L4:
`Simulation` не изменится ни на строку, а цепочка «бур → лента → лента → ящик»
поедет. Это лекция про главную выгоду хорошего интерфейса — **новое поведение без
правки старого кода**.

## 🧠 Теория: протокол вместо частного случая — паспорт приёма

*15 минут чтения.*

### Имя и источник

**Рус.:** протокол вместо частного случая (открытый список реализаций общего
интерфейса). **Англ.:** program to an interface, not an implementation —
принцип открытости/закрытости (Open/Closed Principle, «О» из SOLID).

Первоисточники: **Bertrand Meyer, *Object-Oriented Software Construction*, 2-е
издание (1997), глава 3 «Modularity»** — там принцип сформулирован впервые
(«open if… available for extension», «closed if… available for use»); и
**Gamma, Helm, Johnson, Vlissides, *Design Patterns: Elements of Reusable
Object-Oriented Software* (1994), глава 1** — раздел «Program to an Interface,
not an Implementation», и **глава 5 «Behavioral Patterns»** — паттерн
**«Стратегия» (Strategy)**, частным случаем которого является наше решение
(взаимозаменяемый алгоритм за общим интерфейсом).

### Проблема (на материале игры)

Нужно, чтобы предметы ехали по лентам. Напрашивается: «допишу в симуляцию систему,
которая двигает ленты». Но подумайте, что это значит: симуляция начнёт **знать про
устройство ленты**. А завтра — про печь, сборщик, развилку. Есть ли способ добавить
ленту, **не трогая симуляцию вообще**?

### Конкурирующие решения

**Решение 1: частный случай в симуляции.**

```java
// В Simulation.step — отдельная система «двигать ленты»:
private void moveBelts() {
    world.forEachBuilding((x, y, b) -> {
        if (b instanceof Belt belt) {
            // лезем во внутренности ленты: берём её предмет, ищем соседа,
            // перекладываем... — симуляция теперь знает, КАК устроена лента
        }
    });
}
```

Работает. Но симуляция срослась с лентой: изменится лента — меняем симуляцию;
появится второй переносчик (подземка в L10) — ещё одна система-двойник,
копирующая двухфазную логику `moveItems` (сбор → штамп клетки → исполнение,
~15 строк) почти дословно. И снова `instanceof`-разбор, за которым никто не
следит на полноту.

**Решение 2: здание двигает себя само.**

```java
// В Belt.update — толкнуть предмет соседу самостоятельно:
public void update(TickContext ctx) {
    Building next = /* ...а откуда лента знает соседа? своих координат у неё нет! */;
}
```

Даже не «работает, но хуже» — **не работает вовсе**: у здания нет ссылки на карту
и свои координаты, значит, самостоятельно найти соседа ему нечем. Двигать через
соседей может только тот, у кого есть карта, — симуляция.

**Решение 3 (наше): лента говорит на общем протоколе.**

```java
public final class Belt implements Building {
    private @Nullable Item item;
    public Optional<Handoff> output() {           // отдаю груз вперёд
        return item == null ? Optional.empty() : Optional.of(new Handoff(item, dir));
    }
    public boolean canAccept(Item i) { return item == null; } // свободна?
    public void accept(Item i) { this.item = i; }             // приняла
    public void removeOutput() { this.item = null; }          // отдала
}
```

`Simulation` — **ни одной новой строки.** Цепочка лент едет, потому что для
`moveItems` лента неотличима от любого источника с выходом.

### 🚫 Доказательство: во что обходится отказ от протокола

Если бы мы пошли по Решению 1, конкретная цена расширения при каждом новом
переносящем здании (подземка L10, манипулятор и т.п.):
**+1 метод-двойник в `Simulation`, +1 ветка `instanceof`, и copy-paste всей
двухфазной логики арбитража клетки** (`claim`, сбор `Move`, исполнение) —
именно то, что уже написано один раз в `moveItems`. Скопировать легко; забыть
поправить копию при следующем изменении протокола — тоже легко, и это баг,
который компилятор не ловит: тесты по одной ленте останутся зелёными, а второй
переносчик тихо разъедется в поведении.

### Где так делают

- **`java.util.List`**: код против интерфейса `List` работает с `ArrayList`,
  `LinkedList`, `CopyOnWriteArrayList` — новую реализацию добавляют, вызывающий код
  не трогают.
- **Паттерн «Стратегия»** (GoF, гл. 5): взаимозаменяемый алгоритм прячут за
  интерфейсом, и вызывающий код работает с любой реализацией, не меняясь. Самый
  знакомый пример — `Comparator`: `list.sort(comparator)` сортирует по любому
  правилу сравнения, а сам `sort` при этом не трогают. Любая плагинная
  архитектура — то же в большом масштабе: расширяемся новыми реализациями
  интерфейса, ядро закрыто.

### Границы применимости

Приём держится, **пока поведение ленты влезает в протокол** «один выход, один приём».
Настоящая лента возит НЕСКОЛЬКО грузов и рисует их плавно между клетками — этого
протокол `output/accept` не выражает. Когда абстракция перестаёт вмещать
поведение, честный ход — не городить костыли, а **сменить абстракцию** (транспортные
линии со слотами) под защитой тестов. Ровно это L6–L7: старые тесты движения должны
пройти не изменившись — тогда рефакторинг доказанно ничего не сломал. Сегодня же нам
хватает «одного предмета на клетку».

### Связь с принципом

Это и есть **принцип открытости/закрытости** (О из SOLID, Meyer): код *открыт для
расширения* (новое здание) и *закрыт для изменения* (старая симуляция не тронута).
Работает он благодаря тому, что симуляция зависит от **протокола** (`Building`), а
не от конкретных классов — «программируй к интерфейсу» (GoF).

**Куда почитать:** SOLID, буква O (Open/Closed Principle); R. Martin, *Clean
Architecture* (гл. про OCP).

## ШАГ 1. `Belt`: здание-переносчик (⏱ 30 мин)

### Зачем

Лента держит один предмет и отдаёт его вперёд. Ничего не «работает» в `update` —
движение делает `moveItems`. Вся лента — это реализация протокола L4.

### Тест-ворота шага

Новый файл `src/test/java/com/rustorio/sim/MovementTest.java` — вставьте целиком, он
красный (нет класса `Belt`), работаете до зелёного.

```java
package com.rustorio.sim;

import com.rustorio.core.Config;
import com.rustorio.core.Direction;
import com.rustorio.core.Item;
import com.rustorio.core.TickContext;
import com.rustorio.core.Tool;
import com.rustorio.model.Belt;
import com.rustorio.model.Building;
import com.rustorio.model.Chest;
import com.rustorio.model.World;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

/**
 * Тесты ДВИЖЕНИЯ предметов по лентам (L5). Лента переиспользует протокол передачи из
 * L4 — {@code Simulation} не менялась, а цепочки уже едут.
 */
class MovementTest {

    private static void step(World world) {
        new Simulation(world).step(new TickContext(Config.TICK));
    }

    private static void stepTimes(World world, int n) {
        Simulation simulation = new Simulation(world);
        TickContext ctx = new TickContext(Config.TICK);
        for (int i = 0; i < n; i++) {
            simulation.step(ctx);
        }
    }

    @Test
    @DisplayName("Цепочка бур → лента → лента → ящик доставляет руду")
    void minerBeltChestDelivers() {
        World world = World.generate(20, 20);
        int x = 6, y = 5; // центр залежи руды
        assertTrue(world.tile(x, y).hasOre(), "предусловие: под (6,5) руда");
        world.place(x, y, Building.create(Tool.MINER, Direction.EAST).orElseThrow());
        world.place(x + 1, y, Building.create(Tool.BELT, Direction.EAST).orElseThrow());
        world.place(x + 2, y, Building.create(Tool.BELT, Direction.EAST).orElseThrow());
        world.place(x + 3, y, Building.create(Tool.CHEST, Direction.EAST).orElseThrow());

        stepTimes(world, 60);

        assertTrue(((Chest) world.tile(x + 3, y).building()).items() >= 1,
                "ящик за цепочкой лент должен получить хотя бы один предмет");
    }

    @Test
    @DisplayName("Передача по ленте — это перемещение, а не копирование (ровно на клетку)")
    void itemMovesExactlyOneCellPerTick() {
        World world = World.generate(4, 1);
        world.place(0, 0, Building.create(Tool.BELT, Direction.EAST).orElseThrow());
        world.place(1, 0, Building.create(Tool.BELT, Direction.EAST).orElseThrow());
        ((Belt) world.tile(0, 0).building()).accept(Item.IRON_ORE);

        step(world);

        assertTrue(((Belt) world.tile(0, 0).building()).item().isEmpty(),
                "источник должен опустеть");
        assertEquals(Item.IRON_ORE, ((Belt) world.tile(1, 0).building()).item().orElse(null),
                "приёмник должен получить ровно тот же предмет");
    }

    @Test
    @DisplayName("Две ленты в одну клетку кладут ровно один предмет за тик (штамп)")
    void twoBeltsIntoOneMoveOnlyOne() {
        World world = World.generate(3, 1);
        world.place(0, 0, Building.create(Tool.BELT, Direction.EAST).orElseThrow());  // → (1,0)
        world.place(1, 0, Building.create(Tool.BELT, Direction.EAST).orElseThrow());
        world.place(2, 0, Building.create(Tool.BELT, Direction.WEST).orElseThrow());  // → (1,0)
        ((Belt) world.tile(0, 0).building()).accept(Item.IRON_ORE);
        ((Belt) world.tile(2, 0).building()).accept(Item.IRON_PLATE);

        step(world);

        assertTrue(((Belt) world.tile(1, 0).building()).item().isPresent(),
                "средняя лента должна получить один предмет");
        boolean leftHeld = ((Belt) world.tile(0, 0).building()).item().isPresent();
        boolean rightHeld = ((Belt) world.tile(2, 0).building()).item().isPresent();
        // `^` для boolean — исключающее ИЛИ: истинно, когда верно РОВНО одно из двух.
        assertTrue(leftHeld ^ rightHeld,
                "ровно один источник остался с грузом — второй не пролез в занятую клетку");
    }
}
```

К третьему тесту — деталь, которую стоит заметить: победитель на самом деле всегда
один и тот же (обход детерминирован по сетке кусков, левая лента идёт первой). Тест
нарочно не прибивает это гвоздями — `^` допускает любого из двух: «кто первый в
обходе» — деталь реализации, а не обещание протокола. Но несправедливость «первый в
обходе выигрывает всегда» настоящая — это называется **голоданием** (starvation)
второго источника (термин — для кругозора, на защите не спросят); чинить её будет
L10 («честная очередь выходов»).

### Что должно уметь

```java
// model/Belt.java
public final class Belt implements Building {
    public Belt(Direction dir)
    @Override public void update(TickContext ctx)      // пусто: движение — дело moveItems
    @Override public Optional<Handoff> output()        // Handoff(груз, dir), если не пуста
    @Override public boolean canAccept(Item incoming)  // свободна ⇔ item == null
    @Override public void accept(Item incoming)        // положить груз
    @Override public void removeOutput()               // отдала — стала пустой
    @Override public Optional<Direction> direction()
    public Direction dir()                             // для отрисовки
    public Optional<Item> item()                       // для отрисовки груза
}
```

### 🧠 Приём шага: движение как следствие протокола

Обратите внимание, чего в `Belt` НЕТ: ни поиска соседа, ни `claim`, ни «переложить».
Лента только **отвечает на вопросы** протокола («что отдаёшь?», «примешь?») и хранит
один предмет. Двигает — `moveItems`. Разделение: здание знает СВОЁ состояние,
симуляция знает ПРАВИЛА передачи. Поэтому одна и та же система возит и руду от бура, и
груз по ленте.

### 🚫 Как без этого

```java
// Лента сама себя двигает в update — «толкну предмет соседу»:
public void update(TickContext ctx) {
    Building next = /* ...а откуда лента знает соседа? своих координат у неё нет! */;
}
// Тупик: здание не знает, где стоит. Двигать через соседей может только тот, у кого
// есть карта — симуляция. Лента и не должна: её дело — хранить и отвечать протоколу.
```

### Предскажи-1

`moveItems` вы в этой лекции не открываете. Почему тогда цепочка лент поедет? Что
именно в ленте позволяет L4-системе двигать её груз, не зная, что это лента? Ответ:
[П1](L05-solutions.md#п1).

### ⚙️ Алгоритм

1. **Подготовка теста:** вставьте `MovementTest`. → Красный: `cannot find symbol:
   class Belt`.
2. **Каркас класса:** создайте `Belt implements Building`. Поле `private final
   Direction dir;` и `private @Nullable Item item;` (импорт
   `org.jspecify.annotations.Nullable`).
3. **Реализация протокола передачи:** `output()` — `item == null ? empty :
   Optional.of(new Handoff(item, dir))`; `canAccept` — `item == null`; `accept` —
   `this.item = incoming`; `removeOutput` — `item = null`. `update` — пустое тело с
   комментарием.
4. **Служебные методы для отрисовки:** `direction()` → `Optional.of(dir)`; чтения
   `dir()`, `item()` (→ `ofNullable`). → Компилируется? Пока НЕТ: `Belt` ещё не в
   `permits` (это шаг 2). Тесты запустятся после шага 2.

### Как проверить

После шага 2 — `MovementTest` зелёный. Здесь же: класс написан, протокол закрыт.

## ШАГ 2. Включить ленту: `permits` + `create` (⏱ 15 мин)

### Зачем

Лента написана, но вне закона: её нет в `permits`, и фабрика её не делает. Добавим —
и компилятор превратится в чек-лист по всем `switch`, где не хватает ветки `Belt`.

### Предскажи-2

## ШАГ 3. Отрисовка: лента и груз на ней (⏱ 35 мин)

### Зачем

Видимый результат: спрайт ленты, повёрнутый по направлению и анимированный (бегущая
дорожка), и груз, едущий по клеткам к ящику.

### Что должно уметь

- `BuildingRenderer.renderSprites` получает **настенное время** `elapsed` (для смены
  кадров ленты) и рисует ленту повёрнутым спрайтом.
- `BuildingRenderer.renderOverlays`: у ленты стрелки нет — `case Belt _ -> { }`.
- `ItemRenderer.render`: `case Belt` рисует груз ленты **по центру** клетки.
- `Renderer` копит `elapsed += delta` и передаёт в `renderSprites`.

### 🧠 Приём шага: анимация — на настенных часах, не на тике

Кадр «бегущей дорожки» ленты меняется по РЕАЛЬНОМУ времени (`elapsed`), а не по тику
симуляции. Это важно: анимация — украшение, она **не меняет мир** и потому может
идти с частотой кадров. `ArchitectureTest` даже запрещает домену трогать «настенные
часы» — но рендеру они законны. Отсюда `elapsed` живёт в `Renderer`, а не в модели.

### 🚫 Как без этого — почему груз «прыгает», и чем плоха альтернатива

Сегодня груз рисуется в центре той клетки, где он лежит **сейчас**. Симуляция шагает
5.5 раза в секунду, поэтому на экране предмет перескакивает клетка-в-клетку. Плавное
скольжение (интерполяция по `tickAlpha` между прошлой и текущей клеткой) — это L6–L7,
где предмет получит дробную позицию. Сегодня прыжки — честное упрощение, а не баг.

Соблазн: привязать кадр анимации к номеру тика (`tickCount % 2`) вместо `elapsed`.
Тогда дорожка меняла бы кадр рывками (5,5 раза в секунду, а не плавно) и **замирала
бы на паузе** вместе с миром — хотя окно открыто и рендер продолжает рисовать кадры.
Кадры дорожки — украшение, миру не принадлежат: им положено настенное время.

### ⚙️ Алгоритм

1. **Спрайт ленты:** в `BuildingRenderer` — константа `BELT_ANIM_SPEED = 4.0f`;
   смените сигнатуру `renderSprites(World, TileRange, float elapsed)`. Ветка:
   ```java
   case Belt belt -> {
       int frame = (int) (elapsed * BELT_ANIM_SPEED) % 2;
       batch.draw(textures.belt[frame], px, py, TILE / 2, TILE / 2,
               TILE, TILE, 1f, 1f, beltRotation(belt.dir()));
   }
   ```
   Хелпер `beltRotation(Direction)` (угол по направлению, спрайт нарисован вдоль East)
   — из решения. В `renderOverlays` — `case Belt _ -> { }`.
2. **Груз на ленте:** в `ItemRenderer` — `case Belt belt -> belt.item().ifPresent(it ->
   drawItemCentered(px, py, it));` и приватный `drawItemCentered` (в центре клетки).
3. **Настенные часы:** в `Renderer` — поле `private float elapsed;`, в `render` —
   `elapsed += delta;` и вызов `renderSprites(world, visible, elapsed);`.
   → `./gradlew run`.

### 🔍 Трасса одного тика (свяжите с L4)

```
Simulation.step(ctx)                       ← НЕ ИЗМЕНИЛСЯ ни на строку
 ├─ world.beginTick()
 ├─ runMachines(ctx)                        ← бур копает, если готов
 └─ moveItems()                             ← код L4; лента для него — просто Building
      фаза 1 (только чтение):
        лента(7,5).output() = Handoff(IRON_ORE, EAST)   ← Belt.output(), не Simulation
        neighborBuilding(7,5,EAST) = лента(8,5); canAccept? да (item == null)
        claimNeighbor(7,5,EAST) → (8,5).claim(tick)=true → moves += Move(лента7, лента8)
      фаза 2 (запись):
        лента(7,5).removeOutput() → item = null → готова принять следующую
        лента(8,5).accept(руда)   → item = IRON_ORE → на следующем тике сама источник
```

Один тик — один шаг вдоль цепочки; поэтому в тесте `minerBeltChestDelivers` даётся
с запасом 60 тиков, чтобы руда успела пройти бур → лента → лента → ящик.

### Как проверить (видимый результат лекции)

Клавиша **1** → бур на руду; **2** → протяните ЛКМ несколько лент на восток от бура;
**4** → ящик в конце. Руда едет по ленте (груз перескакивает клетка-в-клетку) и
копится в ящике — счётчик растёт. Лента визуально «бежит».

💡 Подсказка: [П3](L05-solutions.md#п3) · 📄 Решение: [Р3](L05-solutions.md#р3)

## ШАГ 4. Эксперименты (⏱ 15 мин)

Правки временные — откатывайте их точечно, той же правкой в обратную сторону
(НЕ `git restore .`: в дереве есть несохранённый код лекции).

### Э1. Доказать, что симуляция не менялась

Выполните `git diff --stat src/main/java/com/rustorio/sim/Simulation.java`. Изменений
— **ноль**. Вся лекция добавила поведение (лента едет), не тронув симуляцию. Это и
есть Open/Closed вживую: сравните с тем, что было бы, впиши вы `moveBelts` в `step`.

### Э2. Сломать проходимость (проверяем заблуждение «canAccept знает про направления»)

Поставьте бур, две ленты, ящик — но вторую ленту разверните (клавиша `R`) навстречу
первой. Сначала случится неожиданное: встречная лента груз **примет** — `canAccept`
смотрит только «свободна ли я» и ничего не знает про направления, так что груз может
даже метнуться назад (встречная лента честно отдаёт его по своему `dir`). Но как
только бур подложит второй предмет, обе ленты окажутся заняты и заблокируют друг
друга навсегда: каждая может отдать только в занятую соседку. Поток встал — затор
виден на экране. Проговорите вслух: протокол «один выход, один приём» не умеет
выразить «принимаю только сзади» — ещё одна граница абстракции, которую расширит
L6–L7. Разверните обратно.

### Э3. Убрать `Belt` из `permits`

Закомментируйте `Belt` в `permits`. Компилятор посыплется:
`class is not allowed to extend sealed class: Building (as it is not listed in
its 'permits' clause)` (в самом `Belt`) и `the switch statement does not cover all
possible input values` — во всех `switch`, куда вы добавляли ветку. Это тот же
чек-лист, что вёл вас в шаге 2, только наоборот. Верните.
