<a id="разогрев"></a>
## Р+ — Ответы разминки (одной строкой, не подглядывая до попытки)

1. Линия — один объект со списком предметов на целочисленных слотах, а не N
   независимых зданий; `assertInvariants()` проверяет, что клетки идут подряд по
   направлению и что предметы не пересекаются и не идут не по порядку (два в одном
   слоте или нарушенный порядок слотов).
2. `Tile.claim` — штамп «эту клетку уже застолбили в этом тике»; защищает от
   ситуации, когда два соседа за один тик попытаются положить предмет в одну и ту
   же клетку — присвоение проходит только у первого застолбившего.
3. Чтобы результат не зависел от порядка обхода зданий: в фазе 1 только читаем и
   собираем список запланированных передач, в фазе 2 применяем — иначе здание,
   обработанное раньше по случайному порядку обхода, получало бы незаслуженное
   преимущество.
4. Инвариант за фасадом — правило, которое объект поддерживает САМ, не полагаясь
   на вызывающий код; в вашем коде — например, `BeltSegment` сам не даёт двум
   предметам оказаться в одном слоте (через `canInsertAt`), а не полагается на то,
   что вызывающий код проверит это сам.

<a id="п1"></a>
## П1 — Что происходит с передней линией при склейке

Подсказка: посмотрите на код L6 внутри `if (front != null) { ... }` — он уже
считает сдвиг `(newTileIndex + 1) * SLOTS`, просто раньше до него не доходило
исполнение при непустом `back`.

Ответ на «Предскажи-1»: позиции предметов передней линии ДОЛЖНЫ сдвинуться —
на `(длина задней линии в клетках + 1) × SLOTS_PER_TILE` слотов, потому что перед
ними встаёт задняя линия ПЛЮС наша новая клетка. Без сдвига предметы передней
линии оказались бы на неправильных (слишком маленьких) номерах слотов внутри новой
объединённой линии — визуально они «телепортировались» бы назад.

<a id="р1"></a>
## Р1 — `onBeltPlaced`: снимаем ограничение

```java
    /**
     * На клетку поставили ленту. Четыре случая:
     * <ol>
     *   <li>соседей нет — новая линия из одной клетки;</li>
     *   <li>есть линия СЗАДИ (везёт в нас) — клетка становится её новой головой;</li>
     *   <li>есть линия СПЕРЕДИ (мы повезём в неё) — клетка становится её хвостом;</li>
     *   <li>есть и сзади, и спереди — <b>СКЛЕЙКА</b>: две линии и наша клетка → одна.</li>
     * </ol>
     * Случай 4 — тот самый, где предметы удваиваются или пропадают: позиции
     * предметов передней линии обязаны сдвинуться на длину задней плюс нашу клетку.
     */
    void onBeltPlaced(Cell cell, Belt belt) {
        Direction dir = belt.dir();
        BeltSegment back = segmentOfBeltAt(cell.x() - dir.dx(), cell.y() - dir.dy(), dir);
        BeltSegment front = segmentOfBeltAt(cell.x() + dir.dx(), cell.y() + dir.dy(), dir);

        List<Cell> tiles = new ArrayList<>();
        List<BeltItem> items = new ArrayList<>();

        if (back != null) {
            tiles.addAll(back.tiles());
            items.addAll(back.rawItems());
            segments.remove(back);
        }

        int newTileIndex = tiles.size();
        tiles.add(cell);

        if (front != null) {
            int shift = (newTileIndex + 1) * SLOTS;
            for (BeltItem it : front.rawItems()) {
                it.slot += shift;
                it.prevSlot += shift;
                items.add(it);
            }
            tiles.addAll(front.tiles());
            segments.remove(front);
        }

        createSegment(dir, tiles, items);
    }
```

Единственное отличие от L6 — строка `BeltSegment front =
segmentOfBeltAt(cell.x() + dir.dx(), cell.y() + dir.dy(), dir);` без тернарного
условия «только если back == null». Весь остальной метод был готов к склейке уже
в L6.

```java
    int shift = newTileIndex * SLOTS; // ← забыли +1 — не учли саму новую клетку
```

<a id="п2"></a>
## П2 — Куда попадает предмет на снесённой клетке и как пересчитывается правая половина

Подсказка: снесённая клетка `k` занимает ПОЛУИНТЕРВАЛ слотов
`[k·SLOTS, (k+1)·SLOTS)`. Всё вне этого полуинтервала распределяется по сторонам,
внутри — уничтожается.

Ответ на «Предскажи-2»: предмет ровно на снесённой клетке (индекс 2, слоты `[4,
6)` при `SLOTS=2`) попадает НИ В ОДНУ из половин — он легально уничтожается
(комментарий кода: «иначе предмет стоял на снесённой клетке — уничтожен»).
Предмет с клетки 4 (слоты `[8, 10)` в исходной линии) после разреза (`cutTo = 6`)
получает новый слот `slot - cutTo`, то есть уезжает на 6 слотов назад: клетка 4
исходной линии становится клеткой с индексом 1 в НОВОЙ правой линии (`right`),
и её слоты внутри неё — `[2, 4)`, что и проверяет тест
(`right.countItemsOnTile(1)`).

<a id="р2"></a>
## Р2 — `onBeltRemoved`: честный разрез

```java
    /**
     * С клетки убрали ленту: линия разрезается надвое.
     *
     * <p>Предметы делятся по слоту. Границы {@code <} и {@code >=} здесь —
     * то самое место, где рождается «ошибка на единицу»: предмет, попавший в обе
     * половины, — это удвоение, не попавший ни в одну — потеря. Предмет, стоявший
     * НА снесённой клетке, уничтожается вместе с ней — это законно: игрок снёс
     * ленту с грузом.
     */
    void onBeltRemoved(Cell cell, Belt belt) {
        BeltSegment segment = belt.segment();
        if (segment == null) {
            return;
        }
        int k = belt.indexInSegment();
        List<Cell> tiles = segment.tiles();
        segments.remove(segment);
        belt.detach();

        int cutFrom = k * SLOTS;          // первый слот снесённой клетки
        int cutTo = (k + 1) * SLOTS;      // первый слот ЗА снесённой клеткой

        List<BeltItem> leftItems = new ArrayList<>();
        List<BeltItem> rightItems = new ArrayList<>();
        for (BeltItem it : segment.rawItems()) {
            if (it.slot < cutFrom) {
                leftItems.add(it); // позиции не меняются: хвост остался на месте
            } else if (it.slot >= cutTo) {
                it.slot -= cutTo;
                it.prevSlot = Math.max(0, it.prevSlot - cutTo);
                rightItems.add(it);
            }
            // иначе предмет стоял на снесённой клетке — уничтожен
        }

        List<Cell> leftTiles = new ArrayList<>(tiles.subList(0, k));
        List<Cell> rightTiles = new ArrayList<>(tiles.subList(k + 1, tiles.size()));

        if (!leftTiles.isEmpty()) {
            createSegment(segment.dir(), leftTiles, leftItems);
        }
        if (!rightTiles.isEmpty()) {
            createSegment(segment.dir(), rightTiles, rightItems);
        }
    }
```

`Math.max(0, it.prevSlot - cutTo)` — `prevSlot` мог быть МЕНЬШЕ `cutTo` (предмет
только что въехал на этот слот с прошлого тика) — без ограничения снизу интерполяция
рендера на один кадр показала бы отрицательный, бессмысленный слот.

### ❌ Частые неправильные варианты (шаг 2)

```java

    ...
}

// условие — молча «уничтожится», хотя должен был уехать направо. Три сценарных

// на операции №302 при фиксированном зерне 42.
```

```java

// subList(0, k+1) включает индекс k — снесённую клетку — в ЛЕВУЮ половину.
```

<a id="п3"></a>
## П3 — Почему фиксированное зерно обязательно

Подсказка: `Random()` без аргумента берёт seed из текущего времени — при каждом
запуске он другой.

Ответ на «Предскажи-3»: НЕТ, без фиксированного зерна воспроизвести падение нельзя
— при следующем запуске `Random()` выберет ДРУГОЙ seed, и последовательность
операций будет уже другой, так что упавшая вчера комбинация действий, скорее
всего, просто не повторится. С `new Random(42)` тест гарантированно проходит ТОЧНО
ТЕ ЖЕ 2000 операций в том же порядке при каждом запуске — упавший тест
воспроизводим, и можно спокойно отлаживать именно операцию №302 (а не гадать,
какая последовательность была вчера).

<a id="билет"></a>
## Ответы на выходной билет

1. Убедительнее — потому что перебирает тысячи комбинаций длин/позиций/порядка
   операций, которые автор сценарных тестов физически не может придумать все
   сразу; не заменяет — потому что не документирует конкретное намерение так же
   ясно, как `@DisplayName`-сценарий, и труднее локализовать причину падения.
2. Чтобы падение было ВОСПРОИЗВОДИМЫМ: тот же seed даёт ту же последовательность
   случайных операций при каждом запуске — иначе баг, найденный сегодня, завтра
   может просто не проявиться снова.
3. `Belt.java`, `BeltSegment.java`, `World.java`, `Simulation.java` — не менялись
   вообще; это доказывает, что границы, проведённые в L4–L6 (протокол передачи,
   линия как объект, вызовы `onBeltPlaced`/`onBeltRemoved` из `World`), оказались
   ровно там, где нужно: вся сложность сегодняшней лекции уместилась в ОДНОМ файле.
