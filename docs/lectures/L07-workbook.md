## 0. Что мы делаем — в трёх предложениях

В L6 транспортная линия — объект, который умеет ехать, но не умеет по-настоящему
редактироваться: снос ленты из середины убивал всю линию, а лента в промежуток
между двумя готовыми линиями не склеивала их. Сегодня `BeltNetwork` дописывается до
конца: склейка и честный разрез без потери и удвоения предметов. А чтобы ДОКАЗАТЬ,
что это действительно работает — не в трёх придуманных случаях, а всегда, —
появляется property-тест: две тысячи случайных построек, сносов и шагов симуляции,
после каждой из которых код сам себя проверяет.

## 🆕 Новое в языке

**`java.util.Random`** — генератор псевдослучайных чисел. У него есть конструктор
С СЕМЕНЕМ (seed): `new Random(42)` делает последовательность чисел
ВОСПРОИЗВОДИМОЙ — тот же seed при каждом запуске даёт ТУ ЖЕ последовательность.
Без явного seed (`new Random()`) программа берёт seed из текущего времени —
последовательность меняется от запуска к запуску, и упавший тест невозможно
повторить.

```java
Random a = new Random(42);
Random b = new Random(42);
a.nextInt(10) == b.nextInt(10); // всегда true — оба генератора видят одно семя
```

**Куда почитать:** [Javadoc — `java.util.Random`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Random.html).

## 🧠 Теория: тестирование по свойствам — паспорт приёма

*20 минут чтения.*

### Имя и источник

**Рус.:** тестирование по свойствам (property-based testing). **Англ.:**
property-based testing.

**Источник:** Koen Claessen & John Hughes, *«QuickCheck: A Lightweight Tool for
Random Testing of Haskell Programs»*, ICFP 2000 — статья, представившая технику и
получившая в 2010 году приз «самая влиятельная статья ICFP 2000» за десятилетие
влияния на индустрию тестирования.

### Проблема (на материале игры)

`BeltNetworkTest` из L6 (первый тест) проверял ОДИН сценарий: пять лент подряд —
одна линия. Сегодняшние склейка и разрез — это код, где ошибка на единицу в
границе слота теряет или удваивает предмет. Сколько бы сценариев мы ни придумали
руками (склейка ровно посередине; разрез ровно по центру; разрез у самого края) —
автор тестов подвержен ТЕМ ЖЕ слепым пятнам, что и автор кода: если не подумал про
конкретную комбинацию длин и позиций, тест её не проверит.

### Конкурирующие решения

**Решение 1: писать больше сценарных тестов.** Работает, и такие тесты нужны — они
документируют КОНКРЕТНОЕ намерение и сразу говорят, что именно сломалось. Но
каждый новый тест — это ещё один случай, придуманный ЧЕЛОВЕКОМ; исчерпать все
комбинации длин, позиций и порядка операций вручную нереально.

**Решение 2 (наше): проверить ИНВАРИАНТ на множестве СЛУЧАЙНЫХ последовательностей
операций.** Вместо «вот эти три сценария работают» — «сколько ни случайно строй и
сноси ленты, число предметов меняется ТОЛЬКО легально (создал/уничтожил), и линия
всегда остаётся внутренне непротиворечивой». Компьютер перебирает случаи, а не
автор теста.

**Решение 3 (упомянуть, не сегодня): формальная верификация/model checking** —
доказать свойство математически, а не проверить на выборке случаев. Мощнее, но
не входит в бюджет курса; property-тест — практичный средний путь между «несколько
сценариев» и «полное доказательство».

### 🚫 Доказательство: конкретный баг, который ловит только Решение 2

Мы проверили это по-настоящему при подготовке лекции: заменили `it.slot >= cutTo`
на `it.slot > cutTo` в разрезе (граница «на единицу» не там) — **все три сценарных
теста остались зелёными** (ни один не ставил предмет ровно на нужный слот), а
property-тест **упал на операции №302** с сообщением `expected: <2> but was: <1>` —
предмет незаметно потерялся. Вот конкретная цена отказа от property-теста: этот баг
ушёл бы в игру необнаруженным, и три «умных» сценарных теста ничего бы не заметили.

### Где так делают

**jqwik** — движок property-based тестирования для JUnit 5
(<https://jqwik.net>) — прямой потомок QuickCheck для нашего стека: генерирует
случайные входные данные и проверяет объявленное свойство. Сегодняшний тест мы
написали руками, тем же принципом (генератор случайных действий + проверка
инварианта после каждого), без библиотеки — это тоже честный, распространённый
подход, когда операции — не просто данные, а последовательность вызовов с
состоянием.

### Границы применимости

Property-тест силён для ИНВАРИАНТОВ («что всегда должно быть истинно»), но не
заменяет конкретные документирующие тесты: «вот баг №123, который мы уже ловили» —
`@DisplayName`-сценарий читается человеком яснее, чем случайная последовательность
из двух тысяч операций. При падении property-теста ещё и сложнее ЛОКАЛИЗОВАТЬ
причину (см. «Для сильных» №3) — короткий сценарный тест сразу показывает, что
именно сломалось. Хорошая практика — держать ОБА вида тестов, как у нас: три
сценарных плюс один property.

### Связь с принципом

Продолжение приёма L6 — **рефакторинг под защитой тестов** (Fowler): property-тест
— это САМАЯ СИЛЬНАЯ защита именно для рефакторингов, трогающих инварианты
структуры данных (как сегодняшний разрез/склейка), потому что он не ограничен
воображением автора теста.

## ШАГ 1. Склейка: снимаем ограничение (⏱ 20 мин)

### Зачем

В L6 `onBeltPlaced` присоединялся только к линии СЗАДИ, если линии были с обеих
сторон сразу. Сегодня — четвёртый случай эталона: если сзади И спереди уже есть
готовые линии, наша клетка сшивает их в одну.

### Тест-ворота шага

Новый файл `src/test/java/com/rustorio/model/BeltNetworkTest.java` — вставьте
целиком. Первый тест (`beltsInARowFormOneSegment`) сразу ЗЕЛЁНЫЙ — это наследство
L6 (случаи 1–3 уже работали). Второй (`placingBetweenTwoSegmentsMergesThem`) —
красный.

```java
package com.rustorio.model;

import com.rustorio.core.Config;
import com.rustorio.core.Direction;
import com.rustorio.core.Item;
import com.rustorio.core.Tool;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.util.Random;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertSame;

/**
 * Тесты сборки и разборки линий (L7) — самое тонкое место игры.
 *
 * <p>Здесь предметы теряются и удваиваются: при разрезе ошибка на единицу в
 * границе отправляет предмет либо в обе половины, либо ни в одну. Поэтому в конце
 * стоит property-тест: тысяча случайных построек и сносов с проверкой того, что
 * предметы не рождаются и не пропадают сами по себе.
 */
class BeltNetworkTest {

    private static void placeBelt(World world, int x, Direction dir) {
        world.place(x, 0, Building.create(Tool.BELT, dir).orElseThrow());
    }

    private static BeltSegment segmentAt(World world, int x) {
        Belt belt = (Belt) world.tile(x, 0).building();
        assertNotNull(belt, "на (" + x + ",0) должна быть лента");
        BeltSegment segment = belt.segment();
        assertNotNull(segment, "лента должна быть привязана к линии");
        return segment;
    }

    private static void checkAll(World world) {
        for (BeltSegment segment : world.belts().segments()) {
            segment.assertInvariants();
        }
    }

    @Test
    @DisplayName("Пять лент в ряд — это ОДНА линия, а не пять")
    void beltsInARowFormOneSegment() {
        World world = World.generate(8, 1);
        for (int x = 0; x < 5; x++) {
            placeBelt(world, x, Direction.EAST);
        }
        checkAll(world);

        assertEquals(1, world.belts().segments().size());
        BeltSegment segment = segmentAt(world, 0);
        assertEquals(5, segment.tileCount());
        assertEquals(5 * Config.SLOTS_PER_TILE, segment.lengthSlots());
        for (int x = 1; x < 5; x++) {
            assertSame(segment, segmentAt(world, x));
        }
    }

    @Test
    @DisplayName("Лента, построенная МЕЖДУ двумя линиями, склеивает их — предметы целы")
    void placingBetweenTwoSegmentsMergesThem() {
        World world = World.generate(8, 1);
        placeBelt(world, 0, Direction.EAST);
        placeBelt(world, 1, Direction.EAST);   // линия A: клетки 0,1
        placeBelt(world, 3, Direction.EAST);
        placeBelt(world, 4, Direction.EAST);   // линия B: клетки 3,4
        assertEquals(2, world.belts().segments().size());

        segmentAt(world, 0).insert(Item.IRON_ORE, 0);     // предмет в хвосте A
        segmentAt(world, 3).insert(Item.IRON_PLATE, 0);   // предмет в хвосте B
        assertEquals(2, world.belts().itemCount());

        placeBelt(world, 2, Direction.EAST); // ← склейка
        checkAll(world);

        assertEquals(1, world.belts().segments().size(), "должна остаться одна линия");
        BeltSegment merged = segmentAt(world, 0);
        assertEquals(5, merged.tileCount());
        assertEquals(2, world.belts().itemCount(), "предметы не потерялись и не удвоились");

        assertEquals(1, merged.countItemsOnTile(0), "предмет линии A — на клетке 0");
        assertEquals(1, merged.countItemsOnTile(3), "предмет линии B — по-прежнему на клетке 3");
    }

    @Test
    @DisplayName("Снос середины разрезает линию надвое; предмет на снесённой клетке уничтожен")
    void removingMiddleSplitsSegment() {
        World world = World.generate(8, 1);
        for (int x = 0; x < 5; x++) {
            placeBelt(world, x, Direction.EAST);
        }
        BeltSegment segment = segmentAt(world, 0);
        segment.insert(Item.IRON_ORE, 0);                          // клетка 0
        segment.insert(Item.IRON_PLATE, 2 * Config.SLOTS_PER_TILE); // клетка 2 — её снесут
        segment.insert(Item.IRON_ORE, 4 * Config.SLOTS_PER_TILE);   // клетка 4
        assertEquals(3, world.belts().itemCount());

        world.remove(2, 0); // ← разрез
        checkAll(world);

        assertEquals(2, world.belts().segments().size(), "должно стать две линии");
        assertEquals(2, world.belts().itemCount(),
                "уничтожен ровно один предмет — тот, что стоял на снесённой клетке");

        BeltSegment left = segmentAt(world, 0);
        BeltSegment right = segmentAt(world, 3);
        assertEquals(2, left.tileCount());
        assertEquals(2, right.tileCount());
        assertEquals(1, left.countItemsOnTile(0), "предмет левой половины на месте");
        assertEquals(1, right.countItemsOnTile(1), "предмет правой половины пересчитан верно");
    }

    @Test
    @DisplayName("Никакая последовательность построек и сносов не создаёт и не теряет предметы")
    void itemsAreConservedUnderRandomEdits() {
        // Зерно фиксировано: упавший тест должен воспроизводиться.
        Random random = new Random(42);
        int width = 10;
        World world = World.generate(width, 1);
        int expected = 0;

        for (int op = 0; op < 2000; op++) {
            int x = random.nextInt(width);
            switch (random.nextInt(4)) {
                case 0 -> // построить ленту (всегда EAST: тогда одинаковую не пересоздаём)
                        placeBelt(world, x, Direction.EAST);
                case 1 -> {
                    // снести ленту: законно уничтожаются предметы, стоявшие на ней
                    if (world.tile(x, 0).building() instanceof Belt belt) {
                        BeltSegment segment = belt.segment();
                        assertNotNull(segment);
                        expected -= segment.countItemsOnTile(belt.indexInSegment());
                        world.remove(x, 0);
                    }
                }
                case 2 -> {
                    // положить предмет на ленту
                    if (world.tile(x, 0).building() instanceof Belt belt
                            && belt.canAccept(Item.IRON_ORE)) {
                        belt.accept(Item.IRON_ORE);
                        expected++;
                    }
                }
                default -> world.belts().step(Config.BELT_SLOTS_PER_TICK);
            }

            checkAll(world);
            assertEquals(expected, world.belts().itemCount(),
                    "после операции №" + op + " число предметов разошлось с ожидаемым");
        }
    }
}
```

### Предскажи-1

В `onBeltPlaced` из L6 было условие «если сзади есть линия — переднюю не ищем
вовсе» (`front = back == null ? ... : null`). Что случится с предметами передней
линии при склейке — их позиции остаются как есть или должны сдвинуться? На сколько
слотов? Ответ: [П1](L07-solutions.md#п1).

### 🧠 Приём шага: склейка — это не новый случай, а снятие ограничения

Взгляните на код `onBeltPlaced` из L6: он уже умел строить список клеток и
предметов из ЗАДНЕЙ линии и добавлять свою клетку. Код для ПЕРЕДНЕЙ линии (сдвиг
слотов на длину задней части плюс новая клетка) там уже был написан — L6 просто не
давал ему сработать, когда сзади уже что-то нашлось. Убрать ограничение — значит
довериться уже написанной арифметике сдвига.

### ⚙️ Алгоритм

1. **Снять ограничение:** в `onBeltPlaced` замените тернарный поиск `front` на
   безусловный: ищите линию СПЕРЕДИ независимо от того, нашлась ли линия сзади.

## ШАГ 2. Честный разрез: `onBeltRemoved` целиком (⏱ 40 мин)

### Зачем

Сегодня — самый рискованный код лекции: разрезать список клеток и список
предметов на «левую» и «правую» половины так, чтобы ни один предмет не потерялся
и не продублировался.

### Предскажи-2

Линия из 5 клеток (индексы 0..4), сносим клетку с индексом 2. Предмет стоит РОВНО
на снесённой клетке. В какую половину он попадёт — левую, правую, ни в одну? А
предмет, стоявший на клетке с индексом 4 (после сдвига позиций) — на каком слоте
он окажется в НОВОЙ правой линии? Ответ: [П2](L07-solutions.md#п2).

### Что должно уметь

```java
// model/BeltNetwork.java (правки)
void onBeltRemoved(Cell cell, Belt belt)   // честный разрез, а не снос всей линии
```

### 🧠 Приём шага: где рождается «ошибка на единицу»

Снесённая клетка с индексом `k` занимает слоты `[k·SLOTS, (k+1)·SLOTS)` — это
ПОЛУИНТЕРВАЛ: левая граница включена, правая — нет. Всё, что СТРОГО МЕНЬШЕ
`k·SLOTS` (`cutFrom`), — левая половина, БЕЗ изменения позиций (хвост остался
хвостом). Всё, что БОЛЬШЕ ЛИБО РАВНО `(k+1)·SLOTS` (`cutTo`), — правая половина, СО
сдвигом позиций на `cutTo` (у правой половины теперь новый, свой хвост). Всё, что
попало МЕЖДУ (`cutFrom <= slot < cutTo`) — стояло на снесённой клетке и легально
уничтожается. Три диапазона, ни одного пропуска и ни одного пересечения между
ними — вот что не даёт предмету продублироваться или потеряться.

### 🚫 Как без этого — исчисляемая цена ошибки на единицу

```java
// Всего один символ не так — здесь `>` вместо `>=`:
} else if (it.slot > cutTo) {
    // ...
}
// Предмет РОВНО на слоте cutTo (первый слот правой половины) не попадёт
// НИ В ОДНО из условий (не < cutFrom, не > cutTo) — он тихо пропадает,
// как будто стоял на снесённой клетке, хотя на самом деле должен был
// уехать в правую линию. Три сценарных теста (см. шаг 1) этого не поймают:
// ни один из них не ставит предмет ровно на этот слот. Ловит только
// property-тест — см. эксперимент Э1 ниже.
```

### ⚙️ Алгоритм

1. **Захват фактов о клетке — до сноса:** сохраните `k = belt.indexInSegment()` и
   `tiles = segment.tiles()`, уберите сегмент из `segments`, отвяжите саму
   снесённую клетку (`belt.detach()`).
2. **Границы разреза:** `cutFrom = k * SLOTS` (первый слот снесённой клетки),
   `cutTo = (k + 1) * SLOTS` (первый слот ЗА ней).
3. **Три диапазона — разбор предметов:** пройдите по `segment.rawItems()`: `slot <
   cutFrom` → в `leftItems` без изменений; `slot >= cutTo` → сдвиньте `slot`/
   `prevSlot` на `cutTo` назад и добавьте в `rightItems`; иначе — предмет на
   снесённой клетке, никуда не добавляется (уничтожен).
4. **Две новых линии:** `leftTiles = tiles.subList(0, k)`, `rightTiles =
   tiles.subList(k + 1, tiles.size())`; если список не пуст — `createSegment` для
   каждой половины (использует уже написанный в L6 метод без изменений).
   → `removingMiddleSplitsSegment` зелёный.

### Как проверить

`removingMiddleSplitsSegment` зелёный; `placingBetweenTwoSegmentsMergesThem` и
`beltsInARowFormOneSegment` по-прежнему зелёные.

💡 Подсказка: [П2](L07-solutions.md#п2) · 📄 Решение: [Р2](L07-solutions.md#р2)
