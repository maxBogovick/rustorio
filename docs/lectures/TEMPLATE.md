# Канон рабочей тетради

> Эталон канона — **[L02-workbook.md](L02-workbook.md)** + **[L02-solutions.md](L02-solutions.md)**.
> Все тетради обязаны иметь ту же структуру: читатель всегда знает, где искать
> «зачем», где «что писать», где «почему именно так» и где «я застрял».
>
> Блоки v2 (Ц «Цели лекции», Р+ «Разогрев-повторение», «Выходной билет»,
> 🧩 Parsons, задание «с ИИ») добавлены в канон 16.07.2026. В L0–L5 их нет —
> это норма: лекции, написанные по v1, задним числом не переписываются.
>
> Правило номер один: **в тетради нет ни одной строчки готового решения шага.**
> Код живёт в `L<NN>-solutions.md`, куда ведут ссылки. Пока читатель не перешёл —
> ответ ему на глаза не попадается. (Тесты-ворота — исключение: они спецификация,
> а не решение, и даются в тетради целиком.)

## 1. Обязательные части тетради (в этом порядке)

| # | Раздел | Что в нём | Зачем |
|---|--------|-----------|-------|
| — | **Шапка** | ссылка на решения; две ступени 💡→📄; «заглянуть — не поражение»; сложность 🟢/🟡/🔴; зависимости от лекций; общее время с выделенной долей теории | правила игры видны сразу |
| П | **Что нужно знать до** | чек-лист пререквизитов со ссылками (dev.java и т.п.); что объяснено внутри и знать заранее не нужно | студент не тонет и не листает в панике |
| Р+ | **Разогрев-повторение** | 3–4 вопроса на ВСПОМИНАНИЕ прошлых лекций, отвечать не подглядывая; ≥1 вопрос из L≤NN−3 (для NN<3 — из любой предыдущей); ответы одной строкой в solutions; подпись «разминка памяти, не проверка»; ≤12 строк | retrieval practice: вспоминание закрепляет лучше перечитывания |
| 0 | **Что мы делаем — в трёх предложениях** | суть, видимый результат, роль лекции в курсе | прочитал только это — всё равно понял главное |
| Ц | **Цели лекции** | 3–5 измеримых целей «после лекции могу <глагол Блума>…» (объяснить → применить → спроектировать/оценить; «понимать»/«знать» запрещены), каждая со ссылкой на место проверки (тест-ворота / видимый результат / вопрос защиты / билет); ≤8 строк | backward design: цель без проверки — не цель |
| Я | **🆕 Новое в языке** | КАЖДАЯ языковая конструкция, встречающаяся в лекции впервые: что это, минимальный пример, зачем, ссылка на JEP/dev.java. Если конструкций нет — раздел опускается | главный источник когнитивной перегрузки гасится ДО шагов |
| Т | **🧠 Теория: шаблон крупным планом** | центральный приём лекции по **паспорту приёма**: имя (рус/англ + ТОЧНЫЙ первоисточник: автор, книга/глава или статья), проблема на материале игры, 2–4 конкурирующих решения С КОДОМ, «где так делают» с точным адресом (класс/метод/глава), **границы применимости** (когда приём НЕ подходит и что вместо — обязательно); если приём — проявление именованного принципа (OCP, SRP, «программируй к интерфейсу»…), принцип называется, расшифровывается и показывается на этом же коде — принцип без кода рядом брак | это и есть «лекция»; без неё тетрадь — рабочий листок |
| 1 | **Карта: кирпичи** | ASCII-схема + таблица «файл → одна причина существования» + абзац «не многовато ли классов?» при необходимости | сначала целое, потом детали |
| 2 | **Порядок работы** | таблица `Шаг · Что появляется · Проверка · Бюджет` + правило порога: **1,5 × бюджета → идти в подсказку** | после каждого шага компилируется и зелено; застревание ограничено |
| 3…N | **ШАГИ** | структура шага — см. §2 ниже | человек пишет код сам, но не вслепую |
| — | **Трасса кадра/вызова** | что происходит в runtime после действия игрока, по фазам цикла (обычно внутри «сборочного» шага) | связывает новый код с циклом из L0 |
| N+1 | **Эксперименты** | ломаем нарочно: разбудить стражу (компилятор/ArchUnit/тест), прочитать ошибку, вернуть. Правки временные, `git restore .` | границы гарантий прощупаны руками |
| N+2 | **💪 Для сильных** | 1–3 задания на ПЕРЕНОС (спроектировать на бумаге; тест, который нельзя написать; посчитать/предсказать поведение по коду), не «ещё того же». Одно из заданий (здесь или в экспериментах) — задание «с ИИ» из белого списка форм: «объясни мне код, потом я объясню тебе — найди дыры», «сгенерируй тест и найди, что он НЕ проверяет», «прожарь моё объяснение тремя вопросами»; занимает существующий слот, не сверх; форма «напиши за меня» запрещена (правило L0). Только материал, доступный студенту в его репозитории — никаких отсылок к внешним путям/репозиториям. Ответов в решениях нет — это проговаривается первой строкой блока | сильные не скучают, слабых не пугает: «по желанию»; ИИ — тренажёр объяснений, не автор кода |
| — | **Выходной билет** | 3 вопроса самопроверки на 2 минуты: по памяти, письменно, одной фразой; ответы в solutions; НЕ дублируют вопросы защиты (билет — себе, защита — преподавателю); ≤8 строк | testing effect: самопроверка до защиты |
| N+3 | **Что считается «сделано»** | чек-лист `[ ]`, включая «могу объяснить вслух: …» | объективная граница готовности |
| N+4 | **Вопросы на защите** | 5–7 вопросов преподавателю для устной проверки | отсекает бездумное копирование (в т.ч. из ИИ) |
| N+5 | **Шпаргалка: симптом → где искать** | таблица «что видите → куда смотреть», сообщения компилятора — ДОСЛОВНЫЕ | экономит вечера отладки |
| N+6 | **Если совсем застряли** | 3 шага (таблица шагов → печать состояния → за помощью с картинкой) + ссылка на правила разговора с ИИ из L0 | план на случай «всё пропало» готов заранее |

## 2. Структура одного ШАГА

Порядок внутри шага (пропускать можно только неприменимое):

1. **Заголовок с бюджетом**: `## ШАГ N. <Название> (⏱ NN мин)`.
2. **Зачем** — мотивация в 2–4 предложениях.
3. **Предскажи-N** — вопрос ДО кода с ссылкой на ответ в решениях. Хотя бы 2–3
   предсказания на лекцию, желательно проверяемых машиной (тестом/запуском).
4. **Тест-ворота** (если шаг про модель): готовый тест целиком, red → green,
   с комментариями `// дано / когда / тогда`. Новые термины в тестах (AAA,
   идемпотентность…) объясняются на месте.
5. **Что должно уметь** — голые сигнатуры, без тел.
6. **🧠 Приём шага** (если есть локальный приём: статическая фабрика, инвариант,
   default-метод…) — имя, суть, ТОЧНЫЙ первоисточник, 1 абзац границ; если приём —
   проявление именованного принципа, принцип объясняется на этом же коде.
7. **🚫 Как без этого** — работающий ПЛОХОЙ код + конкретный сценарий боли
   («скомпилируется, тесты зелёные, а через неделю…»). Обязателен для каждого
   приёма; это половина убедительности. **Цена отказа — исчисляемая**: число
   правок/файлов при расширении, невозможный тест, класс молчаливых багов;
   общие слова («так хуже», «неудобно») — брак.
8. **⚙️ Алгоритм** — нумерованные действия с **ожидаемыми состояниями
   компилятора** между ними: «сделай X → компилятор скажет `<дословно>` — это не
   ошибка, это следующая задача». Все сообщения проверены реальным javac
   (см. §5). Группы действий подписываются ЦЕЛЬЮ (subgoal label), а не действием:
   не «добавьте поле tick», а «— *Арбитраж клетки:* 1) поле tick… 2) claim…».
   Уровень детализации — по убыванию от лекции к лекции (faded
   scaffolding): ранние лекции ведут за руку, поздние дают только контракты.
9. **Как проверить** — команда + что увидеть глазами/в тестах.
10. Строка ссылок: `💡 Подсказка: [Пn] · 📄 Решение: [Рn]`.

## 3. Файл решений `L<NN>-solutions.md`

- Шапка-предупреждение: заходить по ссылке из шага, не читать подряд.
- `## Пn — <тема>`: подсказка-направление (НЕ ответ) + ответы на «Предскажи».
- Для 1–2 самых трудных шагов лекции между Пn и Рn допускается **🧩
  Parsons-заготовка**: строки НАСТОЯЩЕГО решения Рn, перемешанные и помеченные
  буквами; задача студента — выписать порядок. Порядок блоков:
  `Пn → 🧩 → строка-предупреждение «⬇ ниже — готовое решение» → Рn`; ссылка из
  шага — тремя ступенями `💡 → 🧩 → 📄`. Если валидных порядков строк несколько —
  сказать это в задании. Markdown не спрячет Рn от скролла — «заглянуть — не
  поражение», как и всюду.
- `## Рn — <тема>`: реализация целиком, **с javadoc и комментариями** — они часть
  ответа. Код совпадает с эталонным проектом 1:1, если срез лекции не требует
  упрощения (тогда — комментарий, какая лекция доведёт до эталона).
- `### ❌ Частые неправильные варианты` — после Р-блоков шагов, где ошибки
  предсказуемы: плохой код + почему компилируется/зеленеет, но неправилен.
- Якоря ссылок из тетради обязаны совпадать с заголовками — проверять глазами.

## 4. Правила тона

- **Каждое «странное» решение объясняется там, где впервые встречается**, а не
  свалкой в начале. Читатель узнаёт «почему» в момент, когда ему это нужно.
- **Ловушки называются заранее, с ценой**: «эта ошибка стоит вечера», «этот баг
  тесты не поймают».
- **Свои ошибки — вслух.** Выяснилось, что план тетради врал (сообщение
  компилятора другое, стража не ловит константы) — так и пишем, с разбором.
  Учебный проект учит и на этом.
- **Никакого «просто сделайте X».** Непонятно, зачем шаг, — это баг тетради.
- **Новые термины** (идемпотентность, инвариант, батчинг…) определяются при
  первом употреблении. Термин без определения — баг тетради.
- Функциональные цепочки (`Optional`, лямбды) впервые показываются **сначала
  многословно, потом свёрнуто**; обе версии объявляются равнозначными.
- Обращение — «вы»; выделения — умеренно; эмодзи — только маркеры блоков
  (🧠 🚫 ⚙️ 🆕 💪 ⏱ 💡 📄).

## 5. Обязанности автора ДО публикации тетради (чек-лист проверки)

Тетрадь, не прошедшая этот чек-лист, не публикуется:

- [ ] **Прогон в рабочем дереве** (правило от 16.07.2026, вместо scratchpad-копии):
      код решений применяется ПРЯМО в исходниках `rustorio_lesson` по мере
      написания шагов — преподаватель видит, что материал работает. Код берётся
      из ЭТАЛОНА (`rustorio`) 1:1, как требует §3, — не пишется с нуля. Отправная
      точка — текущее дерево (в нём уже применены решения предыдущих лекций).
      После каждого шага — компилируется, тесты зелёные; в конце `./gradlew test`
      зелёный → `./gradlew run` без исключений → видимый результат воспроизводим
      (если нельзя кликнуть — временная инъекция состояния, потом убрать).
      Код лекции остаётся в дереве НЕзакоммиченным — коммит за преподавателем.
- [ ] **Каждый эксперимент проделан**: обещали «стража поймает» — сломали и
      увидели; обещали «упадёт тест X со строкой Y» — упал именно он.
      Эксперименты откатываются ТОЧЕЧНОЙ обратной правкой — никогда
      `git restore`/`git checkout`: в дереве нескоммиченный код лекции, массовый
      откат его уничтожит (`git restore .` в тетради — инструкция студенту,
      не автору).
- [ ] **Каждое цитируемое сообщение компилятора** получено от реального javac
      той версии, что в toolchain, и вставлено дословно.
- [ ] **Каждая внешняя ссылка** открыта и ведёт туда, куда обещает.
- [ ] **Каждый внутренний якорь** (П/Р, разделы) проверен.
- [ ] Scratchpad вычищен от временных файлов; в рабочем дереве — только код
      решений лекции (следов экспериментов нет); ничего не закоммичено.
- [ ] Время: сумма бюджетов шагов + теория ≈ заявленному времени в шапке.
- [ ] **Трассировка целей**: таблица «цель → где проверяется» без дыр; каждый
      вопрос защиты замаплен на цель.
- [ ] **Бюджет новизны отчитан поимённо**: 1 центральный шаблон, ≤2 новые
      языковые конструкции, ≤7 новых терминов-понятий (термин = то, что
      выносится на проверку: цели/защита/билет).
- [ ] **🧩 Parsons честный**: строки взяты из реального Рn (сверка дословная) и
      собираются обратно в компилируемый код — собрать вручную и убедиться.
- [ ] **Заблуждения предъявлены**: для каждого заявленного в срезе — конкретное
      место в тексте, где оно расстреляно.
- [ ] **Разогрев и выходной билет — на вспоминание**: вопрос, на который можно
      ответить, перечитав соседний абзац и не вспоминая, — брак.

## 6. Пределы

- Тетрадь ≈ 600–1000 строк, решения ≈ 300–1000. Больше — лекцию надо делить.
- Не влезает в лимит → сужать срез или делить лекцию. Резать ради лимита
  🧠-теорию, 🚫-блоки или шпаргалку — запрещено: это ядро ценности курса.
- Один центральный шаблон (§Т) на лекцию. Два — делить лекцию.
- Каждая лекция заканчивается видимым в игре результатом. Нет видимого
  результата — пересмотреть срез.
