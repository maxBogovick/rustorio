# A8 — Рабочая тетрадь: здание, которое не трогает графику

> **Как этим пользоваться.** Здесь нет ни одной строчки решения — только объяснение,
> **зачем** нужен очередной кусок, **что** он обязан уметь и **как** проверить, что он это
> умеет. Код вы пишете сами.
>
> Когда упрётесь — подсказки и реализации лежат **в отдельном файле**:
> **[A8-solutions.md](A8-solutions.md)**. Из каждого шага туда ведёт ссылка. Пока вы по ней
> не перешли, ответ вам на глаза не попадётся.
>
> Две ступени: **💡 Подсказка** — направление, но не ответ (открывайте, если сидите минут
> пятнадцать). **📄 Решение** — код целиком (открывайте, если и подсказка не помогла, — или
> **после** того, как написали своё, чтобы сравнить).
>
> Заглянуть в решение — **не поражение**. Поражение — сидеть три вечера в одном месте.
>
> **Сложность:** 🟡 · **Зависит от:** трека A (спрайты, атлас) · **Когда делать:** когда в
> игре уже есть несколько зданий и стало больно добавлять новое.

---

## 0. Что мы делаем — в трёх предложениях

Сейчас, чтобы добавить в игру новое здание, приходится открывать слой отрисовки и
дописывать `switch` по типу здания в четырёх местах — иначе код не компилируется.

Мы разворачиваем зависимость: пусть **здание само рассказывает о себе** в игровых терминах
(«у меня стрелка туда, полоска настолько, на мне лежит вот такой предмет»), а слой `render`
просто исполняет этот рассказ.

После этого новое здание добавляется **без единой строчки в графике**: незнакомое зданию
рисуется подписанной плашкой автоматически — и вы весь урок думаете про логику, а не про
пиксели.

---

## 1. Карта: кто про кого знает

Вся суть — в одной стрелке зависимости, которую мы разворачиваем.

```
   БЫЛО (плохо):                         СТАЛО (хорошо):

   render ──switch по типу──▶ Miner      render ──читает──▶ Appearance
          ──switch по типу──▶ Furnace                          ▲
          ──switch по типу──▶ Chest                            │ отдаёт
          ──switch по типу──▶ ...                       Miner/Furnace/...
                                                        (каждое здание)

   новое здание ⇒ 4 правки в графике     новое здание ⇒ 0 правок в графике
```

| Кирпич | Файл | Зачем существует (одна причина) |
|--------|------|--------------------------------|
| `Appearance` | `core/Appearance.java` | Описать «как показать здание» в игровых терминах, **без пикселей** |
| `Building.appearance()` | `model/Building.java` | Единственная «дверь» здания в графику |
| `renderOverlays/Outlines` | `render/BuildingRenderer.java` | Рисуют стрелку/полоску/рамку **по описанию**, не зная типов |
| `renderSprites` | `render/BuildingRenderer.java` | Рисует спрайт известным зданиям, а незнакомым — **плашку** |
| `ItemRenderer` | `render/ItemRenderer.java` | Рисует иконку/счётчик **по описанию** |

**«Не слишком ли много ради одной стрелки?»** Наоборот — мы удаляем код. Четыре `switch`
превращаются в четыре коротких `if (описание говорит...)`. Появляется один новый тип
(`Appearance`) и один метод на здание — а взамен графика перестаёт знать зоопарк зданий, и
каждое новое здание больше её не касается. Это размен «немного данных сейчас — ноль правок
графики на каждом будущем здании».

## 2. Порядок работы

| Шаг | Что появляется | Что уже можно проверить |
|-----|----------------|-------------------------|
| 1 | `Appearance` — дескриптор в `core` | компилируется; `core` ни от кого не зависит |
| 2 | `Building.appearance()` + реализация в 8 зданиях | компилятор провёл по всем зданиям, ни одно не забыто |
| 3 | `render` читает `Appearance` (убираем `switch`) | **игра выглядит ровно как раньше** |
| 4 | новое здание `Buffer` — и ни одной правки в `render` | клавиша 9 ставит буфер; среди ошибок компилятора нет ни одного файла из `render` |

После каждого шага код компилируется, а тесты (`./gradlew test`) зелёные. Если после шага
красно — не идём дальше, чиним здесь.

## ШАГ 1. Дескриптор: как показать здание, не рисуя

### Зачем

Графика знает про каждое здание только потому, что `switch` по типу физически написан в
слое `render`. Уберём знание из графики — перенесём его в **данные**, которые здание отдаёт
о себе. Эти данные должны быть в игровых терминах: не «спрайт номер 3» и не «цвет RGBA», а
«стрелка туда», «прогресс 0.4», «на мне лежит шестерёнка». Тогда описание не тащит за собой
libGDX и спокойно живёт в `core`.

### Что должно уметь

```java
package com.rustorio.core;

/** Как показать здание — в игровых терминах, без единого пикселя. */
public record Appearance(
        String label,          // подпись на плашке, если спрайта нет
        Direction arrow,       // направление стрелки-накладки; null — нет
        boolean working,       // цвет стрелки: работает (зелёная) / простаивает (красная)
        float progress,        // полоска прогресса 0..1; NaN — нет полоски
        boolean alert,         // тревожная рамка (бур не на руде)
        Item icon,             // предмет-иконка на здании; null — нет
        int counter) {         // число на здании; отрицательное — не показывать

    static Appearance of(String label);       // основа: одна подпись, без деталей
    Appearance arrow(Direction dir, boolean working);
    Appearance progress(float fraction);
    Appearance alert(boolean on);
    Appearance icon(Item item);
    Appearance counter(int value);
    boolean hasProgress();                     // не NaN?
    boolean hasCounter();                       // counter >= 0?
}
```

### Почему запись, а не набор геттеров на здании

Можно было бы оставить у здания семь методов (`arrowDirection()`, `progressFraction()`, …).
Но тогда графике пришлось бы **знать, какие из них у какого здания есть** — то есть снова
`switch`. Один самодостаточный `Appearance` собирает все ответы в одном месте, и графика
работает с ним единообразно: у ленты `arrow == null`, у печи — не `null`, а код рисования
один и тот же.

### Почему «пустые» значения — это `null`/`NaN`/`-1`, а не `Optional`

Это горячий путь: `appearance()` зовётся для каждой видимой клетки каждый кадр. Плодить
`Optional` на стрелку, иконку и счётчик — мусор на ровном месте. Sentinel-значения
(`null`, `NaN`, `-1`) здесь честнее, а методы `hasProgress()/hasCounter()` прячут их за
осмысленным именем.

### Почему фабрики (`of/arrow/progress/…`), а не конструктор на семь аргументов

`new Appearance("Furnace", dir, true, 0.4f, false, null, -1)` — ребус. А
`Appearance.of("Furnace").arrow(dir, true).progress(0.4f)` читается как фраза и не даёт
перепутать местами два `boolean`. Каждая фабрика возвращает **новую** запись (она
неизменяемая) — это дёшево и безопасно.

### Как проверить

Код компилируется. `Appearance` лежит в `core` и импортирует только `Direction` и `Item`
(тоже `core`) — ни одного `com.badlogic`. Если тянется что-то из `render` или libGDX — вы
описываете пиксели, а не игру; вернитесь к списку полей.

> 💡 Подсказка: [П1](A8-solutions.md#п1--каркас-appearance) · 📄 Решение: [Р1](A8-solutions.md#р1--appearance-целиком)

## ШАГ 2. Здание рассказывает о себе

### Зачем

Теперь дадим каждому зданию голос. Добавляем в интерфейс `Building` **один** абстрактный
метод — и компилятор тут же покраснеет во всех восьми зданиях: «вы не реализовали
`appearance()`». Это и есть карта задач: идём по ошибкам сверху вниз, ни одно здание не
забудем.

### Что должно уметь

```java
public sealed interface Building ... {
    // ... прежние методы ...

    /** Как меня показать — в игровых терминах. Единственная дверь здания в графику. */
    Appearance appearance();
}
```

Дальше — по зданию на реализацию. Не пишите код сразу; сначала **словами** ответьте на
вопрос «что это здание про себя говорит»:

| Здание | Подпись | Стрелка | Полоска | Рамка | Иконка | Счётчик |
|--------|---------|---------|---------|-------|--------|---------|
| Бур | «Miner» | да, зелёная пока копает | — | тревога, если не на руде | руда на выходе | — |
| Лента | «Belt» | — | — | — | — | — |
| Печь | «Furnace» | да, зелёная пока работает | прогресс плавки | — | что показывает | — |
| Ящик | «Chest» | — | — | — | — | сколько лежит |
| Сборщик | «Assembler» | да, пока работает | прогресс сборки | — | что показывает | — |
| Развилка | «Splitter» | — | — | — | — | — |
| Подземка | «Underground» | — | — | — | — | — |
| Лаборатория | «Lab» | — | прогресс изучения | — | — | сколько очков |

Заметьте: у ленты, развилки и подземки направление **есть**, а стрелки в описании **нет**.
Это не ошибка. Направление у них читается по повороту спрайта, а стрелка-накладка — только
у машин, где важно видеть, куда пойдёт продукт. Описание — про то, что **показать**, а не
про то, что у здания есть внутри.

### Ловушка, которая стоит не ошибки, а путаницы

Соблазн — навесить `appearance()` `default`-методом на интерфейс, чтобы «не писать в каждом
здании». Не надо. Именно то, что метод **абстрактный**, заставляет компилятор потребовать
описание у нового здания — иначе через полгода кто-то добавит здание, забудет `appearance()`,
и оно молча нарисуется пустой безымянной плашкой. Пусть лучше не скомпилируется.

### Как проверить

После реализации во всех восьми — компилируется. Игра пока выглядит **как раньше**: мы лишь
добавили зданиям метод, но графику ещё не переключили на него. Это нормально: шаг 3 —
отдельный.

> 💡 Подсказка: [П2](A8-solutions.md#п2--что-говорит-о-себе-здание) · 📄 Решение: [Р2](A8-solutions.md#р2--appearance-во-всех-зданиях)

## ШАГ 3. Графика начинает слушать

### Зачем

Пока `appearance()` есть, но им никто не пользуется: `render` по-прежнему делает `switch` по
типу. Меняем графику так, чтобы стрелки, полоски, рамки, иконки и счётчики брались из
описания. После этого шага графика перестаёт знать типы зданий — и это **последний раз**,
когда мы вообще открываем `render` в этой истории.

### Что должно уметь

Три `switch` исчезают, один остаётся с запасным выходом:

- **`BuildingRenderer.renderOverlays`** — вместо `switch` по типу: спросить `b.appearance()`
  и, если `arrow != null`, нарисовать стрелку; если `hasProgress()`, нарисовать полоску.
- **`BuildingRenderer.renderOutlines`** — рамку рисуем, если `appearance().alert()`.
- **`ItemRenderer`** — иконку, если `icon != null`; счётчик, если `hasCounter()`.
- **`BuildingRenderer.renderSprites`** — `switch` спрайтов **оставляем** (это «арт» готовых
  зданий), но добавляем ветку `default`, которая рисует **подписанную плашку** для здания
  без спрайта.

### Почему `renderSprites` — единственный, где `switch` уцелел

Спрайты бура, ленты, печи — это анимация и повороты, честная забота графики. Их место —
здесь. Но теперь `switch` не обязан быть исчерпывающим: ветка `default` ловит **любое**
здание без спрайта (в том числе будущее, которого ещё нет) и рисует плашку. Поэтому новое
здание этот `switch` не ломает — оно проваливается в `default`.

### Ловушка: плашке нужны две вещи, которых у `BuildingRenderer` пока нет

Плашка — это крашеный квадрат плюс подпись. Значит, нужны:

1. Белый регион 1×1 в `Textures` (его красят через `batch.setColor`) — иначе нечем рисовать
   заливку в проходе спрайтов.
2. `BitmapFont` в `BuildingRenderer` — его придётся **передать из `Renderer`** в
   конструктор (сейчас шрифт живёт только в `Renderer`).

И отдельная мина: покрасив квадрат через `batch.setColor(...)`, **верните цвет в белый**
сразу после. Иначе следующий спрайт в этом же проходе нарисуется вашим цветом плашки — и вы
полчаса будете гадать, почему печь позеленела.

### Как проверить

Запустите игру (по правилам вашего трека). Она обязана выглядеть **точно как до шага 3**:
те же спрайты, те же стрелки, те же счётчики. Мы не меняли внешний вид — мы поменяли то,
**откуда** графика берёт данные. Если что-то пропало (например, счётчик ящика) — значит,
это здание в шаге 2 не рассказало про себя всю правду; чините описание, не графику.

> 💡 Подсказка: [П3](A8-solutions.md#п3--как-render-читает-описание) · 📄 Решение: [Р3](A8-solutions.md#р3--generic-render)

## ШАГ 4. Награда: новое здание, не открывая графику

### Зачем

Ради этого всё и затевалось. Добавим **буфер** — здание, которое копит до восьми предметов
и отдаёт по одному в свою сторону (сглаживает рывки производства). И убедимся: пройти
придётся по `Tool`, `Building` и сохранению — но **ни разу по `render`**.

### Что должно уметь

```java
public final class Buffer implements Building {
    Buffer(Direction dir);
    Buffer(Direction dir, List<Item> contents);   // для загрузки сохранения
    // update / output / canAccept / accept / removeOutput / direction / appearance
    List<Item> contents();                          // для снимка сохранения
}
```

Буфер играет по **обычному** протоколу `Building`: `output()` называет головной предмет и
направление, стандартная фаза передачи сама доставит его соседу. Никакой новой фазы в
`Simulation` не нужно — только данные и договор.

### Порядок — идите по ошибкам компилятора

1. Написали класс `Buffer` — он ещё ни к чему не подключён.
2. Добавили `Tool.BUFFER("Buffer", 9)` — теперь `Building.create` не компилируется
   (`switch` по `Tool` неполон). Чините — добавляете ветку `case BUFFER`.
3. Добавили `Buffer` в `permits` интерфейса `Building` — теперь не компилируется
   `SaveService` (`switch` по зданию неполон). Чините.
4. `LoadService` тоже покраснел (`switch` по `Tool`). Чините.

**Смотрите на список файлов, которые вы открывали**: `core/Tool`, `model/Buffer`,
`model/Building`, `persist/*`. Ни одного из `render/`. Графика провалила буфер в `default`
и нарисовала плашку с подписью «Buffer», стрелкой и счётчиком — по его же `appearance()`.

### Про сохранение — маленькая честная работа

Буфер хранит список предметов. В снимке `BuildingDto` для этого нужно **своё поле** (рядом
с уже существующими `machine`, `splitter`, `underground` — это тот же приём «поле на
здание»). Схема сохранения при этом растёт **аддитивно**: старый сейв без нового поля
читается новым кодом — поле становится пустым. Поднимите `SCHEMA_VERSION`.

### Как проверить

- Клавиша **9** выбирает буфер, он ставится на поле и виден как подписанная плашка.
- Поставьте бур → буфер → ленту. Буфер копит и отдаёт, счётчик на нём меняется.
- F5/F9: после загрузки предметы в буфере на месте.
- Загляните в `git diff --stat`: среди изменённых файлов **нет ни одного из `render/`**.

> 💡 Подсказка: [П4](A8-solutions.md#п4--как-провести-buffer-по-цепочке) · 📄 Решение: [Р4](A8-solutions.md#р4--buffer-и-сохранение)

## Шпаргалка: симптом → где искать

| Что видите | Куда смотреть |
|------------|---------------|
| `Appearance` не компилируется, тянет libGDX | описываете пиксели вместо игры — уберите всё, кроме `Direction`/`Item` |
| Здание рисуется пустой плашкой без подписи | в `appearance()` не задан `label` (или забыли `Appearance.of(...)`) |
| Пропал счётчик/иконка после шага 3 | здание не рассказало про них в `appearance()` — правьте описание, не графику |
| Печь/бур позеленели после шага 3 | не вернули `batch.setColor(Color.WHITE)` после плашки |
| Новое здание не появляется по клавише | забыли `hotkeySlot` в `Tool` или ветку в `Building.create` |
| Старый сейв не грузится | сломали аддитивность — новое поле должно быть `@Nullable` и не ломать чтение |
| Компилятор гонит вас в `render` при новом здании | в `render` остался исчерпывающий `switch` без `default` — вы не доделали шаг 3 |

## Если совсем застряли

1. Вернитесь к таблице шагов (раздел 2) и найдите, на каком шаге стало красно. Дальше не
   идите — чините там.
2. Напечатайте описание: в проблемном здании временно `System.out.println(appearance())` —
   `record` печатает все поля. Часто сразу видно, что `arrow` не тот или `counter` = -1.
3. Идите за помощью с **картинкой**: скриншот поля + вывод `git diff --stat`. Половина
   вопросов снимается фразой «а, у тебя правка уехала в `render`, значит `default` не на месте».
