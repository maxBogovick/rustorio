# B1 — Первое здание с нуля: бур (Miner) и восемь швов готового здания

Это первый урок блока B. Блок строит здания игры **с нуля, по одному за урок, в порядке панели**:
Miner → Belt → Furnace → Chest → … Готовая игра в репозитории содержит все десять зданий сразу;
эти уроки ретроспективно проходят путь, которым каждое из них ДОБАВЛЯЛОСЬ, — чтобы ты умел
добавить своё точно так же. Поэтому код здесь показан не целиком, а **ровно в том объёме, что
накопился к текущему шагу**: в этом уроке в проекте пока ОДНО здание, и enum, и семья `Building`
состоят из одной строки. В B2 добавится вторая, в B3 — третья.

Первое здание — бур (`Miner`): он стоит на руде и по таймеру выдаёт её соседу. Почему именно он
первый: без источника в игре нечему двигаться и плавиться — бур запускает всю цепочку. И он не
самый простой (у ящика из B4 меньше методов), но зато на нём сразу виден ПОЛНЫЙ скелет готового
здания — направление, таймер, отдача, связь с клеткой, сохранение. Разобрав его, дальше ты будешь
лишь менять наполнение тех же восьми швов.

**Что значит «готовое здание».** Не «тикает», а работает целиком: его можно выбрать и поставить,
оно обновляется, отдаёт предмет, ПЕРЕЖИВАЕТ сохранение/загрузку и рисуется. «Полуготовое»
(строится, но не грузится; тикает, но невидимо) — самая частая ошибка новичка, потому что швов
больше, чем кажется. Вот все восемь — держи список перед глазами, дальше идём ровно по нему:

```
1. core/Tool.java            — пункт в меню + горячая клавиша
2. model/<Здание>.java       — сам класс, implements Building (вся логика)
3. model/Building.java       — permits (впустить в sealed-семью) + create (фабрика)
4. model/World.java          — нужна ли зданию инфа о клетке при постройке?
5. persist/BuildingDto.java  — поле для его состояния в снимке
6. persist/SaveService.java  — как здание превратить в снимок (save)
7. persist/LoadService.java  — как из снимка собрать здание (load)
8. render / Appearance       — как показать (обычно БЕСПЛАТНО, шаг 8)
```

**Важно про первое здание.** Для ПЕРВОГО здания несколько из этих швов ты СОЗДАЁШЬ (сам `switch`
в фабрике и в сохранении рождается сейчас, с одной веткой). Для каждого следующего здания те же
`switch` уже существуют, и ты лишь ДОБАВЛЯЕШЬ в них по ветке — причём компилятор сам этого
потребует. Отсюда и растущий по строке код: B1 закладывает швы, B2+ их наполняет.

**Зависит от:** ничего, это фундамент. Полезно рядом держать [D1](D1.md) — там объяснено, ПОЧЕМУ
`Building` сделан `sealed`; здесь мы этим пользуемся как инструментом.

## Шаг 1. `core/Tool.java` — пункт меню и клавиша

`Tool` — это «что выбрано в панели», из чего игра строит здание. Сейчас в игре одно здание,
поэтому и enum — одна строка:

```java
public enum Tool {
    MINER("Miner", 1);          // первое и пока единственное здание: имя для HUD + слот 1

    private final String displayName;
    private final int hotkeySlot;

    Tool(String displayName, int hotkeySlot) {
        this.displayName = displayName;
        this.hotkeySlot = hotkeySlot;
    }

    public String displayName() { return displayName; }
    public int hotkeySlot()     { return hotkeySlot; }
}
```

Может показаться, что для одного здания тут много обвязки — имя, номер слота, конструктор, два
геттера. Это минимум, который нужен ЛЮБОМУ выбираемому зданию: панель показывает `displayName`, а
клавиша строится из `hotkeySlot`. Ценность именно НОМЕРА станет очевидна в B2, когда второму
зданию понадобится своя клавиша: номер — часть самого инструмента, поэтому забыть его при
добавлении здания нельзя, а раздавать клавиши можно циклом.

Слот — это ЧИСЛО, а не клавиша движка: пакет `core` не имеет права знать про libGDX (это стережёт
`ArchitectureTest`). Превращение слота в реальную клавишу — работа слоя ввода, и написана она раз
и навсегда так, что новых зданий уже не касается:

```java
// graphics/input/InputHandler: перебирает ВСЕ инструменты и вешает клавишу по слоту.
for (Tool tool : Tool.values()) {
    if (Gdx.input.isKeyJustPressed(keyForSlot(tool.hotkeySlot()))) { … выбрать tool … }
}
// keyForSlot(slot) = Input.Keys.NUM_0 + slot;
```

Смысл цикла: клавишу получает КАЖДЫЙ элемент enum автоматически. Добавишь в B2 второе здание со
слотом 2 — клавиша «2» заработает сама, и лезть в `InputHandler` не придётся ни разу за весь блок.

## Шаг 2. `model/Miner.java` — сам класс

Здание — это реализация `sealed`-интерфейса `Building`. Интерфейс перечисляет ВСЁ, что здание
обязано уметь; компилятор не даст оставить метод нереализованным. Разберём бур по частям — эти
восемь методов будут у КАЖДОГО здания блока, дальше меняется лишь их содержимое.

**Состояние и конструкторы.** У бура есть направление, таймер-кулдаун и готовая руда на выходе:

```java
public final class Miner implements Building {

    private final Direction dir;         // куда отдаёт — задаётся при постройке и не меняется
    private boolean onOre;               // стоит ли на руде — сообщит мир (шаг 4)
    private float cooldown;              // сколько осталось до следующей руды
    private float cycleTime = Config.MINER_TIME;   // длина цикла (для полоски/анимации)
    private @Nullable Item output;       // готовая руда на выходе; null — выход пуст

    public Miner(Direction dir) {
        this.dir = dir;
        this.cooldown = Config.MINER_TIME;
    }

    /** Восстановить бур с уже готовой рудой на выходе — для загрузки (шаг 7). */
    public Miner(Direction dir, @Nullable Item output) {
        this(dir);
        this.output = output;
    }
```

Направление — это НЕ изменяемое в игре состояние, поэтому оно `final` и приходит раз, в
конструктор. Второй конструктор нужен ради загрузки (шаг 7): чтобы воссоздать бур уже с рудой на
выходе. Отдельный конструктор, а не сеттер, — чтобы восстановленный объект был целостен сразу и
«забыть задать поле» было нельзя.

**`update` — работа во времени.** Сердце источника: отсчитать время и по истечении цикла положить
руду:

```java
    @Override public void update(TickContext ctx) {
        if (output != null || !onOre) {
            return;                      // выход занят ИЛИ копать негде — стоим
        }
        cycleTime = Config.MINER_TIME / ctx.balance().speed(Tool.MINER);   // апгрейды ускоряют
        cooldown -= ctx.dt();            // тратим время тика
        if (cooldown <= 0f) {
            output = Item.IRON_ORE;      // руда готова, лежит на выходе
            cooldown = cycleTime;        // завод таймера на следующий цикл
            ctx.events().publish(Item.IRON_ORE, 1);   // сообщить статистике (Observer, D2)
        }
    }
```

Три детали, которые встретятся во всех «работающих во времени» зданиях:

- **`ctx.dt()`** — длина тика. Любой таймер меряет время через неё; на этом же строится ускорение
  из [D6](D6.md).
- **`ctx.balance().speed(Tool.MINER)`** — множитель скорости типа машины (апгрейды тех-дерева).
- **`ctx.events().publish(...)`** — здание сообщает «произвёл предмет», не зная, кто слушает
  (Observer, [D2](D2.md)). Все эти три вещи приходят зданию в одной «коробке» `TickContext`.

**Отдача и приём.** Бур — источник: ничего не принимает, а отдаёт по направлению:

```java
    @Override public Optional<Handoff> output() {
        return output == null ? Optional.empty() : Optional.of(new Handoff(output, dir));
    }
    @Override public boolean canAccept(Item item) { return false; }   // источник, вход закрыт
    @Override public void accept(Item item)        { }                // отдать буру нечего
    @Override public void removeOutput()           { output = null; } // сосед забрал руду

    @Override public Optional<Direction> direction() { return Optional.of(dir); }
    @Override public Tool tool() { return Tool.MINER; }
```

`output()` предлагает соседу `Handoff(руда, направление)`, пока руда готова. `removeOutput()`
освобождает выход, когда сосед забрал, — иначе `update` навсегда застрянет в ветке «выход занят».
`direction()` возвращает `dir` — по нему рисуется стрелка (шаг 8). `tool()` — обратная связь с
шагом 1: по живому зданию можно узнать его `Tool`, не разбирая тип снаружи.

**`appearance()`** разберём на шаге 8 — это восьмой метод интерфейса.

## Шаг 3. `model/Building.java` — создаём `permits` и `create`

Вот где видно «первое здание». Мы не добавляем ветку в существующий `switch` — мы СОЗДАЁМ сам
`sealed`-интерфейс с одним разрешённым зданием и фабрику с одной веткой:

```java
public sealed interface Building permits Miner {          // ← пока в семье один бур

    // ... объявления методов интерфейса (update, output, canAccept, …) ...

    static Building create(Tool tool, Direction dir) {
        return switch (tool) {
            case MINER -> new Miner(dir);                 // ← единственная ветка фабрики
        };
    }
}
```

`switch` в `create` — исчерпывающий по `enum Tool`, без `default`. Сейчас `Tool` содержит один
`MINER`, поэтому одной ветки достаточно и всё компилируется. Как только в B2 ты добавишь
`Tool.BELT`, этот `switch` перестанет собираться, пока не появится ветка для ленты, — компилятор
приведёт тебя сюда сам. Это «карта задач» из [D1](D1.md): забыть шаг физически нельзя.

## Шаг 4. `model/World.java` — нужна ли зданию инфа о клетке?

Некоторым зданиям в момент постройки надо знать что-то про клетку. Бур — ровно такой случай: ему
важно, лежит ли под ним руда. Здания принципиально не знают своих координат, поэтому это сообщает
мир — единственный, кто знает и клетку, и что на ней:

```java
public void place(int x, int y, Building building) {
    // ... поставить здание в сетку ...
    if (building instanceof Miner miner) {
        miner.setOnOre(tile.hasOre());   // мир сообщает буру факт про клетку — ОДИН раз
    }
}
```

```java
    // в Miner:
    void setOnOre(boolean onOre) { this.onOre = onOre; }
```

Почему один раз при постройке, а не каждый тик параметром `update`? Потому что руда сегодня не
иссякает — факт неизменен, и таскать его через `update` каждому зданию значило бы навязать всем
то, что нужно одному. Бур КЭШИРУЕТ факт. Честная оговорка: появись «истощение руды», мир будет
ОБЯЗАН сообщить буру об изменении — иначе тот продолжит копать из пустоты.

Запомни вопрос этого шага: **«моя работа зависит от того, на ЧТО меня поставили?»** У бура — да.
У большинства зданий дальше в блоке (лента, ящик, печь) — нет, и там шаг 4 будет осознанным нулём:
пришёл, убедился, что placement-инфа не нужна, пошёл дальше. Пропустить шаг и пропустить его
осознанно — разные вещи.

## Шаги 5–7. Сохранение и загрузка

Здание, которое не переживает save/load, не готово. Персистентность — три шва, и здесь мы, как и
в шаге 3, отчасти СОЗДАЁМ их для первого здания.

**Шаг 5. `persist/BuildingDto.java` — поле под состояние.** Снимок здания — это `record` с полями;
у бура надо сохранить руду на выходе:

```java
public record BuildingDto(Tool type, int x, int y, @Nullable Direction dir, int amount,
                          /* … */ @Nullable Item minerOutput, /* … */) { }
//                                 ↑ готовая руда бура; null, если выход пуст
```

Поля-состояния делают `@Nullable` и добавляют АДДИТИВНО: старый сейв, где поля ещё нет, читается
как «этого у здания нет» — самая дешёвая миграция формата. `amount` (счётчик) тоже здесь — он
пригодится ящику в B4; бур им не пользуется и пишет 0.

**Шаг 6. `persist/SaveService.java` — здание → снимок.** Снова исчерпывающий `switch`, у первого
здания — с одной веткой:

```java
private static BuildingDto toDto(int x, int y, Building building) {
    return switch (building) {
        case Miner m -> new BuildingDto(Tool.MINER, x, y, m.dir(),
                0, null, null, null, m.outputItem().orElse(null), null);
        //                                          ↑ dir сохранён   ↑ руда в minerOutput
    };
}
```

Обрати внимание: `cooldown`/`progress` НЕ сохраняются — это «аналоговый» таймер. Сохраняем
дискретное (готовую руду на выходе), а недокопанный цикл после загрузки начнётся заново. Тратить
формат снимка на дробные доли секунды незачем.

**Шаг 7. `persist/LoadService.java` — снимок → здание.** Зеркало шага 6; тут в дело идёт второй
конструктор из шага 2:

```java
private static Building fromDto(BuildingDto dto) {
    Direction dir = dto.dir() != null ? dto.dir() : Direction.EAST;
    return switch (dto.type()) {
        case MINER -> new Miner(dir, dto.minerOutput());   // направление + руда обратно
    };
}
```

Оба `switch` (шаги 6 и 7) — исчерпывающие. Добавив в B2 новое здание, ты получишь ошибки
компиляции ровно в этих двух местах: игра не выпустит здание, пока оно не умеет и сохраняться, и
грузиться. Полуготовое здание отсекается механически.

## Шаг 8. Отрисовка — обычно бесплатно

Приятная часть. Здание НЕ рисует себя пикселями и ничего не знает про экран. Оно ОПИСЫВАЕТ себя в
игровых терминах через `Appearance`, а слой `render` это описание исполняет:

```java
@Override public Appearance appearance() {
    return Appearance.of("Miner")
            .arrow(dir, output == null && onOre)   // стрелка: зелёная, пока копает; красная — нет
            .alert(!onOre)                         // тревожная рамка, если стоит не на руде
            .icon(output);                         // иконка готовой руды на выходе
}
```

`Appearance.of(label)` даёт плашку с подписью; `.arrow/.alert/.icon/.counter/.progress` навешивают
детали — все они уже есть в `Appearance`. Пока у здания нет собственного спрайта, `render` рисует
подписанную плашку САМ, поэтому новое здание не требует ни строчки в графике. Спрайт —
необязательное украшение потом, а не условие готовности. Из восьми швов это единственный, который
компилятор НЕ проверяет механически, — и, как видишь, он же самый дешёвый.

## Порядок, в котором это делают на практике

Не пиши восемь швов «слепо». Пусть ведёт компилятор:

1. Заведи `Tool.MINER` (шаг 1) и `sealed interface Building permits Miner` (шаг 3).
2. Собери проект. Компилятор потребует: реализовать все методы `Building` (создаёшь класс, шаг 2)
   и закрыть `switch` в `create`, `SaveService`, `LoadService` (шаги 3, 6, 7).
3. Иди по ошибкам сверху вниз.
4. Загляни в `World.place` (шаг 4) — реши, нужна ли placement-инфа (буру — да, добавь ветку).
5. `appearance()` (шаг 8) компилятор потребует сразу, как часть интерфейса.

Когда `./gradlew compileJava test` зелёный — здание готово целиком: семь из восьми швов
компилятор проверил механически.
