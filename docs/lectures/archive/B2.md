# B2 — Лента (Belt): здание, которое почти не хранит себя

Второе здание блока, слот 2. Сразу честно: **лента — самое сложное здание в игре**, и не потому,
что у неё много методов (их как раз минимум), а потому, что она первой ломает удобное допущение
из [B1](B1.md) — «здание = самодостаточная клетка со своим состоянием». У ленты состояния почти
нет: предметы едут не в клетке, а в ТРАНСПОРТНОЙ ЛИНИИ — отдельной сущности, в которую клетка лишь
входит. Из-за этого несколько швов чек-листа указывают НАРУЖУ класса `Belt`, а вокруг него живёт
целая маленькая подсистема.

Не пугайся заранее и не жди, что каждое здание такое: Miner, Furnace, Chest — самодостаточные,
как обещал B1. Лента — исключение, и главный смысл урока — увидеть, ПОЧЕМУ она им стала и когда
фича заслуживает собственной подсистемы.

**Инкрементально.** В проекте после B1 было одно здание. Теперь добавляем второе — и здесь
впервые окупается «карта задач» из [D1](D1.md): дописав `Tool.BELT` и `Belt` в `permits`, ты
получишь ошибки ровно в трёх `switch`, и компилятор проведёт тебя по ним.

**Зависит от:** [B1](B1.md) (восемь швов и порядок «иди по ошибкам компилятора» — оттуда).
Всплывёт устройство симуляции (фазы тика) и сохранения «производных» сущностей.

## Шаг 0. Код вырос на одну строку — и три `switch` это заметили

Было одно здание, стало два. Смотри, что растёт:

```java
// Tool: +одна строка
public enum Tool {
    MINER("Miner", 1),
    BELT("Belt", 2);            // ← клавиша «2» заработает сама (цикл из B1, шаг 1)
}

// Building: +одно имя в permits
public sealed interface Building permits Miner, Belt { … }
```

Как только это добавлено, перестают компилироваться ТРИ исчерпывающих `switch` — фабрика и оба
конца персиста, — требуя ветку для ленты:

```java
// create:            case BELT -> new Belt(dir);
// SaveService.toDto:  case Belt b -> …
// LoadService.fromDto: case BELT -> …
```

Это и есть обещанная инкрементальность: скелет, заложенный в B1, теперь просто дорастает на одну
ветку в каждом `switch`. Забыть ни одну из трёх нельзя — сборка не пройдёт.

## Шаг 2. `model/Belt.java` — тонкая оболочка над линией

Вот первое большое отличие от бура. Класс `Belt` хранит почти НИЧЕГО: направление, ссылку на свою
линию (`BeltSegment`) и свой номер в ней. Предметы — не здесь.

```java
public final class Belt implements Building {

    private final Direction dir;
    private @Nullable BeltSegment segment;   // линия, в которую входит эта клетка
    private int indexInSegment = -1;         // какая я по счёту в линии (0 — хвост)

    public Belt(Direction dir) { this.dir = dir; }

    // Привязку к линии делает ТОЛЬКО BeltNetwork (шаг 4), не конструктор:
    void attach(BeltSegment segment, int indexInSegment) {
        this.segment = segment; this.indexInSegment = indexInSegment;
    }
```

**`update` пустой — и это важно.** У бура `update` крутил таймер. У ленты он пуст:

```java
    @Override public void update(TickContext ctx) {
        // Лента сама не работает: предметы двигает ФАЗА ЛЕНТ в симуляции, не клетка.
    }
```

Почему? Если бы каждая клетка ленты двигала свой предмет в `update`, сто клеток были бы сотней
зданий с сотней предметов, и предмет раз в тик перепрыгивал бы в соседнюю клетку. Вместо этого
непрерывная цепочка лент — ОДИН объект `BeltSegment` со списком предметов, и его двигают целиком,
одной операцией на всю линию. Это первый шов, которого не было у бура: **движение ленты — не в
`update`, а в отдельной фазе симуляции.** Загляни в `Simulation.step`:

```java
public void step(TickContext ctx) {
    runMachines(ctx);      // здесь бур копает — building.update(ctx)
    moveBelts(ctx);        // ← а здесь двигаются ленты: world.belts().step(...)
    moveUnderground(ctx);
    moveItems();           // передача предметов между зданиями (стык машина↔лента)
    moveSplitters();
}
```

Выигрыш такого устройства тройной: поток плотный (несколько предметов на клетку), движение линии —
одна операция вместо сотни, и у предмета появляется дробная позиция, то есть плавная анимация
достаётся бесплатно.

**Приём и отдача — ДЕЛЕГИРУЮТСЯ линии.** Наружу лента остаётся обычным зданием (договор
`output/canAccept/accept` тот же, что у бура), но внутри просто переадресует всё своей линии:

```java
    @Override public Optional<Handoff> output() {
        // Отдаёт только ГОЛОВНАЯ клетка и только когда предмет доехал до конца линии.
        if (segment == null || indexInSegment != segment.tileCount() - 1) return Optional.empty();
        return segment.headItem().map(item -> new Handoff(item, dir));
    }
    @Override public boolean canAccept(Item i) { return segment != null && segment.canInsertAt(entrySlot()); }
    @Override public void accept(Item i)       { segment.insert(i, entrySlot()); }
    @Override public void removeOutput()       { if (segment != null) segment.removeHeadItem(); }

    @Override public Optional<Direction> direction() { return Optional.of(dir); }
    @Override public Tool tool() { return Tool.BELT; }
```

Ключевой момент: бур и печь НЕ ЗНАЮТ, что ленты устроены так хитро. Они видят тот же `output()` и
`canAccept()`, что у любого здания, и общая фаза передачи `moveItems` стыкует их с лентой ровно
так же, как с ящиком. Сложность спрятана за неизменным договором `Building` — в этом и смысл.

## Шаг 3. `create` — здание без координат

Фабрика создаёт ленту, ещё НЕ ЗНАЯ, куда её поставят:

```java
case BELT -> new Belt(dir);      // segment пока null — координат тут нет
```

Координаты появляются только в `World.place`. Поэтому лента рождается «в воздухе», без линии, а
привязка к линии откладывается до шага 4. Сравни с буром: буру в конструкторе хватило `dir`, а
его связь с клеткой (`onOre`) тоже ставилась позже, в `place`. Здесь та же идея, но крупнее.

## Шаг 4. `World.place` — ВОТ ГДЕ вся сложность ленты

У бура шаг 4 сообщал одному зданию один факт (`setOnOre`). У ленты шаг 4 — это перестройка ОБЩЕЙ
структуры. Поставить клетку ленты может разрезать линию, удлинить её или склеить две в одну:

```java
public void place(int x, int y, Building building) {
    // ... поставить здание в сетку ...
    if (building instanceof Belt newBelt) {
        belts.onBeltPlaced(new Cell(x, y), newBelt);   // мир зовёт сеть лент
    }
}
public void remove(int x, int y) {
    if (tile.building() instanceof Belt belt) {
        belts.onBeltRemoved(new Cell(x, y), belt);     // снос → разрез линии
    }
    // ...
}
```

Вся тонкая логика собрана в отдельном классе `BeltNetwork` — намеренно, в ОДНОМ месте, потому что
именно здесь предметы теряются и удваиваются. Постройка ленты разбирает четыре случая:

```
1. соседей нет            → новая линия из одной клетки
2. линия СЗАДИ (везёт в нас) → наша клетка становится её новой головой
3. линия СПЕРЕДИ (мы в неё)  → наша клетка становится её хвостом
4. и сзади, и спереди     → СКЛЕЙКА: две линии + наша клетка = одна
```

Случай 4 — самый опасный: позиции предметов передней линии обязаны сдвинуться на длину задней
плюс нашу клетку, иначе предмет «перескочит». Снос — зеркально: линия режется по слоту, а предмет,
стоявший на снесённой клетке, законно уничтожается (игрок снёс ленту с грузом).

Почему это отдельный класс `BeltNetwork`, а не пара строк в `World`? Потому что склейка,
удлинение и разрез — по сути одна операция «взять такие-то клетки и предметы и собрать линию», и
её держат в единственном месте, чтобы прочитать и покрыть тестами целиком. Это и есть главный урок
ленты: **для неё шаг 4 — не «зависит ли работа от клетки», а «постройка/снос перестраивает общую
сущность».** Такого у самодостаточных зданий не бывает.

## Шаги 5–7. Сохранение: линию не пишут, её ПЕРЕСОБИРАЮТ

Здесь тоже всё иначе, и по хорошей причине. Линия — сущность ПРОИЗВОДНАЯ: её при загрузке заново
соберёт `BeltNetwork` из расставленных лент. Значит, сохранять надо не линию, а то, из чего её
восстановят.

**Снимок самой клетки (`BuildingDto`) хранит только направление** — никаких предметов:

```java
case Belt b -> new BuildingDto(Tool.BELT, x, y, b.dir(),
        0, null, null, null, null, null);   // груз ленты здесь НЕ хранится
```

**Груз хранится ОТДЕЛЬНЫМ списком** — по одному предмету, с абсолютными координатами:

```java
public record BeltItemDto(int x, int y, int slot, Item item) { }
//                        клетка + позиция ВНУТРИ клетки (0..slots-1) + предмет
```

Почему координата клетки, а не «слот 7 от начала линии»? Потому что до пересборки линии никакого
«седьмого слота линии» ещё не существует, а клетка и позиция в ней абсолютны и переживают
пересборку. Отсюда — порядок загрузки в две очереди (шаг 7):

```java
// 1) сперва расставить ВСЕ ленты — тогда BeltNetwork соберёт линии
case BELT -> Building.create(Tool.BELT, dir);
// 2) и только ПОТОМ вернуть предметы по клетке+позиции:
for (BeltItemDto it : snapshot.beltItems())
    world.restoreBeltItem(it.x(), it.y(), it.slot(), it.item());
```

Принцип, который стоит унести: **сохраняй абсолютное (клетка + позиция в клетке), восстанавливай
производное (линию).** У бура состояние было своё и лежало в его же `BuildingDto`; у ленты
состояние принадлежит линии, которой в момент загрузки ещё нет, — поэтому его выносят наружу и
возвращают вторым проходом.

## Шаг 8. Отрисовка — у клетки пусто, груз рисуется вдоль линии

`appearance()` ленты — самый бедный в игре: ни стрелки, ни счётчика, ни полоски.

```java
@Override public Appearance appearance() {
    return Appearance.of("Belt");   // никаких накладок
}
```

Груз рисуется не клеткой, а линией — отдельным путём, где у предмета есть дробная позиция между
прошлым и текущим слотом (та самая бесплатная плавность из шага 2). Но с точки зрения ГОТОВНОСТИ
здания это по-прежнему ноль строк в `render`: клетка описывает себя пустой плашкой, а рисование
едущих предметов — общий механизм линий, который новых зданий не касается.

## Почему у ленты столько машинерии — и когда это оправдано

Собери счёт: помимо восьми швов лента притащила `BeltSegment` (линия), `BeltNetwork` (сборка
линий), `BeltItem` (предмет с позицией), отдельную фазу `moveBelts` в симуляции и отдельный список
в сохранении. Это МНОГО против бура, у которого всё уместилось в одном классе.

Оправдано это тем, что лента — не «здание на клетке», а клетка, УЧАСТВУЮЩАЯ в линии. Как только
захотели плотный поток, плавную анимацию и одно движение на всю цепочку вместо сотни — «предмет в
клетке» перестало годиться, и появилась линия как самостоятельная сущность. Все клетки-обёртки
стали тонкими, а вся трудная логика (склейка/разрез с сохранением предметов) съехала в один
класс-подсистему, который можно прочитать и протестировать отдельно.

Вывод урока — не «ленты сложные», а инженерный: **самодостаточное здание держи в одном классе;
заводи отдельную подсистему только тогда, когда сущность перерастает клетку** (поток, а не
предмет). Miner, Furnace, Chest этого порога не переходят — и правильно, что они простые. Лента
перешла осознанно, ради конкретных выигрышей, и заплатила за них машинерией.
