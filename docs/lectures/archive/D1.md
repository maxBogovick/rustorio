# D1 — Шаблон Strategy: сортировщик

Цель урока — не «написать здание», а отработать шаблон **Strategy**: вынести из объекта
семейство взаимозаменяемых алгоритмов. Решение разворачивается по шагам: сначала
прямолинейная версия, затем её ограничение, затем вынос алгоритма и встраивание в игру.

**Что строим.** Сортировщик — здание с одним входом и тремя выходами. Направление предмета
зависит от его типа. Требование: правило выбора направления должно быть **заменяемым, без
правки здания**.

**Зависит от:** [A8](A8-workbook.md) (добавление здания без правок в `render`). Весь код урока лежит
в `core`, `model`, `persist`. `render` не затрагивается.

---

## 1. Прямолинейная версия: правило внутри здания

Сортировщик реализует обычный контракт `Building`: держит один предмет, принимает пока
пусто, отдаёт через `output()`. Правило маршрутизации на этом шаге зашито в теле метода.

```java
package com.rustorio.model;

import com.rustorio.core.Appearance;
import com.rustorio.core.Direction;
import com.rustorio.core.Item;
import com.rustorio.core.TickContext;
import org.jspecify.annotations.Nullable;

import java.util.Optional;

public final class Sorter implements Building {

    private final Direction dir;
    private @Nullable Item item;

    public Sorter(Direction dir) {
        this.dir = dir;
    }

    @Override
    public void update(TickContext ctx) {
        // Пассивен: держит предмет, отдаёт через output().
    }

    @Override
    public Optional<Handoff> output() {
        if (item == null) {
            return Optional.empty();
        }
        Direction right = dir.rotateCw();
        Direction left = right.rotateCw().rotateCw();
        Direction target = switch (item.ordinal() % 3) {   // правило зашито здесь
            case 0 -> dir;
            case 1 -> right;
            default -> left;
        };
        return Optional.of(new Handoff(item, target));
    }

    @Override public boolean canAccept(Item incoming) { return item == null; }
    @Override public void accept(Item incoming) { this.item = incoming; }
    @Override public void removeOutput() { this.item = null; }
    @Override public Optional<Direction> direction() { return Optional.of(dir); }

    @Override
    public Appearance appearance() {
        return Appearance.of("Sorter").arrow(dir, item != null).icon(item);
    }

    public Direction dir() { return dir; }
}
```

Замечание по симуляции: отдельная фаза в `Simulation` не нужна. Развилке (`Splitter`) своя
фаза нужна, потому что она за один тик перебирает выходы. Сортировщику перебор не нужен: у
предмета один целевой выход, и если он занят — предмет ждёт (стандартная фаза передачи
оставляет его в здании). Это корректное поведение: предмет не должен уходить в чужой выход.

Версия рабочая. Ограничение проявляется при втором правиле.

## 2. Что ломается при добавлении второго правила

Нужен второй сортировщик — «всё прямо», без сортировки. Прямолинейное решение: флаг и ветка.

```java
    private final boolean sortByType;   // true — по типу, false — всё прямо

    @Override
    public Optional<Handoff> output() {
        if (item == null) {
            return Optional.empty();
        }
        Direction right = dir.rotateCw();
        Direction left = right.rotateCw().rotateCw();
        Direction target = sortByType
                ? switch (item.ordinal() % 3) { case 0 -> dir; case 1 -> right; default -> left; }
                : dir;
        return Optional.of(new Handoff(item, target));
    }
```

Три конкретных следствия:

1. **Рост.** Каждое новое правило — новая ветка в `output()`. Класс знает все правила сразу.
2. **Несамостоятельность.** Правило нельзя вызвать или проверить в отрыве от здания: оно
   вплавлено в метод, зависящий от `item`, `Handoff`, `Optional`.
3. **Две ответственности в одном классе (SRP).** «Хранить и отдавать предмет» и «выбирать
   направление» — независимые причины изменения. Правил может стать десять, механика
   хранения при этом неизменна.

Вывод: «выбор направления» — это алгоритм, а алгоритм в Java выражается объектом.

## 3. Решение: алгоритм как объект

### 3.1. Интерфейс стратегии

Один метод — выбор направления. Геометрию (право/лево) считает здание и передаёт готовой;
политика отвечает только за смысл выбора и не дублирует `rotateCw()`.

```java
package com.rustorio.model.routing;

import com.rustorio.core.Direction;
import com.rustorio.core.Item;

/** Политика маршрутизации: куда направить предмет. Шаблон Strategy. */
public interface RoutingPolicy {

    /**
     * @param front выход «прямо», right/left — направо/налево от него
     * @return одно из трёх направлений
     */
    Direction route(Item item, Direction front, Direction right, Direction left);

    /** Короткое имя политики — для интерфейса и сохранения. */
    String name();
}
```

Интерфейс детерминирован по контракту: одинаковый вход — одинаковый выход (иначе разойдутся
сохранения; это же проверяет `ArchitectureTest`).

### 3.2. Правила — отдельные классы

```java
package com.rustorio.model.routing;

import com.rustorio.core.Direction;
import com.rustorio.core.Item;

/** Всё прямо. Базовый представитель семейства. */
public final class PassThroughPolicy implements RoutingPolicy {
    @Override public Direction route(Item item, Direction front, Direction right, Direction left) {
        return front;
    }
    @Override public String name() { return "pass"; }
}
```

```java
package com.rustorio.model.routing;

import com.rustorio.core.Direction;
import com.rustorio.core.Item;

/** По типу предмета: каждому виду — свой выход. */
public final class BySortPolicy implements RoutingPolicy {
    @Override public Direction route(Item item, Direction front, Direction right, Direction left) {
        return switch (item.ordinal() % 3) {
            case 0 -> front;
            case 1 -> right;
            default -> left;
        };
    }
    @Override public String name() { return "sort"; }
}
```

### 3.3. Здание делегирует

`Sorter` получает политику в конструкторе и вызывает её вместо собственного `switch`. Веток
маршрутизации в здании больше нет.

```java
package com.rustorio.model;

import com.rustorio.core.Appearance;
import com.rustorio.core.Direction;
import com.rustorio.core.Item;
import com.rustorio.core.TickContext;
import com.rustorio.model.routing.RoutingPolicy;
import org.jspecify.annotations.Nullable;

import java.util.Optional;

public final class Sorter implements Building {

    private final Direction dir;
    private final RoutingPolicy policy;   // стратегия приходит снаружи
    private @Nullable Item item;

    public Sorter(Direction dir, RoutingPolicy policy) {
        this.dir = dir;
        this.policy = policy;
    }

    /** Для загрузки сохранения: с удерживаемым предметом. */
    public Sorter(Direction dir, RoutingPolicy policy, @Nullable Item item) {
        this(dir, policy);
        this.item = item;
    }

    @Override public void update(TickContext ctx) { }

    @Override
    public Optional<Handoff> output() {
        if (item == null) {
            return Optional.empty();
        }
        Direction right = dir.rotateCw();
        Direction left = right.rotateCw().rotateCw();
        return Optional.of(new Handoff(item, policy.route(item, dir, right, left)));
    }

    @Override public boolean canAccept(Item incoming) { return item == null; }
    @Override public void accept(Item incoming) { this.item = incoming; }
    @Override public void removeOutput() { this.item = null; }
    @Override public Optional<Direction> direction() { return Optional.of(dir); }

    @Override
    public Appearance appearance() {
        return Appearance.of("Sorter").arrow(dir, item != null).icon(item);
    }

    public Direction dir() { return dir; }
    public RoutingPolicy policy() { return policy; }
    public @Nullable Item heldItem() { return item; }
}
```

## 4. Проверка расширяемости

Критерий, что Strategy применён верно: новое правило добавляется классом и не требует правок
в `Sorter`.

```java
package com.rustorio.model.routing;

import com.rustorio.core.Direction;
import com.rustorio.core.Item;

/** Руду — прямо, остальное — направо. Sorter не меняется. */
public final class OreStraightPolicy implements RoutingPolicy {
    @Override public Direction route(Item item, Direction front, Direction right, Direction left) {
        return item == Item.IRON_ORE ? front : right;
    }
    @Override public String name() { return "ore"; }
}
```

Если для нового правила пришлось открыть `Sorter` — часть решения осталась в здании.

## 5. Встраивание в игру

Подключение идёт по ошибкам компилятора (как в [A8](A8-workbook.md)). `render` в списке не появится.

**`core/Tool.java`** — слоты 1..9 заняты, берётся клавиша «0»:

```java
    LAB("Lab", 8),
    BUFFER("Buffer", 9),
    SORTER("Sorter", 0);
```

**`model/Building.java`** — `permits` и фабрика; здесь выбирается политика по умолчанию:

```java
public sealed interface Building
        permits Miner, Belt, Furnace, Chest, Assembler, Splitter, UndergroundBelt, Lab, Buffer,
                Sorter {

    static Building create(Tool tool, Direction dir) {
        return switch (tool) {
            // ...
            case BUFFER -> new Buffer(dir);
            case SORTER -> new Sorter(dir, new com.rustorio.model.routing.BySortPolicy());
        };
    }
}
```

Подстановка стратегии — это передача другого объекта в конструктор, а не правка здания.

**`persist/SaveService.java`** и **`persist/LoadService.java`** — по ветке. Сохранение
минимальное: политика восстанавливается по типу здания, хранится только направление
(удерживаемый предмет здесь транзиентный; как сохранить и его — см. A8):

```java
        // SaveService.toDto

                0, null, null, null, null, null);
```

```java
        // LoadService.fromDto

```

**`test/core/ToolTest.java`** — диапазон слотов расширяется до реальной клавиатуры:

## 6. Почему `Building` закрыт, а `RoutingPolicy` открыт

Разные цели — разные инструменты:

- `Building` — `sealed`: набор зданий фиксирован намеренно, чтобы компилятор требовал ветку
  в каждом исчерпывающем `switch` (фабрика, сохранение).
- `RoutingPolicy` — обычный интерфейс: набор правил должен расширяться одним классом без
  правок существующего кода. Это и есть точка расширения шаблона Strategy.

## 7. Вариант на enum

Если политик немного и они без состояния, семейство можно записать как `enum`, реализующий
интерфейс. `name()` и `valueOf()` тогда бесплатны (удобно для сохранения):

```java
public enum StandardPolicy implements RoutingPolicy {
    PASS_THROUGH {
        @Override public Direction route(Item i, Direction f, Direction r, Direction l) { return f; }
    },
    BY_SORT {
        @Override public Direction route(Item i, Direction f, Direction r, Direction l) {
            return switch (i.ordinal() % 3) { case 0 -> f; case 1 -> r; default -> l; };
        }
    };
    @Override public String name() { return super.name().toLowerCase(); }
}
```

Размен: `enum` закрыт (новое правило снаружи не добавить), зато даёт бесплатную
сериализацию. Для фиксированного набора — `enum`; для расширяемого (плагины) — интерфейс с
классами.
