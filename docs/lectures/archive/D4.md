# D4 — Данные вместо кода: рецепты и принцип Open/Closed

Цель урока — не «добавить предмет», а прожить принцип **Open/Closed**: код закрыт для
изменения, но открыт для расширения. Мерило успеха численное — сколько строк КОДА пришлось
тронуть, чтобы добавить целую производственную цепочку. У правильной архитектуры ответ:
почти ноль, всё расширение — это строки ДАННЫХ.

Решение разворачивается по шагам: сначала наивная версия, где рецепт — это код; затем
конкретная боль, в которую она упирается; затем версия, где рецепт — это данные; и наконец
честная граница — где данные заканчиваются и почему это не дефект, а корректный шов.

**Что делаем.** Добавляем медную цепочку со СЛИЯНИЕМ ветвей:

```
COPPER_ORE ──(печь)──> COPPER_PLATE ──(сборщик)──> WIRE
                            │                        │
                            └────────┬───────────────┘
                            (сборщик) │
                                      ▼
                                   CIRCUIT      (COPPER_PLATE + 2×WIRE)
```

Требование: добавление этой цепочки НЕ должно открывать `ProcessKernel`, `Furnace`,
`Assembler`, `Lab`, сохранение, HUD и статистику. Всё это — уже написанный код, и он должен
остаться нетронутым.

**Зависит от:** [D1](D1.md) (там `Building` закрыт, а `RoutingPolicy` открыт — здесь тот же
принцип с другой стороны). Код урока живёт в `core` и `model`; из `render` затрагивается
ровно один файл — и это, как выяснится, правильно.

---

## 1. Наивная версия: рецепт как код

Забудем на время, что в репозитории уже есть `Recipe`. Представим первую реализацию печи и
сборщика — так, как их пишут «в лоб»: машина сама знает, во что превращать вход.

```java
// Наивная печь: правило превращения зашито в тело метода.
public final class Furnace implements Building {
    private @Nullable Item input;

    private @Nullable Item smelt(Item ore) {
        return switch (ore) {
            case IRON_ORE -> Item.IRON_PLATE;
            default -> null;              // остальное печь не плавит
        };
    }
    // ... accept копит input, update по таймеру заменяет input на smelt(input) ...
}
```

```java
// Наивный сборщик: своя таблица-switch, живёт в другом файле.
public final class Assembler implements Building {
    private @Nullable Item input;

    private @Nullable Item assemble(Item part) {
        return switch (part) {
            case IRON_PLATE -> Item.GEAR;
            default -> null;
        };
    }
}
```

Версия рабочая ровно до тех пор, пока рецепт — «один предмет → один предмет» и каждая машина
знает свою горстку правил.

---

## 2. Что ломается

Попробуем добавить всего одну вещь — механизм: `IRON_PLATE + 2×GEAR → MECHANISM`. Наивная
модель рассыпается сразу на трёх уровнях.

**2.1. Составной рецепт не влезает в `switch (input)`.** У механизма ДВА разных
ингредиента, а `smelt(Item)` / `assemble(Item)` принимают ОДИН предмет. Сырьё приезжает по
одному предмету за раз и его надо где-то КОПИТЬ, а потом решать: «набралось ли на механизм?».
Одного поля `input` не хватает — нужен склад. Правило перестаёт быть выражением `switch` и
становится алгоритмом сопоставления «что на складе» против «что требует рецепт».

**2.2. Выбор из нескольких рецептов.** Теперь у сборщика два правила: `плита → шестерёнка`
и `плита + 2 шестерёнки → механизм`. Если на складе есть и плиты, и шестерёнки — подходят
ОБА. Машина должна выбрать, и выбор должен быть детерминированным. В наивной версии это ещё
одна ветка руками, зашитая внутрь сборщика.

**2.3. Лаборатория вообще не строится.** Она ест предметы, а выдаёт очки исследований —
не предмет. Тип `Item smelt(Item)` этого не выражает: на выходе нет предмета. Пришлось бы
заводить машину с принципиально другой сигнатурой — четвёртый вариант «того же самого».

И над всем этим — **дробовик изменений (shotgun surgery)**: каждая новая цепочка правит
несколько файлов-машин, и каждый добавляет ветки в свой `switch`. Пятьсот рецептов игры — это
пятьсот правок кода в десятке файлов. Класс машины знает ВСЕ правила своего типа сразу и
растёт с каждым.

Вывод: «во что превращается вход» — это не поведение машины, а **данные**. Машина —
исполнитель, одинаковый для всех рецептов. Разнятся только таблицы.

## 3. Версия на данных: рецепт — это запись, а не код

Именно так устроен код в репозитории. Рецепт — неизменяемая запись; вход и выход —
множества (`Map<Item,Integer>`), чтобы вместить и составной рецепт, и «выход без предмета».

```java
// core: com/rustorio/model/Recipe.java (сокращённо)
public record Recipe(Tool machine, Map<Item, Integer> inputs, Map<Item, Integer> outputs,
                     float time, int science) {

    /** Таблица рецептов игры. Единственное место, где они перечислены. */
    private static final List<Recipe> ALL = List.of(
            new Recipe(Tool.FURNACE,   Map.of(IRON_ORE, 1),   Map.of(IRON_PLATE, 1), SMELT_TIME),
            new Recipe(Tool.ASSEMBLER, Map.of(IRON_PLATE, 1), Map.of(GEAR, 1),       ASSEMBLE_TIME),
            new Recipe(Tool.ASSEMBLER, Map.of(IRON_PLATE, 1, GEAR, 2), Map.of(MECHANISM, 1), MECHANISM_TIME),
            new Recipe(Tool.LAB,       Map.of(GEAR, 1),       Map.of(),  RESEARCH_TIME, 1),
            new Recipe(Tool.LAB,       Map.of(MECHANISM, 1),  Map.of(),  RESEARCH_TIME, 3)
    );
}
```

Три `switch (input)` из трёх машин исчезли. Вместо них — ОДНА машина-исполнитель на всех,
`ProcessKernel`, которая читает таблицу:

```java
// model/ProcessKernel.java (суть): выбрать рецепт по складу, списать вход, выложить выход.
private @Nullable Recipe chooseRecipe() {
    for (Recipe recipe : Recipe.forMachine(machine)) {   // «сложные сначала» — детерминизм
        if (recipe.isSatisfiedBy(stock)) return recipe;
    }
    return null;
}
```

Обрати внимание, чем `ProcessKernel` НЕ занимается: он не знает ни одного конкретного
предмета. Ни `IRON_ORE`, ни `MECHANISM` в нём не встречаются. Он умеет «набрать склад по
рецепту и обменять вход на выход» — и всё. Это и есть закрытость для изменения: логика
переработки написана один раз и не зависит от того, сколько в игре рецептов.

## 4. Упражнение: добавить медную цепочку

Теперь — сам замер. Добавляем цепочку из раздела 0 и считаем, сколько тронули кода.

### 4.1. Новые предметы

`core/Item.java` — четыре константы. Комментарий в enum честно предупреждает: предмет
добавляется здесь и в спрайты, больше нигде.

```java
public enum Item {
    IRON_ORE, IRON_PLATE, GEAR, MECHANISM,
    // Медная ветка.
    COPPER_ORE, COPPER_PLATE, WIRE,
    /** Сходятся две ветки: медная плита + провода. */
    CIRCUIT
}
```

### 4.2. Новые рецепты — чистые ДАННЫЕ

`Recipe.ALL` — четыре строки. Ни одной новой ветки, ни одного нового метода, ни одного
`if`. Разбор происходящего — в комментариях:

```java
    // Медь плавится так же, как железо: та же машина FURNACE, другой рецепт.
    new Recipe(Tool.FURNACE,   Map.of(COPPER_ORE, 1),   Map.of(COPPER_PLATE, 1), SMELT_TIME),

    // Линейный шаг: из одной плиты — два провода (выход тоже кратный, count = 2).
    new Recipe(Tool.ASSEMBLER, Map.of(COPPER_PLATE, 1), Map.of(WIRE, 2),         ASSEMBLE_TIME),

    // СЛИЯНИЕ ветвей: плита + 2 провода -> схема. Составной рецепт, как механизм.
    new Recipe(Tool.ASSEMBLER, Map.of(COPPER_PLATE, 1, WIRE, 2), Map.of(CIRCUIT, 1), MECHANISM_TIME),
```

Проверь, что заработало бесплатно, — это и есть суть урока:

- **Выбор рецепта.** У сборщика теперь ЧЕТЫРЕ рецепта. `forMachine` уже сортирует «сложные
  сначала», поэтому сборщик, куда приехали и медные плиты, и провода, соберёт схему
  (2 ингредиента), а не будет молоть плиты в провода (1 ингредиент). Код выбора не тронут.
- **Кратный выход `WIRE, 2`.** `ProcessKernel.complete` кладёт в очередь выхода `count`
  предметов циклом. Двойка ниоткуда не «особенная» — она просто число в данных.
- **Приём на склад.** `canAccept` пускает предмет, только если он нужен какому-то рецепту
  машины и на складе его ещё не хватает. Провода теперь «нужны» сборщику — он начал их
  принимать. Ни строчки правки.
- **Сохранение, HUD, статистика производства.** `Item` сериализуется по ИМЕНИ (Jackson),
  а не по числовому индексу и не через `switch`. Новые предметы грузятся, считаются в
  `ProductionStats` и рисуются в панели производства сами собой.

### 4.3. Спрайты — единственная правка вне данных

`graphics/render/Textures.itemTexture` — исчерпывающий `switch (item)` БЕЗ `default`.
Добавив предмет, ты обязан дать ему картинку, и компилятор не даст забыть:

```java
    TextureRegion itemTexture(Item item) {
        return switch (item) {
            case IRON_ORE -> ironOre;
            case IRON_PLATE -> ironPlate;
            case GEAR -> gear;
            case MECHANISM -> mechanism;
            case COPPER_ORE -> copperOre;      // + поля/загрузка спрайтов, как у железных
            case COPPER_PLATE -> copperPlate;
            case WIRE -> wire;
            case CIRCUIT -> circuit;
        };
    }
```

Это НЕ дыра в архитектуре, а корректный шов — см. раздел 5.

## 5. Граница: где данные заканчиваются

Урок был бы нечестным, если бы утверждал «всё — данные». Две вещи данными не выражаются, и
обе — осмысленно.

**5.1. Спрайт (раздел 4.3).** Новый предмет — это новая СУЩНОСТЬ на экране, и у неё должен
быть вид. Картинку нельзя «вывести» из имени константы. Здесь важно КАК устроен шов:
`switch` без `default` делает пропуск ошибкой КОМПИЛЯЦИИ, а не пустым квадратом в рантайме.
Компилятор превращает «не забудь дорисовать» в невозможность собраться. Это лучший вид шва:
он громкий и срабатывает до запуска.

**5.2. Источник сырья.** `COPPER_ORE` должен откуда-то попадать в мир. А `Miner` сегодня
жёстко добывает железо:

```java
    output = Item.IRON_ORE;                 // model/Miner.java — единственный источник руды
    ctx.events().publish(Item.IRON_ORE, 1);
```

Это НЕ рецепт. Рецепт — про то, во что превращается уже существующий предмет; источник — про
то, откуда предмет БЕРЁТСЯ в мире вообще. Разные вопросы, разные механизмы. Чтобы запустить
медную цепочку целиком, буру нужен второй вид руды, а это тянет за собой карту ресурсов мира:
на какой клетке лежит медь, а на какой — железо. Это отдельная фича (мир, а не рецепты) и
отдельный урок. Для проверки медной ветки СЕЙЧАС достаточно скормить `COPPER_ORE` печи
вручную из ящика (`Chest`) — переработка от плиты до схемы работает независимо от того,
откуда взялась руда.

Вывод раздела: данные покрывают весь ПРОЦЕССНЫЙ граф (что во что и на какой машине
превращается). За его пределами — вид предмета и его появление в мире; и то и другое честно
остаётся кодом, потому что это новые ВОЗМОЖНОСТИ, а не новые правила.

## 6. Open/Closed, сформулированный точно

Принцип: программные сущности должны быть **открыты для расширения, но закрыты для
изменения**. Разложим по нашему коду, кто здесь что:

- **Закрыто для изменения** — `ProcessKernel`, `Furnace`, `Assembler`, `Lab`, а также
  сохранение, HUD и `ProductionStats`. Медная цепочка их не открыла ни на строку. Этот код
  написан один раз и не растёт с числом рецептов.
- **Открыто для расширения** — таблица `Recipe.ALL`. Точка роста игры: новые рецепты
  добавляются ДАННЫМИ, дописыванием строк, а не правкой поведения.

Разделение проходит по линии «механизм против политики»: `ProcessKernel` — это механизм
(универсальный исполнитель), рецепты — политика (что конкретно делать). Механизм закрыт,
политика открыта.

Это тот же принцип, что в [D1](D1.md), с другой стороны. Там `Building` был `sealed`
(закрыт: набор зданий фиксирован, чтобы компилятор требовал ветку в каждом `switch`), а
`RoutingPolicy` — открытым интерфейсом (расширяется новым классом). Здесь исполнитель закрыт,
а таблица данных открыта. **Закрывают то, что должно быть исчерпывающим и проверяемым;
открывают то, что обязано расти.** Инструмент выбирается под роль, а не по привычке.

## 7. Где держать данные: код или внешний файл

`Recipe.ALL` — это `List.of(...)` прямо в коде. Данные, записанные на Java. Разумный вопрос:
не вынести ли рецепты в JSON/CSV и не читать ли их при старте?

Размен честный, в обе стороны:

- **Данные-в-коде (`List.of`).** Проверяются компилятором: опечатка в имени предмета —
  ошибка сборки, а не тихо пропущенный рецепт. Не нужен парсер и обработка битого файла.
  Менять рецепты без пересборки нельзя, и не-программист их не отредактирует.
- **Данные во внешнем файле.** Правит геймдизайнер без пересборки; можно грузить моды. Цена:
  парсер, валидация (что если в файле предмет `COPER_ORE` с опечаткой?), и ошибки уезжают из
  compile-time в runtime.

Важно, что этот выбор — **локальный**. `ProcessKernel` уже читает рецепты через `Recipe`, ему
всё равно, откуда взялась таблица. Замена `List.of(...)` на «прочитать из файла» не тронет ни
одну машину. Это премия за то, что данные и исполнитель уже разделены: источник данных можно
менять, не трогая того, кто их потребляет. В проекте, кстати, парсер уже есть — Jackson в
`persist`; переключение — тема отдельного захода, если владелец захочет моды.

Правило по умолчанию: пока рецепты меняет только программист — держи их в коде и пользуйся
проверкой компилятора. Внешний файл вводят под конкретную потребность (правки без пересборки,
моды), а не «на всякий случай».
