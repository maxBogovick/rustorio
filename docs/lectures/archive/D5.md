# D5 — Когда паттерн НЕ нужен: State против обычного флага

Прошлые уроки D-блока показывали паттерн с хорошей стороны: боль от наивного решения, потом
паттерн — и боль ушла. Этот урок — про обратную дисциплину. Паттерн — это тоже расход:
классы, косвенность, место, где сопровождающему надо держать в голове больше. Мерило успеха
здесь не «применил паттерн», а **принял верное решение — применять или нет**, и можешь его
обосновать. Инженер, который знает только «когда паттерн нужен», опасен ровно так же, как тот,
кто не знает паттернов вовсе: первый расставляет их везде.

Разбираем самый заманчивый для «раннего» ООП-паттерн — **State** (состояние-объект). У нас
уже есть готовая машина с состояниями. Посмотрим на неё в лоб, потом честно перепишем через
State — и посчитаем, что это дало. Ответ, к которому идём: здесь — ничего, кроме церемонии, и
это правильный ответ. А в конце — где та же машина State окупилась бы, чтобы граница была
конкретной, а не «паттерны — это сложно».

**Зависит от:** [D4](D4.md) (тот же `ProcessKernel` — наш подопытный) и [D1](D1.md) (там мы
ВЗЯЛИ паттерн — Strategy; полезно рядом держать пример, где взяли, и пример, где отказались).
Код урока — только `model/ProcessKernel.java`; трогать его в упражнении НЕ нужно, урок про
чтение и решение, а не про правку.

---

## 1. Машина, у которой уже есть состояния

Открой `ProcessKernel.update` (это ядро печи и сборщика из D4). Явного слова «состояние» там
нет, но машина каждый тик находится ровно в одной из трёх фаз:

```java
void update(TickContext ctx) {
    if (!ready.isEmpty()) {
        return;                         // ФАЗА BLOCKED: выход занят, ждём, пока заберут
    }
    if (active == null) {
        active = chooseRecipe();
        if (active == null) {
            progress = 0f;
            return;                     // ФАЗА IDLE: сырья не хватает ни на один рецепт
        }
    }
    // ФАЗА WORKING: рецепт выбран, крутим таймер
    cycleTime = active.time() / ctx.balance().speed(machine);
    progress += ctx.dt();
    if (progress >= cycleTime) {
        complete(active);
        active = null;                  // WORKING -> IDLE (или BLOCKED, если выход занят)
        progress = 0f;
    }
}
```

Три состояния — **IDLE**, **WORKING**, **BLOCKED** — и переходы между ними. Это буквально
конечный автомат. Он «спрятан» в двух полях: `ready` (пуста ли очередь выхода) и `active`
(выбран ли рецепт). Состояние не названо отдельным типом — оно ВЫВОДИТСЯ из значений полей.

И вот тут у человека, недавно прочитавшего книжку по паттернам, срабатывает рефлекс: «состояния
в полях — это же запашок; правильно вынести каждое состояние в класс, как учит паттерн State».
Проверим этот рефлекс делом.

## 2. Тот же автомат, честно переписанный через State

Паттерн State: заводим интерфейс состояния, каждое конкретное состояние — отдельный класс со
своим `update`, а сам `update` возвращает следующее состояние. Машина хранит ссылку на текущее
состояние и делегирует ему.

```java
// Интерфейс состояния. Каждое состояние умеет прожить один тик и сказать, куда перейти.
interface KernelState {
    KernelState update(ProcessKernel k, TickContext ctx);
}

// IDLE: пытаемся выбрать рецепт. Получилось — уходим в WORKING, нет — остаёмся.
final class Idle implements KernelState {
    public KernelState update(ProcessKernel k, TickContext ctx) {
        Recipe r = k.chooseRecipe();
        if (r == null) { k.resetProgress(); return this; }
        k.setActive(r);
        return new Working();
    }
}

// WORKING: крутим таймер. Готово — завершаем цикл и решаем, куда дальше.
final class Working implements KernelState {
    public KernelState update(ProcessKernel k, TickContext ctx) {
        if (!k.ready().isEmpty()) return new Blocked();     // а вдруг заняли выход
        k.advance(ctx);
        if (!k.cycleDone()) return this;
        k.complete(k.active());
        k.setActive(null);
        return k.ready().isEmpty() ? new Idle() : new Blocked();
    }
}

// BLOCKED: выход занят, ждём. Освободился — назад в IDLE.
final class Blocked implements KernelState {
    public KernelState update(ProcessKernel k, TickContext ctx) {
        return k.ready().isEmpty() ? new Idle() : this;
    }
}
```

А сам `ProcessKernel.update` схлопывается в делегирование:

```java
private KernelState state = new Idle();

void update(TickContext ctx) {
    state = state.update(this, ctx);
}
```

Красиво? На первый взгляд — да: `update` в одну строку, каждое состояние «изолировано».
Прежде чем радоваться, посчитаем, что мы за это заплатили.

## 3. Что этот рефакторинг стоил — и не окупил

**3.1. Три класса и интерфейс вместо двух полей.** Было: `ready`, `active`, читаются на
месте. Стало: `KernelState` + `Idle` + `Working` + `Blocked` — четыре новых типа, четыре файла
(или один раздутый). Строк кода стало БОЛЬШЕ, а поведение — то же.

**3.2. Инкапсуляция вывернута наизнанку.** Раньше `stock`, `ready`, `active`, `progress` были
приватной кухней ядра — никто снаружи их не видел. Теперь состояния-классы ЖИВУТ снаружи ядра,
а работать им надо с той же кухней. Пришлось прорубить в `ProcessKernel` дыры: `chooseRecipe()`,
`setActive()`, `active()`, `advance()`, `cycleDone()`, `complete()`, `ready()`, `resetProgress()`
— всё стало пакетно-видимым. Мы разгерметизировали инкапсуляцию РАДИ паттерна. Данные и логика,
которые работают над ними, теперь в РАЗНЫХ классах — это ровно то, от чего ООП обычно уводит,
а тут паттерн нас туда привёл.

**3.3. Полиморфизма-то и нет.** State окупается, когда `update` каждого состояния — это
существенно РАЗНОЕ поведение, и вызывающему всё равно, в каком мы состоянии. Здесь `update`
каждого состояния — две-три строки, и все три дёргают ОДНУ и ту же кухню ядра. Никакой
подстановки Лисков в дикой природе: никто не держит `KernelState` и не вызывает у него методы,
не зная типа, — кроме самого ядра, которое тут же его и меняет. Мы получили издержки
полиморфизма (косвенность, аллокацию нового объекта состояния на каждом переходе) без его
выгоды.

**3.4. Автомат стало ХУЖЕ видно, а не лучше.** Раньше все три перехода читались в одном
`update` сверху вниз, как абзац. Теперь, чтобы понять «а что после WORKING», надо прыгать между
тремя файлами и собирать граф переходов в голове. Для трёх состояний с тривиальными переходами
локальность важнее «изоляции». Изолировать имеет смысл то, что и правда независимо; наши
состояния сцеплены общими данными и читаются как единое целое.

Итог замера: **+4 типа, разгерметизированная инкапсуляция, минус локальность, ноль нового
поведения.** Это не «дело вкуса» — это чистый расход без дохода. Флаг здесь не «недопаттерн»,
которого мы стесняемся; флаг здесь — правильный инструмент.

## 4. Когда те же три состояния оправдали бы State

Чтобы граница была честной, а не «паттерны страшные», перечислим условия, при которых мы бы
сами потянулись за State для этой же машины. State окупается, когда выполняется НЕСКОЛЬКО из:

- **Состояний и событий много, и они образуют таблицу.** Не «3 состояния, 3 перехода», а
  «6 состояний × 5 входных событий», где почти каждая клетка — своё поведение. Вложенный
  `if/switch` на такую таблицу превращается в нечитаемую лестницу; вот тогда «класс на
  состояние» окупает себя, разнося клетки по методам.
- **Переходы легко перепутать, и цена ошибки высока.** Когда забытый переход — это тихий баг
  (машина зависла в невозможной комбинации флагов). Тип-состояние делает недопустимые переходы
  структурно труднее: из `Blocked` просто нет пути в `Working`, если ты его не написал.
- **Поведение в состояниях существенно РАЗНОЕ и объёмное.** Десятки строк на состояние, где
  общего мало. Тогда «всё в одном `update`» — это тысяча строк с флагами, и разнести их полезно.
- **Состояния добавляют независимо и часто.** Если новые режимы прибывают пачками (моды,
  плагины), «добавить класс, не трогая остальные» начинает стоить дешевле «вписаться в общий
  `switch`».

Наш `ProcessKernel` не проходит ни по одному пункту: три состояния, тривиальные переходы,
поведение — по три строки, новые состояния не появляются. Поэтому — флаг.

А вот пример из ЭТОЙ игры, который к порогу ближе: экранные режимы приложения — `MENU`,
`PLAYING`, `PAUSED`, `SAVING`, `RESEARCH_TREE` — и события `key`, `click`, `tick`,
`saveDone`. Тут состояний и событий уже таблица, поведение в каждом режиме своё и толстое
(меню рисует одно, игра — другое), а недопустимый переход (`ввод игрока прилетел во время
SAVING`) — реальный источник багов. Вот там «класс на экран» начинает окупаться. Разница с
ядром не в «сложности паттерна», а в форме задачи: **State — про таблицу состояние×событие;
флаг — про один бит фазы.**

## 5. Эвристика, которую стоит унести

Правило-ориентир, короткое настолько, чтобы держать в голове у клавиатуры:

> Флаг (или `@Nullable` поле, из которого выводится фаза) — это автомат на один-два бита.
> Тянись за State, когда биты начинают ПЕРЕМНОЖАТЬСЯ: много состояний × много событий, и
> клетки этой таблицы — разное поведение. До этого порога State добавляет типы, а не ясность.

И обратная сторона того же правила — про профессиональную честность. Соблазн из раздела 1
(«состояние в полях — запашок, вынесу в классы») — это **проектирование от паттерна**: сначала
инструмент, потом ищем, куда его воткнуть. Правильно наоборот — от задачи: измерить, что даёт
изменение, и оставить его, только если баланс положительный. В D1 баланс был положительным
(Strategy убрал `switch` и открыл точку роста), и мы паттерн взяли. Здесь — отрицательный, и
мы отказались. Одна и та же дисциплина; разные ответы. Умение сказать «здесь паттерн не нужен»
и обосновать — такой же навык, как умение его применить, и более редкий.

Отдельно: «не нужен паттерн» ≠ «пиши как попало». Наш флаговый `ProcessKernel.update` всё равно
аккуратен — фазы прокомментированы, переходы читаются сверху вниз, поля приватны. Отказ от
State — это выбор в пользу более простого инструмента, а не в пользу небрежности.
