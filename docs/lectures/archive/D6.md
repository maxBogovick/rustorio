# D6 — Decorator: апгрейд на КОНКРЕТНУЮ машину (и налог, который берёт `sealed`)

В игре уже есть апгрейды — но глобальные: технология «быстрая печь» ускоряет ВСЕ печи сразу
(`Balance`, `Effect`, урок про исследования). Этот урок — про другую ось прогрессии: вставить
модуль в ОДНУ конкретную печь, чтобы быстрее работала только она, а соседняя — нет. И чтобы
модули **складывались** (два модуля скорости — быстрее, чем один).

Мерил успеха у урока два, и второе важнее первого:

1. Ускорить один экземпляр печи, **не трогая класс `Furnace`** и не ускоряя остальные печи.
2. Честно посчитать, во что обходится подружить нужный для этого паттерн — **Decorator** — с
   тем, что `Building` у нас `sealed` (см. [D1](D1.md)). Decorator по природе хочет ОТКРЫТУЮ
   иерархию, а `sealed` — закрытая. Это столкновение — сердце урока, а не досадная деталь.

**Зависит от:** [D1](D1.md) (там `Building` сделали `sealed` — и сейчас мы за это платим),
[D5](D5.md) (там же дисциплина: считать расход паттерна, а не брать по привычке). Код урока —
`model/` (новый декоратор) и по одному шву в `Building.create` и `SaveService`; сам разбор
покажет, почему швов ровно два, а не десять.

---

## 1. Что уже есть и почему этого не хватает

Скорость машины сегодня приходит из баланса, общего на весь ТИП машины:

```java
// ProcessKernel.update: время цикла делится на множитель скорости ЭТОЙ МАШИНЫ (типа).
cycleTime = active.time() / ctx.balance().speed(machine);   // speed(Tool.FURNACE) — одно на всех
```

`Balance.speed(Tool)` — это `Map<Tool, Float>`: одно число на `FURNACE`, одно на `ASSEMBLER`.
Технология-апгрейд умножает это число, и ускоряются разом все печи мира. Для тех-дерева это
правильно. Но выразить «вот ЭТА печь быстрее соседней» здесь нечем: у `Balance` нет и не должно
быть записи про отдельный экземпляр — он не знает, где какая печь стоит, и не обязан.

Значит, «быстрее обычного» — это свойство КОНКРЕТНОГО объекта-здания, а не типа. Его надо
навесить на экземпляр.

## 2. Наивная версия: поле в каждой машине

Первый порыв — добавить машинам поле-бонус и учесть его в расчёте времени.

```java
// В Furnace, потом в Assembler, потом в Miner, потом в Lab…
private float speedBonus = 1f;
public void installSpeedModule(float factor) { speedBonus *= factor; }

// и в каждом update — не забыть домножить:
cycleTime = active.time() / (ctx.balance().speed(machine) * speedBonus);
```

Работает — и рассыпается ровно так же, как рассыпался рецепт-`switch` в [D4](D4.md):

**2.1. Дробовик изменений.** Поле и его учёт надо вписать в КАЖДЫЙ класс машины: `Furnace`,
`Assembler`, `Miner`, `Lab`… Скорость сейчас считают в двух местах (`ProcessKernel` и `Miner`) —
уже две правки, и обе легко забыть в третьей машине, которая появится завтра.

**2.2. Каждый новый вид модуля — ещё поле везде.** Захотели модуль «эффективности» (тратит
меньше сырья) или «продуктивности» (бонусный выход) — это ещё одно поле и ещё одна правка во
всех машинах. N модулей × M машин правок.

**2.3. Стек — руками.** «Два модуля скорости» надо самому свести в `speedBonus *= factor`, и
следить, чтобы снять модуль означало поделить обратно. Логика модуля размазана по машинам,
которые модулем как таковым не занимаются.

Вывод тот же, что и раньше: «работать быстрее/эффективнее» — это не про внутренности печи.
Это обёртка ПОВЕРХ машины, одинаковая для всех машин. А значит, ей место в отдельном объекте,
а не в поле каждого класса.

## 3. Decorator: здание, обёрнутое поверх здания

Паттерн Decorator: сделать объект, который реализует ТОТ ЖЕ интерфейс, что и обёрнутый, держит
ссылку на «внутренний» объект, по умолчанию всё ему делегирует — и подменяет ровно одно
поведение. Снаружи декоратор неотличим от обычного здания: его можно поставить на клетку,
передать соседу, нарисовать — везде, где ждут `Building`.

Ключевой трюк — КАК ускорить машину, не зная её внутренностей. Все машины меряют время
одинаково: через `ctx.dt()` (длину тика). `Miner` вычитает `dt` из кулдауна, `ProcessKernel`
прибавляет `dt` к прогрессу. Значит, чтобы машина отработала быстрее, декоратору не нужно лезть
ни в кулдаун, ни в прогресс — достаточно дать обёрнутой машине тик, который «длиннее» в
`factor` раз:

```java
// model: декоратор скорости. Реализует Building, оборачивает Building.
public final class SpeedModule implements Building {

    private final Building inner;
    private final float factor;   // 1.5 — «работает в полтора раза быстрее»

    public SpeedModule(Building inner, float factor) {
        this.inner = inner;
        this.factor = factor;
    }

    @Override
    public void update(TickContext ctx) {
        // Единственное изменённое поведение: обёрнутая машина видит тик длиннее в factor раз,
        // поэтому её таймер (любой — кулдаун бура ИЛИ прогресс ядра) добегает быстрее.
        // TickContext — record, дешёвая «коробка»; balance и шину событий отдаём как есть.
        inner.update(new TickContext(ctx.dt() * factor, ctx.balance(), ctx.events()));
    }

    // Всё остальное — прозрачная передача внутрь. Декоратор в эти двери не вмешивается.
    @Override public Optional<Handoff> output()      { return inner.output(); }
    @Override public boolean canAccept(Item item)    { return inner.canAccept(item); }
    @Override public void accept(Item item)          { inner.accept(item); }
    @Override public void removeOutput()             { inner.removeOutput(); }
    @Override public Optional<Direction> direction() { return inner.direction(); }
    @Override public Tool tool()                     { return inner.tool(); }

    @Override
    public Appearance appearance() {
        // Показать модуль на экране БЕЗ единой правки render: берём вид машины и вешаем счётчик
        // модулей. counter — готовая «дверь» Appearance (тем же полем рисуется число в ящике/лабе).
        return inner.appearance().counter(moduleCount());
    }
}
```

Разберём, что здесь произошло:

- **Скорость навешена на ЭКЗЕМПЛЯР.** Обёрнута конкретная печь; её соседка, необёрнутая,
  работает как прежде. Класс `Furnace` не тронут ни строкой.
- **Модуль не знает внутренностей машины.** Он не упоминает ни `cycleTime`, ни `cooldown`, ни
  рецепты. Он умеет ровно одно — растянуть тик. Поэтому один и тот же `SpeedModule` ускоряет и
  бур, и сборщик, и лабораторию: всё, что меряет время через `dt`.
- **Стек — это вложенность.** `new SpeedModule(new SpeedModule(furnace, 1.5f), 1.5f)` даёт
  `dt * 1.5 * 1.5`. Никакого ручного учёта: два модуля — это две обёртки, и арифметика
  складывается сама.

## 4. Новый вид модуля — новый класс, машины не тронуты

Модуль эффективности «тратит меньше сырья»? Модуль продуктивности «даёт бонусный выход»? Каждый
— НОВЫЙ декоратор, который подменяет СВОЮ дверь и делегирует остальные. `EfficiencyModule` мог
бы вмешиваться в `accept`/расход, `ProductivityModule` — в `output`. Классы машин при этом не
меняются: расширение идёт наружу, обёртками, а не правкой ядра. Сравни с наивной версией из
раздела 2, где каждый новый модуль — поле во всех машинах: там расширение шло ВНУТРЬ и правило
всех.

Это тот же Open/Closed, что в [D4](D4.md), но в другой технике: там точкой роста была таблица
данных, здесь — набор декораторов. Машина закрыта для изменения, поведение вокруг неё открыто
для расширения.

## 5. Налог: Decorator против `sealed Building`

Вот честная цена, ради которой урок и написан. `Building` — `sealed` (это весь смысл [D1](D1.md):
закрытый набор зданий, чтобы `switch` по нему был исчерпывающим и компилятор ловил забытую
ветку). А Decorator — это НОВАЯ реализация `Building`. Две философии сталкиваются лбами.

Смотрим, где именно больно, а где — нет.

**5.1. Полиморфные методы — бесплатно.** `update`, `output`, `accept`, `appearance`, `tool`,
`direction` — это методы интерфейса. Их вызывают по ссылке `Building`, не разбирая тип. Декоратор
их просто реализует и делегирует — и подходит везде, где ждут `Building`, без единой правки в
вызывающем коде. Мир тикает `building.update(ctx)`, рендер зовёт `building.appearance()` — им
всё равно, что внутри обёртка.

**5.2. Исчерпывающие `switch` — берут налог.** В коде осталось РОВНО ДВА места, где по зданию
разбирают конкретный тип, и оба — `switch` без `default` по sealed-типу:

- `Building.create(Tool, dir)` — фабрика: `Tool → Building`.
- `SaveService.toDto(building)` — сохранение: `switch (building) { case Miner m -> …, case Furnace f -> … }`.

Чтобы `SpeedModule` стал полноправным `Building`, его надо вписать в `permits` — одна строка. И
как только вписал, ОБА этих `switch` перестанут компилироваться: компилятор потребует ветку
`case SpeedModule`. Это и есть налог, и он не случайность — это ровно та гарантия, за которую в
D1 платили: sealed заставляет учесть новый вариант ВЕЗДЕ, где тип разбирают снаружи.

- В `create` ветка простая: модуль не «строится инструментом» напрямую — он навешивается на уже
  построенное здание, так что `create` его не порождает (можно бросить понятную ошибку «модуль
  создаётся не так»).
- В `toDto`/загрузке — реальная работа: снимок должен сохранить, что здание ОБёрнуто (тип и
  фактор модулей), а при загрузке — заново обернуть. Сохранение декоратора = «сохранить внутреннее
  здание + список модулей». Это цена того, что модуль — часть иерархии зданий.

**Мораль налога:** Decorator дёшев ровно там, где диспетчеризация полиморфна (методы интерфейса),
и дорог ровно там, где она — внешний исчерпывающий `switch` (сохранение). Это зеркало [D1](D1.md):
`sealed` купил исчерпываемость ценой лёгкого оборачивания. Ни то, ни другое не «бесплатно» —
выбран размен.

## 6. Развилка: а точно Decorator? (честный вопрос из D5)

Прежде чем платить налог из раздела 5, спроси то же, что в [D5](D5.md): а нужна ли обёртка
именно как `Building`? Есть альтернатива без `sealed`-налога — **композиция полем**: машина
держит `List<Module>` и сама применяет их в своём цикле, а модуль НЕ реализует `Building`.

Размен точный:

- **Decorator (модуль — это `Building`).** Плюс: модуль прозрачен ВЕЗДЕ, где ходит здание —
  его можно передать, нарисовать, положить в мир как обычное здание; поведение стыкуется через
  делегирование. Минус: платит налог `sealed` в каждом внешнем `switch` (сохранение, фабрика).
- **Поле `List<Module>` в машине.** Плюс: `sealed` не тронут, внешние `switch` не знают о
  модулях. Минус: применять модули должна КАЖДАЯ машина сама (риск дробовика из раздела 2, если
  не вынести в общий базовый шаг), и модуль перестаёт быть «зданием» — он не ходит по миру
  самостоятельно.

Правило выбора то же, что в D5: **инструмент под форму задачи, а не по привычке.** Если модуль
должен вести себя как здание всюду, где есть здания, — Decorator, и налог оправдан. Если модули
живут только внутри машин и наружу их «зданиевость» не нужна — поле проще и честнее. Урок дальше
идёт по пути Decorator, потому что второе мерило успеха (раздел 0) — как раз прожить этот налог,
а не обойти его.
