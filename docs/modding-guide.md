# Часть 0 — быстрогайд

## Мод за минуту

Мод — это папка в `resources/mods/`. Ни компиляции, ни регистрации где-либо ещё.

```
resources/mods/mymod/
├── mod.json
├── textures/            # PNG зданий: файл foo.png → спрайт mymod:foo
└── content/
    ├── items/*.json     # предметы
    ├── fluids/*.json    # жидкости
    ├── kinds/*.json     # именованные пулы рецептов
    ├── recipes/*.json   # рецепты
    ├── buildings/*.json # здания
    ├── techs/*.json     # технологии
    └── maps/*.json      # карты
```

`mod.json`:

```json
{
  "id": "mymod",
  "version": "1.0.0",
  "dependencies": [{ "modId": "rustorio", "range": ">=1.0.0" }]
}
```

## Руда → слиток за четыре файла

```jsonc
// content/items/titan_ore.json
{ "path": "titan_ore", "label": "Titan Ore", "colorRgb": "#8899AA", "shape": "CIRCLE", "tool": "ore" }
```
```jsonc
// content/items/titan_plate.json
{ "path": "titan_plate", "label": "Titan Plate", "colorRgb": "#CCD5E0", "shape": "SQUARE" }
```
```jsonc
// content/recipes/titan_plate.json   ← имя файла = id рецепта
{ "ingredients": ["titan_ore"], "output": "titan_plate", "time": 7, "kind": "FURNACE" }
```
```jsonc
// content/maps/titan_field.json      ← иначе руды не будет на карте
{
  "path": "titan_field", "label": "Titan field",
  "orePatches": [
    { "ore": "titan_ore",      "cx": 20, "cy": 20, "radius": 4 },
    { "ore": "rustorio:coal",  "cx": 26, "cy": 20, "radius": 3 }
  ]
}
```

## Своё здание

```jsonc
// content/buildings/titan_furnace.json
{
  "path": "titan_furnace",
  "category": "production",
  "label": { "en": "Titan furnace", "ru": "Титановая печь" },
  "archetype": "FURNACE",
  "cost": { "item": "rustorio:iron_plate", "amount": 10 },
  "placement": "NEEDS_PASSABLE_TERRAIN",
  "texture": "mymod:titan_furnace",
  "fuel": "rustorio:coal",
  "bufferMax": 20,
  "acceptsSpeedEffects": true
}
```

Рецепт попадёт в приватный пул этого здания, если написать в рецепте `"kind": "titan_furnace"`.

`"texture"` обязано указывать на **существующий** файл: `mymod:titan_furnace` — это
`mymod/textures/titan_furnace.png`. Нет файла — отрисовка падает с исключением, заглушки нет. Пока
художки нет, ставь ванильный спрайт: `"texture": "rustorio:furnace_cold"`.

## Проверка

```bash
./gradlew game
```

Первая строка лога: `Loaded N mod(s) [...]: 22 items, 4 fluids, ... 14 recipes`. Твоего мода нет —
ищи `WARNING ... was skipped:`, там причина.

## Шпаргалка по полям

| Файл | Обязательно | Часто нужно |
|---|---|---|
| `mod.json` | `id`, `version` | `dependencies`, `entryPoint`, `renames`, `minEngineVersion` |
| `items/*` | `path`, `label`, `colorRgb`, `shape` | `researchGrade`, `tool` |
| `fluids/*` | `path`, `label`, `colorRgb` | — |
| `kinds/*` | `path`, `label` | — |
| `recipes/*` | `ingredients`, `output`, `time`, `kind` | `path` |
| `buildings/*` | `path`, `label`, `archetype`, `cost`, `placement`, `texture` | `category`, `kind`, `fuel`, `bufferMax`, `footprint*`, `fluidInput`, `fluidOutput`, `power`, `acceptsSpeedEffects`, `speedMultiplier` |
| `techs/*` | `path`, `label`, `cost` | `prerequisites`, `effects` |
| `maps/*` | `path`, `label` | `orePatches`, `terrainPatches` |

Полные схемы — [docs/schemas/](schemas/), они машинно сверяются с реальным контентом тестом
`ContentSchemaTest`.

## Архетипы одной строкой

`MINER` · `ELECTRIC_MINER` — копает руду под собой.
`BELT` · `SPLITTER` · `UNDERGROUND_IN` · `UNDERGROUND_OUT` · `INSERTER` · `FILTER` · `CHEST` — логистика.
`FURNACE` · `PRESS` · `ASSEMBLER` — предметы → предмет по рецепту.
`PIPE` · `TANK` — трубы. `PUMP` — источник жидкости. `BOILER` — жидкость + топливо → жидкость.
`GENERATOR` — жидкость → ток. `POLE` — покрытие электросети. `LAB` — предметы → очки исследований.

## Шесть правил, которые сэкономят час

1. **Ссылка без двоеточия — в твоём пространстве имён.** `"coal"` в моде `mymod` это `mymod:coal`,
   а не уголь ваниллы. Ванильный уголь — `"rustorio:coal"`. Три исключения, и все три —
   не-ссылки: имя архетипа заглавными в `kind`, имя правила заглавными в `placement` и голое имя
   вкладки в `category` (оно резолвится в `rustorio`, а не в твой мод) — подробнее в 1.7 и 1.8.
2. **Незнакомый ключ = мод не грузится.** Опечатка `"fluidOutut"` — ошибка с именем файла и списком
   допустимых ключей, а не тихое игнорирование. Полей «на будущее» в файлах быть не должно.
3. **`fuel` и ингредиент — разные вещи.** Предмет, названный топливом машины, перехватывается
   раньше подбора рецепта и ингредиентом в ней быть уже не может.
4. **`kind` по умолчанию — приватный пул этого здания** (равный его id). Хочешь в общий ванильный
   пул — пиши имя архетипа заглавными: `"kind": "FURNACE"`.
5. **`footprintWidth/Height` читают только `FURNACE`/`PRESS`/`ASSEMBLER`.** У остальных архетипов
   поле молча ничего не меняет.
6. **Жидкость не превращается в предмет.** Из жидкости можно сделать только другую жидкость
   (`BOILER`) или электричество (`GENERATOR`). Проектируй цепочку с этим знанием, а не вопреки.

# Часть 1 — как это устроено

## 1.1. Контент, идентификаторы, реестры

Всё, что мод добавляет, — **контент**: предмет, жидкость, рецепт, пул рецептов, прототип здания,
технология, карта. У каждой единицы контента есть `ContentId` вида `пространство:путь`, где
пространство — это `id` мода из `mod.json`, а путь — поле `path` (у рецепта — имя файла).
Оба сегмента строчные, из `[a-z0-9_]`.

Контент живёт в **реестрах** — по реестру на вид. Реестр умеет `register` (добавить), `update`
(заменить чужое), `remove` (убрать), `peek` (посмотреть). Из JSON доступен только `register`;
`update`/`remove` — это уже код-мод.

Почему не enum и не switch: чтобы «добавить руду» было **регистрацией**, а не правкой движка.
Развёрнутое обоснование — [why-registries.md](why-registries.md).

## 1.2. Порядок загрузки

1. Папки модов из `resources/mods/` сортируются по имени — чтобы порядок не зависел от файловой
   системы.
2. Разрешаются зависимости (`dependencies` в `mod.json`): мод грузится после тех, кого назвал.
   **Ссылаешься на чужой контент — объяви зависимость**, иначе его может ещё не быть.
3. Для каждого мода в этом порядке читается `content/`: сначала `kinds`, потом `items`, `fluids`,
   `maps`, `recipes`, `buildings`, `techs`. Внутри мода — файлы по алфавиту.
4. Раунды кода (только для jar-модов): `registerContent` у всех → `modifyContent` у всех →
   `finalFixes` у всех.
5. Реестры **замораживаются**. Дальше только чтение.
6. Итоговая проверка: висящие ссылки, несуществующие пулы, циклы в дереве технологий.

**Сломанный мод не роняет игру.** Загрузчик выбрасывает виновника, пишет
`WARNING Mod 'x' was skipped: причина` и грузит остальных заново. Моды, зависевшие от выброшенного,
уедут следом.

## 1.3. `mod.json`

```json
{
  "id": "petrochem",
  "version": "1.0.0",
  "name": "Petrochemistry",
  "description": "Нефть: добыча, переработка, полимеры",
  "minEngineVersion": "0.1.0",
  "dependencies": [{ "modId": "rustorio", "range": ">=1.0.0" }],
  "renames": { "petrochem:old_id": "petrochem:new_id" },
  "entryPoint": "com.petrochem.Entry"
}
```

- `id` — он же пространство имён; должен совпадать с именем папки по смыслу (по имени папки мод
  опознаётся, если сам `mod.json` не читается).
- `minEngineVersion` — движок старее откажется грузить мод и назовёт обе версии. Текущая версия
  движка — `0.1.0` (`EngineVersion.CURRENT`).
- `renames` — `староеId → новоеId` для **прототипов зданий**: старые сейвы продолжают грузиться
  после переименования.
- `entryPoint` — только для jar-мода, см. [часть 3](#часть-3--движок-в-коде-jar-мод).

## 1.4. Предметы

```json
{
  "path": "plastic",
  "label": { "en": "Plastic Bar", "ru": "Пластик" },
  "researchGrade": false,
  "colorRgb": "#E2DED3",
  "shape": "SQUARE",
  "tool": "ore"
}
```

- `label` — строка или объект локалей; фолбэк — `en`, затем сам id.
- `shape` (`CIRCLE`/`SQUARE`/`TRIANGLE`) + `colorRgb` — это и есть внешний вид предмета:
  **своих картинок у предметов пока нет**.
- `researchGrade: true` — лаборатория принимает предмет и превращает в очки исследований.
  Очки пропорциональны «глубине» предмета в дереве рецептов (сумма времён всех рецептов до сырья),
  так что дорогой предмет ценнее дешёвого; шкала привязана к шестерне — 10 очков за неё. Порядок
  величин: ванильное шасси — 51 очко за партию, полимерный набор из части 2 — 68.
- `tool` — подсказка **редактору карт**, игра это поле не читает.

**Предмет становится рудой не флагом, а упоминанием в карте.** Любой предмет, названный в
`orePatches`, лежит в земле; любой предмет, названный в `terrainPatches`, — это местность.

## 1.5. Карты и руда

```json
{
  "path": "oil_field",
  "label": { "en": "Oil field", "ru": "Нефтяное поле" },
  "orePatches": [
    { "ore": "oil_sand",     "cx": 30, "cy": 30, "radius": 5 },
    { "ore": "rustorio:coal","cx": 20, "cy": 40, "radius": 4 }
  ],
  "terrainPatches": [
    { "terrain": "WATER", "cx": 50, "cy": 45, "radius": 4 }
  ]
}
```

- Пятно — круг: центр и радиус.
- **Порядок в файле значим при перекрытии:** клетку забирает **первое** пятно, которое её накрыло,
  а руда всегда бьёт местность — озеро, налитое поверх нефтяного пятна, не появится ни одной
  клеткой. Хочешь остров руды внутри озера — объяви руду раньше воды (это и так единственный
  работающий порядок).
- `terrain` — тоже ссылка на предмет; `"WATER"` и `"ROCK"` заглавными оставлены как совместимые
  псевдонимы для `rustorio:water` / `rustorio:rock`.
- Клетка без пятна — обычная земля.
- **Карта всегда 256×256.** Размера в файле нет: сетка фиксирована движком
  (`PatchOreLayout.STANDARD_WIDTH/HEIGHT`), а часть пятна, вылезшая за край, просто обрезается.
- Руда **истощается**: клетка отдаёт полновесно первые 6000 добыч, дальше — каждая десятая.
  Тонкий бесконечный «хвост», а не ноль.
- **Твоя карта попадает в меню.** Экран «Новая игра» перечисляет «Vanilla map» и все
  зарегистрированные карты, выбранная становится картой мира — подключать её отдельно не надо.
  Строкой там стоит **id** (`petrochem:oil_field`), а не `label`: не удивляйся, что подпись не
  видна.
- Правятся карты руками или веб-редактором контента (`./gradlew editor`).

## 1.6. Жидкости

```json
{ "path": "crude_oil", "label": { "en": "Crude Oil", "ru": "Сырая нефть" }, "colorRgb": "#2B2118" }
```

Три поля, всё. Ни температуры, ни давления — жидкость это имя, объём и цвет.

Как жидкость движется:

- Труба (`PIPE`) и бак (`TANK`) — один архетип, отличаются `bufferMax` (у ванильных: труба 100,
  бак 2500). `bufferMax` — ёмкость **одной клетки**.
- **Связные клетки труб — это одно ведро**: ёмкость сети равна сумме `bufferMax` её клеток,
  заполненность одинакова во всех клетках. Труба сама по себе ничего не «тикает» — сеть трогают
  только машины на её краях.
- В одной сети живёт **одна** жидкость: пока в сети есть нефть, газ туда не войдёт. Разные
  жидкости — физически разные ветки труб.
- **Кто с какой стороны**: помпа и генератор работают со стороной, **в которую смотрят**; котёл
  берёт вход **сзади** и отдаёт **вперёд**. Отдельного поля «где порт» нет: направление здания и
  есть ответ.

## 1.7. Рецепты и пулы

```json
{ "ingredients": ["oil_sand", "rustorio:coal"], "output": "plastic", "time": 30, "kind": "chemistry" }
```

- Идентификатор рецепта — **имя файла** (или `path`, если задан). Именно им чужой мод сможет твой
  рецепт поправить или удалить.
- **Количеств нет**: ровно по одной штуке каждого ингредиента, ровно одна штука на выходе. Нужно
  «2 пластины» — это пока не выражается.
- `time` — тики на партию (60 тиков = 1 секунда).
- `kind` — **пул**, в котором рецепт лежит:
  - имя архетипа заглавными (`FURNACE`, `PRESS`, `ASSEMBLER`, …) — общий ванильный пул;
  - ссылка (`chemistry`, `mymod:chemistry`) — именованный пул из `content/kinds/`;
  - id здания (`plastic_plant`) — его приватный пул.

Пул можно объявить явно, чтобы его видел редактор и ловились опечатки:

```json
{ "path": "chemistry", "label": { "en": "Chemistry", "ru": "Химия" } }
```

Что запрещено и что разрешено внутри одного пула:

- **два рецепта с одинаковым набором ингредиентов** — ошибка загрузки: их невозможно различить;
- **два рецепта, пересекающихся по ингредиенту** — законно: машина не угадывает, а ждёт, пока
  игрок выберет рецепт вручную. Пока выбор не сделан, неоднозначный предмет **не принимается**.
  Если хочешь, чтобы машина заводилась сама, держи в её пуле один рецепт.

Машина «забывает» рецепт, когда её входные буферы опустели, и готова переключиться на другой.

## 1.8. Здания

Здание из JSON **одалживает Java-поведение существующего архетипа**. Новое поведение данными не
описывается — это jar-мод.

| Архетип | Что делает | Что реально читает из JSON (сверх общего) |
|---|---|---|
| `MINER`, `ELECTRIC_MINER` | копает руду под собой, партия за 3 тика, отдаёт **вперёд** | `power.demand`, `acceptsSpeedEffects` |
| `FURNACE`, `PRESS`, `ASSEMBLER` | предметы → предмет по рецепту | `kind`, `fuel`, `bufferMax`, `speedMultiplier`, `footprintWidth/Height`, `acceptsSpeedEffects` |
| `BELT`, `SPLITTER`, `UNDERGROUND_IN`, `UNDERGROUND_OUT` | транспорт | — |
| `INSERTER`, `FILTER` | перекладывает / фильтрует | — |
| `CHEST` | буфер на 100 предметов (**`bufferMax` не читает**) | `acceptsSpeedEffects` |
| `LAB` | research-grade предметы → очки | `acceptsSpeedEffects` |
| `PIPE`, `TANK` | клетка жидкостной сети | `bufferMax` |
| `PUMP` | наливает `fluidOutput` в сеть перед собой: 100 единиц раз в 10 тиков | `fluidOutput` |
| `BOILER` | `fluidInput` сзади + `fuel` → `fluidOutput` вперёд, 10 за тик, 1 топливо на 60 тиков | `fluidInput`, `fluidOutput`, `fuel` |
| `GENERATOR` | сжигает `fluidInput` (5 за тик) → `power.output` мощности | `fluidInput`, `power.output` |
| `POLE` | покрывает и связывает клетки в радиусе | `power.radius` |

Обязательные поля у всех: `path`, `label`, `archetype`, `cost`, `placement`, `texture`.
`category` необязательна (без неё — вкладка «прочее»).

**Размещение** (`placement`) — одно из четырёх:
`ALWAYS` (сквозь препятствия — так стоит только тоннель), `NEEDS_PASSABLE_TERRAIN` (проходимая
земля), `NEEDS_ORE` (проходимая земля **и любая руда** под клеткой), `ADJACENT_TO_WATER`
(проходимая земля **и** клетка воды на одной из четырёх сторон). Новое **условие** размещения —
код-мод; данными выбирается одно из готовых **или** зарегистрированное чужим код-модом — ссылкой
вида `"mymod:on_bitumen"` (см. 3.12).

**Категории** (`category`) — вкладка в панели строительства: `mining`, `logistics`, `production`,
`fluids`, `power_category`; без ключа — вкладка «прочее». Своё пространство имён
(`"mymod:robots"`) даёт отдельную вкладку.

**Топливо** (`fuel`): предмет, который машина жжёт. Она принимает его до 5 штук и **не пускает в
рецепт**. Печь без `fuel` работает без топлива вообще (так устроены ванильные пресс и сборщик).

**`bufferMax`** — вместимость входного буфера у печи и объём клетки у трубы. Одно поле на две роли,
потому что здание никогда не является и тем и другим.

**Размер больше клетки** — только у `FURNACE`/`PRESS`/`ASSEMBLER`:

```json
"footprintWidth": 2, "footprintHeight": 2
```

У остальных архетипов поле принимается загрузчиком, но поведение его не читает: здание всё равно
займёт одну клетку. Это ловушка, а не фича.

## 1.9. Электричество

Ток **опционален**: здание без ключа `power` к электричеству не относится вовсе.

```jsonc
"power": { "radius": 5 }    // POLE:      покрытие и связность сети
"power": { "output": 120 }  // GENERATOR: мощность за тик
"power": { "demand": 20 }   // потребитель
```

Сеть строят **столбы радиусом**, а не смежность зданий: генератор и потребитель должны попадать
в покрытие связанных столбов. Мощность не копится — что не потрачено в этот тик, пропало.

Ванильная цепочка целиком — образец, на который стоит смотреть, проектируя свою:

```
река ──насос──► [вода] ──► котёл(+уголь) ──► [пар] ──► генератор ──► [ток] ──► электробур
```

**Важное ограничение сегодня:** `power.demand` реально проверяет только архетип бура
(`MINER`/`ELECTRIC_MINER`) — единственный, кто запрашивает мощность в тике. Печь или сборщик с
`demand` объявят потребность, но остановиться без тока не смогут. Проверяется тривиально: вызов
`drawPower` в `src/main/java` есть только в `Miner`. Значит, электричество сейчас — это механика
добычи, и цепочку надо проектировать так, чтобы током питался бур. Машина, которая должна честно
вставать без тока, пишется на Java — [часть 3](#часть-3--движок-в-коде-jar-мод).

## 1.10. Технологии

```json
{
  "path": "oil_processing",
  "label": { "en": "Oil processing", "ru": "Нефтепереработка" },
  "cost": 200,
  "prerequisites": ["rustorio:fast_mining"]
}
```

Загрузчик проверяет, что все `prerequisites` и `effects` существуют и что в дереве нет циклов.

**Эффекты из JSON.** Поле `"effects": ["rustorio:big_buffer_effect"]` (или голое имя в своём
namespace) выдаёт named effect, пока технология открыта. Здания спрашивают
`research.hasEffect(…)` — сундук и буфер печи слушают `big_buffer_effect`, подземки —
`long_tunnel_effect`. Скорость бур/печь/лаб по-прежнему через трейт `speedTech` на здании
(ванильные `fast_*_effect` зарегистрированы, но сами по себе машину не ускоряют).

Пример: своя технология, которая удваивает вместимость сундуков без открытия ванильного
`big_buffer`:

```json
{ "path": "wide_pockets", "label": "Wide pockets", "cost": 50,
  "effects": ["rustorio:big_buffer_effect"] }
```

Балансный мод, который `update`-ит чужую технологию, должен **повторить** `effects` — иначе
список заменяется целиком и бонус пропадёт.

Отсюда практический вывод: самый ценный «полезный предмет», который может сделать data-мод, — это
`researchGrade` предмет. Он ускоряет **ванильные** исследования, и это работает без единой строчки
Java. Named effects — второй рычаг без jar.


## 1.11. Текстуры и локализация

- PNG кладётся в `<мод>/textures/`. Файл `refinery.png` регистрируется как спрайт `mymod:refinery`
  — ровно это имя пишется в поле `texture`.
- **Ловушка:** имя, оканчивающееся цифрой (`refinery_1`), упаковщик атласа разберёт как «имя +
  индекс», и спрайт не найдётся. Суффиксы — буквами: `refinery_a`.
- **Спрайт без файла роняет отрисовку.** Не «показывается заглушка», а
  `IllegalArgumentException: No packed texture for sprite: mymod:foo` в тот момент, когда движок
  впервые рисует это здание, — а панель строительства рисует **все** зарегистрированные, так что
  до постройки дело даже не дойдёт. Заглушка в движке ровно одна и только для ванильной
  лаборатории. Правило простое: **имя в `texture` обязано иметь файл**. На время прототипирования
  указывай ванильный спрайт (`rustorio:boiler`, `rustorio:assembler`, `rustorio:pump`…) — так
  сделано в моде из части 2 — и меняй на свой, когда художка появится.
- У предметов картинок нет — только `shape` + `colorRgb`.
- `label` где угодно принимает `{ "en": ..., "ru": ... }`; язык берётся из настроек, фолбэк — `en`.

## 1.12. Сейвы и совместимость

- В сейв пишется `ContentId` прототипа и состояние здания. Переименовал прототип — объяви
  `renames` в `mod.json`, иначе постройка в старом сейве считается исчезнувшим контентом.
- Удалять предмет, который лежит в чужом сейве, — значит ломать этот сейв. Загрузчик проверяет
  висящие ссылки в контенте, но не в сохранённых играх.
- Публичные имена (id предметов, зданий, пулов) — это API: их видят другие моды и сейвы. Меняй до
  публикации, не после.

## 1.13. Границы данных: что нельзя без Java

Список короткий, но именно он определяет дизайн мода. Каждый пункт — проверяемое свойство движка,
а не мнение:

1. **Жидкость не становится предметом и наоборот.** Единственные потребители жидкости — `BOILER`
   (делает другую жидкость) и `GENERATOR` (делает ток). Ни один рецепт не принимает и не выдаёт
   жидкость: рецепт оперирует только предметами.
2. **Новое поведение здания** (своя механика приёма, две разные жидкости на входе, конвейер с
   приоритетом) — код-мод.
3. **Новое условие размещения** — код-мод: данными выбирается одно из четырёх готовых.
4. **Эффект технологии** — JSON `"effects"` для named bonuses (`big_buffer_effect`, …); jar — если
   нужен свой эффект или свой `hasEffect`-потребитель.
5. **Количества в рецепте** (2 пластины на 1 шестерню) движок не выражает.
6. **`power.demand` останавливает только бур** (см. 1.9).
7. **`footprint*` работает только у печеподобных** (см. 1.8).
8. **Правка чужого контента** (`update`/`remove`) — код-мод, см. [3.6](#36-правка-чужого-контента).

## 1.14. Отладка

Что печатает загрузчик:

| Строка | Значение |
|---|---|
| `Loaded 5 mod(s) [rustorio 1.0.0, petrochem 1.0.0, ...]: 22 items, 4 fluids, ...` | порядок загрузки и итоговые счётчики |
| `Mod 'x' was skipped: <причина>` | мод выброшен целиком; причина названа |
| `A later mod overwrote the items 'x:y'` | кто-то переписал чужой контент (в строке стоит имя реестра: `items`, `recipes`, `buildings`…) |

Ошибки в JSON называются файлом и полем: неизвестный ключ (со списком допустимых), неизвестный
архетип (со списком), неразрешённая ссылка на предмет/жидкость, неизвестное правило размещения,
пустой или отрицательный `power`, `radius <= 0` у пятна.

Проверка на неизвестный ключ работает и **внутри вложенных объектов** (`cost`, `power`), куда
JSON-схемы не заглядывают: опечатка `"demmand"` внутри `power` — ошибка загрузки, а не молча
неэлектрическое здание. Обратная сторона того же правила: держать в файлах контента ключи «на
будущее» нельзя, движок откажется грузить мод целиком.

Чек-лист перед тем, как считать мод рабочим:

- [ ] `./gradlew game` — мод в списке, счётчики выросли на ожидаемое число;
- [ ] каждое здание можно поставить (правило размещения выполнимо на твоей карте);
- [ ] у каждого нового предмета есть способ появиться (руда на карте или рецепт);
- [ ] цепочка **стартует с нуля**: нет узла, который требует собственного выхода;
- [ ] в каждом пуле, где машина должна заводиться сама, ровно один подходящий рецепт;
- [ ] топливо машины не совпадает с её ингредиентом;
- [ ] у **каждого** имени в `texture` есть файл (или это ванильный спрайт) — иначе отрисовка упадёт.

# Часть 2 — пример: мод «Нефтепереработка»

Делаем мод `petrochem`: новая руда — нефтеносный песок, её добыча, нефтяная помпа,
нефтеперерабатывающий завод, завод пластика и завод полимерных изделий. Сначала — **проектирование**,
потому что именно оно отличает работающую цепочку от набора красивых JSON-файлов.

## 2.1. Чего мы хотим и что мешает

Хотим: нефть как ресурс, две ветки её использования (энергия и химия), полезный конечный продукт.

Мешают три ограничения из [1.13](#113-границы-данных-что-нельзя-без-java):

1. Жидкость нельзя превратить в предмет. Значит **пластик не может быть сделан из нефти-жидкости** —
   у химической ветки вход обязан быть твёрдым.
2. Ток останавливает только бур. Значит **электричество имеет смысл только если им питается бур**.
3. Технология из JSON ничего не делает. Значит «полезный продукт» должен быть полезен механикой,
   которая уже есть, — а это лаборатория и `researchGrade`.

Отсюда конструкция, где каждое ограничение стало опорой, а не проблемой:

```
                 ┌─ помпа (PUMP на руде) ─[сырая нефть]─► НПЗ (BOILER, топливо уголь)
нефтяное поле ───┤                                             │
                 │                                        [топливный газ]
                 │                                             ▼
                 │                                   газовый генератор (GENERATOR)
                 │                                             │
                 │                                          [ток] ──► столбы
                 │                                                       │
                 └─ нефтяной бур (ELECTRIC_MINER) ◄──────────────────────┘
                              │
                       [нефтеносный песок] ──┬──► завод пластика (ASSEMBLER) ◄── уголь
                                             │              │
                                             │          [пластик]
                                             │              ▼
                                             └──► завод изделий (ASSEMBLER) ◄── шестерня
                                                            │
                                                   [полимерный набор] ──► лаборатория
```

Три решения, которые стоит проговорить:

- **Помпа стоит на руде, а не у воды.** Правило `NEEDS_ORE` требует любую руду под клеткой —
  значит нефтяное поле годится, и помпа выглядит как скважина, а не как водозабор. Побочный эффект,
  о котором надо знать: помпа руду **не тратит**, её источник бесконечен. Это осознанный баланс:
  бесконечная нефть-жидкость, но только на энергию, и конечный (истощающийся) песок на химию.
- **НПЗ топится углём, а не собственным песком.** Соблазн замкнуть цикл («завод жжёт то, что
  добыл бур») ломает старт: бур электрический, ток даёт генератор, газ даёт НПЗ, а НПЗ ждал бы
  песок от неработающего бура. Уголь разрывает петлю: жидкостная ветка запускается **до** того,
  как появилось электричество. Это и есть пункт «цепочка стартует с нуля» из чек-листа.
- **Конечный продукт — research-grade набор.** Он даёт очки в лаборатории, и очки идут на ванильное
  дерево технологий. То есть мод без единой строчки Java получает продукт, который реально нужен.
  Цифра тут не на глаз: партия полимерного набора стоит **68 очков** против 10 за шестерню и 51 за
  ванильное шасси — движок сам оценил его по глубине цепочки, никакого поля «ценность» нет.

## 2.2. Баланс: откуда числа

Числа архетипов фиксированы движком, и цепочка сходится, если их сложить:

| Кто | Сколько |
|---|---|
| Помпа | 100 единиц раз в 10 тиков = **10/тик** |
| НПЗ (`BOILER`) | конвертирует **10/тик**, 1 топливо на 60 тиков |
| Генератор | сжигает **5/тик** |
| Бур с `demand: 20` | 20 мощности за тик |

Одна помпа кормит один НПЗ ровно; один НПЗ кормит **два** генератора; генератор при
`"output": 120` кормит **шесть** буров. Итого связка «помпа + НПЗ + 2 генератора» держит
12 нефтяных буров. Ванильные ориентиры для сравнения: генератор — 100, электробур — 10, столб —
радиус 5.


Почему уголь здесь ингредиент, а не топливо: у сборщика поля `fuel` нет, поэтому уголь доезжает до
подбора рецепта. Допиши заводу `"fuel": "rustorio:coal"` — и он начнёт жечь уголь вместо того, чтобы
класть его в пластик, а рецепт встанет навсегда. Это правило 3 из быстрогайда в чистом виде.

## 2.4. Как это собирается в игре

Минимальная рабочая расстановка (проверена в headless-прогоне):

```
(28,30) сундук ◄── (29,30) нефтяной бур [смотрит влево]
(30,30) помпа [вправо] ─► (31,30) труба ─► (32,30) НПЗ [вправо] ─► (33,30) труба ◄─ (34,30) генератор [влево]
(32,32) столб — накрывает и генератор, и бур
уголь на НПЗ — лентой или манипулятором
```

Порядок запуска, он же порядок отладки: помпа наполняет трубу → НПЗ получает уголь и начинает
гнать газ → генератор загорается `WORKING` → бур перестаёт показывать `NO_POWER` и идёт копать →
песок с ленты уходит на завод пластика, туда же вторая лента с углём → пластик и шестерни едут на
завод изделий → полимерный набор в лабораторию.

Если что-то стоит, смотри на статус здания — движок называет причину сам: `NO_POWER`, `NO_FUEL`,
`NO_INPUT`, `OUTPUT_FULL`, `NO_ORE`.

## 2.5. Куда расширять

- **Второй рецепт в `chemistry`** — например, пластик из песка и железной пластины. Как только
  рецептов в пуле два и они пересекаются по ингредиенту, машина перестаёт заводиться сама, и
  рецепт выбирает игрок. Это нормально — но это дизайн-решение, а не побочный эффект.
- **Бак на газовой ветке** (`TANK` с большим `bufferMax`) сглаживает паузы, когда уголь на НПЗ
  приезжает рывками.
- **Нефтяной бур без электричества** как дешёвый первый тир: тот же файл без блока `power`.
- **Эффект технологии, свои правила размещения, машина на две жидкости** — это уже jar-мод. Мод
  `petrochem` его уже имеет: [часть 3](#часть-3--движок-в-коде-jar-мод) разбирает его кодовую
  половину строка за строкой.

# Часть 3 — движок в коде (jar-мод)

Данными описывается **контент**. Кодом — **поведение**: своя механика здания, реакция на события,
правка чужого контента, capability, которой у движка нет. Ниже — весь путь и весь API, на живом
примере: мод `petrochem` из части 2 получает кодовую половину — **электрокрекер**, машину, которая
варит пластик из песка, платя за каждый тик работы электричеством.

Почему именно она: у данных здесь есть дыра, названная в [1.9](#19-электричество) — `power.demand`
проверяет только бур. Здание, которое реально встаёт без тока и при этом что-то производит,
данными не выразить. Это и есть критерий «пора писать код»: не «хочу красивее», а «данными не
говорится».

## 3.1. Когда нужен код

| Хочу | Данные | Код |
|---|---|---|
| новый предмет, жидкость, рецепт, карту, технологию | ✅ | |
| здание на существующем поведении (быстрее, дороже, свой пул) | ✅ | |
| **новую механику здания** | | ✅ |
| **правку чужого рецепта/прототипа** (`update`, `remove`) | | ✅ |
| **новое условие размещения** | | ✅ |
| **эффект технологии** (named, JSON `"effects"`) | ✅ | ✅ свой потребитель |
| **capability** (HTTP, часы, что угодно вне карты) | | ✅ |
| **реакцию на события** (что-то произвели, что-то поставили) | | ✅ |
| **свой вид контента** (собственный реестр) | | ✗ пока никак, см. 3.5 |

## 3.2. Из чего состоит код-мод

Папка мода та же, что у data-мода, плюс jar:

```
resources/mods/petrochem/
├── mod.json            ← + "entryPoint": "com.petrochem.PetrochemMod"
├── petrochem.jar       ← имя строго <id>.jar
├── javasrc/            ← исходники (движок их не читает, это твоя папка)
├── content/            ← JSON никуда не делся, код его дополняет
└── textures/
```

**Три имени должны совпадать**, иначе мод не загрузится:

1. `entryPoint` в `mod.json`;
2. полное имя класса, реализующего `com.rustorio.api.mod.RustorioMod`;
3. строка внутри jar в файле `META-INF/services/com.rustorio.api.mod.RustorioMod`.

Jar находится **по `ServiceLoader`** через service-файл, а имя из `mod.json` только сверяется —
поэтому забытый service-файл выглядит как «мод молча пропал». Ищи `WARNING ... was skipped:`.

## 3.3. Что моду видно, а что нет

Мод грузится своим загрузчиком классов, который делегирует наружу **только** эти префиксы:

```
com.rustorio.api.    com.rustorio.domain.    java.    javax.    jdk.    sun.
```

из `com.rustorio.domain` **исключены** (нет в `rustorio-api`, загрузчик тоже откажет):

- весь пакет `com.rustorio.domain.world` (`World`, планировщик, …) — соседняя клетка через
  `TickContext`, не через мир целиком;
- весь пакет `com.rustorio.domain.action` (undo-стек игрока: `PlayerAction`, `PlaceAction`, …) —
  это кухня ввода/истории, не контракт здания;
- кухня `domain.building`: сети (`FluidNetwork`/`PowerNetwork`), `FluidNode`/`PowerNode`,
  ванильные concretes (`Pipe`, `Furnace`, …), `VanillaBuildings`, `BuildingFactory`, `NetworkWiring`.

Из `domain.building` мод видит **allowlist контрактов**: `Building`, `TickContext`, `Codec`,
`BuildingPrototype`, `BuildingServices`, `SimpleCrafter`, `TransportNode`+`BeltSegment`, `FluidPort`,
traits, …
`BeltSegment` нужен только для L3-лент. Жидкость/энергия — через `TickContext` / `FluidPort`.

Всё остальное ищется **внутри твоего jar** и больше нигде. Четыре следствия, каждое стоило кому-то
вечера:

- **`ModLoader`, `com.graphics`, `persistence`, `World`, `PlayerAction` мод назвать не может.** Это
  не соглашение, а загрузчик: имя из закрытого пакета — `ClassNotFoundException` в игре (а при
  сборке против `rustorio-api` — ошибка компиляции, что честнее).
- **Свои библиотеки клади внутрь jar.** Движок тянет Jackson — но моду его не отдаст. Библиотека,
  на которую ты скомпилировался «потому что она есть у движка», превратится в
  `NoClassDefFoundError` при первом запуске.
- **API подключай как `compileOnly`**, не `implementation`. Копия классов движка внутри твоего jar
  — это **другие** типы: `instanceof` не сработает, поиск в реестре не найдёт, и всё это молча.
- **Моды не видят друг друга.** У каждого jar свой загрузчик, и класс соседнего мода не виден,
  даже если называется точно так же. Взаимодействие между модами идёт только через общее: контент
  по `ContentId`, черты по `TraitKey`, capability по `ServiceKey`. Зачем так — в
  [why-registries.md](why-registries.md#изоляция-модов).

## 3.4. Жизненный цикл мода

```
для всех модов: content/*.json → registerContent()      ← раунд 1
для всех модов: modifyContent()                          ← раунд 2
для всех модов: finalFixes()                             ← раунд 3
                freeze() всех реестров
для всех модов: subscribeEvents(bus)
```

| Метод | Когда | Для чего |
|---|---|---|
| `registerContent` | раунд 1 | свой новый контент |
| `modifyContent` | раунд 2 | править **чужое** — к этому моменту оно точно зарегистрировано |
| `finalFixes` | раунд 3 | последние поправки перед заморозкой |
| `subscribeEvents` | после заморозки | подписаться на игровые события |

Два факта, которые снимают половину вопросов:

- **Свой `content/` уже прочитан к моменту твоего `registerContent`** — JSON того же мода грузится
  прямо перед его точкой входа. Поэтому крекер спокойно берёт `petrochem:oil_sand` из реестра.
- **До заморозки читай `peek`, а не `get`.** `get`, `iterate`, `size`, `rawId` требуют замороженного
  индекса и бросают исключение. Мод, споткнувшийся об это, не падает громко — он **скипается**, и
  единственный след останется в логе.

```java
ItemType mechanism = context.items().peek(ContentId.of("rustorio:mechanism")).orElseThrow(
        () -> new IllegalStateException("не виден: объяви зависимость от rustorio"));
```

## 3.5. Реестры

`RegistrationContext` — единственная дверь к контенту. Именованные аксессоры:
`items()`, `fluids()`, `buildings()`, `recipes()`, `kinds()`, `techs()`, `maps()`,
`placementRules()`. Под ними один общий метод `registry(RegistryKey<T>)`.

| Операция | Когда легальна | Смысл |
|---|---|---|
| `register(id, value)` | до заморозки | добавить своё; повторная регистрация id — ошибка |
| `update(id, old -> new)` | до заморозки | заменить чужое; попадёт в лог перезаписей |
| `remove(id)` | до заморозки | убрать; удаление несуществующего — ошибка, а не no-op |
| `peek(id)` / `knownIds()` | всегда | посмотреть, не требуя заморозки |
| `get(id)` / `get(rawId)` / `iterate()` / `size()` | после заморозки | чтение в игре |

`rawId` — плотный числовой индекс, который выдаётся при заморозке в порядке сортировки
`ContentId`. Он **не зависит** от порядка модов, и на этом держится воспроизводимость.

**Свой вид контента — пока нельзя, и это стоит знать заранее.** `RegistryKey` — открытый класс, и
javadoc движка говорит, что мод «может передать свой ключ», но двери для этого нет:
`RegistrationContext` умеет только **достать** реестр по ключу (`registry(key)` бросает
`NoSuchElementException` на незнакомом), а единственный метод, который реестр **заводит**, —
package-private в `com.rustorio.mod`, то есть в пакете, который загрузчик модов моду не отдаёт и
`rustorio-api` не содержит.

Что делать сейчас: держи свою коллекцию обычным полем точки входа (как счётчик в 3.7). Ты потеряешь
`rawId`, заморозку и строку в сводке загрузки — всё остальное работает.

## 3.6. Правка чужого контента

```java
@Override
public void modifyContent(RegistrationContext ctx) {
    // плавка железа вдвое дольше
    ctx.recipes().update(ContentId.of("rustorio:iron_plate"),
            old -> new Recipe(old.id(), old.ingredients(), old.output(), old.time() * 2, old.type()));

    // ванильный пресс дороже
    ctx.buildings().update(ContentId.of("rustorio:press"), old -> new BuildingPrototype(
            old.id(), old.label(), new BuildingCost(old.cost().item(), 20), old.placementRule(),
            old.texture(), old.footprintWidth(), old.footprintHeight(), old.bufferMax(),
            old.speedMultiplier(), old.acceptsSpeedEffects(), old.behavior(), old.restoreBehavior(),
            old.codec(), old.recipeKind(), old.fuelItem(), old.traits()));

    ctx.recipes().remove(ContentId.of("rustorio:chassis_press"));
}
```

Именно `modifyContent`, а не `registerContent`: в первом раунде чужого может ещё не быть. Каждая
перезапись видна игроку в логе строкой `A later mod overwrote the recipes '...'`. Что после твоего
`remove` какой-то предмет стал недостижим — твоя ответственность: загрузчик проверяет висящие
ссылки, а не достижимость.

## 3.7. Своё здание

**Сначала L2.** Обычный станок «один вход → N тиков → один выход» — через
`ctx.content().building(…).simpleCrafter(…)`, без телескопного конструктора и без своего `Codec`.
Пошагово: [hello-building.md](hello-building.md). Каркас: `./gradlew initMod -PmodId=…`.

```java
ctx.content().building("polisher")
        .label("Amber Polisher")
        .cost("rustorio:iron_plate", 8)
        .placement("needs_passable_terrain")
        .texture(VanillaSprites.ASSEMBLER)
        .simpleCrafter("amber_ingot", "amber_polished", 15)
        .register();
```

Контракты здания для нового кода — из `com.rustorio.api.building` (facade на те же интерфейсы,
что в `domain.building`).

**L3** ниже — когда батарейки мало (несколько выходов, сеть, HTTP, свой UI). Здание тогда —
это **два** объекта: `BuildingPrototype` (данные + фабрики) и класс, реализующий
`Building` (поведение). Прототип регистрируется, класс создаётся фабрикой прототипа.

> Фрагменты ниже — **сокращённые** выдержки из
> [`resources/mods/petrochem/javasrc/`](../resources/mods/petrochem/javasrc): тела условий сжаты в
> строку, часть методов опущена. Полный текст — в файлах.

### Класс поведения

```java
final class ElectroCracker implements Building, InspectableBuilding {

    private final BuildingPrototype prototype;
    private final Direction direction;
    private final ItemType input;
    private final ItemType output;
    private int buffered;
    private int ticksLeft;
    private @Nullable ItemType held;
    private BuildingStatus status = BuildingStatus.NO_INPUT;

    @Override
    public boolean accept(TickContext world, ItemType item) {
        if (!item.equals(input) || buffered >= INPUT_MAX) {
            return false;           // не свой предмет — не берём, иначе лента забьёт буфер
        }
        buffered++;
        return true;
    }

    @Override
    public void tick(TickContext world, int x, int y) {
        if (held != null) { deliver(world, x, y); return; }
        if (buffered == 0) { status = BuildingStatus.NO_INPUT; return; }

        PowerSpec spec = prototype.power();
        int demand = spec == null ? 0 : spec.demand();
        if (demand > 0 && !world.drawPower(x, y, demand)) {
            status = BuildingStatus.NO_POWER;   // таймер не двигаем: не оплачен — не работал
            return;
        }
        if (ticksLeft == 0) { ticksLeft = CRACK_TICKS; }
        status = BuildingStatus.WORKING;
        if (--ticksLeft > 0) { return; }

        buffered--;
        held = output;
        world.notifyProduced(output);
        deliver(world, x, y);
    }

    @Override public ContentId prototypeId() { return prototype.id(); }
    @Override public CrackerState state() { return new CrackerState(direction, buffered, ticksLeft, held); }
}
```

Обязательных методов ровно три: `appearance()` (чем рисоваться), `state()` (что сохранять) и
`prototypeId()` (под каким именем сохранять). Всё остальное — `tick`, `accept`, `status`,
`heldItem`, `outputDirection`, `rotatedClockwise`, `footprint*` — имеет значения по умолчанию;
`status()` по умолчанию берётся из `appearance()`, поэтому переопределять его стоит там, где
статус считается в тике, как здесь.

Правила, которые движок соблюдает сам и ждёт от тебя:

- **«Держи, пока не отдал».** Произвёл — держи у себя, пока сосед не примет. Производство,
  обгоняющее доставку, молча уничтожает предметы.
- **Статус считается в тике, а не в кадре.** `status()` возвращает поле, посчитанное последним
  тиком: рендер зовёт его каждый кадр.
- **Не аллоцируй в тике** и не сканируй мир: тик — горячий путь, у проекта есть бенчмарк на него.
- **Сравнивай предметы по личности** (`equals` по id) и бери `ItemType` из реестра **того мира**,
  в котором живёшь, — экземпляры из разных миров разные.

### Capability-интерфейсы

Вместо «движок знает про мой класс» — «мой класс реализует интерфейс». Все они доступны моду:

| Интерфейс | Что даёт |
|---|---|
| `InspectableBuilding` | строки в панели осмотра (`inspectionDetails`) |
| `EditableBuilding` + `FieldSpec` | настраиваемые игроком поля в общем модальном окне |
| `ViewableBuilding` + `BuildingImage` | целая картинка вместо текста (монитор, карта, превью) |
| `TransportNode` + `SettlesEachTick` | встроиться в ленточную «змейку» наравне с лентой |
| ~~`FluidNode` / `PowerNode` / `PowerProducer`~~ | **не в публичном API** — порты `TickContext` |
| ~~`RecipeSelectable`~~ | движок; свой UI — `EditableBuilding` / `ViewableBuilding` |

Ни один из них не требует правки рендера или движка: панель, сеть и планировщик спрашивают
интерфейс, а не конкретный класс.

### Прототип и его фабрики

```java
context.buildings().register(CRACKER_ID, new BuildingPrototype(
        CRACKER_ID,
        "Электрокрекер",
        new BuildingCost(mechanism, 12),
        // Через реестр, а не константой интерфейса: правило мог заменить другой мод. Идентификатор
        // — готовая константа, а не напечатанная руками строка.
        context.placementRules().peek(VanillaPlacementRules.NEEDS_PASSABLE_TERRAIN).orElseThrow(),
        VanillaSprites.ASSEMBLER,      // заимствованный спрайт, пока нет своего PNG
        1, 1,                          // footprint
        0, 1, false,                   // bufferMax, speedMultiplier, acceptsSpeedEffects
        (self, direction, factory) -> new ElectroCracker(self, direction,                // BehaviorFactory
                factory.items().get(OIL_SAND), factory.items().get(PLASTIC), plasticCounter),
        (self, decodedState, factory) -> {                                               // RestoreFactory
            ElectroCracker.CrackerState state = (ElectroCracker.CrackerState) decodedState;
            return new ElectroCracker(self, state.direction(),
                    factory.items().get(OIL_SAND), factory.items().get(PLASTIC), plasticCounter,
                    state.buffered(), state.ticksLeft(), state.held());
        },
        CODEC,
        CRACKER_ID,                    // свой приватный пул рецептов
        null,                          // топливо: нет
        Traits.of(traits())));         // мощность + категория панели
```

- **`BehaviorFactory`** строит новое здание, **`RestoreFactory`** — восстановленное из сейва.
  Приведение типа внутри восстановления безопасно: движок передаёт ровно то, что расшифровал
  **твой же** кодек.
- `factory.items().get(...)` — предметы **этого мира**, а не запомненные статически.
- Лямбды — это **замыкания**: `plasticCounter` здесь обычное поле точки входа мода, и так здание
  получает то, чем владеет мод. Статическое поле сделало бы то же самое, но пережило бы и мир, и
  тест, — а если состояние должно быть **своим у каждого мира**, это уже сервис (см. 3.9).
- Хочешь одолжить чужое поведение — возьми готовый прототип и передай его фабрики:
  `VanillaBuildings.frozen().get(VanillaBuildings.idFor(BuildingType.BELT))`. Так сделан
  `examples/examplemod`.

### Черты (`Traits`)

Необязательные свойства прототипа живут не полями, а парами «ключ — значение». Те же самые ключи
читает JSON-загрузчик, так что код и данные говорят об одном:

```java
Map<TraitKey<?>, Object> traits = new LinkedHashMap<>();
traits.put(VanillaTraits.POWER, new PowerSpec(0, 0, 30));       // radius, output, demand
traits.put(VanillaCategories.CATEGORY, VanillaCategories.PRODUCTION);
Traits.of(traits);
```

Своя черта — это свой `TraitKey<>(id, "имяВJson", Тип.class)`. Читается через `prototype.traits()`
любым модом, который знает ключ.

## 3.8. `TickContext` — что зданию доступно из мира

Здание не видит `World`. Оно видит узкий порт:

| Метод | Что делает |
|---|---|
| `offerForward(x, y, item)` | отдать предмет **одному** соседу по адресу |
| `peek(x, y)` | посмотреть на клетку, ничего не двигая |
| `research()` | спросить, открыта ли технология |
| `notifyProduced(item)` | сообщить статистике/событию о произведённом предмете |
| `addResearchPoints(n)` | добавить очки (это делает лаборатория) |
| `fluidPort(x, y, side)` | ручка на жидкостную сеть с одной стороны |
| `drawPower(x, y, amount)` | оплатить тик мощностью; `false` = сети нет или не хватило |
| `service(key)` | capability мира (см. 3.9) |

`fluidPort` возвращает сеть, у которой есть `fluid()`, `amount()`, `capacity()`,
`insert(fluid, n)`, `extract(fluid, n)`. Порядок операций важен: **сначала спроси, сколько влезет
на выходе, потом забирай на входе** — иначе жидкость будет уничтожаться каждый тик, когда фабрика
забита. Ровно на этом построен ванильный котёл.

## 3.9. Сервисы: capability, которой у движка нет

Сервис — это объект, не являющийся ни контентом, ни клеткой карты: HTTP-клиент, часы, генератор
импульсов. Ключ объявляет мод, движок про него ничего не знает.

```java
public static final ServiceKey<PulseService> KEY =
        new ServiceKey<>(ContentId.of("servicemod:pulse"), PulseService.class);

// в registerContent — ПРОВАЙДЕР, а не экземпляр: он вызывается один раз на КАЖДЫЙ мир
context.registerService(KEY, PulseService::new);

// в здании — один раз, не каждый тик
private PulseService service(TickContext world) {
    if (!resolved) { service = world.service(PulseService.KEY).orElse(null); resolved = true; }
    return service;
}
```

- Провайдер, а не готовый объект: иначе два мира делят один пул потоков, и закрытие одной игры
  ломает следующую.
- Пусто — это **норма**, а не ошибка: мир без сервиса (тест, инструмент, игра без мода-поставщика)
  должен деградировать, как бур без руды, а не падать.
- Держит поток или соединение — реализуй `AutoCloseable`: движок закроет вместе с миром.
- Живой пример целиком — `examples/servicemod`, боевой — мод `webminer` в этом репозитории.

## 3.10. Сохранения: `Codec`

Домен не знает про JSON. Состояние здания превращает в «простые типы» его собственный кодек:

```java
private static final Codec<CrackerState> CODEC = new Codec<>() {
    @Override public Object encode(CrackerState state) {
        Map<String, Object> data = new LinkedHashMap<>();
        data.put("direction", state.direction().name());
        data.put("buffered", state.buffered());
        data.put("ticksLeft", state.ticksLeft());
        data.put("held", Codec.encodeItem(state.held()));
        return data;
    }
    @Override public CrackerState decode(Object raw, Registry<ItemType> items) {
        Map<?, ?> data = (Map<?, ?>) raw;
        return new CrackerState(
                Direction.valueOf(Codec.requireField(data, "direction")),
                Codec.requireField(data, "buffered"),
                Codec.requireField(data, "ticksLeft"),
                Codec.decodeItem(data.get("held"), items));
    }
};
```

- «Простые типы» — это `Map`, `List`, `String`, числа, `Boolean`, `null`. Ни `Direction`, ни
  `ItemType` напрямую: перевод — работа кодека, и это то, что держит Jackson вне домена. **Аннотаций
  Jackson в моде быть не может** — он их даже не увидит (см. 3.3).
- Помощники: `Codec.encodeItem` / `Codec.decodeItem` / `Codec.requireField`.
- `decode` получает реестр предметов **того мира**, куда грузится сейв, — поэтому модовый предмет
  восстанавливается правильно.
- Переименовал прототип — объяви `renames` в `mod.json`. Поменял **форму** состояния —
  для этого есть `StateMigration` (функция «версия N → версия N+1»), пока не подключённая ни к
  одному ванильному прототипу.

## 3.11. События

```java
@Override
public void subscribeEvents(EventBus events) {
    events.subscribe(ItemProducedEvent.class, event -> {
        if (event.item().id().equals(PLASTIC)) {
            plasticCounter.increment();     // крекер показывает это число в панели осмотра
        }
    });
    events.subscribe(BuildingPlaceEvent.class, event -> {
        if (event.x() < 5) {
            event.cancel();                 // отказать в постройке
        }
    });
}
```

| Событие | Когда |
|---|---|
| `WorldInitEvent(width, height)` | мир построен, ещё ничего не поставлено и не тикнуло |
| `TickEvent(tickCount)` | конец каждого тика |
| `ItemProducedEvent(item)` | один произведённый предмет (партия из пяти — пять событий) |
| `BuildingPlaceEvent(id, x, y)` | **до** постройки, можно отменить (`cancel()`) |
| `BuildingPlacedEvent(id, x, y)` | постройка игроком состоялась (не при загрузке сейва) |
| `ResearchCompleteEvent(tech)` | технология действительно открыта |

`subscribeEvents` идёт **после** заморозки: регистрировать контент здесь уже поздно.
`BuildingPlaceEvent` приходит только на действие игрока — мод не может стирать чужие постройки при
загрузке сейва. Отменённая отмена невозможна: `cancel()` в одну сторону.

**Шина одна на загрузку игры, а не на мир.** Начал новую игру — подписки те же самые, и счётчик,
который ты на них построил, не обнулился. Величина, которая должна быть своей у каждого мира, —
это сервис (3.9), потому что его провайдер вызывается один раз на каждый мир. Считать миры по
`WorldInitEvent` и держать состояние в подписчике можно, но это ты уже пишешь то, что сервис даёт
даром.

## 3.12. Своё правило размещения

Правила — такой же реестр, как остальные:

```java
context.placementRules().register(ContentId.of("mymod:on_bitumen"),
        (x, y, oreLayout) -> oreLayout.oreAt(x, y)
                .filter(ore -> ore.id().equals(BITUMEN)).isPresent());
```

После этого **любой** мод, включая data-моды, может написать в JSON `"placement": "mymod:on_bitumen"`.
Так расширяется единственное свойство здания, которое раньше было закрыто.

## 3.13. Сборка jar

Три способа, все рабочие. Выбирай по тому, где живёт твой код.

**A. Отдельный проект (рекомендуется для сторонних модов).** `examples/external-mod-template` — канонический **L2**
Gradle-проект (ContentDsl + SimpleCrafter). То же копирует `./gradlew initMod -PmodId=…`:

```bash
# в чекауте движка — опубликовать API локально
./gradlew publishToMavenLocal
# в проекте мода
./gradlew installMod -PgameDir=/path/to/rustorio
```

Ключевая строка его `build.gradle` — `compileOnly 'com.rustorio:rustorio-api:0.1.0'`.

**B. В этом репозитории (`resources/mods/<id>/javasrc/`).** Учебные `petrochem` и `lightbulb`, а также
`src/mods/webminer` (другая раскладка исходников, та же задача упаковки):

```bash
./gradlew modJars           # все jar-моды разом
./gradlew petrochemModJar   # один мод
./gradlew lightbulbModJar
./gradlew webminerModJar
```

Gradle перекладывает плоский `javasrc/*.java` (с `package com.<id>`) в нормальное дерево пакетов,
читает `entryPoint` из `mod.json`, пишет `META-INF/services/com.rustorio.api.mod.RustorioMod` и
кладёт `<id>.jar` рядом с `mod.json`. Файл в git не коммитится (см. `.gitignore`). `./gradlew build`
и `./gradlew test` вызывают `modJars` автоматически.

Data-only моды (`rustorio`, `sandbox`, …) — только JSON в `content/`; отдельной сборки не требуют.

**C. Вручную, `javac` + `jar` (устарело для in-repo модов).** Раньше так собирали `petrochem.jar`:

```bash
./gradlew apiJar
JSPECIFY=$(find ~/.gradle/caches -name 'jspecify-1.0.0.jar' | head -1)
javac --release 25 -cp "build/libs/rustorio-api-0.1.0.jar:$JSPECIFY" -d /tmp/modbuild \
      resources/mods/petrochem/javasrc/*.java
mkdir -p /tmp/modbuild/META-INF/services
echo 'com.petrochem.PetrochemMod' > /tmp/modbuild/META-INF/services/com.rustorio.api.mod.RustorioMod
jar --create --file resources/mods/petrochem/petrochem.jar -C /tmp/modbuild .
```

Два места, где здесь легко споткнуться:

- `--release 25` — не украшение: класс, скомпилированный более новым javac без этого флага, игра
  просто не загрузит (`UnsupportedClassVersionError`).
- **JSpecify в `rustorio-api` не входит.** `@Nullable` в исходниках мода (он есть в
  `ElectroCracker`) требует эту библиотеку **на компиляции**; без неё сборка падает на импорте.
  В jar она не едет и в рантайме не нужна — аннотации CLASS-retention никто не читает. Именно так
  устроен и шаблон: `compileOnly 'org.jspecify:jspecify:1.0.0'`.

**C. Исходники внутри репозитория движка** (как у `webminer`) — отдельный source set в
`build.gradle`. Годится для модов, которые едут вместе с движком, и требует правки сборочного
файла: в этом репозитории он под запретом без разрешения владельца.

## 3.14. Отладка код-мода

Сообщения ниже загрузчик печатает буквально — по ним и ищи.

| Что видно | Что случилось |
|---|---|
| `Mod 'x' was skipped: …` | мод выброшен целиком, причина в той же строке |
| `no META-INF/services/com.rustorio.api.mod.RustorioMod entry found` | класс есть, объявления сервиса в jar нет — самая частая первая ошибка |
| `mod.json declares entryPoint '…' but ServiceLoader found '…'` | два из трёх имён разошлись; они должны совпадать буквально |
| отказ из-за двух реализаций `RustorioMod` в одном jar | точка входа у мода ровно одна |
| jar вообще не найден | файл обязан называться `<id>.jar` и лежать в папке мода |
| `IllegalStateException: cannot get() before freeze()` | `get` вместо `peek` в раунде регистрации |
| `NoClassDefFoundError` на библиотеку | библиотека не упакована внутрь jar |
| `ClassNotFoundException` на класс движка | назван пакет вне `com.rustorio.api` / `com.rustorio.domain` |
| `UnsupportedClassVersionError` | скомпилировано новее, чем `--release 25` |
| `peek` на чужой контент вернул пусто | ссылка в `registerContent` вместо `modifyContent`, или нет зависимости в `mod.json` |
| «мой предмет не равен их предмету» | `ItemType` взят из другого мира/реестра, а не из `factory.items()` |

Полезное свойство загрузчика: **сломанный мод скипается, игра стартует**. Это удобно в игре и
коварно в разработке — привыкай смотреть первые строки лога, а не экран.

## Что проверено в этом документе

Мод `petrochem` лежит в репозитории целиком — данные, `javasrc/` и собранный `petrochem.jar`.
И — что важнее — **обещания этого документа держат тесты, а не честное слово**: они запускаются
каждой сборкой, так что документ не может тихо разойтись с движком.

| Что утверждает документ | Кто это стережёт |
|---|---|
| цепочка помпа → НПЗ → генератор → столб → электробур запускается с нуля | `PetrochemGuideAcceptanceTest` |
| здание из jar варит пластик на этом токе и докладывает свой `prototypeId` | там же |
| без тока оно встаёт в `NO_POWER` — то, чего данными не выразить | там же |
| его состояние переживает сейв через собственный `Codec` | там же |
| подписка на `ItemProducedEvent` доходит до панели осмотра | там же |
| перекрытые пятна достаются первому объявленному, за 256×256 руды нет | там же |
| `petrochem.jar` не разошёлся с `javasrc/` по составу классов | там же |
| у каждого здания любого мода спрайт подкреплён файлом | `ModSpriteCoverageTest` |
| JSON примера соответствует схемам в `docs/schemas/` | `ContentSchemaTest` |

Каждый из новых тестов проверен на «красноту»: спрайт заменён на несуществующий — падает;
`POWER_DEMAND` обнулён — падает; в `javasrc/` добавлен лишний класс — падает.

Остальное — разовые замеры этой сессии, а не тесты:

- **Загрузка.** `./gradlew game` печатает
  `Loaded 5 mod(s) [rustorio 1.0.0, petrochem 1.0.0, sandbox 1.0.0, waterworks 1.0.0, webminer 1.0.0]`;
  число зданий выросло с 35 до 36 — тридцать шестое зарегистрировал jar, а не JSON.
- **Ценность продукта.** 68 / 51 / 10 очков (полимерный набор / шасси / шестерня) — замер через
  `RecipeBook.depthOf` и формулу лаборатории, а не арифметика на бумаге.
- **Сборка.** `./gradlew build` — зелёная с модом на месте.
- **Не проверено:** как всё это выглядит на экране. Оконный запуск (`./gradlew run`) в headless-
  сессии невозможен, поэтому спрайты, вкладки панели строительства и подсветка сетей глазами не
  смотрелись. Отсюда же вычитанный, а не увиденный вывод: здания мода одалживают ванильные
  спрайты, потому что имя без файла роняет `Textures.forSprite` — путь в коде безусловный, но
  падение в окне в этой сессии не воспроизводилось.
